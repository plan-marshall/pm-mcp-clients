= Post-Landing Verification Protocol: Conformance, Anti-Patterns & Runtime Integrity
:toc: left
:toclevels: 3
:nofooter:
:sectnums:

This document establishes the authoritative, mandatory post-landing verification protocol governing **Step 8 (Post-Landing Verification & Archival)** of link:../agy/runbook.md[`doc/agy/runbook.md`].

It operationalizes the orchestrator's verification responsibility across all landed plans in `pm-mcp-clients` and sits alongside link:emit_rules.adoc[`doc/meta/emit_rules.adoc`] and link:implement_use-cases.adoc[`doc/meta/implement_use-cases.adoc`].

== 1. Context & Retrospective: Why Verification Must Be Active

A green continuous integration build (`./mvnw verify -Ppre-commit`, GitHub Actions) and code-review approval (`CodeRabbit`, `SonarCloud`) are necessary baseline prerequisites, but they are **insufficient to declare a work package verified**.

=== Historical Failure Modes

Previous implementation waves suffered from four critical blind spots:

1. **Passive "Receipt Checking"**:
   * Verification previously checked only whether the worker submitted a completion report, whether unit tests passed, and whether CI was green.
   * Passing tests only verify what the tests *assert*. If a test asserts a stubbed view (`WorkspaceView`), a relaxed mock engine, or a massive hardcoded fallback dictionary (`fallbackMessages`), the test suite passes while the architectural contract is violated.
2. **Siloed Component Execution without Cross-Module Handshakes**:
   * Plans were executed within isolated module worktrees.
   * Cross-module runtime handshakes (e.g., real HTTP/SSE dispatch between `pm-operator`/`pm-web-app` and `pm-mock-runtime`, `start.sh`/`stop.sh` script lifecycles, and port bindings) were not smoke-tested in live subprocesses, allowing lifecycle regressions and scenario drift to reach `main`.
3. **Absence of Negative and Boundary Auditing**:
   * The mock runtime accumulated 60 fragmented, brittle micro-scenarios without enforcing closed schemas or fail-closed parsing on unknown fields.
   * Web views bypassed internationalization message catalogues via hardcoded fallback dictionaries (~780 lines in `fallbackMessages`).
4. **Uncritical Acceptance of Worker Reports**:
   * Orchestrators trusted the worker's completion report claims without independent AST/diff refutation.

To prevent regressions and architectural drift, the orchestrator session **must conduct an active, independent 4-pillar audit** for every plan landing on `main` before moving its report into `doc/agy/verified/`.

== 2. The 4-Pillar Verification Protocol

[source,text]
----
┌────────────────────────────────────────────────────────────────────────┐
│              POST-LANDING VERIFICATION AUDIT (STEP 8)                  │
├────────────────────────────────┬───────────────────────────────────────┤
│ Pillar 1: Traceability Matrix  │ Direct comparison against .adoc specs │
│ Pillar 2: Anti-Pattern Scans   │ AST/grep heuristics per module        │
│ Pillar 3: Subprocess Lifecycle │ Live start.sh, port, & SSE handshakes │
│ Pillar 4: Independent Diff     │ Adversarial review of git delta       │
└────────────────────────────────┴───────────────────────────────────────┘
----

=== Pillar 1: Specification & Contract Conformance Matrix (Traceability Audit)

Every plan originates from formal specifications in `plan-marshall-documentation` or `doc/plans/`. The orchestrator must verify that:

1. **Full Scope Delivery**:
   * Every use-case criterion (e.g. `UC-STA-1` through `UC-STA-9`, `UC-ONB-1..10`, `UC-ENT-1..2`) cited in the plan's traceability section is implemented.
   * No feature or dialogue state is stubbed out or deferred unless explicitly authorized in the roadmap.
2. **Zero Stubs / Placeholders**:
   * Grep the diff for `TODO`, `FIXME`, `STUB`, `placeholder`, `UnsupportedOperationException`, or temporary mock branches.
   * Verify that temporary landing pages (such as `WorkspaceView`) are completely retired when real views land.
3. **Closed Enumerations & Wire Contracts**:
   * Verify that all newly introduced state enums, dispositions, and failure causes match the closed catalogues defined in the specification.
   * Verify that all JSON responses in `pm-api` round-trip through Jackson streaming codecs with zero databind dependencies.

---

=== Pillar 2: Architectural & Code Hygiene Anti-Pattern Scans

The orchestrator must run strict, automated module-by-module heuristics against the landed changeset:

==== A. Web Client (`pm-web-app`)
* **Zero Fallback Dictionaries**:
  * The codebase must **never** contain fallback message dictionaries (e.g., `fallbackMessages` or inline literal string maps).
  * Grep check: `git grep "fallbackMessages" pm-web-app/` must return 0 results.
* **Catalogue Purity**:
  * 100% of user-facing strings must resolve through the Paraglide / message catalogue infrastructure (`messages/en.json`, `messages/de.json`).
  * `npm test -- catalogue.test.ts` must pass across all `.svelte` and `.ts` files with zero exclusions or waivers.
* **Readable-Label Shield**:
  * No raw dot-separated translation keys rendered in UI when a key is missing from the catalogue.
* **Responsive Layout**:
  * All views must adhere to responsive mobile/desktop layout invariants down to 320px viewport width without horizontal scrollbars.
* **Full URL Routing & History**:
  * Every view and sub-dialogue must possess a deterministic URL route and support standard browser forward/back navigation.

==== B. Mock Runtime Engine (`pm-mock-runtime`)
* **Closed Schema Enforcement**:
  * `ScenarioLoader` and `MockRuntimeEngine` must enforce closed schemas and `pm-api` codec validation. Unknown fields must fail closed.
* **Standard Scenarios Architecture**:
  * Micro-scenario fragmentation is prohibited. Scenarios must integrate into the canonical multi-state scenarios defined in `StandardScenarios` (`onboarding`, `projects-and-start`, `running-work`, `reports-system-designer`, `fully-onboarded`).
* **SSE Stream Integrity**:
  * Event streams (`MockEventStream`) must support scoped replay via `Last-Event-ID` headers and handle `reset` events deterministically without hanging clients.
* **Request Dispatch Precedence**:
  * Exact path routes must take precedence over dynamic/parameterized routes (`/api/v1/.../{id}`).

==== C. CLI Terminal Operator (`pm-operator`)
* **Terminal Safety Boundary**:
  * All output from external tools, forge issues, and user input must pass through `TerminalSanitizer` / `OutputSafety`.
  * C0/C1 control codes, DEL, CSI cursor movements, OSC 52 clipboard hijacking, and DCS/SOS/PM/APC sequences must be neutralized.
* **Clean State Restoration**:
  * Full-screen TUI modes must install shutdown hooks and signal traps ensuring the terminal screen buffer, cursor, and echo states are restored cleanly on `SIGINT`, `SIGTERM`, or abnormal exit.
* **Native Measurements & Formatting**:
  * Native measurement tests (`NativeMeasurementsIT`) must validate terminal dimensions and ANSI stripping.
* **Catalogue-Driven Bilingual Console**:
  * Zero literal strings in command outputs; all messages sourced from `operator_messages_{en,de}.properties`.

==== D. Domain Contracts (`pm-api`)
* **Pure Streaming Codecs**:
  * `pm-api` must depend strictly on `jackson-core`. Any dependency on `jackson-databind` or annotations is an immediate rejection.
* **Java 25 Immutable Records**:
  * All resource models must be immutable Java 25 records with explicit null-safety validation in canonical constructors.

=== Pillar 3: Subprocess Lifecycle & Cross-Module Handshake Pre-Flight

Unit tests inside an IDE or Maven runner mock the runtime environment. Post-landing verification requires smoke-testing the real subprocess lifecycle:

1. **Lifecycle Scripts Smoke Test**:
   * Execute `pm-mock-runtime/start.sh` and verify:
     ** Output matches expected PID file creation in `target/`.
     ** Standard scenario selection functions correctly (`./start.sh onboarding`).
     ** Script properly handles macOS Bash 3.2 empty array safety (`set -u` parameter expansion).
   * Execute `pm-mock-runtime/stop.sh` and verify clean process teardown without orphaned PID files or zombie processes.
2. **Network Handshake & Port Binding**:
   * Verify default port assignment (e.g. `8080` or `7420` for mock runtime) and verify HTTP `GET /api/v1/entry` returns valid JSON with `Content-Type: application/json`.
3. **Client-Runtime Compatibility**:
   * Verify that client commands or views successfully load the active scenario without deserialization errors or connection refusals.

---

=== Pillar 4: Independent Diff & AST Verification (Adversarial Audit)

The orchestrator must conduct an independent inspection of the git diff on `main`:

1. **Attribution & Commits**:
   * Verify all commits include the required trailer:
+
[source,text]
----
Co-Authored-By: plan-marshall <noreply@cuioss.de>
----
2. **Boundary Discipline**:
   * Verify that changes did not leak outside the plan's declared module boundaries.
   * Ensure pre-existing tests or configuration files were not weakened, skipped, or commented out to force a green build.
3. **No Unintended Reverts**:
   * Verify that automated formatting tools (e.g. OpenRewrite parent drift) did not silently revert concurrent improvements made by parallel branches.

== 3. Orchestrator Step 8 Execution Workflow

When a plan lands on `main`, the orchestrator executes this sequence:

[source,bash]
----
# 1. Update main branch
git checkout main && git pull --rebase origin main

# 2. Inspect the git diff against base
git log -n 1 --stat
git diff HEAD~1..HEAD

# 3. Execute Anti-Pattern Scans
git grep "fallbackMessages" pm-web-app/ || true
git grep "TODO" $(git diff --name-only HEAD~1..HEAD) || true

# 4. Verify Subprocess Lifecycle (when mock-runtime or lifecycle scripts are touched)
(cd pm-mock-runtime && ./start.sh --help)

# 5. Review Completion Report vs Code Diff
# Compare claims in doc/agy/<topic>-plan-report.md with actual git diff
----

=== Verification Verdicts

[cols="1,3",options="header"]
|===
|Verdict |Action

|**PASSED**
|1. Move `doc/agy/<topic>-plan-report.md` to `doc/agy/verified/<topic>-plan-report.md`
2. Check off Step 8 in `doc/agy/implemented/<topic>-plan.md`
3. Update index in `doc/agy/verified/README.md`, `doc/agy/implemented/README.md`, and dashboard in `doc/agy/README.md`
4. Commit and land verification housekeeping on `main` via PR with `--label "skip-bot-review"`.

|**FAILED (Gaps / Anti-patterns detected)**
|1. Do NOT move report to `verified/`.
2. Author a remediation plan in `doc/agy/<topic>-remediation-plan.md` targeting the exact gap.
3. Schedule remediation in the appropriate stream (CLI, Mock, Web).
|===
