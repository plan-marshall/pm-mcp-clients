== Result in Short

The main flows of the use cases work in the web app. An operator can onboard the machine, follow a plan, answer a
decision, start a plan from a description, and clean up. The app falls short in three ways:

. *Variations are absent.* Many use cases list variations (advice, a change link, the steward, a fix action, the
  intent record). The app shows the happy path and leaves them out.
. *Raw data replaces the designed screen.* Some states have no designed screen. For them, the app shows a generic
  card with the state id (`Machine · harness.none`, `Machine · entry.lan-open`) or a raw error code (`plan_not_found`).
. *Actions are not offered by state.* The system view offers stop, restart, and upgrade while the runtime drains. The
  plan view offers a completion report for a plan that still runs.

The use-case documents are in good shape. They need five additions, mainly for the speed the operator needs in
production (link:proposals.adoc#documents[Proposals, Changes to the Use-Case Documents]).

[#gaps]
== Main Gaps

. *The generic state card.* `OnboardingView.svelte` renders any state without a designed screen as a card with the
  title, the scope, and the state id. The operator sees `Machine · harness.none`. A state without a screen must be a
  defect the build finds, not a screen the operator sees (link:proposals.adoc#UC-P-01[UC-P-01]).
. *Actions not derived from the state.* The use cases say "actions by state" (principle `actions-by-state` of
  `06-controlling-work.adoc`). The app has fixed button sets per view (link:proposals.adoc#UC-P-02[UC-P-02]).
. *Variations of the onboarding.* Advice, the steward, change links, a fix for a credential, and the meaning of
  each plan default are absent (link:proposals.adoc#UC-P-03[UC-P-03]).
. *The plan's intent and the phase workflow.* UC-PLN-1 drills from a phase to its workflow, taken and not taken.
  The app stops at the phase (link:proposals.adoc#UC-P-04[UC-P-04]).
. *Feedback after an act.* The decision answer reports the wrong channel and an index instead of the option
  (link:proposals.adoc#UC-P-05[UC-P-05]).

[#mock]
== The Mock as a Test Bed

The mock is good enough for the main flows. For conformance work it has two limits:

* Most views read domain data from the engine, not from the state of the scenario. A jump to `control.holds` or
  `process.pruned-lane` does not change the plan view. The e2e specs work around this with their own fixtures.
* The README of `pm-mock-runtime` lists scenarios that no longer exist, and the scenario descriptions name use cases
  that do not exist (`UC-CTL-6`, `UC-CTL-7`, `UC-DEC-1` to `UC-DEC-3`).

link:proposals.adoc#UC-P-08[UC-P-08] makes every state of a scenario visible in the views it concerns, so that a
conformance walk in Chrome is possible for all 39 use cases.
