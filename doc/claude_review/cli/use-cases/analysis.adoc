== Result in Short

The client reads well and acts badly:

. *Reading works.* `status`, `plans`, the plan view, the printed epic, `reports`, `system`, `projects` and
  `web devices` show what the use cases ask, often in more depth than the web app.
. *Acting is absent or unsafe.* The dialogues that change state are stubs, are broken, or have no way out:
** The guided onboarding never begins.
** `answer` shows the question but no options.
** The pause dialogue pauses on any input.
** `runtime stop` stops at once.
** `cleanup` lists but does not ask.
** `project setup` prints a placeholder.
. *Events do not reach the console.* The console expects a field the runtime does not send, so no decision, hold, or
  answer elsewhere is ever pushed to the prompt.

The design of the terminal client (`doc/design/terminal-client/`) describes all of these dialogues in detail, with
transcripts. The gap is in the implementation, not in the design or the use cases.

[#gaps]
== Main Gaps

. *No state dialogue.* The design says the client "renders whatever state the runtime reports". For the onboarding,
  the client has no renderer of a state: `EntryFlow` asks one question and ignores the answer, and `OnboardCommand`
  prints the raw links. The same gap stops the project onboarding (link:proposals.adoc#CLI-UC-P-01[CLI-UC-P-01]).
. *No strict choice prompt.* Every dialogue parses its own input. The pause dialogue takes any input as its default;
  others print a usage dump for `q` (link:proposals.adoc#CLI-UC-P-02[CLI-UC-P-02]).
. *Acts without confirmation.* `runtime stop` and the cleanup skip the dialogues of `25-system.adoc` and
  `26-cleanup.adoc` (link:proposals.adoc#CLI-UC-P-05[CLI-UC-P-05]).
. *The answer dialogue fails silently.* The error is swallowed, so the operator sees only that nothing happens
  (link:proposals.adoc#CLI-UC-P-03[CLI-UC-P-03]).
. *Event contract.* The console reads `type` from the event data. The runtime names the event (`decision.opened`) and
  sends no `type` (link:proposals.adoc#CLI-UC-P-04[CLI-UC-P-04]).

[#tests]
== Why the Tests Did Not Catch It

`TuiCapabilityIT` proves that each view opens and that the fallbacks work. `TranscriptDialogueIT` proves `status`,
`web pair`, the console, the console settings, and the plan start. No PTY test runs a dialogue that acts on a plan, a
decision, the onboarding, the cleanup, or the runtime. The unit tests of those dialogues feed scripted input to fakes.
So the defects of the real terminal path (a swallowed exception, a closed terminal, an ignored answer) stay hidden
(link:../cross-cutting/findings.adoc#CLI-CC-F-09[CLI-CC-F-09]).
