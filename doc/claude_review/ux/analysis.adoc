== Result in Short

The app is built from the server's point of view: one view per resource, and each view shows the resource
completely. That is correct and honest. It is not yet a tool for an operator who must react fast:

. *No answer to the first question.* "What needs me now?" has no single answer. It is spread over the overview
  sidebar, the decisions page, the reports page, the "Nebenher" block at the bottom of one project, and rows inside
  epics.
. *No next action.* Each view offers all acts with equal weight. The epic offers nine buttons; the plan offers four plus
  five controls in its head. Nothing tells the operator which one the state asks for.
. *Destructive acts dominate.* Red links on every project card, red buttons on every device row, and a red "abandon"
  as the strongest button of the project onboarding.
. *Dead ends.* Several paths end in a raw error code or a loading text that never ends.
. *One layout per view.* Page width, header form, and control style change from view to view. The operator relearns
  each page.

The prototype has strong parts to build on (link:findings.adoc#keep[Findings, Patterns to Keep]).

== Information Architecture Today

[source,text]
----
Header (flat, 7 items + 2 toggles + machine badge)
├── Laufende Arbeit ── project sidebar ── by plan | by epic ── ended work
│                                     └── plan page ── activity of a task
│                                     └── epic page ── findings / watches review
│                                     └── start (entry) ── sources ── ready ── started
├── Projekte ── project cards ── setup (project onboarding) | release | unenrol
├── Entscheidungen (count)
├── Berichte (count) ── completion report
├── Prozess-Designer
├── System ── cleanup
└── Einstellungen der Maschine ── /settings/machine  ⇄  /settings (devices, listener, credentials)
----

Observations:

* All seven items are peers. Items for daily work (running work, decisions) sit beside items for rare work (designer,
  system, settings).
* The counts in the header (decisions, reports) are the only signal of attention. Holds, failed landings, setup
  questions, and expiring tokens have no count.
* The plan and the epic are reached only through the overview or a breadcrumb. There is no search and no jump by id.
* Settings are split over two pages that link to each other.

[#direction]
== Direction

The proposals turn the app from "a window per resource" into "a control room":

* A home that answers "what needs me" (the attention inbox, UC-PLN-7 proposed).
* A left rail with three groups: work, records, machine. A command palette to jump by name (UC-PLN-8 proposed).
* Four page templates (triage list, object page, wizard, dashboard), used by every view.
* One primary act per state; the rest secondary; destructive acts only behind an overflow menu and a confirmation.
* One error pattern and one loading pattern, so no path ends without a way on.

Details: link:proposals.adoc[Proposals].
