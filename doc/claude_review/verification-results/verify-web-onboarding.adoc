This document records the three checks of the onboarding's screen registry and its variations against the merged
code. The checks come from link:../use-cases/verification.adoc[Use Cases, Verification]: `UC-V-02`, `UC-V-03`, and
`UC-V-05`. Each check ran against the mock runtime in Chrome, in `en` and `de`, dark and light, at 1440 px and
390 px, and every one of the mock scenario's 92 states was walked. Two checks fail as written and are routed to the
epic inbox (`rb-71-verify-web-onboarding-001` and `-002`). Nothing that was found was fixed.

The re-grounding of 2026-11-25 binds over the body of the plan where they differ. It retires `UC-V-03`'s
settings-frame expectation: `entry.*` states have no web screen (operator decision 2026-11-10,
`doc/design/web-app/onboarding.adoc:45`), so the fallback screen was verified instead and the check's own text is
stale. It also replaces `UC-V-05`'s reference to `MachineSettingsView.svelte`, which no longer exists, by the
screens the epic shipped.

== What the Checks Found

Two checks fail and are routed, each as one `finding` message to the epic inbox of `ui-improvements`:

. *`UC-V-02`* — three visible texts match the check's regex outside a `<code>` element: the two install-hint hostnames
on `harness.none` in a `<span class="…mono">`, and the example model id `e.g. anthropic/claude-sonnet-4-6` in the
model-id field's placeholder on `catalogue.select` (`pm-api/src/main/resources/messages/onboarding.en.properties:79`).
None is a state id; the fix is the element (or the check's wording). Plan concerned: PLAN-66 (D5, `harness.none`), and
the catalogue text of `UC-P-03`'s `catalogue.select` row.

. *`UC-V-05`* — `harness.none` does not show the per-harness name, path, failed check, answer, and fix that the
`UC-P-03` row asks for; the state carries the install hints and the engine's catalogue puts the per-harness cause
and fix under `harness.blocked`. Either the check's row or the state's contract has to move. The same message
records the clauses that could not be verified in the mock (the advice's recommendation on `catalogue.select`, the
conflict notice on the settings place, and the unavailable-provider variant on `defaults.review`) and the stale
`UC-V-03` text. Plans concerned: PLAN-66 (D5, `harness.none`), and the review documents for the two stale rows.

The messages are `rb-71-verify-web-onboarding-001` and `rb-71-verify-web-onboarding-002`. Nothing was fixed here.

[#residue]
== Residue

* *A visit to `entry.onboarding` withdraws the state resource.* Once a state that offers
  `GET /api/v1/onboarding/state` is left, that act answers `409 act_not_available` for every later state
  (`MockRuntimeEngine.java:3059-3087` keeps the offering state per request key). A walk that visits `entry.onboarding`
  in the middle therefore cannot draw any later screen. This run walked all 92 states, left `entry.onboarding` last,
  and restarted the mock between passes. The consequence for the check: no state id leaked even in the error card
  ("The onboarding state could not be loaded."). What the walk does not provide is a view of the 17 auto-advancing
  screens as themselves — the reload lands after their advance — so `UC-V-02`'s state-id clause is `not verified` for
  those 17 and proven for the 75 captured as themselves.

* *Auto-advancing states cannot be held.* Seventeen states carry an `auto` block and advance between 250 and 900 ms
  (`auto.scan`, `harness.probe`, `harness.enrol`, `harness.install-profile`, `catalogue.models`, `catalogue.advise`,
  `catalogue.record`, `roles.validate`, `store.check`, `store.record`, `github.check`, `providers.verify`,
  `providers.record`, `defaults.validate`, `defaults.record`, `settings.record` at 250 to 300 ms, and `wait.check` at
  900 ms); `harness.probe-failed` additionally fires its events at 100 and 200 ms but stays. A reload after the jump
  shows the state that followed; the walk records both, and the working screen itself is not screenshotable this way.
  Every other state was captured as itself.

* *The German arms show the mock's English summaries as the card heading.* The interface chrome, the buttons, the
  labels and the step bar are German; nine screens carry the state's `facts.summary` as their heading and the mock's
  summaries are English sentences ("Everything is decided.", "Choose the models plans may use", "Look for harnesses on
  this machine?"). `AutoResultScreen.svelte:74-78` and the screens beside it render the summary as delivered, the
  same rule the terminal client applies to runtime text. It is the mock's text, not the app's; the check's language
  clause is about the app's own texts and passes.

* *The `sessionStorage`/`localStorage` language choice is the browser's, by design.* Setting `pm_locale` by hand
  suppresses the adoption; the check was run with no stored choice, which is a browser that has not decided yet.

* *The daemon-routed `module-tests` run failed with exit `1` and its job log is outside this repository.* The
  in-process run of the same command is green and is what this document cites. The Maven guard reports
  `indeterminate` for the web module because vitest writes no Surefire report; the suite's own summary (188 files,
  3481 tests) is the evidence.
