[#launcher-runtime-loss]
== Runtime Loss
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

A step of the termination protocol of the runtime (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/01-pipeline-and-subprocesses.adoc#_process_termination_cancellation_protocol[Job Runtime Specification, Process Termination & Cancellation Protocol]) that the launcher takes alone:

* [[runtime-loss]]*Runtime Loss* (_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-44[PM-WATCH-JOB-44]_): A worker or a probe whose runtime died has no route out and no relay, but its process would run on until the next start settles it, with the copy of its harness's login in its data directory (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#worker-data-home[Per-Worker Data Home]). The launcher of these two kinds therefore notes the runtime's PID when it starts and checks its parent at least once per second; when its parent is no longer that process (the kernel reparented the launcher), it ends the command's tree as on the runtime's `SIGTERM` (the sweep of step 3a; on macOS, where the runtime's record of the process tree died with the runtime, through the process tree the launcher records itself) and exits. `PR_SET_PDEATHSIG` is not used: it fires when the thread that started the launcher ends, not when the runtime does. The recovery at the next start finds the job's process gone and settles the job `killed` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/runtime-lifecycle/01-startup-recovery-drain.adoc#per-project-recovery[Runtime Lifecycle Specification, Per-Project Recovery]). The other job kinds keep running: a build ends by its own exit or its budget, and the recovery settles it.
