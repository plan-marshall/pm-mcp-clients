[#launcher-linux-mechanisms]
== Linux Mechanisms of the Launcher
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

On Linux the launcher applies these mechanisms beside the Landlock read and write sets of every job (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement]):

* [[abi-floor]]*ABI Floor* (_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-41[PM-WATCH-JOB-41]_): ABI 1 denies every cross-directory rename and link (`LANDLOCK_ACCESS_FS_REFER` arrives with ABI 2), which breaks Gradle, npm, and Java `Files.move` with `EXDEV`. A kernel offering only ABI 1 is therefore treated as a kernel without Landlock: the runtime applies no ruleset and records `confinement: unavailable` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement], *Unavailable Landlock*). Below ABI 3 the ruleset does not govern truncation (`LANDLOCK_ACCESS_FS_TRUNCATE` arrives with ABI 3): a job can empty with `truncate(2)` or `open(O_TRUNC)` every file the user may write, outside its write set too, for example the settings file with a worker's deny rules (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement], *Consequence for the harness configuration*). On a kernel offering ABI 2 the runtime therefore applies the ruleset and records `confinement: partial(abi=2)`; it reports a job as `confined` only where ABI >= 3 was applied, and both clients show `partial(abi=2)` beside `confined` and `unavailable`. The value `partial(abi=2)` joins the `confinement` enumeration of the launch report and job record schemas with its implementation. The truncation below ABI 3 is an accepted residual platform risk (`PM-SEC-5`). Rights that later ABIs add are handled where the kernel offers them, and the applied ABI is recorded in every job record (`landlock_abi`).
* [[landlock-scopes]]*Scopes* (_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-42[PM-WATCH-JOB-42]_): every job runs as the operator's user, like the runtime and the operator's own processes. Landlock confines `ptrace(2)` wherever a ruleset is applied, which is from ABI 2 (<<abi-floor>>): a job cannot trace or read the memory of a process outside its domain, the runtime included, whatever `kernel.yama.ptrace_scope` says. Signals are confined only from ABI 6, through the scope `LANDLOCK_SCOPE_SIGNAL`, which `pm-exec` applies to every job wherever the kernel offers it: a job then cannot signal the runtime, another job, or a process of the operator, while the runtime still signals the job and the launcher still signals the job's descendants, which share its domain. For a worker and a probe `pm-exec` also applies `LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET` from ABI 6, so that neither reaches an abstract Unix socket outside its domain; a worker's network namespace already holds no abstract socket of the host, the scope is its second guard. Below ABI 6 a job can signal every process of the user, the runtime included; the damage is availability, since a killed runtime also ends every worker's egress proxy and relay (link:01-pipeline-and-subprocesses.adoc#runtime-loss[Runtime Loss]), and it is an accepted residual platform risk (`PM-SEC-5`) that the job record states through `landlock_abi`.
* [[seccomp-filter]]*System call filter* (_Implementation watch: link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-43[PM-WATCH-JOB-43]_): Landlock bounds what a job reaches on the filesystem, not the kernel interfaces it calls; a model whose weights carry a backdoor can try a kernel exploit through them. `pm-exec` therefore installs a seccomp filter (`SECCOMP_SET_MODE_FILTER` after `PR_SET_NO_NEW_PRIVS`, the BPF program compiled into the launcher, applied via FFM) as the last step before `execve` of the command, after the Landlock ruleset and, for a worker, after the launcher created its namespaces, so that the filter never denies the launcher's own setup. The filter allows by default, checks the architecture of every call (a call of another architecture or of the x32 ABI is killed), and refuses:
** creating namespaces and changing the mount table: `unshare`, `clone` with any `CLONE_NEW*` flag, `setns`, `mount`, `umount2`, `pivot_root`, `chroot`, and the mount API (`open_tree`, `move_mount`, `fsopen`, `fsconfig`, `fsmount`, `fspick`, `mount_setattr`); `clone3`, whose flags lie in memory the filter cannot read, fails with `ENOSYS`, so that the C library falls back to `clone`,
** kernel interfaces no build or harness needs: `bpf`, `perf_event_open`, `userfaultfd`, `kexec_load`, `kexec_file_load`, `init_module`, `finit_module`, `delete_module`, `keyctl`, `add_key`, `request_key`; `io_uring_setup`, `io_uring_enter`, and `io_uring_register` fail with `ENOSYS`, so that a runtime that tries `io_uring` falls back to ordinary I/O,
** sockets of any family but `AF_UNIX`, `AF_INET`, `AF_INET6`, and `AF_NETLINK` (no `AF_PACKET`, `AF_VSOCK`, `AF_BLUETOOTH`, `AF_ALG`, …).
+
A refused call fails with `EPERM` unless named above, so a tool sees an ordinary error. The filter is inherited by every descendant and cannot be removed. The same filter applies to every job kind; a build that needs a refused call (a rootless container engine started by the build itself) fails with its tool's error, and the container engine of the enrolment opt-in, which runs outside the job, is unaffected (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#container-engine[Job Runtime Specification, Container Engine]). The launch report states the filter (`seccomp: applied`), and every job record carries it (the member `seccomp` joins the launch report and job record schemas with its implementation); a kernel that refuses the filter makes the launcher exit `126`, as for a ruleset that cannot be applied. On macOS, which has no seccomp, the sandbox profile is the guard and the job record states `seccomp: not_applicable` (<<macos-confinement>>).
* [[job-without-network]]*A job without network*: a job of a kind that needs no network, the `speech` job of the local transcription (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/01-roles-and-configuration.adoc#transcribe-role[Model Work Specification, Speech Transcription (`transcribe`)]), gets none: on Linux the launcher starts it in an empty network namespace of its own (a new user and network namespace, unprivileged, without the forwarded proxy port of a worker), on macOS its sandbox profile denies the network and the resolver's Mach services (<<macos-confinement>>); where that confinement cannot be applied, the job is refused before it receives its input.

[#macos-confinement]
== macOS Confinement (Seatbelt)
_Implementation watch: link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/implementation-watch/job-runtime.adoc#PM-WATCH-JOB-40[PM-WATCH-JOB-40], link:../../implementation-watch/job-runtime.adoc#PM-WATCH-JOB-42[PM-WATCH-JOB-42]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-SEC-5[PM-SEC-5: Subprocess Environment Sanitization & Linux Filesystem Confinement]_

On macOS the `pm-exec` launcher confines every job before `execve` with a sandbox profile of the platform (Seatbelt, applied with `sandbox_init` before the job's image starts), which every descendant inherits and which the job cannot remove:

* *The same sets*: the profile denies by default and allows reading the whole filesystem except `<PM_MCP_BASE>` (its own job-private directory excepted, as on Linux), for a worker only its listed read set (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#worker-read-set[Job Runtime Specification, Worker Read Set]), and writing exactly the write set of the Linux ruleset (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement (Landlock)]), computed from the same enrolment at job start. `PR_SET_NO_NEW_PRIVS` has no macOS counterpart; the profile denies `process-exec` of setuid and setgid files instead.
* *Network*: for a worker the profile allows outbound connections to the loopback port of its egress proxy and to the runtime socket only (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#worker-egress[Job Runtime Specification, Worker Egress Proxy]); for a job without network it denies the network and the resolver's Mach services (<<job-without-network>>); for the other job kinds it allows the network, but a connection to a Unix socket only to one of the job's socket list or one the job itself created (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#pathname-sockets[Job Runtime Specification, Unix sockets]), so that no job reaches a terminal multiplexer, a Mac app's local server, or the container engine without the opt-in.
* *Name resolution*: on macOS a lookup goes to the system resolver over Mach IPC, which the network rules do not govern. For a worker the profile therefore denies the lookup of the resolver's services (`mach-lookup` of `com.apple.mDNSResponder` and `com.apple.dnssd.service`), so that a worker resolves no name of its own (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#worker-name-resolution[Job Runtime Specification, Name Resolution]); for a job without network it denies them as well (<<job-without-network>>); for the other job kinds it allows them.
* *Signals and other processes*: the profile denies a job sending a signal to a process outside its own sandbox (`signal` with target `others`) and reading the information of such a process (`process-info*` with target `others`), the counterpart of the Landlock scopes (<<landlock-scopes>>).
* *Verified per release*: the profile language is a platform interface Apple does not document. The release verifies the profile on every macOS version it supports with the confinement tests of the Linux ruleset (a write outside the set, a read of `<PM_MCP_BASE>`, a connection that bypasses the proxy, a worker's name lookup, a signal to the runtime, each refused); a macOS version on which the profile cannot be applied refuses a job without network before it receives its input (<<job-without-network>>), runs the other jobs unconfined and records `confinement: unavailable` in every job record and the runtime status, with the consequence for a chat's worker of an unavailable Landlock (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/job-runtime/02-confinement-and-environment.adoc#_linux_filesystem_confinement_landlock[Job Runtime Specification, Linux Filesystem Confinement (Landlock)]).
* *Recorded*: a confined job records `confinement: seatbelt` in its job record.
