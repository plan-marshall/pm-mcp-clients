[#web-app]
== Web App (`pm-web-app`)

* *Build*: SvelteKit 3 (release candidate, pinned; moved to 3.0 final when released) with Svelte 5 and TypeScript, built as a static single-page app (`@sveltejs/adapter-static`, `ssr = false`, fallback page) by `frontend-maven-plugin` with pinned Node and npm (`npm ci` from `package-lock.json`), tested with Vitest, and packaged as a resource JAR (`META-INF/resources`) that `pm-mcp-server` depends on and `pm-mcpd` serves. The npm packages are covered by the CycloneDX SBOM. During development the Vite dev server proxies `/api` to the loopback listener of a running runtime.
* *Views*: The web app's views are its design (link:../../design/web-app/README.adoc[Web App]): the entry and pairing, the machine's onboarding and settings, the projects with their onboarding, starting work, the overview of running and ended work, a plan's process and an epic, the decisions, the holds and the acts on plans and epics, the reports, the system view, the cleanup, the paired devices, and the process designer. Each reads the operator representations and event streams of the local API (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#local-api[Runtime & Interaction Model Specification, Local API]), never a store and never a model-facing representation.
* *Dependable view and channel*: Both clients of the operator are dependable views of every plan, epic, worker, and task and dependable channels of every operator wait (`PM-SEC-7`, `PM-WF-12`, `PM-WF-20`). The web app shows every open operator wait with its facts, its proposal, and its operator links, a decision with its parts, options, support, and recommendation (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#decision-structure[Model Work Specification, The Decision Structure]), and answers it through the scope-qualified answer endpoint of the local API (channel `web`; the first valid answer wins, a later one is refused `already_answered`). On the event of a newly opened decision or waiver request it raises a browser notification where the device granted the permission; a decision answered in the terminal client is withdrawn with a note that says so.
* *Texts*: The web app holds no text of its own besides its fallback for a failed load: it loads the message catalogue of the interface language from the runtime and renders every runtime text from its message key and arguments, and external and model text as plain text, as the runtime serves it without hidden characters (link:../runtime-model/06-event-catalogue.adoc#client-text-hidden-characters[Runtime & Interaction Model Specification, No Hidden Character Reaches a Client]), a role's reply in the chat as the Markdown subset of <<web-chat-text>> (link:../../../../plan-marshall-documentation/doc/specification/module-structure.adoc#i18n[Module Structure Specification, Languages and Internationalisation]).
* *Live updates*: The app reads the event streams with `fetch()` and a `ReadableStream`, because `EventSource` cannot send an `Authorization` header; a credential never appears in a URL. It reconnects with `Last-Event-ID`.
* *Browser storage*: The device secret is kept in `localStorage` with its `device_id`, so the pairing survives browser restarts, and is sent as `Authorization: Bearer <device secret>` on every API request but the redemption of a code (`POST /api/v1/pair`, which carries no credential); the app never uses cookies. Its exposure to injected script is contained by the security headers (xref:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-security-headers[Request Validation & Security Headers]), Trusted Types, no third-party scripts or origins, no `{@html}` or other raw-HTML sink (all server text, the activity of a worker included, is rendered as text, the chat's replies as elements the app creates, <<web-chat-text>>), and lockfile-pinned dependencies; revocation and idle expiry are the recovery. Sender-constrained credentials (a non-extractable WebCrypto key, DPoP) are deferred (link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#L-2[Later Improvements, L-2]).

[#web-diagrams]
=== Diagrams

The web app draws a positioned layout (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#process-layout[Runtime & Interaction Model Specification, Layout]) as SVG elements it creates itself, styled by classes of its own stylesheet; it never inserts markup it received. A fenced Mermaid block in text a model wrote is rendered in the browser by the bundled renderer `pele` (MIT, no runtime dependency) to an SVG string with links, images, and icons switched off and the renderer's source bound; the string is shown as an image from an object URL, never inserted into the document, with the colours of both colour schemes written into the SVG, since an image does not read the page's stylesheet. A block the renderer refuses is shown as its source with the error as text. The security headers of the web listeners stay unchanged for both (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-security-headers[Request Validation & Security Headers]).

[#web-chat-text]
=== The Chat's Text

A role's reply in the chat (`format: markdown`, link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#chat-routes[Runtime & Interaction Model Specification, The Chat's Routes]) is rendered as a closed subset of Markdown: paragraphs, emphasis, inline code, block quotes, lists, tables, code blocks without colours, links, and references: each entry of the turn's `refs` (a task id, a file as `path:line`, a decision's address, a plan id) where its text names it, shown as a link to its target. A fenced Mermaid block in a reply is a diagram of <<web-diagrams>>. The app splits the text into tokens with the bundled lexer `marked` (MIT, no runtime dependency) and creates an element of its own for each token of the subset, its text in a text node; it never inserts markup and holds no HTML string. Raw HTML and every token outside the subset are shown as their source text, a link only with `http` or `https` and opened in a new tab, an image as a link and never loaded. The operator's messages, untrusted turns, and notices are never passed to the lexer. The security headers of the web listeners stay unchanged (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-security-headers[Request Validation & Security Headers]).

[#web-voice]
=== Voice Input

The app opens the microphone only from the operator's press until _Stop_ or _Cancel_, after the browser asked for the permission on first use; the security headers allow it for the app's own origin only (`Permissions-Policy: microphone=(self)`, link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-security-headers[Request Validation & Security Headers]). It offers the browser's own recognition only where the machine allows that method, the project of the field does not narrow it away, and the browser has it, and sends a recording only to its own origin, to the transcription endpoint (link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#transcriptions[Runtime & Interaction Model Specification, Transcriptions]), keeping it in memory until the text arrives or the operator discards it, never in storage. Which allowed method a browser uses is a choice of that browser, kept in its own storage. The dictation of the operating system needs nothing of the app.

[#web-pairing-page]
=== The Pairing Page

The web app's pairing page reads the code from the fragment (or from manual input, normalized to upper case without `-` and spaces) and removes the fragment with `history.replaceState`. An app that holds a device secret the runtime still accepts (a `200` on an authenticated request) does not redeem the code and shows its start view: the browser keeps its device, no second device is created for it, and the unredeemed code stays open for another device. Any other failure of that request but a `401` is shown as a retryable error and redeems nothing. Only an app without a device secret, or whose secret the runtime refused with `401`, sends `POST /api/v1/pair` with `{code}` and the label it proposes from the browser and its machine. The runtime redeems the code and answers `{device_id, label, device_secret}` once, or the same `pairing_invalid` for every failure (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-pairing[Pairing Protocol]); the app keeps what it received as its browser storage says (<<web-app>>, Browser storage). A browser that holds no device secret, another browser or one whose storage was cleared, shows the pairing page, which names `pm-operator web open --pair` and the terminal client.
