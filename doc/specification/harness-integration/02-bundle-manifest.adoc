== Embedded Harness Bundle `bundle-manifest.json` Schema
_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-DIST-1[PM-DIST-1: Single Version Authority & Embedded Harness Bundles]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-DIST-2[PM-DIST-2: Embedded Bundle Extraction & Interactive Harness Installer]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-DIST-3[PM-DIST-3: Worker MCP Connection per Launch]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-DIST-4[PM-DIST-4: Bundle Upgrade Detection & Atomic Reconciliation]_

_See Requirement link:../../../../plan-marshall-documentation/doc/Requirements.adoc#PM-DIST-5[PM-DIST-5: Multi-Harness Concurrent Coexistence on One Machine]_

_Implementation watch: link:../../implementation-watch/harness-integration.adoc#PM-WATCH-CLIENT-5[PM-WATCH-CLIENT-5]_

The runtime binary `pm-mcpd` embeds the templates for all supported harness bundles under `classpath:/bundles/<harness_id>/` (`claude`, `opencode`, `antigravity`, `codex`) and applies them on the operator's acts of both clients, `pm-operator harness install|update|remove` and the same acts in the web app, the onboarding's offer of each enrolled harness's bundle among them (link:../cli-and-security/01-cli-and-installer.adoc#harness-installer[CLI, Coordination & Security Specification, Harness Bundle Installer]); `pm-operator harness status` needs no runtime and reads the install records directly. The bundle version is the release version, which every binary of a release carries; `pm-operator harness status` evaluates the drift checks against its own. A bundle installs no MCP configuration into a harness: a harness is a worker only, and a worker's MCP connection is the per-call configuration the runtime composes into its launch (`PM-DIST-3`, `PM-CLIENT-1`; link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/model-work/04-worker-launch.adoc#launch-contract[Model Work Specification, Launch Contract]). Multiple harnesses (`claude`, `opencode`, `antigravity`, `codex`) can be installed and operated concurrently on the same machine and repository (`PM-DIST-5`).

[#bundle-manifest-scopes]
*One manifest per harness, two scopes*: A harness has exactly one manifest. Files that both scopes install (the shim skill) are declared once in `files[]` and placed through the scope's `directories` map; the `scopes` object holds a `user` and a `project` section, each with its target root, its `directories`, its `shared_configs[]` (harness configuration files with owned keys and owned elements), and the files that only that scope installs (`files[]` inside the section, with a `target_path` relative to the target root). `pm-operator harness install --scope <scope>` selects one section; a harness that supports only one scope declares only that section. `pm-operator harness install|update --scope project` refuses while the project has non-terminal plans or epics and names them; the `user` scope is unaffected (link:../cli-and-security/01-cli-and-installer.adoc#harness-installer[CLI, Coordination & Security Specification, Harness Bundle Installer]). The install record stores the scope (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#machine-state-records[Store Schemas Specification, Machine State Records]).

*Owned elements*: Besides owned keys (a whole value at a dotted key path), a shared configuration owns individual elements of arrays that other parties share, identified by their exact normalized value:

* `permission_rule`: a harness permission rule in the harness's `deny`, `ask`, or `allow` list, classed `enforcement` (a defense-in-depth boundary whose removal or weakening is operator-gated, link:../cli-and-security/01-cli-and-installer.adoc#harness-operator-gate[CLI, Coordination & Security Specification, Operator Gate]) or `convenience`. The normalized value is the rendered rule text (placeholders `{pm_mcp_base}` and `{home}` resolved, surrounding whitespace removed). A rule template naming `{pm_mcp_base}` renders to one owned element per path form of the harness's rule syntax: for `claude` always the absolute form (`Read(//<abs>/**)`, `Edit(//<abs>/**)`) and, when `<PM_MCP_BASE>` lies under `{home}`, additionally the home-relative form (`Read(~/<rel>/**)`, `Edit(~/<rel>/**)`, `<rel>` relative to `{home}`).

A rule that names a machine path (the `<PM_MCP_BASE>/**` deny rules) is never written into a team-shared, git-tracked file: in the `project` scope it goes to the harness's machine-local project settings file (for `claude`, `.claude/settings.local.json`), so the shared files keep zero user-specific paths (`PM-DIST-2`).

=== Normative `bundle-manifest.json` JSON Schema (Draft 2020-12)

[source,json]
----
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://cuioss.de/plan-marshall-mcp/schemas/harness-bundle-manifest-v1.json",
  "title": "HarnessBundleManifest",
  "description": "Manifest of the files, shared configuration keys, and shared configuration elements owned by PM-MCP for one client, with one section per installation scope.",
  "type": "object",
  "$defs": {
    "relativePath": {
      "type": "string",
      "pattern": "^(?!/)(?!.*\\.\\.)[A-Za-z0-9_./-]+$"
    },
    "sha256": {
      "type": "string",
      "pattern": "^[0-9a-f]{64}$"
    },
    "fileBase": {
      "type": "object",
      "properties": {
        "bundle_path": {
          "$ref": "#/$defs/relativePath",
          "description": "Relative path under classpath:/bundles/{client}/files/{bundle_path}."
        },
        "kind": {
          "type": "string",
          "const": "shim_skill",
          "description": "shim_skill: the shim skill of PM-SKILL-4."
        },
        "sha256": {
          "$ref": "#/$defs/sha256",
          "description": "SHA-256 hex digest of the exact UTF-8 file content."
        },
        "mode": {
          "type": "string",
          "enum": ["0644", "0755"]
        }
      },
      "required": ["bundle_path", "kind", "sha256", "mode"]
    },
    "sharedFile": {
      "description": "A file installed by every scope, declared once and placed through the scope's directories map.",
      "allOf": [{ "$ref": "#/$defs/fileBase" }],
      "properties": {
        "bundle_path": true, "kind": true, "sha256": true, "mode": true,
        "target_dir": {
          "type": "string",
          "const": "skills",
          "description": "Key into the selected scope's directories map."
        },
        "target_name": {
          "type": "string",
          "pattern": "^[A-Za-z0-9_.-]+(/[A-Za-z0-9_.-]+)?$",
          "description": "File name below the target directory; a skill is placed as <skill-name>/SKILL.md."
        }
      },
      "required": ["target_dir", "target_name"],
      "unevaluatedProperties": false
    },
    "scopeFile": {
      "description": "A file installed only by one scope.",
      "allOf": [{ "$ref": "#/$defs/fileBase" }],
      "properties": {
        "bundle_path": true, "kind": true, "sha256": true, "mode": true,
        "target_path": {
          "$ref": "#/$defs/relativePath",
          "description": "Target path relative to the scope's target root."
        }
      },
      "required": ["target_path"],
      "unevaluatedProperties": false
    },
    "ownedElement": {
      "type": "object",
      "properties": {
        "kind": {
          "type": "string",
          "const": "permission_rule"
        },
        "array_path": {
          "type": "string",
          "minLength": 1,
          "description": "Dotted key path of the shared array (e.g. 'permissions.deny')."
        },
        "list": {
          "type": "string",
          "enum": ["deny", "ask", "allow"],
          "description": "The harness list the rule belongs to."
        },
        "class": {
          "type": "string",
          "enum": ["enforcement", "convenience"],
          "description": "Enforcement rules are operator-gated on removal or weakening."
        },
        "value": {
          "type": "string",
          "minLength": 1,
          "description": "The rule text (placeholders {pm_mcp_base} and {home} allowed)."
        }
      },
      "required": ["kind", "array_path", "list", "class", "value"],
      "additionalProperties": false
    },
    "sharedConfig": {
      "type": "object",
      "description": "Shared harness configuration file where PM-MCP merges only owned keys and owned elements.",
      "properties": {
        "target_path": { "$ref": "#/$defs/relativePath" },
        "format": {
          "type": "string",
          "enum": ["json", "toml"]
        },
        "owned_keys": {
          "type": "array",
          "items": {
            "type": "string",
            "description": "Dotted key path owned by PM-MCP."
          }
        },
        "entries": {
          "type": "object",
          "description": "Map from each owned_key to the JSON/TOML value to merge into target_path."
        },
        "owned_elements": {
          "type": "array",
          "items": { "$ref": "#/$defs/ownedElement" }
        },
        "sha256": {
          "$ref": "#/$defs/sha256",
          "description": "SHA-256 hex digest of the canonicalized 'entries' object and 'owned_elements' array."
        }
      },
      "required": ["target_path", "format", "owned_keys", "entries", "owned_elements", "sha256"],
      "anyOf": [
        { "properties": { "owned_keys": { "minItems": 1 } } },
        { "properties": { "owned_elements": { "minItems": 1 } } }
      ],
      "additionalProperties": false
    },
    "scope": {
      "type": "object",
      "properties": {
        "target_root": {
          "type": "string",
          "enum": ["user_home", "project_root"],
          "description": "user_home for the user section, project_root for the project section."
        },
        "directories": {
          "type": "object",
          "description": "Target directory of each target_dir used by the shared files, relative to the target root.",
          "propertyNames": { "const": "skills" },
          "additionalProperties": { "$ref": "#/$defs/relativePath" }
        },
        "shared_configs": {
          "type": "array",
          "items": { "$ref": "#/$defs/sharedConfig" }
        },
        "files": {
          "type": "array",
          "items": { "$ref": "#/$defs/scopeFile" }
        }
      },
      "required": ["target_root", "directories", "shared_configs", "files"],
      "additionalProperties": false
    }
  },
  "properties": {
    "schema_version": {
      "type": "integer",
      "const": 1
    },
    "harness_id": {
      "type": "string",
      "enum": ["claude", "opencode", "antigravity", "codex"]
    },
    "bundle_version": {
      "type": "string",
      "pattern": "^[0-9]+\\.[0-9]+\\.[0-9]+(-[A-Za-z0-9.-]+)?$",
      "description": "Equals the release version of the binaries that embed the bundle."
    },
    "manifest_sha256": {
      "$ref": "#/$defs/sha256",
      "description": "SHA-256 hex digest over the canonicalized 'files' array and 'scopes' object."
    },
    "files": {
      "type": "array",
      "items": { "$ref": "#/$defs/sharedFile" }
    },
    "scopes": {
      "type": "object",
      "properties": {
        "user": {
          "allOf": [{ "$ref": "#/$defs/scope" }],
          "properties": { "target_root": { "const": "user_home" } }
        },
        "project": {
          "allOf": [{ "$ref": "#/$defs/scope" }],
          "properties": { "target_root": { "const": "project_root" } }
        }
      },
      "minProperties": 1,
      "additionalProperties": false
    }
  },
  "required": [
    "schema_version",
    "harness_id",
    "bundle_version",
    "manifest_sha256",
    "files",
    "scopes"
  ],
  "additionalProperties": false
}
----

The settings file names and rule forms of the `claude` example are established Claude Code conventions; the corresponding values of the other harnesses are _(provisional)_ like their other harness facts and are verified against a live harness before their bundle ships.

[#recommended-permission-rules]
*Recommended permission rules*: On every harness with permission rules, each scope's bundle installs as `enforcement` rules the machine root deny rules (Ownership & Digest Verification, item 5) and one deny rule for the whole operator binary `pm-operator` (`Bash(pm-operator:*)`), rendered in the harness's rule syntax and placed in its `ask` list where the harness has no `deny` list. The rule covers every verb of `pm-operator`; no rule names a sub-command, and the relay binary `pm-mcp`, whose one verb is `serve` (`pm-mcp serve --job`, the job relay a worker's launch starts), stays allowed. The rules keep a model-driven shell from running operator verbs through the harness's shell tool by accident; they are defense in depth only, since the operator proof rests on the checks of `pm-operator` (link:../cli-and-security/02-operator-channel.adoc#operator-channel-isolation[CLI, Coordination & Security Specification, Operator Channel Isolation], link:../../../../plan-marshall-documentation/doc/later-improvements.adoc#L-1[Later Improvements, L-1]).

=== Ownership & Digest Verification on Install/Update/Remove
_Implementation watch: link:../../implementation-watch/harness-integration.adoc#PM-WATCH-CLIENT-7[PM-WATCH-CLIENT-7], link:../../implementation-watch/harness-integration.adoc#PM-WATCH-CLIENT-9[PM-WATCH-CLIENT-9], link:../../implementation-watch/cli-and-security.adoc#PM-WATCH-CLI-12[PM-WATCH-CLI-12]_

1. *Install Record Persistence (`PM-DIST-2`, `PM-DIST-4`)*: When `pm-operator harness install` or `update` applies a manifest, the runtime records per `(harness_id, scope, target root)` the installed `bundle_version`, the `scope`, the absolute target root, the `sha256` of every written file and owned key value, and every owned element with its normalized value and its `sha256` in `<PM_MCP_BASE>/state/install-records.json` (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/store-schemas/12-machine-stores.adoc#machine-state-records[Store Schemas Specification]).
2. *Modification Conflict Protection (`PM-DIST-4`)*: During `pm-operator harness update` or `remove`, before overwriting or deleting any recorded file or owned key, the runtime computes the current on-disk SHA-256 and compares it with the recorded `sha256`; a recorded owned element is unmodified only while an element with its recorded normalized value is present in its array. A modified entry (digest mismatch, or an element edited or deleted by the user) is skipped and reported in the client, and the user's change is preserved unless `--force` is confirmed interactively.
3. *Surgical Shared Configuration Merging (`PM-DIST-5`)*: For `shared_configs[]`, the runtime parses the existing JSON/TOML file and changes *only* the keys listed in `owned_keys` and the recorded owned elements: `install` appends a missing owned element (one already present with the same normalized value is neither duplicated nor recorded as owned), `update` replaces the recorded elements and appends new ones, and `remove` deletes the recorded elements only. All other MCP servers, hooks, rules, and settings owned by the user or by sibling AI harness installations are preserved, including their order.
4. *Permission Rule Grammar (`PM-DIST-2`, `PM-CRED-3`)*: `pm-operator harness install` and `update` refuse to render a harness permission rule with a non-terminal `*` and refuse a deny rule for a path containing whitespace (such a path cannot be protected by a deny rule), reporting the machine-root rule they could not install. The rule grammar check has one implementation, shared by the build-time bundle manifest tests and the installer.
5. *Machine Root Deny Rules (`PM-CRED-3`, `PM-SEC-2`)*: On every harness with file-tool permission rules, the bundle installs deny rules for `<PM_MCP_BASE>/**`, which cover the file credential store, as `enforcement` `permission_rule` elements in the absolute form and, when `<PM_MCP_BASE>` lies under the home directory, also in the home-relative form (<<bundle-manifest-scopes,Owned elements>>), so harness file tools cannot read or write the enrolment files `enrolments/`, `state/`, `run/` (the runtime token), or the file credential store. This is defense in depth only: a harness shell tool bypasses it, and no `Bash` rule tries to cover shell access vectors to `<PM_MCP_BASE>`; enrolment integrity rests on the runtime's HMAC verification (link:../cli-and-security.adoc[CLI, Coordination & Security Specification]). If `<PM_MCP_BASE>` contains whitespace, the installer refuses under item 4.
6. *Side-by-Side with Legacy `plan-marshall` (`PM-MIG-2`, `PM-DIST-5`)*: A bundle installs no `plan-marshall` executor, no `execute-script.py` permission rule, and never edits, removes, or takes over artifacts or permission rules of an installed `plan-marshall` plugin. Its skill name and its owned configuration elements are distinct from the `plan-marshall` plugin's: the shim skill is `mcp-plan-marshall-skills`, and the bundle installs no command; it installs no agent file, since workers compose their agent per launch (link:https://github.com/plan-marshall/pm-mcp-core/blob/main/doc/specification/harness-profiles/01-profile-schema.adoc#headless-block[Harness Profile Schema, `headless`]); a build-time bundle manifest test fails on a name that collides with the `plan-marshall` plugin's installed names. Both may therefore be installed on one machine and used in the same repository.
7. *Drift Checks (`PM-DIST-4`)*: `bundle_outdated` compares the recorded `bundle_version` with the release version of `pm-operator` (every binary of a release carries the release version, which is the bundle version); `bundle_modified` compares the recorded digests and normalized values with the disk and lists the edited and missing entries. Both are reported by `pm-operator harness status`, shown in both clients as the need `bundle_drift`, and fixed by the update, `pm-operator harness update` or the same act in the web app (`--force` for modified entries) (link:../cli-and-security/01-cli-and-installer.adoc#bundle-drift-notice[CLI, Coordination & Security Specification, Bundle Drift Notice]).
