= Work Packages of `pm-mcp-clients`
:toc: left
:toclevels: 2
:nofooter:

One plan file per work package. A work package is what one session takes up and lands as one pull request here, updating the documents in `plan-marshall-documentation` as part of the same work. The files hold the tasks; what the tasks mean and require is stated in the documentation repository and linked by relative paths. The links assume the repositories checked out beside each other (`../plan-marshall-documentation`, `../pm-mcp-clients`, `../pm-mcp-core`, `../plan-marshall-mcp`); they do not resolve in the web view of a single repository.

The modules of this repository, their packages and their dependency rules are listed only in the link:../../../plan-marshall-documentation/doc/specification/module-structure.adoc[Module Structure Specification]; each package file names where it lands.

[#packages]
== Packages

The packages listed serve roadmap Milestones 2 to 4, and the packages of the link:epic-clients.adoc[client work] (the mock runtime, the two clients, and their test infrastructure, which serve use cases not yet in a roadmap milestone); later milestones are not cut into packages yet, except the module `pm-web-app` of Milestone 11, which `web-app-foundation` pulls forward for the client work, and a package that names one of them as the home of something says what is left out here. This table is the only place that states the status of a package and what it depends on; the package files do not repeat either. A package is *ready* when its status is `open` and everything in its _Depends on_ column is `done`. Ready packages can be worked in parallel, also across the repositories. A dependency that has no work package yet keeps a package `blocked`; it is replaced by the package when that is planned. A package that depends on a `blocked` package is `blocked` too.

[#how]
== How to Work a Package

* *Design packages are run directly.* A package whose file says _Worked by: a Claude Code session directly_ (`cli-design`, `web-design`) is not worked through plan-marshall and is not part of an epic; its file says how it is run, and its row is set to `done` once the operator accepted the design. The rules below apply to every other package.
* *Take it.* A package is worked in the usual plan-marshall flow: a branch, the commits of the plan, and a pull request opened at finalize. The pull request of the package sets its row to `done` in the table above, within its commits. Nothing marks a package as taken before that pull request is open, so list the open pull requests of this repository for one that names the package before starting. A package whose dependency lies in another repository is ready when that dependency is merged there and its `SNAPSHOT` is deployed.
* *Trace first.* The packages are cut from the roadmap items, with the requirements, sections, and watch documents the roadmap names. Before code, build the trace matrix of the project skill `traced-implementation` (`../plan-marshall-documentation/.claude/skills/traced-implementation/SKILL.md`) for the package: every requirement bullet, every specification section, and every watch item anchored to them, each with its destinations. Split or extend the package where the matrix shows it; a row left out is recorded `out of slice` with its reason.
* *Present and remaining.* The roadmap item a package serves states what the code already covers. Read it first: a package delivers the remainder, never a second form of what exists.
* *Dependencies are the order.* The roadmap milestone a package serves says for which exit it is needed, not when it may start. Add a dependency you discover, and a new package, to the table above.
* *Done.* A package is done with its guarding tests, `verify`, `verify -Ppre-commit` (its rewrites reviewed and committed), `verify -Pcoverage`, and `verify -Pintegration-tests` green, and the native build where it touches a binary.
* *Documents.* The code documentation of a package and its work package file with the index live here. The specification and requirement documents live in `plan-marshall-documentation`: a statement of a requirement or specification that a package proves wrong is corrected there, never worked around in code, and the concept, developer, and user documentation of the package, the deletion of the implemented specification sections and watch items, and the update of the roadmap item are made there as well. The plan of the package updates those documents directly, as part of its own work, and merges that pull request itself once the code is on `main` here.
