== What

The package implements in `pm-api` and `pm-mock-runtime` the client side of the specification sections listed under _Trace_; the engine side is `pm-mcp-core`'s `project-onboarding-unit`. A statement of them that the implementation proves wrong is corrected in `plan-marshall-documentation` in the same plan (link:README.adoc#how[How to Work a Package]).

* *The projects of the machine* (UC-PRJ-2): every enrolled project (`GET /api/v1/projects?all`: display name, remote, ready or what its setup needs, `needs_operator`, counts, last activity, released), the favourites with their order (`PUT /api/v1/explorer/favourites`), recent and most used; the event `project.changed`.
* *A project's onboarding* (UC-PRJ-1), opened by `POST /api/v1/project-onboardings` and addressed as an entry until `project.enrol` moves it into the project's workspace scope (`entry.moved`), represented on the scheme of `operator-interaction-contract` in the setup's order: `project.checkout`, `project.consent` (`inspect_checkout`: reads the checkout and runs the host tools' version probes, changes nothing), `project.detect`, `project.run-consent` (yes, yes for this project remembered in `consents.json` by the scripts' digests, never in the enrolment; _no_ going on to `project.identity` with what the scripts would have found `unknown`, the version among it, and not asked again in the run), `project.probe`, `project.identity`, `project.enrolment`, `project.enrol`, the setup's first states (`setup.entry` to `setup.check-operator-files`), `project.operator` (the operator's values only: model language, allowed models, role assignment, method and asking axes, integration variant and credential of each provider, commit identity) with `setup.probe-integration-variants` and the credentials returning to it, and a value changed meanwhile refused with `conflict` and its current value (as `onboarding-contract` represents it), `setup.project-settings`, `setup.detect-domains`, `setup.discover-modules`, `setup.seed-build-map`, `setup.select-providers`, `setup.configure-finalize` (the landing variant, a machine default that does not fit refused with the reason), `setup.probe-merge-queue` and `setup.merge-queue`, the two consents of tokens (kind `model_cost`, `setup.qualify-consent` and `setup.enrich-consent`) with their _no_ skipping the step, `setup.commit-changes` and `setup.land-changes`, `setup.needs-repair` with its retry; the login environment the web app's onboarding takes from the one captured last, said so.
* *The release and the unenrolment* (UC-PRJ-3, `POST /api/v1/projects/{project_id}/release` and `…/unenrol`): `project.release-confirm` with what they end (every plan with the outcome `released`, every epic with the `terminal_reason` `released`, archived in the project's machine store with the epic's ledger left in `.marshall/epics/`, the pending entries deleted with their sources, a running onboarding of the project ended), `project.release-wait` for a running short landing within its bound and the refusal `release_landing_pending` when it does not finish, ending nothing; the refusal `scope_active` of an unenrolment while work runs; an unenrolment that removes the enrolment only, the project's machine store and its archive kept and found again by an enrolment from the same checkout.
* *The scenarios of the mock runtime* (`projects-<case>`): no project, projects with favourites and recent ones, a project not ready, a released project, an onboarding run to the end, one stopped at a failing check and retried, a script of the checkout run on consent, remembered for the project, and refused, a credential refused in the own settings, a machine landing that does not fit the project, a qualification and an enrichment refused (the step skipped, the project ready), a commit without a push remote, a later run of one step, an operator value changed in two clients with the second refused as `conflict`, a question of the setup answered (one a task asked, its chat with that task's role, and one the setup's workflow raised, its chat disabled with the reason); a release with plans in every state, an epic, a pending entry, and a running onboarding, one waiting for a removal from git, and one refused because the removal does not finish; an unenrolment refused while work runs.
