== What

* *Specification first*: the package writes the change The Projects of the Machine, and the client side of Onboarding a Project as One Process, into `plan-marshall-documentation` as part of its own work (link:../../../plan-marshall-documentation/doc/discussions/client-specification-changes.adoc#slicing[Specification Changes for the Clients, Packages]), once the use cases are agreed, and opens that pull request beside its own.
* The resource records of every enrolled project (display name, remote, ready or what its setup needs, `needs_operator`, counts, last activity, released), the favourites with their order, recent and most used; the writes of a favourite and of its order.
* The representation of the project onboarding's states for both clients, on the scheme of `operator-interaction-contract`, in the setup's order: `project.consent` (`inspect_checkout`: reads the checkout and runs the host tools' version probes, changes nothing), `project.run-consent` (yes, yes for this project remembered in `consents.json` by the scripts' digests, never in the enrolment; no going on without the scripts, not asked again in the run), `project.identity`, `project.enrolment`, the setup's first states, `project.operator` (the operator's values only: model language, allowed models, role assignment, method and asking axes, integration variant and credential of each provider, commit identity) with the probe of the variants and the credentials returning to it, and a value changed meanwhile refused with `conflict` and its current value (as `onboarding-contract` represents it), `setup.project-settings`, `setup.detect-domains`, `setup.discover-modules`, `setup.seed-build-map`, `setup.select-providers`, `setup.configure-finalize` (the landing variant, a machine default that does not fit refused with the reason), `setup.probe-merge-queue` and `setup.merge-queue`, the two consents of cost with their _no_ skipping the step, `setup.commit-changes` and `setup.land-changes`, `setup.needs-repair` with its retry.
* The release and the unenrolment of a project: the confirmation with what they end (every plan with the outcome `released`, every epic with the `terminal_reason` `released`, the pending entries deleted with their sources, a running onboarding of the project ended), the wait for a running `git.land-removal` within its bound (`project.release-wait`) and the refusal when it does not finish, ending nothing; the refusal of an unenrolment while work runs; an unenrolment that removes the enrolment only, the project's machine store and its archive kept and found again by an enrolment from the same checkout.
* The scenarios of the mock runtime: no project, projects with favourites and recent ones, a project not ready, a released project, an onboarding run to the end, one stopped at a failing check and retried, a script of the checkout run on consent, remembered for the project, and refused, a credential refused in the own settings, a machine landing that does not fit the project, a qualification and an enrichment refused (the step skipped, the project ready), a commit without a push remote, a later run of one step, an operator value changed in two clients with the second refused as `conflict`, a question of the setup answered (one a task asked, its chat with that task's role, and one the setup's workflow raised, its chat disabled with the reason); a release with plans in every state, an epic, a pending entry, and a running onboarding, one waiting for a removal from git, and one refused because the removal does not finish; scenario names `projects-<case>`.
