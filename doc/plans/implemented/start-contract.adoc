== What

The package implements in `pm-api` and `pm-mock-runtime` the client side of the specification sections listed under _Trace_; the engine side is `pm-mcp-core`'s `start-from-clients`, `recipe-workflows`, `forgejo-provider`, and `chat`. A statement of them that the implementation proves wrong is corrected in `plan-marshall-documentation` in the same plan (link:README.adoc#how[How to Work a Package]).

* The records of an entry (its kind, its project, its sources with their kind, reference, state, trust, and screening verdict, the proposed title and id), of a source's failure (among the causes `not granted` after a refused grant, `no credential`, and `rate_limited` with the time the limit resets, `resets_at`, for an issue or a pull request whose fetch the forge refused for its rate limit, with or without a credential, never retried by itself), of a flagged source with its spans, and of an unscreened one (`source-<kind>.unscreened`: the screener failed or no configuration of the role qualifies; try again, remove, or accept as untrusted with a reason); a pull request's changed files as its stored head, with their trust (untrusted unless the operator authored it); the request that opens an entry under its project and the one that adds each kind of source.
* *An entry is addressed at the top level by its id* once opened (`/api/v1/entries/{entry_id}`, its events at `/api/v1/entries/{entry_id}/events`), as plans and epics are; only the opening request names the project.
* The listing of files for the web app's picker, confined as the specification says.
* The representation of the entry's states for both clients (`start.choose`, `start.sources`, `start.ready`, `start.recipe`, `start.recipe-create`, `start.refused`, `start-epic.adopt` and `start-epic.adopt-failed`, the source sub-workflows, `recipe.choose`, `recipe.parameters`, `recipe.create`), on the scheme of `operator-interaction-contract`: `start.sources` offering only the kinds that combine with those in the list; `source-documents.mode` only while the machine's `sources.documents_mode` is `ask` (its default), `copy` preselected, _always_ writing `copy` or `move`; `start.sources` not offering the local changes while the project's landing in force is `landing.files`, with the reason naming the project's setting `landing`; `start.ready` for a recipe too, with the title changeable, the plan id derived from the recipe's key and the time (`recipe-{recipe_key}-{yyyy-mm-dd-hh-mm-ss}`) and not changeable, and asking no landing; `epic.parallelization_scope` never asked at the start, and an epic's `start.ready` showing the project's `epic.auto_start` as the value in force with its origin, never asking it.
* The scenarios of the mock runtime: a plan from one description; a plan from description, documents, and an issue of another repository on Codeberg with its grant; documents copied and moved, a directory, a file tracked by git, a file refused; an issue not found and tried again; a flagged issue accepted and one removed; an issue whose grant is refused; an issue and a pull request left unscreened (the screener failing, no qualified configuration) and accepted as untrusted; a lesson whose premise no longer holds, used anyway, retired, and removed, and a lesson claimed meanwhile returning to the choice with its cause; an issue fetched without a credential and one with a credential refused as `rate_limited`, tried again after the reset; local changes, and local changes not offered while the project's landing is `landing.files`, with the reason; a pull request from a fork with its untrusted changed files; an epic from documents; an existing epic adopted at `start-epic.adopt`, and an adoption failed (`start-epic.adopt-failed`); a start refused at `start.refused` with its reason; a recipe with parameters through `start.ready`, and one with a parameter without an option; an entry left and continued, with no time limit (an entry never expires and no sweep removes it); a start chat (below); scenario names `start-<case>`.
* *The start chat* (the sub-workflow `chat` of `pm-mcp-core`, represented as in `control-contract`): _Chat_ as a link of `start.sources` and `start-epic.sources`, available once a source is stored and every source from outside the machine is screened, disabled with its reason while the role does not qualify, absent for a recipe; the entry as its scope and its routed role (`refine` for a plan, `decompose` for an epic); a description rewritten or added, read back and stored through `start.store-description`; the transcript kept with the entry and moved with its source directory at `start.create`, deleted when the entry is abandoned; a chat still open at create or abandon ended first, its transcript complete. Scenarios: a plan's entry with a question only, an addition to the description accepted, a rewrite rejected, an epic's entry, a description-only entry with Chat available at once, Chat disabled while an issue is not yet screened, a create and an abandon each while a chat is still open (the chat ended and its transcript complete before the source directory moves or is deleted).
* *The follow-up plan of a chat about ended work* (`control-contract`): the entry the accepted proposal opens, with its description stored and the ended plan or epic named in it, at `start.sources`; scenario `start-follow-up`, with one case from an ended plan and one from an ended epic.
