Plan of the repository `pm-mcp-clients` for link:../../../plan-marshall-documentation/doc/roadmap.adoc[Roadmap] Milestone 2. == Scope

Modules of this repository in the milestone: `pm-api`, `pm-relay` (binary `pm-mcp`), `pm-operator`.

The milestone delivers the always-on daemon on its Unix socket, the session relay, the operator CLI, process coordination, and the security foundation. What it means and requires is stated in the documentation repository and only referenced here: the requirements the milestone names, the specifications and their watch documents. This plan holds the tasks: what this repository does for the milestone, in which module and package, in which order, and how each task is proven.

The other two plans: link:../../../pm-mcp-core/doc/plans/milestone-02-runtime-relay-operator.adoc[`pm-mcp-core`] and link:../../../plan-marshall-mcp/doc/plans/milestone-02-runtime-relay-operator.adoc[`plan-marshall-mcp`].

== How to Work a Task

* *Trace first.* The tasks are cut from the roadmap items, with the requirements, sections, and watch documents the roadmap names. Before code, the implementing session builds the trace matrix of the project skill `traced-implementation` (`../plan-marshall-documentation/.claude/skills/traced-implementation/SKILL.md`) for the task: every requirement bullet, every specification section, and every watch item anchored to them, each with its destinations. A task is split or extended where the matrix shows it; a row left out is recorded `out of slice` with its reason.
* *Present and remaining.* Each roadmap item of the milestone states what the code of Milestone 0 already covers. Read it before a task: a task delivers the remainder, never a second form of what exists.
* *Order.* First of the three. `pm-mcp-core` and `plan-marshall-mcp` build against its `SNAPSHOT`, so a task that changes the contract of `pm-api` merges before the tasks that consume it.
* *Done.* A task is done with its guarding tests, `verify`, `verify -Ppre-commit` (its rewrites reviewed and committed), `verify -Pcoverage`, and `verify -Pintegration-tests` green, and the native build where the task touches a binary.
* *Documents.* A statement of a requirement or specification that a task proves wrong is corrected in the documentation repository, never worked around in code. The concept, developer, and user documentation of a task, the deletion of the implemented specification sections and watch items, and the ticks in the roadmap go into one pull request in `plan-marshall-documentation` that names the code pull request and merges after it.

[[M2-CL-1]]
=== M2-CL-1: API contract of `/api/v1` in `pm-api`

Where:: pm-api, package `api.resource`
What::
* Resource records of the resources the daemon serves in this milestone (runtime status, web access, runtime stop, credential status, the runtime-wide event stream), the link relations, and the closed error codes.
* The JSON codec over the streaming API of `jackson-core`; no `jackson-databind`.
* The TOON codec is the undecided point of PM-WATCH-MOD-4 (one encoder in `pm-api`, or a JSON-only API). Decide it first, as a correction task of the documentation pull request, and delete the watch item.
Trace::
* Requirements: link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-ARCH-1[PM-ARCH-1], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-1[PM-IMPL-1], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-IMPL-3[PM-IMPL-3]

* Watch: link:../../../plan-marshall-documentation/doc/implementation-watch/module-structure.adoc#PM-WATCH-MOD-4[PM-WATCH-MOD-4]; link:../../../plan-marshall-documentation/doc/implementation-watch/module-structure.adoc#PM-WATCH-MOD-1[PM-WATCH-MOD-1]; link:../../../plan-marshall-documentation/doc/implementation-watch/runtime-model.adoc[Runtime Model]

[[M2-CL-2]]
=== M2-CL-2: Host-detection data in the profile documents

Where:: pm-api, package `api.host`; resources `classpath:/profiles/<client_id>.json`
What::
* Move the detection signals, their precedence, the process markers, the session id variable, and the identity probes out of the Java constants into the `detection` and `identity` objects of one profile document per harness.
* A generic reader of these two objects with the streaming API; it skips the rest of the document and names no harness.
* Build test: no production class of this repository names a harness; every shipped document has both objects in the closed form of the schema, with pairwise different `precedence`.
* The comparison of the Host Integration Table with the documents needs the documentation checkout; plan where that test runs (this repository with the sibling checkout, or the documentation repository) in the trace matrix.
Trace::
* Requirements: link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-3[PM-CLIENT-3], link:../../../plan-marshall-documentation/doc/Requirements.adoc#PM-CLIENT-5[PM-CLIENT-5]
