= The names of the harness, the decision log, and the integrity hold in the code
:nofooter:

link:README.adoc[Work packages of `pm-mcp-clients`] » `harness-decision-log-hold-names`

[horizontal]
Serves:: the client-work track (link:epic-clients.adoc[the client work])
Where:: `pm-api`, `pm-operator`, `pm-relay`, `pm-mock-runtime`, `pm-web-app`, `pm-web-e2e`
Part of:: link:epic-clients.adoc[the client work]
Status and dependencies:: in the link:README.adoc#packages[index], the only place that states them

The documents name the coding agent that runs workers the _harness_ (a _client_ is only one of the operator's two clients), the store of recorded decisions the _decision log_, the intent's record of what was settled its _choices_, and the hold of a store that failed its digest check the _integrity hold_. The code still carries the old names. Every task renames without a change of behaviour, and a record, a document or a message written with an old name stays readable: a reader accepts the old name beside the new one, and every writer writes the new one.

== Tasks

. *The harness identifier.* The profile documents of `pm-api` (`profiles/*.json`) and the catalogue comment of `profiles.index` carry `harness_id`; `ProfileDocumentReader` reads `harness_id` and still accepts `client_id` in a document that has no `harness_id` (a machine or project profile written before), and refuses a document that carries both with different values; `Profile.clientId()`, `HostDetection.clientIds()`, `CLIENT_ID_PATTERN` and their callers in `pm-operator` (`HarnessDiscovery.SUPPORTED_CLIENTS`, `ConfigCommand`, `EnrolHarnessCommand`) and `pm-relay` become `harnessId`, `harnessIds()`, `HARNESS_ID_PATTERN`, `SUPPORTED_HARNESSES`; the path parameter `{client_id}` of `HarnessEnrolmentResource` becomes `{harness_id}`; the option texts (`--allow <harness_id>:<model>`, `--add <harness_id>`) follow the design. The scenario `onboarding.json` of the mock runtime carries `harness_id`.
  Anchor: link:../../../pm-mcp-core/doc/specification/harness-profiles/01-profile-schema.adoc[Harness Profiles § Harness Profile Schema]; link:../design/terminal-client/01-commands.adoc#command-tree[Terminal Client, The Verbs].
  Proof: `ProfileDocumentReaderTest` reads a shipped document with `harness_id`, a fixture with only `client_id`, and refuses one with two different values; `HostDetectionTest` and `OnboardingScenarioTest` assert the new names; a `git grep -E 'client_?[iI]d'` over the modules finds only the reader's fallback and its test.
. *The harness detection.* The package `de.planmarshall.api.host` with `HostDetection` and its tests becomes `de.planmarshall.api.harness` with `HarnessDetection`; the module README names it harness detection.
  Anchor: link:../../../plan-marshall-documentation/doc/requirements/13-harness-profiles.adoc#PM-CLIENT-1[PM-CLIENT-1]; link:../../../plan-marshall-documentation/doc/requirements/08-security.adoc#PM-SEC-3[PM-SEC-3].
  Proof: `HarnessIsolationArchTest` and the operator gate tests (`OperatorGateTest`) pass against the renamed package; no class of the product imports `de.planmarshall.api.host`.
. *The verb `harness`.* `ClientCommand` becomes `HarnessCommand`, registered as `pm-operator harness install|update|remove|status` with its description naming the harness bundles; `OperatorActs` dispatches `harness` (its read subcommand `status` stays a read), the console's verb list (`PmConsole`) and the exceptions that never start the runtime name `harness status`. The verb `client` is removed, not aliased (a usage error, exit `2`).
  Anchor: link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#harness-installer[CLI, Coordination & Security § Harness Bundle Installer]; link:../design/terminal-client/01-commands.adoc#command-tree[Terminal Client, The Verbs].
  Proof: `HarnessCommandTest` (from `ClientCommandTest`) runs the four subcommands; `PmOperatorTest` asserts `harness` registered and `client` a usage error.
. *The texts that name harness sessions and the bundles' update.* The keys `system.runtime.relays_behind` and `system.upgrade.afterwards` keep their names; their texts in both languages say `harness session(s)` (`Harness-Sitzung(en)`), `pm-operator harness update` and `{# harness} other {# harnesses}`, as link:../design/shared/system-texts.adoc[System, Texts] states them.
  Anchor: link:../design/shared/system.adoc[System]; link:../design/shared/system-texts.adoc[System, Texts].
  Proof: `SystemCatalogueTest` compares both packs with the design's texts.
. *The decision-log export verb.* Where `pm-operator` registers the decision export, it is `pm-operator decision-log export`, reading the scope's decision log through `pm://plan/{plan_id}/decision-log` (and its project form); the verb `decisions` is a usage error. Where the verb is not registered yet, the package that registers it uses this name and this task is void.
  Anchor: link:../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-decision-log-export[CLI, Coordination & Security § Decision Export]; link:../../../pm-mcp-core/doc/specification/store-schemas/18-decision-records.adoc#decision-record[Store Schemas § Decision-Log Record].
  Proof: `PmOperatorTest` asserts the verb's name; its command test runs the export against the stub daemon.
. *The intent's choices.* The intent record's list `decisions` becomes `choices`: `PlanIntentResource.FIELD_DECISIONS` becomes `FIELD_CHOICES` (`"choices"`), its item type follows, and `IntentDecider` takes its values from the one decider kind of the store schema (`model` becomes `role`, and a record that still says `model` is read as `role`); the reader accepts a record that still carries `decisions` (and no `choices`) as its choices. The fixtures of the mock runtime's intent scenarios carry `choices`; the operator's decisions (`/api/v1/decisions`, the questions, the `decisions` message area) are the operator's object and keep their names. The terminal and the web app show the section as link:../design/shared/intent-and-outline.adoc#choices[Intent and Outline, Choices and Who Made Them] says.
  Anchor: link:../../../pm-mcp-core/doc/specification/store-schemas/06-task-and-references.adoc#intent-record-store[Store Schemas § Intent Record]; link:../../../pm-mcp-core/doc/specification/store-schemas/18-decision-records.adoc#decider-kind[Store Schemas § Decider]; link:../../../plan-marshall-documentation/doc/requirements/02-workflow.adoc#PM-WF-10[PM-WF-10].
  Proof: `IntentContractTest` reads a record with `choices` and one with only `decisions`, and writes `choices`; `IntentScenarioTest` asserts the fixtures.
. *The integrity hold.* `HoldKind.INTEGRITY_PAUSE`, `NeedsOperatorKind.INTEGRITY_PAUSE` and `EventKind.INTEGRITY_PAUSE` become `INTEGRITY_HOLD` with the wire value `integrity_hold`; each reads `integrity_pause` as `integrity_hold` (an event or a record written before), and writes only `integrity_hold`. The text keys follow the design: `control.hold.kind.integrity_hold`, the selector `integrity_hold` of `control.hold.title`, `overview.needs.integrity_hold`, `operator.console.notice.integrity_hold`, `operator.console.badge.integrity_holds`, with the texts `integrity hold` (`Integritätssperre`) in place of `integrity pause` (`Integritätspause`), also in `operator.actions.cancel.confirm`, `operator.actions.result.ended` and `operator.actions.end.title`. The operator, the mock runtime (`MockRuntimeEngine`, the scenarios `running-work.json` and `fully-onboarded.json`), the web app (`ControlActionsBar`) and the end-to-end tests (`control.spec.js`) follow. The operator's pause (`plan.paused`) is not touched.
  Anchor: link:../design/shared/work-actions.adoc#holds[Work Actions, What Holds a Plan]; link:../design/shared/plan-overview.adoc[Plan Overview]; link:../design/terminal-client/04-console.adoc[Terminal Client, The Console]; link:../../../pm-mcp-core/doc/specification/store-schemas/13-leases-integrity-testing.adoc#store-digest-verification[Store Schemas § Store Digest Verification]; link:../../../plan-marshall-documentation/doc/requirements/14-implementation.adoc#PM-IMPL-7[PM-IMPL-7].
  Proof: `ControlRecordsTest`, `OverviewRecordsTest` and `NeedsAndFindContractTest` read `integrity_pause` and `integrity_hold` alike and write `integrity_hold`; the catalogue tests (`ControlCatalogueTest`, `OverviewCatalogueTest`, `ConsoleTextsTest`, `ActionsCatalogueTest`) compare the keys and texts with the design; `ControlScenarioTest`, `ControlActionsBar.test.ts`, `HoldResolutionModal.test.ts` and `control.spec.js` run the hold under its new name; `git grep -i 'integrity.\?pause'` over the modules finds only the readers' fallbacks and their tests.
