[#console]
== The Console

`pm-operator` without a verb opens the operator's console: a prompt at which the operator types verbs without the program name, which runs the dialogues of xref:03-dialogues.adoc[Dialogues], and which shows what the runtime pushes while it is open, above all the decisions and waiver requests a running plan or epic asks the operator to answer. It is line-oriented, not full-screen: the scrollback, copying, and SSH keep working as in any shell. Transcripts: xref:05-transcripts-entry.adoc#t-console[The Console at Work].

[#prompt]
=== The Prompt

* `pm ›` is the prompt; it is the same in every language.
* *Badges* say what waits for the operator, between `pm` and `›`, only when there is something: `pm [1 question] ›`, `pm [setup 3/7] ›`, `pm [2 questions · 1 waiver request · setup 3/7] ›`. One badge per kind of the runtime's `needs_operator` summary that is not zero (<<pushed>>), with its count, and one per open onboarding: the machine's (`setup 3/7`) and each project's that has not completed (`setup pm-mcp-clients 5/9`). The counts come from the runtime (its `needs_operator` summaries and the open onboarding runs), never from counting in the client, so a question answered in the web app leaves the badge at once. More than three badges are cut to the first three and `+<n>` (`pm [2 questions · 1 waiver request · 1 stalled · +2] ›`); `questions` and `plans` show them all.
* *Connection*: `pm (reconnecting) ›` while the runtime cannot be reached (<<connection>>).
* `Enter` on the empty prompt takes what the badge offers first: an unfinished onboarding continues where it stopped, the first machine or project badge in runtime order when several are open (the machine's first while it is not complete, it gates the others); `project setup --entry -- <entry_id>` continues a specific being-added run's (<<being-added-address>>). Otherwise nothing happens. A question is never taken by `Enter` alone (<<answering>>).
* `/` at the prompt opens the find field (`shared/needs-and-find.adoc#terminal`): text typed after it searches straight away — `/relay` finds the work whose id or title carries `relay` — and a bare `/` opens the field, where `Enter` lists the matches (xref:01-commands.adoc#commands[the verb `find`]). `Esc` leaves the field with nothing sent, and an empty text is refused with the catalogue's own text, never with a usage line. `/` is free at this prompt and is no verb of its own; `/find relay` searches for the text `find relay`, and inside the overview `/` stays the list filter (xref:15-overview.adoc#overview[The Overview]).
* A badge changes while the operator types: the console rebuilds the whole badge set from the runtime on every event that can change what waits — its `needs_operator` summary and the machine's open onboarding (`setup 3/7`, which stays first while the machine is not onboarded) — and the prompt is redrawn with the typed text and the cursor where they were. The prompt of a line that is already being read keeps the badges it was drawn with; the refreshed ones appear at its next draw, and the window title, which carries the same badges, changes at once.

[#pushed]
=== What the Runtime Pushes

The console follows the runtime's event stream (`GET /api/v1/events`) while it is open. Events are of two kinds:

* *Waiting for the operator*: a change of a `needs_operator` summary of a plan, an epic, a project, or the machine that adds an item. Each new item is shown as a notice block, counted in the badge, and, while `console.notify` is `true` (the default), announced by the terminal bell, or by a desktop notification where the terminal supports one (<<notifications>>). A plan the operator paused is no item: it shows by its state in `plans` and `status`, never as a notice or a badge.
* *For information*: a report the runtime wrote (a plan started or ended, an epic started its next plan, a project onboarded; link:../shared/reports.adoc#kinds[Reports]), a worker restarted, a check of a running dialogue reported. At most one quiet line, several of them coalesced into one, without the bell; a report's line names the command of its detail (xref:24-reports.adoc#notice[Reports, While the Console Is Open]), and `reports` lists the unread ones. When the console opens with unread reports, one line says how many (xref:24-reports.adoc#arrival[Reports, On Start]).

Every kind of the closed list of `needs_operator` (link:../shared/plan-overview.adoc[Plan Overview]) has its notice, its badge, and the command that opens it; the label of the kind is the shared `overview.needs.<kind>`, the rest is the console's (<<texts-operator-console>>):

The command in the last column is one derivation: `needs` prints it beside each item, and `!` in the overview runs exactly the command the row prints, never a second reading of the item. The runtime's `needs_operator` summaries name the waiver by the contract's kind `waiver`; the specification's spelling `waiver_request` is read as `waiver` where a runtime still sends it, and no client renders it under a name of its own.

A notice is raised for an item a change adds. What the console's status read at start already showed was badged before and is no addition; an item beyond it — the first credential that arrives after a start whose status read showed none — raises its notice like any later one.

The holds among the kinds are exactly `stalled`, `condition`, `integrity_hold`, `held`, and `landing_failed`; the command of each opens the hold with its acts (xref:19-actions.adoc#holds[What Holds a Plan]). The open onboardings are badges of their own, not notices: `setup 3/7` for the machine (`operator.console.badge.setup`) and `setup cui-parent 5/9` for each project's (`operator.console.badge.setup_project`), whose name is the checkout's directory because a being-added run has no project id (`<<being-added-address>>`).

A notice is printed *above* the prompt: the line the operator is typing is taken off, the notice is printed, and the prompt is drawn again with the typed text and the cursor where they were. Nothing typed is lost, and nothing typed becomes an answer.

----
pm › config roles --pro
◆ Question Q-007 · plan fix-relay · blocks the plan
  The change conflicts with main in RelayServer.java.
  Recommended: 2) Rebase onto main
  answer Q-007   ·   questions
pm [1 question] › config roles --pro
----

[#being-added-address]
=== Addressing a Being-Added Project

A project's run is continued by what the contract carries. Before its enrolment the run has no project id — `BeingAddedProject` in `pm-api` carries the checkout path, the step, and its hypermedia links, and no id — and the run is entry-scoped (link:../shared/project-onboarding.adoc#several[Several Onboardings at Once]). The console therefore reads the address from the run's `continue_link` (`/api/v1/entries/{entry_id}/continue`) and continues the run at the entry resource `/api/v1/entries/{entry_id}`; the badge names the run by the directory of its checkout, and a run whose contract carries no link gets a badge without a continuation — the directory name is not an entry id, and `project add <path>` continues such a run.

The address travels as an argument of the verb, never through a command line the console quotes and parses back: an id with a quote or a backslash reaches the verb unaltered (`project setup --entry -- <entry_id>`). The `--` ends the options, so an id that starts with `--` is never read as an option or as a project selector.

*Open item*: the pre-enrolment run's setup state and its act links at `/api/v1/entries/{entry_id}` — a `GET` of the state and the act surface the dialogue posts a chosen link to. Owner: `plan-marshall/plan-marshall-mcp` (the daemon). Until the daemon serves them, `Enter` on a being-added badge reports the run as unreadable instead of addressing a project that does not exist.

[#answering]
=== Answering a Question

A pushed item never takes the focus: no keystroke typed before it was shown can answer it, and a bare number at the prompt is no answer (`2 is not a command here; help lists them`).

* `questions` lists the open decisions and waiver requests: id, plan or epic, the question in one line, the recommendation, and since when it waits.
* `answer Q-007` opens the decision as the states of its sub-workflow `decision.*`, shown as link:../shared/decisions.adoc[Decisions] says for every client: what is asked and why, the evidence on `?`, the parts one at a time, the options in the workflow's order with their support, and the recommendation placed by what is at stake (link:../shared/decisions.adoc#recommendation[Where the Recommendation Stands]): preselected only where the decision is reversible and the votes agree or no quorum voted; one step away (`?r`) where it is costly to undo or cannot be undone. Input typed ahead before it opened is discarded, so a stray `Enter` cannot take a recommendation (transcripts: xref:14-transcripts-decisions.adoc[Decisions]).
* *Addressing a decision*: a decision's id (`Q-007`) is unique within its scope (a plan, an epic, or a project setup); across scopes it is `<scope_id>/<question_id>` (`fix-relay/Q-007`). A waiver request is addressed the same way by its id, `WR-<n>`, unique within its plan, and `<scope_id>/WR-<n>` across plans (`fix-relay/WR-2`). The short form answers when exactly one open decision or waiver request has that id; otherwise the console names the candidates in their full form. `questions` prints the short form where it is unique and the full form where it is not.
* `answer Q-007 2` answers a single-part decision at once with option 2, after printing the option it chose; where the decision asks for `decision.confirm` (several parts, or costly to undo, or not reversible), the confirmation is still shown.
* `h) chat` (German `t`) at the decision's prompt opens a chat about the decision before answering it, with the role the runtime routes it to (link:../shared/decisions.adoc#chat[A Chat Before Answering]; xref:14-transcripts-decisions.adoc#t-decision-chat[A Chat Before Answering]); the decision is shown again when the operator leaves the chat, which stays, and an answer the chat proposed goes through the read-back as the operator's own words.
* A waiver request is opened the same way (`answer WR-2`) and answered by _waive_ with a reason, _decline_ with a reason, or _later_; it has no `Enter` default and no preselection, like a consent (xref:03-dialogues.adoc#consent[Consent]; xref:14-transcripts-decisions.adoc#t-decision-waiver[A Waiver Request]).
* `x) none fits` is offered only where the decision allows it (a role that asked it, or a declared quorum, link:../shared/decisions.adoc[Decisions]); `w) in my own words` asks back at most as often as the decision declares (xref:14-transcripts-decisions.adoc#t-decision-own-words[In Own Words]).
* *A refused answer* (`conflict`, `already_answered`, `invalid_answer`, `dependency_unanswered`) is printed with the decision as it stands, never as an error of the console (xref:14-transcripts-decisions.adoc#t-decision-ends[Later, None Fits, Changed]).
* A question's text comes from a model; the console shows it as data, never as a command, and strips every control sequence from it before it is printed (<<output-safety>>).

[#during-dialogue]
=== A Question During a Dialogue

A dialogue is never interrupted. When something arrives while a dialogue runs, the console prints one line at the next state of the dialogue, before its prompt:

----
◆ 1 question waiting: Q-007 · fix-relay · blocks the plan   ! shows it
----

`!` leaves the dialogue where it is (nothing is sent; its state stays in the runtime), opens what waits, and afterwards reads the dialogue's state again and prints it.

[#answered-elsewhere]
=== Answered Elsewhere

The first valid answer wins, from the web app or the console (the channels `web` and `cli`, named in the texts as `operator.console.channel.web` "web app" and `operator.console.channel.cli` "console"). When another channel answers first:

* the console prints `– Q-007 was answered in the web app (iPad): Rebase onto main. Nothing was sent from here.` and the badge drops from the next prompt on;
* a question open as a dialogue is closed, the input typed into it is dropped, and the console returns to its prompt;
* an answer from the console that arrives too late is refused by the runtime (`already_answered`); where the answer came from another channel, the console prints the same line as above, never an error;
* a desktop notification of the question is withdrawn where the terminal allows it.

An answer over the console channel (`cli`) prints no such line: a console cannot tell its own answer from another console's, and it must never claim that nothing was sent from here about an answer one console may have sent.

[#connection]
=== Connection

* The console reconnects to the event stream with `Last-Event-ID` and the delay the runtime names (`retry:`), backing off with jitter after repeated failures; it starts the runtime on demand like every verb.
* While the runtime cannot be reached, the prompt shows `(reconnecting)` and one line says why; the typed text stays.
* After a reconnect it always reads the state again (the open questions, a running dialogue's state), because a restarted runtime holds no events to replay, and prints one line: `✓ Reconnected: pm-mcpd 0.9.1, restarted at 14:41. 1 question open, 2 plans running.` The badge set and the window title are rebuilt from that read, so a question answered while the stream was down leaves the badge at the first prompt after the reconnect.
* While a full-screen view is open, the same state is shown in its header instead of at the prompt: `● connected` while the stream is open and `○ reconnecting` (the text `operator.console.badge.reconnecting`) while it is not; on reconnect the view reads its whole snapshot again and redraws, as xref:15-overview.adoc#full-screen-connection[The Overview, The Header's Connection State] says.

[#full-screen-handoff]
=== The Full-Screen Hand-Off

The console and a full-screen view do not own a second terminal; they share the one the console
created on entry.

* `plans` and its alias `tui` open the overview of running work
  (xref:15-overview.adoc#full-screen[The Overview, The Full-Screen View]). `plan <id>`, `projects`,
  and `system` hand off the same way. The verb keeps its trailing arguments, so `tui --by epic` is
  `plans --by epic`.

* The console lends its terminal to the nested command for the dispatch, runs the command, and takes
  the terminal back in a `finally`. A nested command never closes the console's terminal.

* While the view is open, the notices the runtime pushes are held rather than printed above the
  prompt; when the view leaves, one coalesced meanwhile line is printed, by the view itself on the
  console's own writer
  (xref:15-overview.adoc#full-screen-live[The Overview, Live, and Leaving]).

* `--json` runs the verb normally: no view, no notice hold, and JSON on stdout.
* A verb that cannot open the view on this terminal prints one catalogue line naming the reason,
  prints its scrollback instead, and returns the prompt
  (xref:15-overview.adoc#full-screen-not-available[The Overview, Why the View Does Not Open]). The
  greeting's hint is printed only when the view can open.

* After `q` the console redraws its prompt and stays usable; `exit` at the prompt then leaves with
  code `0`. The restoration is asserted on a real pseudo-terminal
  (xref:27-tui-testing.adoc[The TUI's Tests]).

[#console-dialogue-handoff]
=== A Dialogue out of the Full-Screen View

The full-screen view and the console's dialogues do not own the terminal at the same time. When an
act of the view starts a dialogue (a decision with `!`, an action with `a`, a chat, or a verb the
view hands off), the view:

1. restores the cursor and leaves the alternate screen, so the dialogue is printed into the normal
   scrollback and scrolls, copies, and reads with a screen reader like every other dialogue;

2. runs the dialogue on the console's own `LineReader`, with its prompts and its notice handling;
3. on a normal return, enters the alternate screen again, reads a fresh snapshot, and draws the
   level it left, with the selection it had.

An error in the dialogue leaves the terminal in the normal screen; the view re-enters its alternate
screen on the next turn and shows the error in its status row, so the console keeps the view open
rather than reporting the error at its prompt. `Ctrl+C` is the interrupt of
the exit-code table where the dialogue maps it: an action, a hold and a review that the view opens
leave it with `130` and send nothing, and so do the runtime acts (stop, restart, upgrade, check),
project add and setup, and the decision the view opens with `!`, whose confirmations are dialogues of
the view as well. The verb that opened
the view ends the program with that status, so the operator's interrupt reaches the shell; a view
the console opened returns to the console's prompt with it, as every other verb does, and the view's
other dialogues — the chat, a start, the settings and the confirmation — still leave back to the
view as `q` does. The view's
`finally` always restores the terminal state, so a terminal is never left in the alternate screen,
with the cursor hidden, or in keypad application mode.

[#console-raw-mode-decision]
=== Decision: Terminal Raw-Mode Switch and Reader-Ready Condition

Where JLine falls back to the `exec` provider, the prompt a dialogue draws is followed by JLine's `stty` child that switches the terminal to raw mode. Ctrl+C typed in that window can kill the child (`java.io.IOError: Error executing '/bin/stty ...'`) rather than reaching the reader. No output marks the end of that switch, and a probe key would change the dialogue's own state; the drawn prompt is therefore the last condition the harness can read.

[#notifications]
=== Notifications

* While `console.notify` is `true`, what waits for the operator rings the terminal bell once, when it arrives.
* A desktop notification is sent instead, under the same key, where the terminal is known to support one: OSC 9 (iTerm2, Ghostty, WezTerm), OSC 777 (rxvt family), OSC 99 (kitty, which can also withdraw it). Over SSH the sequence reaches the operator's own terminal.
* *Which terminal is known* is read once from the console's environment when it starts; the first rule that applies decides, and every terminal no rule names gets the bell, so the operator is never left with a sequence nobody shows:
+
[cols="3,1",options="header"]
|===
|The environment |Signal

|`TERM=dumb`, or no terminal
|the bell

|`TERMINAL_EMULATOR` begins with `JetBrains` (the terminal of a JetBrains IDE, which shows no desktop notification and may have inherited `TERM_PROGRAM` from the terminal the IDE was started in)
|the bell

|`TERM_PROGRAM=tmux`, or `TERM` begins with `screen` or `tmux` (a multiplexer passes the sequence on only with `allow-passthrough on`, which the console cannot see)
|the bell

|`TERM=xterm-kitty`, or `KITTY_WINDOW_ID` is set
|OSC 99

|`TERM_PROGRAM` is `ghostty`, `iTerm.app` or `WezTerm`, or `TERM` is `xterm-ghostty` or `wezterm`
|OSC 9

|`TERM` begins with `rxvt`
|OSC 777

|anything else
|the bell
|===
+
Over SSH `TERM_PROGRAM` is usually not passed on, so a remote console knows the terminal by `TERM` alone, and rings the bell where `TERM` names none.
* The machine configuration key `console.notify` (link:../../../../pm-mcp-core/doc/specification/store-schemas/12-machine-stores.adoc#machine-config[Machine Configuration Store]) turns them on and off: `true`, the default, sends the desktop notification where known and else rings the bell; `false` sends neither.
* A notification carries the scope and the kind (`plan fix-relay asks a question`, `epic storage-v2 asks a question`, `the setup of pm-mcp-clients asks a question`, `plan fix-relay asks for a waiver`), never the text of the question, which may hold content of the project.

[#output-safety]
=== Output Safety

Every text that comes from the runtime and may come from a model or a repository (a question, a finding, a file name, a branch) is printed only after every control character and terminal sequence (C0 and C1 controls, `ESC`, `CSI`, `OSC`, `DEL`) has been removed or shown as a visible placeholder. Removed as well are the characters that are no visible text: the bidi controls (`U+202A`–`U+202E`, `U+2066`–`U+2069`), which reorder what the terminal shows; the zero-width characters (`U+200B`–`U+200D`, `U+2060`, `U+FEFF`), which hide between the visible ones; and the tag characters (`U+E0000`–`U+E007F`), which can carry a whole hidden text. Removing the zero-width joiner splits a joined emoji into its parts; that loss is accepted. This holds for the notice blocks, the dialogues, the notification payloads, and the window title alike: a crafted text must not move the cursor, write the clipboard, fake a prompt, or change what the operator sees. A line break is kept only where a notice prints a text of several lines, the body of a question: that text is printed behind the notice's indent, one line at a time, so none of its lines starts at the beginning of a terminal line and none can pass for the console's prompt. Every other value of a notice fills one place of a one-line text, and a line break in it becomes a space. Pasted input that contains a line break never answers a question: a bracketed paste is taken as text of the line, never as `Enter`.

[#console-security]
=== The Operator Checks

The console is entered without the operator checks: reading questions, reports, projects, roles, the settings views and a plan or epic view is not an operator act, and the terminal that a coding agent drives may read them (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-operator-channel.adoc#operator-channel-isolation[Operator Channel Isolation], item 2). The checks run on every act: the dispatcher checks the line the operator typed before it runs it, and each act verb checks again before it sends anything, so an act is refused with exit code `4` and the catalogue text whether it was typed in the console or run as one shell command. The exception is the signal `drain`, which keeps its own rules as xref:01-commands.adoc#command-tree[the verb list] says. The entry flow's offer of the web app is an act too — enabling the loopback listener and issuing a pairing code — so in a refused environment the console opens without it. The checks are a speed bump, not a boundary: an agent that drives a real terminal (through `tmux` or `expect`) passes them, which is the accepted risk of the operator channel and stays so. Every answer and every change is audited with channel `cli`.

[#line-editor]
=== Line Editor

The console reads with JLine 4 (`jline-reader`, `jline-terminal`, `jline-terminal-ffm`): it is the only Java line editor that prints above the line being edited and draws it again (`LineReader.printAbove`), reads secrets without an echo and without history, and is built and tested as a GraalVM native image upstream.

* *Terminal access*: through the Foreign Function & Memory API (`ffm`), and through `stty` (`exec`) where that fails; the JNI provider, which unpacks a native library at runtime, is not used. The native libraries that `jline-native` carries for other platforms are kept out of the binary.
* *Platforms*: Linux (`x86_64`, `aarch64`) and macOS on Apple silicon (`arm64`).
* *Threads*: one thread reads; the thread of the event stream only prints above the prompt and redraws it. A verb writes through the console's writer while the console is open, never directly to standard output.
* *A terminal without cursor control* (`TERM=dumb`, a screen reader that reads each redraw): notices are printed between lines, at the next prompt, never into the line being typed; the badge still announces them, and the bell while `console.notify` is `true`.
* *Secrets* (a token in `providers.credentials`, `credentials set`) are read character by character from the terminal with the echo off into a `char[]` that is cleared after the request, never through `LineReader.readLine`, whose result is a `String` that cannot be cleared; they never reach the history.
* *Picocli* stays the parser of verbs and options; completion is computed from picocli's model of the commands.
