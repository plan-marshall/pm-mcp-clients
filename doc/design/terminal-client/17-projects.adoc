What the explorer and a project's onboarding show is link:../shared/project-explorer.adoc[Project Explorer] and link:../shared/project-onboarding.adoc[Project Onboarding], for both clients (link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc[Use Cases, Projects]). This part is how the console draws them. The conventions of the transcripts are those of xref:05-transcripts-entry.adoc#transcripts[Transcripts].

[#commands]
== Commands

----
  projects [--list]                     the explorer, full screen; --list prints it into the scrollback
  project add [<path>]                  onboard a project; the working directory is the proposed checkout
  project setup <project_id> [<step>]   a later run of a project's onboarding, at a step (identity, own,
                                        team, architecture, landing, roles, descriptions, commit); without
                                        a step it asks which, release and unenrol among the choices
  project release <project_id> [--reason <text>]
                                        end every plan and epic of the project as released, delete its
                                        pending entries, and close its plan lifecycle; the reason is asked
                                        when it is missing
  project unenrol <project_id> [--reason <text>]   remove the project's enrolment; refused while work of it runs
  project favourite <project_id> [--off]
----

* All are operator verbs and run in the console or as one shell command (xref:01-commands.adoc#command-tree[The Verbs]); `pm-operator enrol` stays the direct verb of a project's enrolment, with its arguments as the answers of `project.identity` to `project.enrol`.
* `--project ?` of every other verb shows the same list as the explorer, favourites first (xref:02-levels.adoc#addressing[Addressing a Level]).
* `project release` and `project unenrol` are direct verbs (xref:01-commands.adoc#direct-verbs[A Direct Verb Runs a Sub-Workflow]): `--reason` answers the reason, a missing one is asked, and `--no-input` stops there; the confirmation is answered by `--yes`, never by `Enter` alone (<<release>>).

[#explorer]
== The Explorer, Full Screen

`projects` opens the explorer as the first level of the full-screen view of xref:15-overview.adoc[The Overview]: from a project, its actions; from _Running work_, the project's level of the overview; from a plan, its plan view (xref:16-plan-view.adoc[The Plan View]).

----
 Projects                                                         ● connected
 ─────────────────────────────────────────────────────────────────────────────
 Being added
    /home/oliver/git/cui-parent       ② Identity
 Favourites
▶ ★ pm-mcp-clients    ready      ! 2   3 plans · 1 epic    2 min ago
  ★ pm-mcp-core       ready            2 plans                     9 min ago
 Recent
    plan-marshall     setup needs: credential sonar                yesterday
    cui-http          ready                                        3 d ago
 All projects · by name
    API-Sheriff       ready                                        5 weeks ago
    legacy-portal     released                                     2 months ago
    …
 ─────────────────────────────────────────────────────────────────────────────
 ↑↓ move   Enter actions   * favourite   s sort   / filter   + add   q leave
----

* *Being added*: a project's onboarding that has not reached its enrolment yet, by the path of its checkout and the step it waits at; it has no id yet. Once enrolled, the project is listed by its id like every other, with `setup needs: …` until it is ready.
* A released project is listed with `released`; an unenrolled one is not listed.

`Enter` on a project opens its actions in place:

----
▶ ★ pm-mcp-clients    ready      ! 2   3 plans · 1 epic    2 min ago
      e  Add an epic
      p  Add a plan
      r  Running work
      u  Setup
      *  Remove from favourites
----

* *A released project* offers instead `a  Enrol again`, which runs its onboarding again from `project.identity` with its current values (as `pm-operator enrol` does), and `r  Running work` while plans of it still show.
* *A project that is not ready* offers `c  Continue the setup` first; `e` and `p` are shown disabled with the reason (`pm-mcp-core is not ready: credential sonar`).
* *A project with an open entry* (a start not finished) offers `c  Continue starting` first (link:../shared/starting-work.adoc#leaving[Starting Work, Leaving and Coming Back]).
* *A project being added* offers `c  Continue` and `x  Abandon…`; abandoning asks first and deletes the run, of which nothing is enrolled yet.

[cols="1,3",options="header"]
|===
|Key |Action

|`Enter`
|the actions of the selected project; on an action, that action

|`e`, `p`, `r`, `u`
|add an epic, add a plan, running work, setup: directly from the row

|`c`
|continue: the open entry (_Continue starting_), the setup of a project that is not ready (_Continue the setup_), or a project being added

|`x`
|on a project being added: abandon its onboarding

|`a`
|on a released project: enrol it again

|`*`
|mark or unmark the selected project as a favourite

|`J`, `K`
|move a favourite down or up in the favourites

|`s`
|sort _All projects_ by name or by most used

|`/`
|filter by name and id; the groups become one list of matches

|`+`
|add a project: leaves the view and starts `project add`
|===

The keys of the explorer are keys of navigation, the same in every language, like those of the overview (xref:15-overview.adoc#full-screen-keys[Keys]). The two _Add_ actions leave the view and start `epic add` and `plan add` for the project (xref:18-starting.adoc[Starting Work]); _Setup_ leaves the view and starts `project setup <project_id>`, which asks what to change, releasing and unenrolling among the choices (<<release>>).

* `project add <path>` starts with that path; in a checkout, the working directory is the proposal.
* *Checkout*: `n` at the consent to look stays there. The consent to run scripts answers `y` for this run, `p` for this project (remembered in the machine's `consents.json` by the scripts' digests, asked again only for a script that changed), or `n`, which goes on with the version `unknown` and does not ask again in this run.
* *Enrolment*: every line can be changed by its number; `?n` lists what a line holds (`?4` the 12 variables of the build environment). The container engine is line 6, off; `6` opens its choice with its warning (`project.enrolment.container_warning`) before it can be turned on.
* *Own settings* hold the operator's values only; the variants and credentials are checked as soon as they are saved, and one that fails returns to its line with the finding (`✗  sonarcloud: the token is refused (401); choose another variant or credential`).
* *Architecture* holds the build map; it is confirmed there and nowhere else, a route edited with `e`.
* *Landing* holds the team's providers, the finalize steps, and the landing variant; a machine default that does not fit the project is refused on its line (`✗  Commit on main does not fit pm-mcp-clients: main is protected`) and waits for another choice.
* *Roles* and *Descriptions* are asked only where roles need grading and modules a description; each asks a consent of kind `model_cost` with its expected cost, and both can be remembered (`r`). `n` skips the step with its reason, the project is ready without it, and a later run (`project setup pm-mcp-clients roles`, `… descriptions`) offers it again.
* *Commit* makes one commit and pushes it where the checkout has a push remote (`not pushed: no push remote` otherwise); `n` leaves the files uncommitted.
* *A step that cannot pass* waits in `setup.needs-repair` with its cause and fix: `t) try again   q) leave`; `t` runs the step again.
* The keys of the ready line are `operator.key.add_epic`, `operator.key.add_plan`, and `operator.key.running_work` (xref:13-texts-operator.adoc#texts-operator-keys[Keys]).
* A later run (`project setup pm-mcp-clients own`) opens the same states with the project's current values; a project that is not ready continues where its setup stopped.

[#several]
=== Several at Once

Each project's onboarding runs in a scope of its own, so several can be open together; the console shows one badge per open run (xref:04-console.adoc#prompt[The Prompt]). Before its enrolment a run is named by the directory of its checkout, after it by the project's id:

[source,text]
----
pm [setup pm-mcp-clients 4/10] › project add ~/git/cui-parent
[1/10] Checkout · Which checkout is the project?
  …
[2/10] Identity · How should the project be named?
  … q
Left [2/10] Identity of /home/oliver/git/cui-parent. Nothing was sent. Enter continues it.
pm [setup cui-parent 2/10 · setup pm-mcp-clients 4/10] › ⏎
[2/10] Identity · How should the project be named?
  …
pm [setup cui-parent 3/10 · setup pm-mcp-clients 4/10] › project setup pm-mcp-clients
[4/10] Own settings · What pm-mcp-clients takes from the machine, and what it sets of its own
  …
----

* `Enter` on the empty prompt continues the most recent run; `project setup <project_id>` continues a specific one, and `project add <path>` of a checkout whose run is open continues that run.
* A run before its enrolment is listed in the explorer under _Being added_ (<<explorer>>).

[#release]
== Releasing and Unenrolling

What releasing and unenrolling do is link:../shared/project-explorer.adoc#release[Project Explorer, Release and Unenrol]. In the console both are choices of the project's setup and verbs of their own:

[source,text]
----
pm › project setup plan-marshall
plan-marshall · Setup · What do you want to change?
  1) Identity        2) Own settings    3) Team settings   4) Architecture
  5) Landing         6) Roles           7) Descriptions    8) Commit
  9) Release the project…              10) Unenrol the project…
› 9
Release plan-marshall?
  What ends      3 plans, each ended as released and archived; 1 epic,
                 released with its plans and archived
                 1 entry not started yet, deleted with its sources
  Afterwards     the project's plan lifecycle is closed; it stays listed as
                 released and can be enrolled again with its values
  Reason         › the gates move to the new repository
Release the project? y) yes   n) no, keep it   ?   › y
    ▶  waiting for the removal of doc/gates.adoc from git to land   0:41
    ✓  doc/gates.adoc removed from git
    ✓  fix-sonar-gate released and archived
    ✓  gate-timeouts released and archived
    ✓  gate-docs released and archived
    ✓  epic gate-hardening released with its plans and archived
    ✓  entry with 2 sources deleted
✓ plan-marshall released
pm ›
----

* *A removal still landing* is waited for first, within its bound; when it does not land in it, the release is refused and nothing has ended: `✗ plan-marshall was not released: the removal of doc/gates.adoc from git did not land within its bound. Nothing was ended.`, with `→ running plan-marshall` to its row in Running Work.
* *A running onboarding* of the project (a later run of its setup, its badge at the prompt) is ended where it stands, and its badge goes.

[source,text]
----
pm › project unenrol cui-http
✗ cui-http still runs work; unenrolling is refused while it does:
    plan  http-retry-budget     execute · running     plan cancel http-retry-budget
    epic  http-hardening        running               epic cancel http-hardening
  → end them first, or release the project: project release cui-http
pm ›

pm › project unenrol legacy-portal
Unenrol legacy-portal?
  What ends      its enrolment: the project leaves the list; its checkout and
                 the team's configuration in it stay as they are
  Afterwards     it is onboarded again only from the start (project add)
Unenrol the project? y) yes   n) no, keep it   ?   › y
✓ legacy-portal unenrolled
pm ›
----

* The confirmation names what ends before it asks and is answered by `y` or `n`, never by `Enter` alone; its texts are the shared keys `project.release.*` (link:../shared/project-explorer.adoc#release[Project Explorer, Release and Unenrol]).
* An unenrolment refused while work runs lists the running plans and epics, each with the verb that ends it (xref:19-actions.adoc[Actions on Plans and Epics]).
* As one shell command, `pm-operator project release plan-marshall --reason "…" --yes` answers the reason and the confirmation; without `--yes` it asks, and `--no-input` stops there.
