[#commands]
== Commands

The verbs of the specification stay as they are: `status` (the running work, with the runtime's line), `drain` (the signal), and `runtime start|install|uninstall`. The system view and the operator's acts are added beside them, the acts under the existing `runtime`:

----
  system [--project <project_id>|.] [--window hour|today|7d] [--by model|role] [--watch]
                                            the system view; full screen in the console
  runtime start                             start the runtime (the existing verb)
  runtime stop [--when-done|--now] [--yes]  [op]  stop it: when what runs is done, or now
  runtime stop --withdraw                   [op]  withdraw a drain asked from a client
  runtime restart [--when-done|--now] [--yes]  [op]  stop it and start it again
  runtime upgrade --check                              ask the registry for a newer version
  runtime upgrade [<version>] [--when-done|--now] [--yes]
                                            [op]  upgrade to the newest version, or the one named
  runtime upgrade --withdraw                [op]  withdraw an upgrade before its links are switched
  runtime upgrade --notes                         the release notes of the newest version known
----

* *`system`* is a read, like `status`, and no operator verb: in the console it opens the full-screen view (<<full-screen>>), as a shell command, or where the full-screen view is not available, it prints the view once (<<print>>); `--watch` prints it again as figures change, as `status --watch` does. `--window` and `--by` choose the models' window and grouping (default `hour` and `model`), `--project` one project.
* *`runtime stop|restart|upgrade`* are operator verbs: privileged requests of the operator's channel, refused without the operator checks (exit code `4`; xref:04-console.adoc#console-security[The Operator Checks]). Each shows its confirmation (`runtime.confirm-stop`, `runtime.confirm-upgrade`) as a dialogue; `--when-done` (with `--drain` kept as its alias) or `--now` answer its choice of when, `--yes` accepts it. With `--no-input` and no `--when-done` or `--now`, the verb stops at the choice with exit code `3`, as every direct verb (xref:01-commands.adoc#direct-verbs[A Direct Verb Runs a Sub-Workflow]); `--yes` never chooses when.
* *`runtime upgrade --check`* asks the consent `check_updates` where it is not remembered (`runtime.update-consent`; `--consent check_updates` answers it for this run) and prints the answer (`runtime.check-update`); `runtime upgrade` without a version upgrades to the newest version known and checks first where none is.
* *`drain`* is the signal of the specification: it asks nothing, cannot be withdrawn, and works when the runtime does not answer. A refusal of `runtime stop` because the runtime does not answer names it (`operator.system.not_answering`).
* *`status`* keeps its tree; its runtime line carries the lifecycle state while there is one (`Runtime pm-mcpd 0.9.1, stopping when what runs is done (2 left)`) and names `system` for the rest.

----

* The same parts in the same order as link:../shared/system.adoc#view[System, The System View], as words: no meaning is in a colour or a glyph alone, a figure not available says so with its reason.
* *One step* is a command: the last line names the commands of the figures that lead somewhere (link:../shared/system.adoc#one-step[System, One Step to What a Figure Counts]); `plans` opens the overview of running work, `plan <plan_id>` a plan at its task or job, `cleanup` the cleanup job (xref:26-cleanup.adoc[Cleanup]).
* *Models* print tokens and never money: the total with its split, in the number format of link:../shared/texts-and-languages.adoc#numbers[Texts and Languages, Numbers]; a total over calls not measured is a floor with `≥` and the count of those calls (link:../shared/system.adoc#models[System, The Models]). `?` on a line prints its raw components as the harness reported them: input, cache read, cache write, output, reasoning, each `not reported` where the harness does not report it.
* `--project <project_id>` prints the work of that project; without it, every project's together, and a project still recovering says `recovering`.

[#full-screen]
== Full Screen

`system` in the console opens the view on the alternate screen, built as the overview is (xref:15-overview.adoc#full-screen-build[The Overview, How It Is Built]); `S` in the overview of running work opens it as a level of that view, and `Esc` goes back there.

----
 System · pm-mcpd 0.9.1                                           ● connected
 ─────────────────────────────────────────────────────────────────────────────
  Runtime   running since today 08:14 · 6 h 12 min       0.10.0 available
            memory 412 MB of 1 GB · 680 MB resident · CPU 4 %
▶ Work      plans  3 running · 1 waiting for you · 1 held · 2 paused
            epics  1 running · 1 waiting for you
            tasks  4 running · 6 queued
            projects 3 with running work
  Workers   5 · 3 busy · 2 idle
  Jobs      build 1 of 2 slots · 1 queued · test 0 of 1 · locks 3 held
  Models    last hour · 172 calls · ≥ 5.63 M tokens (≥ 5.10 M in · ≥ 0.53 M out)
  Cleanup   due: 12 plans · 2 epics · 40 logs · frees 1.8 GB
 ─────────────────────────────────────────────────────────────────────────────
 ↑↓ move   Enter open   a actions   ? help   q leave   w window   b by role   p per project
----

[cols="1,3",options="header"]
|===
|Key |Action

|`↑` `↓`, `k` `j`
|move between the figures

|`Enter`, `→`, `l`
|follow the selected figure: the workers, the jobs, the locks, or a model's calls as a level of the view; the cleanup's line opens `cleanup` as a level of the view; plans in a state as the overview filtered to it; `Esc` back

|`w`
|the models' window: last hour, today, 7 days

|`b`
|the models per model or per role

|`p`
|all projects or per project

|`a`
|the acts on the runtime below the runtime's line: _Stop…_, _Restart…_, _Upgrade…_, _Check for a newer version_, each only where the runtime offers it; the confirmation leaves the full-screen view and runs as the dialogue of its verb, and `q` after it returns to the view

|`r`
|read the snapshot again

|`?`
|all keys, and the details of the selected figure (what it measures, since when)

|`q`
|leave the view to the prompt
|===

* *Live*: the view follows the runtime's stream and redraws only the figures that changed; the selection stays on its figure. While the runtime drains or upgrades, the progress line stands below the header (link:../shared/system.adoc#draining[System, While It Stops]).
* *Narrow*: below 80 columns the details lines are left out and `?` shows them; below 60 columns the view does not open and `system` prints the snapshot instead, after `operator.system.too_narrow`.
* *Where it was left*: the window, the grouping, and _per project_ are kept with the overview's state in `$XDG_STATE_HOME/pm-operator/overview.json` (xref:15-overview.adoc#overview-persistence[The Overview, Where the Operator Left It]).

[#t-stop]
== Stopping

[source,text]
----
pm › runtime stop
Stop the runtime?
  Running now: 3 plans · 1 epic · 4 tasks · 2 jobs (1 build, 1 test) · 5 workers, 3 busy
  When
    1) When what runs is done   Nothing new starts. Each running task and job finishes,
                                then the runtime stops.
    2) Now                      Running tasks are withdrawn and jobs stopped. Everything
                                goes on from its last committed state at the next start.
  Every client sees that it stops. Start it again on this machine: pm-operator runtime start.
  1) Stop when done   2) Stop now   k) keep it running                          [1] ›
◐ Stopping when what runs is done · 2 left: execute task of fix-relay, build of fix-relay
  runtime stop --now · runtime stop --withdraw
pm [stopping] ›
----

* `Enter` takes `1`, the drain, the preselection of link:../shared/system.adoc#stop[System, Stopping]; `k` (German `l`) sends nothing.
* *In the console* the prompt returns at once with the badge `stopping`; the progress is a quiet line above the prompt each time what is left changes, and the line of the stop itself when it stops. *As a shell command* the verb waits, printing the same lines, bounded as `drain` waits (the bound defined with the drain timeout), and exits `0` when the runtime stopped, or `0` with `The runtime is still draining (PID 48211).` when the bound passed first.
* *Nothing runs*: no choice, `Stop the runtime? Nothing runs.  y) stop  k) keep it running`.

[source,text]
----
pm [stopping] › runtime stop --withdraw
✓ The runtime keeps running; the stop was withdrawn.
pm ›
----

[source,text]
----
pm [stopping] ›
▪ The runtime is stopped (by the console, 14:12). runtime start starts it.
pm (stopped) › runtime start
Starting the runtime …
✓ Runtime pm-mcpd 0.9.1 running since 14:13. 3 plans running again.
pm ›
----

* `runtime stop --withdraw` for a drain of a signal is refused with `The drain was started by a signal; it cannot be withdrawn.` (`operator.system.signal_drain`); too late, it prints `system.stopping.too_late`.
* *Stopped*: the console stays open and does not reconnect by itself (link:../shared/system.adoc#stopped[System, Stopped, and Starting Again]); a verb that needs the runtime starts it and prints `Starting the runtime …` first.

[#t-restart]
== Restarting

[source,text]
----
pm › runtime restart
Restart the runtime?
  Running now: 1 plan · 1 task · 1 job · 5 workers
  Every client connects again by itself.
  When
  1) Restart when done ←      Nothing new starts. Each running task and job finishes,
                              then the runtime stops.
  2) Restart now              Running tasks are withdrawn and jobs stopped. Everything
                              goes on from its last committed state at the next start.
  k) keep it running
◐ Restarting … the clients connect again by themselves.
✓ Reconnected: pm-mcpd 0.9.1, restarted at 14:41. 1 question open, 1 plan running.
pm [1 question] ›
----

* `--when-done` and `--now` answer the choice of when, so the verb asks nothing; without either it
  asks, `Enter` takes the drain, and `k` keeps the runtime running.
* *Not back in time*: `The runtime did not come back. On the machine: pm-operator status.`, and the prompt shows `(reconnecting)` (xref:04-console.adoc#connection[The Console, Connection]).

[#t-upgrade]
== Upgrading

[source,text]
----
pm › runtime upgrade --check
Check for a newer version?
  asks    the organisation's registry, for the newest release of linux-x86_64
  never   sends anything about this machine beyond the request itself
  tokens  none
  y) yes   r) yes, and don't ask again   n) not now                            ›  r
✓ 0.10.0 available (2026-10-11), installed 0.9.1. Release notes: runtime upgrade --notes
pm › runtime upgrade
Upgrade to 0.10.0?
  Running now: 3 plans · 1 epic · 4 tasks · 1 job · 5 workers
  When
  1) Upgrade when done ←      Nothing new starts. Each running task and job finishes,
                              then the runtime stops.
  2) Upgrade now              Running tasks are withdrawn and jobs stopped. Everything
                              goes on from its last committed state at the next start.
  k) keep it running
Upgrading to 0.10.0
  ✓ fetched   ✓ verified   ✓ installed beside 0.9.1, links switched
  ◐ waiting for what runs · 1 left: build of fix-relay              runtime upgrade --now
pm [upgrading] ›
✓ Reconnected: pm-mcpd 0.10.0, restarted at 15:02.
▪ The runtime runs 0.10.0, this console 0.9.1. Leave it and open pm-operator again.
pm ›
----

* The consent is the dialogue of every consent (xref:03-dialogues.adoc#consent[Dialogues, Consent]); remembered, it is not asked again, and the line `Consent remembered: check for a newer version` stands in its place.
* `runtime upgrade --notes` prints the release notes of the version known, as plain text.
* `runtime upgrade --withdraw` is accepted while the release is fetched and verified; once the links are switched it is refused with the reason, and `runtime upgrade --now` shortens the wait.
* *An installation the runtime cannot upgrade*: `runtime upgrade` is refused with `system.upgrade.disabled` and prints the steps by hand of the specification.

[source,text]
----
pm [upgrading] ›
✗ 0.10.0 did not start: no answer within 30 s. 0.9.1 was restored and runs again; running work
  goes on from its last committed state.
✓ Reconnected: pm-mcpd 0.9.1, restarted at 15:03.
pm ›
----

* A failure before the links are switched prints `system.upgrade.failed_before` and the prompt returns without a reconnect; `runtime upgrade` again is _Try again_.

[#t-not-running]
== Not Running

[source,text]
----
$ pm-operator system
The runtime is not running. pm-operator runtime start starts it.
$ pm-operator runtime stop
The runtime is not running; there is nothing to stop.
----

* `system` never starts the runtime, as `status` does not; it exits `0`. `runtime stop` (with `--withdraw` too) never starts it either and exits `0` with its line; `runtime restart` without a runtime starts it (`Starting the runtime …`), as every other verb that needs the runtime does (link:../shared/system.adoc#channels[System, Who May]).
