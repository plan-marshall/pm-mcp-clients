[#levels]
== Levels

[#level-model]
=== Machine, Project, Plan

The onboarding records machine values, and they are defaults, not final values: a project may set its own for every aspect but the three that are facts of the machine (the interface language, the enrolled harnesses, the credential store), and a plan overrides what its overrides allow (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#machine-defaults[Onboarding, The machine sets defaults]). The terminal addresses a level with one option and shows, for every value, the level it comes from.

[cols="2,2,2,2",options="header"]
|===
|Aspect |Machine |Project |Plan

|`language`
|interface and model language (`machine-config.json`)
|model language (`user_language` of `local-config.json`)
|—

|`harnesses`
|the enrolled harnesses, one of them the default
|—
|—

|`models`
|the model catalogue
|the project's allowed models, from those the enrolled harnesses offer (`projects/<project_id>/model-catalogue.json`)
|—

|`roles`
|the machine role assignment
|the project's role assignment (`projects/<project_id>/role-assignments.json`)
|override per role (`overrides.json`)

|`credentials`
|the credential store; a token rotated or replaced with `credentials rotate|set`
|— (entries per project with `pm-operator credentials set --project`)
|—

|`providers`
|availability, variant, and credential per provider
|variant (`integrations.*.variant`) and credential
|the optional providers and the variant of an integration (`overrides.json`)

|`plan-defaults`
|landing, method, asking
|method and asking (`local-config.json`); landing with origin `team`, kept with the team's configuration and changed through the project setup
|landing, method, asking (origin `plan`): set where the plan first needs it, or later as a new instance version
|===

The variants of the landing axis are the sub-workflows `landing.pull-request`, `landing.main`, and `landing.files`; the values of `--landing` are their names without the prefix, as `--method` and `--asking` take those of `method.*` and `ask.*`. The machine settings that are no aspect, `config consents` and `config documents`, have the machine level only.

A dash is not a level of that aspect: `config harnesses --project p` is refused with usage exit code `2` and the text that names the levels the aspect has. The project column of `language` holds only the model language, since the interface language is the operator's.

[#addressing]
=== Addressing a Level

* *Machine* is the default: no level option, or `--machine`. A working directory inside an enrolled project never selects the project on its own: the operator who wants the project says so, so that a command typed in a checkout never changes a project by surprise.
* *Project*: `--project <project_id>`; `--project .` is the project of the working directory by the project resolution rule (link:../../../../pm-mcp-core/doc/specification/filesystem-layout/03-project-store.adoc#project-resolution[Project Resolution Rule]): the working directory's git top-level resolves to the enrolled project it belongs to; a directory that resolves to none is refused (`project_not_enrolled`) with the text that names `--project <project_id>`; `--project ?` (or `--project` with no value) shows a numbered list of the enrolled projects to pick from.
* *Plan*: `--plan <plan_id>`, which names its project too; `--plan ?` lists the live plans, of the project given with `--project`, or of every project.
* Every dialogue on a project or a plan names it in its step line (xref:03-dialogues.adoc#state-frame[The Frame of a State]), so the operator always sees which level the answer goes to.

[source,text]
----
$ pm-operator config roles --plan ?
Which plan?
  1) pm-mcp-clients   cli-onboarding        execute · 3 of 9 tasks
  2) pm-mcp-clients   message-catalogue     outline
  3) pm-mcp-core      session-log           finalize · waiting for review
Plan? 1-3   q) leave   › 1
----

[#origins]
=== Where a Value Comes From

Each value carries its origin, one of `default` (shipped with the release), `machine`, `project`, `team` (the project's team configuration in `.marshall/config/`), and `plan`. The nearest level wins; a value that overrides another names it.

[source,text]
----
$ pm-operator config show plan-defaults --project pm-mcp-clients
Plan defaults · project pm-mcp-clients

  Landing   Branch and Pull Request   team      overrides machine: Commit on the base branch
  Method    Test first                machine
  Asking    At the key points         default

Change: pm-operator config plan-defaults --project pm-mcp-clients
  Landing is set by the project's team (.marshall/config/); change it in the project setup.
----

* The origin is a word in its own column, never a colour only, so it survives a copy into an issue and a terminal without colour.
* `config show` without an aspect or key lists every aspect and then every plain key, grouped as in `machine-config.json`, with the origin column.
* In a dialogue on a project or a plan, a proposal that comes from a lower level says so beside the preselection (`← from machine`), and accepting it records nothing at this level: the level keeps deferring, so a later change of the machine value reaches it. Only a changed line is written at the addressed level.

[#running-plan]
=== A Plan's Own Values

A plan's values are its own level (origin `plan`). `config show plan-defaults --plan <plan_id>` shows the axes with their origin: `plan` where the plan set its own, otherwise the level it takes them from. A plan sets an axis where it first needs it (link:../../../../pm-mcp-core/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#options-when-needed[Asked When Needed]) or later: `config plan-defaults --plan <plan_id>` writes the plan's value, as `config roles --plan <plan_id>` writes the plan's overrides of roles and providers and shows the plan's effective assignment first. Each change composes a new instance version of the plan (link:../../../../pm-mcp-core/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-overrides[Plan Overrides]), and the client says so before the confirmation (`Applies where fix-relay next reads it; the plan's version becomes 7.`, `control.settings.applies`); a part of the plan that has run already keeps what it ran with (link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#UC-CTL-5[UC-CTL-5]). A change whose new version would not contain where the plan is (the landing while the plan lands) is refused with the reason, as is a value that cannot run for the project or the plan (`landing.main` on a protected base branch, `landing.files` for a plan from local changes); where an epic started the plan, its epic is told. The plan's settings are reached the same way from its actions (`o` in its menu, xref:19-actions.adoc[Actions on Plans and Epics]).
