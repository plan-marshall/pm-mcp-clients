[#transcripts]
== Transcripts

One transcript per state or per short sequence of states; the states each one shows are named above it, and xref:08-transcripts-later.adoc#state-coverage[Every State and Its Transcript] lists every state with its transcript. The operator's input follows `› `; `⏎` stands for `Enter` alone. A check is shown as it ended. The transcripts are in English; the German texts are those of xref:09-texts-common.adoc#texts[Texts], and one German transcript (xref:06-transcripts-steps-1-3.adoc#t-language[1 Language (language.detect, language.choose, language.record, language.done)]) shows the switch.

[#t-entry]
=== The Entry `pm-operator`

[#t-entry-desktop]
==== Onboarded, on the Desktop (`entry.runtime`, `entry.pairing`, `entry.where`, `entry.browser`, `entry.show`, `entry.wait`)

The first console after the onboarding, with no browser of this machine paired yet:

[source,text]
----
$ pm-operator
✓ Runtime started (pm-mcpd 0.9.0)
✓ Web access on http://127.0.0.1:7420
✓ Browser opened with a pairing code, valid for 10 minutes
    URL    http://127.0.0.1:7420/pair#code=KXQB-MRTN
    Code   KXQB-MRTN   valid until 14:32
pm › status
…
✓ Paired: local (Firefox on mbp-oliver)
pm › exit
$
----

A later console, with the browser paired:

[source,text]
----
$ pm-operator
✓ Runtime running (pm-mcpd 0.9.0)
✓ Web app: http://127.0.0.1:7420   (paired: Firefox on mbp-oliver)
pm [1 question] ›
----

* `entry.runtime` prints `✓ Runtime running` when one was running already. On the desktop `entry.pairing` issues no code when a browser of this machine is paired (`paired_by: open`); the browser is then not opened again, and `web` opens it (`web pair` pairs another one). In an SSH session it always issues a code (<<t-entry-ssh>>).
* `entry.browser` that cannot start the browser prints `– No browser opened: <reason>` and shows the ways in as over SSH.
* `entry.wait` is the console itself: a pairing is reported above the prompt (`✓ Paired: …`), and a redeemed code is replaced by a new one for a further device, which `web` shows.
* The console's own views are its verbs at that prompt (`status` above, `plans` for the overview of running work); `pm-operator` without a verb never opens one of them, it connects the web app (xref:01-commands.adoc#command-tree[The Verbs]).

* Over SSH `entry.pairing` always issues a code, whatever browser of this machine is paired, since the browser is on the operator's own computer; a browser that holds a valid device secret does not redeem it (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#start[The Terminal Client as the Entry]).

* `entry.other-device` is a choice of the network exposure, not a consent of the onboarding: its preselection is the safe answer `n`, which `Enter` takes, as the use case marks it (`no ←`).
* `entry.lan` opens the LAN listener on its own port `web.lan_port` beside the loopback listener, which stays open with its URL and any SSH forward (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#two-listeners[Loopback and LAN Listeners Side by Side]).
* `entry.lan` that cannot open the listener (the port taken on an interface, no certificate written) returns to `entry.wait` unchanged, with the cause and its fix, and nothing is reachable from the network:

[source,text]
----
Open to the network? y) yes   n) no, keep it on this machine [Enter]   › y
✗ The network listener did not open: port 7421 is in use on 192.168.1.20
  → stop the program that uses it, or choose another port:
    pm-operator config set web.lan_port <port>
pm ›
----

* Turning it off again is `web devices listener-off` (xref:08-transcripts-later.adoc#t-devices[Paired Devices]), which leaves the loopback listener open; `web disable` closes both.

----

* `entry.check-onboarded` prints nothing of its own; it leads to `entry.where-to-onboard` while the onboarding has not reached `onboard.completed`, otherwise to `entry.pairing` (<<t-entry-desktop>>).
* The preselection of `entry.where-to-onboard` is _here_ in an SSH session, as shown, and _in the web app_ on a desktop, where the browser can open (`w) in the web app [Enter]   h) here, in the terminal`).
* _In the web app_ goes on as the onboarded entry does from `entry.pairing` (<<t-entry-desktop>>, <<t-entry-ssh>>) and returns to the prompt with its badge; the web app shows `onboard.mode` or the state the onboarding stopped in. Only then is the kind of session told, over SSH as below:

[source,text]
----

* Left before it completes, the onboarding waits behind the badge, and `Enter` on the empty prompt continues it; a new console asks again, naming where it stopped:

[source,text]
----

----

* Completed here, the onboarding returns to the entry, which goes on as for a ready machine from `entry.pairing` (xref:07-transcripts-steps-4-7.adoc#t-completed[Done]).
* Until the onboarding completes, a verb that needs it is refused with both ways to complete it:

[source,text]
----
$ pm-operator plan add --project .

  in the web app.
----

* The automatic run is the choice `a` of `onboard.mode`, after _here_ in `entry.where-to-onboard`; there is no option for it.
* `auto.consent` has no `r`: the automatic run's consent is never remembered. `n` returns to `onboard.mode` with `Nothing was done.`; nothing of the run has happened.
* `auto.consent` lists the consents the run needs, each by its kind's title (`common.consent.kind.<kind>`) with what it looks for and runs (link:../shared/consents.adoc#auto[Consents, The Automatic Run's One Consent]); `?` lists every check. It covers exactly these, for this run only, and remembers none of them. A kind remembered earlier is listed with `remembered` in place of its detail and is not part of this consent. The automatic run asks no model, so `model_advice` is not listed; `fetch_icons` is, since the runtime fetches the icons for the web app whichever client runs the onboarding.
* The headless call is named because the consent is asked before the scan: whether a harness without a login probe is found is not known yet (link:../../../../pm-mcp-core/doc/specification/client-profiles/01-profile-schema.adoc#login-probe[Login Probe]).
* *A state that needs a token* stops the run there: `providers.credentials` is shown as in the guided run, and the run continues after it. It has no way to skip the provider; a provider can be left out after its check fails (`providers.failed`), or the operator leaves with `q` and the run waits at that state.
* *A step that needs the operator* (`auto.run` stops in a state of a step): the state is shown as in the guided run, under its step line, and the run continues after it:

[source,text]
----

    ✓  logged in
[2/7] Harnesses    ✓ Claude Code 2.4.1 (default), OpenCode 1.9.0

* *Models in the automatic run*: every model a harness lists is allowed. A harness that cannot list its models needs the operator: the run stops in `catalogue.select` for that harness alone, asks its model ids (`Model id for Aider › `, xref:06-transcripts-steps-1-3.adoc#t-models[3 Models]), and continues; the result names the ids with the reason `you were asked`.
* `check_credential_store` is listed only where the run will choose an OS store; with the files it is not asked (link:../shared/consents.adoc#kinds[Consents, The Kinds]).
* `auto.result`: a number runs that step again as a later run (`onboard.next`), its current value as the proposal, as `config <aspect>` would; once the step is done, the result is shown again (`onboard.auto-result`) with the changed value.

[#t-mode]
==== Guided (`onboard.mode`)

After _here_ in `entry.where-to-onboard` (<<t-entry-first>>), or in a console where the onboarding was left before step 1:

[source,text]
----
Set up this machine for plan-marshall

  Seven steps. Nothing on this machine is looked at, run, or changed until
  you say so in that step. You can stop at any point; the next run, here or
  in the web app, continues where you stopped.

    1  Language     the language of plan-marshall and of the models' texts
    …
    7  Plans        how plans run unless a project says otherwise

Begin with step 1? [Enter]   a) decide everything for me   ?   › ⏎
----

* The intro of `onboard.mode` is the shared `onboard.entry.intro` with `onboard.mode.resume`; the entry's question says the same with the console's own hint (`operator.entry.resume_hint`).
