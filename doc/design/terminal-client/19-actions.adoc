= Terminal Client: Actions on Plans and Epics
:toc: left
:toclevels: 3
:nofooter:

link:README.adoc[Terminal Client] » Actions on Plans and Epics

What the actions are, per state, is link:../shared/work-actions.adoc[Actions on Plans and Epics], for both clients (link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc[Use Cases, Controlling Work]). This part is how the console offers them. The conventions of the transcripts are those of xref:05-transcripts-entry.adoc#transcripts[Transcripts].

[#commands]
== Commands

----
  plan pause <plan_id> [--now|--after-task|--after-phase]
  plan start <plan_id>
  plan cancel <plan_id> --reason <text> [--close-pr|--keep-pr]
  plan abandon <plan_id> --reason <text> [--close-pr|--keep-pr]
  epic next <epic_id> [--raise-scope]
  epic decompose <epic_id> [--instruction <text>]   decompose again, with the review
  epic archive <epic_id>
  epic cancel <epic_id> --reason <text> [--with-plans|--without-plans]
  epic findings <epic_id>                the findings review
  epic watches <epic_id>                 the watches review
----

* All are operator verbs, in the console and as one shell command, and direct verbs: an argument answers its state, a missing one is asked, and `--no-input` stops there (xref:01-commands.adoc#direct-verbs[A Direct Verb Runs a Sub-Workflow]).
* An action the state does not allow is refused with the state and the actions it allows (`fix-relay is paused: start, abandon`).
* `pm-operator abort plan` and `abort epic` stay as they are and do what `plan cancel` (or `abandon`) and `epic cancel` do.
* The reviews are dialogues; as one shell command they need a terminal, like every dialogue.

[#full-screen]
== In the Full-Screen View

`a` on a plan or an epic in the overview (xref:15-overview.adoc[The Overview]) or in the plan view (xref:16-plan-view.adoc[The Plan View]) opens its actions below the row, with mnemonic keys in the language of the client:

----
▶ fix-relay              execute · running · 25 min          relay-hardening
      p  Pause…
      x  Cancel…

▶ relay-hardening        epic · 3 running · 1 paused · 4 staged      ! 3
      n  Next plan: relay-reconnect-backoff
      d  Decompose again…
      f  Findings review (3 new)
      w  Watches review (5)
      A  Archive…
      x  Cancel…
----

An action with `…` leaves the view for its dialogue and returns to it afterwards; _Start_ and _Next plan_ act in place and the row follows.

[#plan]
== A Plan

[source,text]
----
pm › plan cancel fix-relay
Cancel fix-relay?
  What ends      the running work: 1 job, 2 tasks
  Pull request   #214 is open   1) close it, with the reason ←   2) leave it open
  Its epic       relay-hardening is told
  Reason         › the approach is replaced by plan relay-v2
Cancel the plan? y) yes   n) no, keep it running   ?   › y
✓ fix-relay cancelled and archived; #214 closed; relay-hardening told
pm ›
----

[source,text]
----
pm › plan pause fix-relay
Pause fix-relay?
  1) now                       2 tasks withdrawn, 1 job stopped; they run again on start
  2) after the current task ←  implement · 4 min, build · 2 min finish
  3) after the current phase   execute runs to its end: 3 of 7 tasks left
  Its epic   relay-hardening is told
› ⏎
✓ fix-relay pausing after the task; relay-hardening told
…
✓ fix-relay paused
pm ›
----

`plan pause` without an answer asks; `--after-task` is the answer of the default, and `--no-input` without one stops.

[#epic-view]
== An Epic's View

`epic <epic_id>` prints the epic's view as a tree into the scrollback (link:../shared/epic-view.adoc[Epic View]); in the full-screen view, `Enter` on an epic opens it as its level, with the workstreams opening like nodes of the plan view and `a` for its actions.

[source,text]
----
pm › epic relay-hardening
relay-hardening · epic · running · 3 of 3 at once · needs you: 3
  WS-1 Reconnect                     2 shipped · 1 running
    shipped    relay-reconnect-backoff     #211 · 2 d ago
    running    relay-cursor-order          execute · 40 min
    paused     relay-reconnect-docs        by you · 1 h
  WS-2 Authentication                1 running · 1 staged
    waiting    relay-auth-v2               refine · a decision · 12 min
    staged     relay-token-rotation        after relay-auth-v2
  sources 2 documents, 1 issue · landings 2 · findings 3 new, 4 open · watches 5
pm ›
----

[#holds]
== What Holds a Plan

[source,text]
----
pm › plan fix-relay
fix-relay · execute · holds: a condition since 14:02
  cause   the plan reads cui-http, which this project may not read
  tried   3 times, last 14:10
  g) grant read access to cui-http…   r) retry   x) end the plan…   ?   › g
----

The acts of a hold are the same as in the shared design (link:../shared/work-actions.adoc#holds[What Holds a Plan]); the terminal offers them on `plan` and `epic` and below a row with `a`.

[#review]
== A Review

[source,text]
----
pm › epic findings relay-hardening
relay-hardening · findings review                         3 of 7 decided
F-0004  Reconnect loses the last event                            open
  Statement   After a reconnect the relay resends from the stored cursor,
              but the cursor is written after the event is delivered.
  Rules       a fix must hold for every transport; covered by a test that
              drops the connection between delivery and cursor write
  Origin      landing of relay-reconnect (#211) · 2 days ago
  Proposal    promote to a plan: it needs a change across two modules
k) keep   d) drop   p) promote ←   e) edit   t) talk   a) accept the remaining 4
›  e
  What should change?
  │ The rule should also name the SSE transport explicitly.
  │
    ▶  the planning role rewrites F-0004
  I changed the rules:
  - a fix must hold for every transport; …
  + a fix must hold for every transport, the SSE stream included; …
Accept? [Enter]   i) instruct again   x) discard   ?   › ⏎
k) keep   d) drop   p) promote ←   e) edit   t) talk   a) accept the remaining 4
›  p
    ▶  the planning role drafts a plan from F-0004
  Plan  relay-cursor-after-delivery
    Objective     write the cursor before an event counts as delivered
    Deliverables  cursor write order; a test per transport
    Surface       pm-relay, pm-api
    Depends on    —
Stage it? [Enter]   e) edit   b) back   ?   › ⏎
    ✓  F-0004 promoted: relay-cursor-after-delivery staged
F-0005  …
----

* `t) talk` opens a conversation inside the review, ended by an empty line; each change the planning role proposes is shown as a read-back like _edit_.
* Leaving the review (`q`, `Ctrl+D`) keeps what was decided; `epic findings relay-hardening` opens it where it stopped.
