== 4 Roles

[#t-roles-review]
=== The Overview (`roles.load`, `roles.default`, `roles.review`, `roles.validate`, `roles.write`, `roles.done`)

[source,text]
----
[4/7] Roles · Give every role a harness and a model
  The default assignment is applied to all 31 roles.

    1) Claude Code · opus-5.5      7 roles   planning and decisions
    2) Claude Code · sonnet-5.5   16 roles   execution and review
    3) OpenCode · qwen-coder       6 roles   screening and checks
    4) ⚠ not assignable             2 roles   no fast model allowed

Assign the 2 open roles first: 4) or e) adjust roles   s) ask the steward to refine   b) back   ?   ›
----

* While a `⚠` line remains, `Enter` is not the primary link and the prompt names what to do first; with none, the prompt is `Use the defaults? [Enter]`.
* `?1` to `?4` list the roles of the group with the advisory of the group.

* The steward runs on the default harness of step 2 with the model its profile maps to the tier `standard`, outside the model catalogue and exempt from qualification; it is not among the 31 roles this step assigns (link:../../../../plan-marshall-documentation/doc/specification/model-work/01-roles-and-configuration.adoc#steward-role[Steward Role]); `config harnesses --default` changes where it runs. == 5 Credentials

[#t-store-choose]
=== Choose (`store.detect`, `store.choose`, `store.consent`, `store.check`, `store.record`, `store.done`)

[source,text]
----
[5/7] Credentials · Where should this machine keep its tokens?
  1) macOS Keychain                                    ★ recommended ←
     Only plan-marshall's runtime reads them without asking you; any other
     program that tries makes macOS ask first.
  2) Files in ~/.plan-marshall-mcp/credentials/
     Readable by every program you run (mode 0600). Works everywhere, also
     without a desktop session.

  The choice holds until you change it; a change moves the tokens and never
  leaves a copy behind.

Use the macOS Keychain? [Enter]   other: 2   b) back   ?   › ⏎
[5/7] Credentials · Check the macOS Keychain with a test entry?
  runs        one test entry written to the Keychain, read back, and deleted
  never       reads or changes any other entry
  tokens      none

y) yes   r) yes, and don't ask again   n) not now   ?   › y
    ✓  write a test entry
    ✓  read it back
    ✓  delete it
✓ Tokens are kept in the macOS Keychain
----

* On Linux the first option is the Secret Service, with its own text (`Every program you run can read it while it is unlocked.`).
* `store.consent` (`check_credential_store`, link:../shared/consents.adoc#kinds[Consents, The Kinds]) is asked for an OS store only: the files lie in the machine's own directory and are checked without it. `n` stays (`Nothing was done.`); a remembered consent prints its line.

=== Not Available Now (`store.check`, `store.unavailable`)

[source,text]
----
[5/7] Credentials · Where should this machine keep its tokens?
  1) Linux Secret Service                              not available now
     Every program you run can read it while it is unlocked.
     ✗ no session bus: this is an SSH session
     → log in at the desktop, or use the files below
  2) Files in ~/.plan-marshall-mcp/credentials/                      ←
     Readable by every program you run (mode 0600). Works everywhere, also
     without a desktop session.

Use the files? [Enter]   l) check again   b) back   ?   ›
----

* Chosen while unavailable, or failing `store.check`, the state is `store.unavailable` with its cause and the two links `l) check again` and `o) choose another store`:

[source,text]
----
[5/7] Credentials · Where should this machine keep its tokens?
  1) Linux Secret Service                              ★ recommended ←
  …
Use the Secret Service? [Enter]   other: 2   b) back   ?   › ⏎
    ✓  write a test entry
    ✗  read it back: the collection was locked while the entry was written
       → unlock it (for example by logging in at the desktop), then check again
    ·  delete it   not run

[5/7] Credentials · The Secret Service is not available now
  ✗ the collection is locked
  → unlock it (for example by logging in at the desktop), then check again

Check again? [Enter]   o) choose another store   ?   › ⏎
    ✓  write a test entry
    ✓  read it back
    ✓  delete it
✓ Tokens are kept in the Secret Service
----

* `store.unavailable` is the operator's choice. `l` (here the primary link) runs `store.detect` again and checks the same store, under the consent already given; `o` returns to `store.choose` with the other stores. Nothing is written to the file store in place of the chosen one.
* Later, a recorded store that has become unavailable makes every step that needs a credential refuse with `credential_store_unavailable` and its fix (`common.error.credential_store_unavailable`, xref:09-texts-common.adoc#texts-common[Common]); `pm-operator status` names it too.

[#t-store-move]
=== A Later Change Moves the Tokens (`config credentials`, `store.confirm-move`, `store.move`)

[source,text]
----
$ pm-operator config credentials --store os
Credentials · Move the tokens to the macOS Keychain?
  moves       7 tokens from ~/.plan-marshall-mcp/credentials/ to the Keychain
  each        written, read back, then deleted from the files
  if stopped  the next run continues the move; no token is lost or doubled

Move 7 tokens? [Enter]   b) back   ?   › ⏎
    ✓  github                   moved
    ✓  sonar                    moved
    …
    ✓  pm-mcp-clients/github    moved
    ✓  the enrolment key moved
✓ Tokens are kept in the macOS Keychain
----

* The new store is checked first (`store.check`); `store.confirm-move` asks for the move with the count, and `store.move` moves each token: written, read back, then deleted from the old store. The enrolment integrity key moves last of all, once the enrolments verify under it in the new store (`onboard.store.move.key_moved`); only then is the new store recorded (`store.record`). A token that does not read back from the new store stays in the old one, is marked ✗ with its cause, and the move stops there; `l) check again` continues it, as does the next run of `config credentials`.

[#t-providers-credentials]
=== A Missing Token (`providers.credentials`)

[source,text]
----
[6/7] Providers · SonarCloud needs a token
  Stored in the macOS Keychain; it is never shown again and never reaches a
  model or a log.

Token (not shown while you type): ›
Store and check it? [Enter]   b) back   ?   › ⏎
✓ Token stored in the macOS Keychain
[6/7] Providers · Check the providers with their tokens?
  runs        a call of github.com and of sonarcloud.io with each token;
              gh auth status
  never       changes anything at the provider; sends the token anywhere else
  tokens      none

y) yes   r) yes, and don't ask again   n) not now   ?   › r
----

* Storing the typed token is the operator's own act and needs no consent; calling the providers with it is `providers.verify-consent` (`verify_providers`), asked once for every selected provider before `providers.verify`. `n` stays (`Nothing was done.`); with every token stored already, the consent follows `providers.select` directly.
* There is no way past a missing token here: `b` returns to `providers.select`, where the provider can be unselected, and a provider whose check fails can be left out in `providers.failed` (<<t-providers-verify>>).

* The token is read with the echo off into a `char[]` (xref:04-console.adoc#line-editor[Line Editor]) and sent in the body of one request to the runtime over its Unix domain socket, which only the user can open; it never crosses a network on its way to the credential store, and nothing of it is printed. `--no-input` stops here and names `pm-operator credentials set sonar`.

=== Check (`providers.verify`, `providers.failed`, `providers.record`, `providers.done`)

[source,text]
----
[6/7] Providers · Checking the providers
  GitHub                                                     ✓ ready
    ✓  github.com reachable
    ✓  token authenticates as oliver-wolff (fine-grained, expires in 41 days)
    ✓  permissions: contents, pull requests, checks (read and write)
    ✓  gh 2.71 is logged in as the same account
  SonarCloud                                                 ✗ not ready
    ✓  sonarcloud.io reachable
    ✗  token refused: 401 "Invalid token"
       → enter the token again

Enter the token again? [Enter]   l) check again   k) continue without SonarCloud   ?   › k
  SonarCloud will be recorded as not available. Projects can still set it up
  on their own.
Continue without SonarCloud? [Enter]   b) back   › ⏎
✓ Providers recorded: GitHub (gh); SonarCloud not available
----

* With every provider `✓`, the state passes on its own to `providers.record`; the client prints the result line.
* `providers.failed` is the operator's choice: `Enter` (_fix credential_) returns to `providers.credentials`, `l` runs `providers.verify` again, `k` records the provider as not available after its confirmation.

[#t-defaults]
== 7 Plans (`defaults.load`, `defaults.review`, `defaults.validate`, `defaults.record`, `defaults.done`)

[source,text]
----
[7/7] Plans · How should plans run on this machine?
  A project's setup and a single plan can choose otherwise.

  Landing   1) Branch and Pull Request ←   review and merge on the provider
            2) Commit on the base branch   no Pull Request, pushed directly
            3) Files only                  nothing is committed; you take over
  Method    4) Test first ←                tests are written before the code
            5) Tests after
  Asking    6) At every phase              you confirm each phase
            7) At the key points ←         the outline, and before the Merge
            8) Only questions              you are asked only what needs you

Use these defaults? [Enter]   change: e.g. 2 5   ?n explains a line   b) back   › 2
  Landing   2) Commit on the base branch ✎
Save these choices? [Enter]   change: 1-8   b) back   ?   › ⏎
    ✓  Commit on the base branch: checked for each project, where its base
       branch is known
    ✓  Test first
    ✓  At the key points
✓ Plan defaults recorded
----

* The three lines of the landing are the variants `landing.pull-request`, `landing.main`, and `landing.files` (link:../../../../plan-marshall-documentation/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-axes[Plan Behaviour Axes]); `?1` to `?3` name the variant with what it lands: the branch, the pull request, its reviews and the merge; a commit pushed on the base branch; no commit, the changes left in the working tree and the plan handed back.
* A variant that cannot run on this machine is listed without a number and with its reason (`Branch and Pull Request   needs a provider: none is available`).
* *A later run* (`config plan-defaults`, or `7` of `config`) adds a fourth line the first run never shows: the posture of a plan (`plan_defaults.posture`), unset by default, so that a plan asks its posture at its start (`init.options`) while no level sets it (link:../../../../plan-marshall-documentation/doc/specification/state-catalogue/19-onboarding-aspects-models-providers.adoc#state-defaults.review[State Catalogue, `defaults.review`]):
+
[source,text]
----
  Posture   9) Not set: each plan asks ←   10) Minimal   11) Standard   12) Full
----
* `defaults.validate` that refuses a line reprints the state with the line marked `✗ <reason>` and the prompt naming it.
* At the machine level it checks only what the machine knows: whether a provider is available for a pull request; the machine default is never checked against a repository. Whether a base branch is protected is checked where a project is known: the landing the project's team chooses in its setup, and a plan's start, which refuse _Commit on the base branch_ on a protected branch with the reason. A machine default that does not fit a project is refused for that project there, and the project or the plan chooses another.
