[#commands]
== Command Model

[#command-tree]
=== The Verbs

`pm-operator` is the operator's console. Without a verb it opens the console (xref:04-console.adoc[The Console]); inside it every verb is typed without the program name (`config roles --project .`), and the same verb also runs as one shell command (`pm-operator config roles --project .`), which does that one thing and exits, for scripts and quick changes. The console and the onboarding add the entry, the console commands, and the aspects of the existing verb `config` to the terminal verbs of `pm-operator` (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#command-tree[Command Tree]). All of them are operator verbs (`[op]`): a choice of the onboarding and an answer to a question are operator acts (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-two-channels[Operator Choices in the Web App and the Terminal], link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#change-cli-answers[Answers from the Terminal Client]), and the entry issues a pairing code, which only an operator verb may do. There is no verb `start` and no verb `onboard`: what to do first follows from the state of the machine.

* *`pm-operator`* without a verb opens the console after the operator checks; it starts the runtime on demand, as every verb does, and then follows the state of the machine:
** *Not fully onboarded* (`entry.check-onboarded` finds that the onboarding has not reached `onboard.completed`): `entry.where-to-onboard` asks where to go on, here or in the web app (xref:05-transcripts-entry.adoc#t-entry-first[Not Fully Onboarded]). _In the web app_ connects the web app as the flow of link:../../../../plan-marshall-documentation/doc/use-cases/02-entry.adoc#UC-ENT-1[UC-ENT-1] does, and the web app shows the onboarding where it stands; the console stays open beside it. _Here_ runs the onboarding dialogue from where it stands: the first run from `onboard.mode`, an interrupted run from the state it stopped in. Left before it completes, the prompt shows the step it stopped at (`pm [setup 3/7] ›`), and `Enter` on the empty prompt continues it.
** *Onboarded*, or once the onboarding run here completes (`onboard.completed`, as for a ready machine): it connects the web app as the flow of link:../../../../plan-marshall-documentation/doc/use-cases/02-entry.adoc#UC-ENT-1[UC-ENT-1] does, without waiting: the web listener is opened, the browser is opened with a pairing code only when no browser of this machine is paired yet, otherwise the URL is printed, and over SSH the ways in are printed (xref:05-transcripts-entry.adoc#t-entry-desktop[Onboarded, on the Desktop], xref:05-transcripts-entry.adoc#t-entry-ssh[Onboarded, over SSH]). Then the prompt, with what is pending. `entry.wait` is the console itself: a pairing is reported above the prompt, and `web` shows the ways in again. The terminal client's own views are reached by its verbs, typed at that prompt or given as a shell command (`plans`, the overview of running work; `projects`; `status`); the command without a verb never opens one of them, it connects the web app.
** `pm-operator --help` prints the verbs, as every picocli command does; it opens no console.
* *`config <aspect>`* starts the sub-workflow of one aspect as a later run (`onboard_run: reconfigure`), with the current values as the proposal, and answers each choice state from its arguments where they give one (<<direct-verbs>>). The aspects are the seven steps of the onboarding: `language`, `harnesses`, `models`, `roles`, `credentials`, `providers`, `plan-defaults`. `config providers --verify` checks the recorded providers again and changes nothing unless a check fails (xref:08-transcripts-later.adoc#t-providers-verify[Providers Checked Again]).
* *The machine settings* (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-10[UC-ONB-10]): `config` without an aspect renders `settings.choose`, every aspect with its value, the providers, the credentials with their status, the remembered consents, and the documents mode, each a number that opens it (xref:08-transcripts-later.adoc#t-settings[The Machine Settings]). Its acts that are no step of the onboarding have verbs of their own: `config consents` lists the remembered consents to withdraw one (`settings.withdraw`, xref:08-transcripts-later.adoc#t-consents[The Remembered Consents]); `config documents` sets `sources.documents_mode` (`settings.documents-mode`, xref:08-transcripts-later.adoc#t-documents[The Documents Mode]); `config credentials --rotate <credential_key>` or `--replace <credential_key>` gives a credential a new secret or a new kind and verifies the providers that use it (`settings.credential`, xref:08-transcripts-later.adoc#t-credential[A Token Rotated or Replaced]). `config credentials` without them is step 5, the store. The existing verbs `pm-operator credentials set|rotate` stay as they are and verify nothing.
* *`config harnesses`* runs step 2 again (xref:08-transcripts-later.adoc#t-config-harness[Harnesses Again]): one scan, the enrolled harnesses with the ones found since and the ones missing. `--add <client_id>` chooses a harness found, `--path <executable>` after it points at a known harness where the scan does not look (its shipped profile is used); `--remove <client_id>` unchecks an enrolled one, refused while roles use it; `--default <client_id>` sets the default, one of the harnesses chosen; `--no-icons` answers the icons consent with no. A harness the profiles do not know is added only in the dialogue (`harness.add`), never by arguments. `config models` asks the enrolled harnesses for their models again; `--no-advice` answers the advice consent with no.
* *`project release` and `project unenrol`* end a project's work on the machine as link:../shared/project-explorer.adoc#release[Project Explorer, Release] says; both are also actions of the project's setup (xref:17-projects.adoc[Projects]).
* *`web devices`* lists the paired devices and acts on them as link:../shared/paired-devices.adoc[Paired Devices] says (xref:08-transcripts-later.adoc#t-devices[Paired Devices]); the console itself needs no pairing and is never listed, so `revoke --others` revokes every paired device. `listener-off` closes the network listener and leaves the loopback listener open, unlike `web disable`, which closes both.
* *Other verbs* never ask where to onboard. A verb that needs a step of the onboarding that is not done yet (a credential before the credential store is chosen, a role before the catalogue exists) is refused, and the refusal names both ways to complete it: the console (`pm-operator`) and the web app (`operator.entry.onboarding_needed`, xref:13-texts-operator.adoc#texts-operator-entry[The Entry]).
* *`config show|set|unset`* keep what `pm-operator config` already is: the operator's configuration keys of `machine-config.json` and `local-config.json`. A key that an aspect or a setting owns (`language.*`, `credentials.store`, `providers.*`, `plan_defaults.*`, `sources.documents_mode`, the role assignment) is changed only through its aspect or setting, because the aspect validates and checks it; `config set` refuses it and names the aspect verb. `show` lists every key, the aspect-owned ones included.
* *`status`* prints the overview of running work as a tree, `--project <project_id>` for one project and `--by epic` with the plans below their epics (xref:15-overview.adoc#status-tree[The Tree]); `status --ended` prints the ended work instead (link:../shared/plan-overview.adoc#ended[Plan Overview, Ended Work]).
* *`reports`* lists the unread reports, `reports read` marks them read, and `reports open` opens a report's detail, which reads it (xref:24-reports.adoc[Reports]; link:../shared/reports.adoc[Reports] is what both clients show). They are operator verbs because reading changes the state every client shows; the console prints the count of unread reports when it opens.
* *The flags of the actions* on plans and epics are those of xref:19-actions.adoc[Actions on Plans and Epics], which says what each does; the listing above repeats them, 19 is the reference.
* *The console commands* (`plans`, `plan`, `epic`, `questions`, `answer`, `web`, `help`, `exit`) exist only inside the console; they are not shell verbs. `web qr` prints the QR code of the open pairing code again, with its URL, and `web pair` replaces the code (link:../../../../plan-marshall-documentation/doc/use-cases/02-entry.adoc#change-fresh-code[A Fresh Code after a Redemption]).

[#one-surface]
=== One Surface in Every Language

Command names, options, option values, aspect names, consent kinds, state ids, and link relations are the same in every language; only the texts are translated (link:../shared/texts-and-languages.adoc#two-languages[Texts and Languages, Two Languages]). A command line, a script, a support answer, and the documentation work in every language without change. The key of a prompt is a mnemonic of its label and therefore a text: it comes from the catalogue with the label and follows the language (`y) yes`, `j) ja`; xref:03-dialogues.adoc#keys[Links as Keys and Numbers]).

[#direct-verbs]
=== A Direct Verb Runs a Sub-Workflow

`config <aspect>` drives the same states as the dialogue; their arguments are answers given in advance. The client walks the workflow:

. It sends the request that starts the run of the aspect.
. In a server state (`[S]`) or a model state (`[M]`) it shows the progress and waits for the next state (xref:03-dialogues.adoc#waiting[Waiting, Progress, and a Model at Work]).
. In a choice state (`[O]`) it looks for an answer among the arguments: an option of the aspect for a choice, `--consent <kind>` for a consent state of that kind, `--no-icons` and `--no-advice` for the no of an optional consent, `--yes` for a confirmation of a displayed change (`harness.confirm`, `harness.add-confirm`, the move of `config credentials`). An answer the state accepts is sent as its link; the state is printed as one line with the answer (`✓ Interface language  Deutsch   (--interface de)`).
. A choice state without an answer among the arguments is shown as the dialogue and asks; with `--no-input` the client stops there instead (xref:03-dialogues.adoc#no-input[Without Prompts]).
. It ends when the sub-workflow reaches its done state (`language.done` and the others) or the onboarding rests in `onboard.completed`.

An argument the state does not accept (a locale without a pack, a model the catalogue does not allow) is not sent: the client shows the state with the refusal in place of the preselection and asks, or with `--no-input` stops with exit code `3` and the refusal. An argument that no state of the run asked for is reported after the run (`--landing main was not used: the landing is set by the project's team`), never silently dropped.

A consent is never implied: no argument but `--consent <kind>` answers a consent state with yes, `--yes` never does, and only `--no-icons` and `--no-advice` answer one with no, where the no lets the step go on (link:../shared/consents.adoc#kinds[Consents, The Kinds]); `--consent` holds for this run only and is never remembered (`yes_remember` exists only as the dialogue's `r`). A secret is never an argument: `providers.credentials` always asks with the echo off, and with `--no-input` stops and names `pm-operator credentials set <credential_key>`.

[#exit-codes]
=== Exit Codes

The exit codes are those of a verb run as one shell command; the console itself exits with `0` (`exit`, `Ctrl+D`) or `4` (operator checks).

[cols="1,4",options="header"]
|===
|Code |Meaning

|`0`
|done: the sub-workflow reached its done state, or a read-only verb answered.

|`1`
|refused by the runtime: an error code of `pm-api` (xref:03-dialogues.adoc#refusals[Refusals and Errors]), printed with its text and fix.

|`2`
|usage: an unknown verb, option, or option value (picocli).

|`3`
|not finished: the run stopped at a choice it was not given (`--no-input`), or the operator left it (`q`) before its done state; the state stays where it is.

|`4`
|operator checks: no interactive terminal, or a coding-agent environment (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[Operator Channel Isolation], item 2).

|`130`
|interrupted with `Ctrl+C`; the state stays where it is, as with `q`.
|===
