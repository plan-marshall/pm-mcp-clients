What the plan view shows, level by level, is link:../shared/plan-view.adoc[Plan View], for both clients (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#UC-PLN-1[UC-PLN-1]). This part is how the console draws it: as the third level of the full-screen view of xref:15-overview.adoc[The Overview], and as a tree in the scrollback. The conventions of the transcripts are those of xref:05-transcripts-entry.adoc#transcripts[Transcripts].

[#plan-view-ways]
== Two Ways

* *In the full-screen view*: `Enter` on a plan in `plans`, in an epic's view, or in ended work opens its plan view in the same view; `Esc` goes back to where it was opened, and `p` and `e` lead to the plan's project and its epic from wherever that was (<<full-screen>>).
* *`plan <plan_id>`* prints the plan's process as a tree into the scrollback, opened down to where the plan is; `--all` opens every level, `--depth <n>` opens n levels (<<tree>>). It is the accessible path and the fallback of the full-screen view, as `status` is for the overview.

[#full-screen]
== In the Full-Screen View

[#full-screen-tree]
=== A Tree to Open and Close

----
 pm-mcp-clients › relay-hardening › fix-relay › execute                ● connected
 fix-relay · execute · running · 2 h 10 min · #214
 tokens so far   412 k (380 k in · 32 k out)
 ─────────────────────────────────────────────────────────────────────────────
   ✓ phase  init                                    done · 2 min
   ✓ phase  refine                                  done · 14 min
   ✓ phase  outline                                 done · 31 min
   ✓ phase  plan                                    done · 9 min
 ▾ ▶ phase  execute                                 running · 25 min
     ✓ envelope-ready                               done ×2
▶  ▾ ▶ envelope-ready                               running · run 3
         ▶ tasks  4 of 7 tasks done
     ○ envelope-close                               planned
 ▸ ○ phase  finalize                                planned
 ─────────────────────────────────────────────────────────────────────────────
 ↑↓ move   Enter details   → open   Esc back   a actions   ? help   q leave   e epic   p project   ← close   . where it is
----

* The plan view is a tree: `▸` a closed node, `▾` an open one; `→` (`l`) opens the selected node one level, `←` (`h`) closes it or moves to its parent.
* It opens with the path to the plan's current position open and the selection on the running leaf; `.` jumps there again from anywhere.
* The header is the path from the plan's project and its epic to the plan and on to the selected node (`pm-mcp-clients › relay-hardening › fix-relay › execute`; a plan of no epic `pm-mcp-clients › docs-typo › execute`; link:../shared/plan-view.adoc#way-out[Plan View, Its Project and Its Epic]), and below it the plan's line: its phase, its state, since when it runs, and its own pull request by its number (a terminal hyperlink, OSC 8, where the terminal shows one).
* `p` opens the plan's project in the overview, its plans and epics (xref:15-overview.adoc#full-screen-project[A Project]); `e` opens its epic's view (xref:19-actions.adoc#epic-view[An Epic's View]), and for a plan opened there goes back to it. A plan of no epic has no `e`: the key line leaves it out. Both are one step from wherever the plan view was opened (the overview, an epic's view, ended work), and `Esc` still goes back to that place; an ended plan leads the same way.
* *The state* is one of the closed list of link:../shared/plan-overview.adoc#texts[Plan Overview, Texts]: `running`, `pausing after the task` or `pausing after the phase`, `paused`, `waiting for you`, `held`. A held plan names its hold after it, with its kind and since when (`execute · held · holds: a condition since 14:02`), and `a` offers its acts (xref:19-actions.adoc#holds[What Holds a Plan]).
* *Tokens so far*: the line below the plan's line (link:../shared/plan-view.adoc#tokens[Plan View, Tokens So Far]): the total with its split, a floor with `≥` and the count of tasks not measured where there are any, `none yet` before the first model call; never money or a limit. `t` shows below the header the same figure by phase and by role, each line with its raw components as the harnesses reported them; `t` again hides it.
* `a` opens the plan's actions below the header (xref:19-actions.adoc#full-screen[Actions]).
* `Enter` on a leaf shows its details below it (<<full-screen-leaf>>); on a node that waits for the operator it leaves the view and opens the decision, as `answer` does.

=== Sub-Workflows

----
 pm-mcp-clients › relay-hardening › fix-relay › finalize › remediation.ci-failure  ● connected
 ─────────────────────────────────────────────────────────────────────────────
 ▾ ▶ phase  finalize                                running · 40 min
     ✓ create-pr                                    done
     ✓ automatic-review                             done
   ▾ ▶ ↳ sub-workflow  remediation.ci-failure       running · run 2
       ✓ analyze                                    done ×2
     ▾ ▶ ↳ sub-workflow  git.commit_and_push        running
▶        ▶ push                                     running · 0:12
         ○ verify-remote                            planned
       ○ await-ci                                   planned
     – await-waiver                                 not taken
     ○ merge                                        planned
 ─────────────────────────────────────────────────────────────────────────────
----

* A sub-workflow's line carries `↳` and the word `sub-workflow`; it opens like a phase, through every level of nesting.
* A branch not taken is `–` with `not taken`; it is shown where the workflow branched and opens to show what it would have run.

[#activity]
=== A Worker at Work

`Enter` on a task of a leaf opens what its worker does as a level of the view, live while it is shown; `plan <plan_id> --activity <task_id>` prints the same into the scrollback, and with `--watch` follows it until `q` (link:../shared/plan-view.adoc#worker[Plan View, A Worker at Work]; link:../../../../pm-mcp-core/doc/specification/client-profiles/01-profile-schema.adoc#worker-activity[What a Worker Does]):

----
  fix-relay › execute › execute.envelope · TASK-003
  implement · claude sonnet · attempt 1 · running 6 min · 48 k tokens
  14:02:11  wrote      Reading the relay's transport before changing it.
  14:02:14  tool       read pm-relay/src/main/java/…/Transport.java
  14:02:20  tool       bash ./mvnw -pl pm-relay test        failed · 4 KiB
  14:03:02  changed    pm-relay/src/main/java/…/Transport.java
  14:03:40  link       submit:TASK-003
  14:03:41  ⚠ off track  repeating (5 of 5): shown
----

* The head, the entries and their kinds, the gap where entries gave way to the journal's bound (`plan.activity.gap`), and a harness without an event stream (`plan.activity.server_only`) are those of the shared design; every text and target is printed after the control sequences are removed (xref:04-console.adoc#output-safety[Output Safety]).
* *Off track*: the head and the entry name the signal (`repeating`, `no_progress`, `over_size`, `outside_footprint`), its value and threshold, and what the server did (`show`, `nudge`, `yield`, `restart`); it needs no act and is never a badge of what needs the operator. A `yield` or a `restart` is also the report `task.off_track` (xref:24-reports.adoc[Reports]).
* The stream is opened only while the level is shown and closed when it is left.

[#full-screen-keys]
=== Keys

The keys of the overview hold here too (xref:15-overview.adoc#full-screen-keys[Keys]); those of this table replace them where both name a key: `→` (`l`) and `←` (`h`) open and close nodes instead of moving between levels, and `Enter` shows a leaf's details instead of opening a row. `Esc` goes back to where the plan view was opened: the project, an epic's view, ended work, or the reports.

[cols="1,3",options="header"]
|===
|Key |Action

|`→`, `l`
|open the selected node one level (replaces _open_ of the overview)

|`←`, `h`
|close the selected node, or move to its parent (replaces _back_ of the overview)

|`Enter`
|on a leaf, its details; on a task of a leaf, what its worker does (<<activity>>); on a node that waits for the operator, the decision (replaces _open_ of the overview)

|`a`
|the plan's actions, below the header; on a node that holds, the acts of the hold

|`.`
|jump to where the plan is

|`p`
|the plan's project: its level of the overview, with its plans and epics

|`e`
|the plan's epic: its epic view (replaces _its epic_ of the overview, which moves to the epic in the view by epic); none for a plan of no epic

|`t`
|show or hide the plan's tokens by phase and by role, with their raw components

|`*`
|open every level below the selected node

|`n`
|show or hide the nodes not in this plan

|`c`
|on an ended plan: its completion report, as a level of the view (xref:24-reports.adoc#completion[Reports, A Completion Report])
|===

[#full-screen-live]
=== Live

The tree follows the plan's events; the selection stays on its node. When the plan changes its composition, the view reads the process again and prints `The plan changed: replan` in the header for a moment; when the plan ends, the header says so and the tree stays as it ended.

[#ended]
=== An Ended Plan

A plan that has ended, opened from ended work (xref:15-overview.adoc#ended[Ended Work]) or by `plan <plan_id>`, shows as it ended, read from the archive: the header names its outcome, its reason, and when it ended (`fix-relay · cancelled 2 d ago · the approach is replaced by plan relay-v2`; the outcomes of link:../shared/work-actions.adoc#outcomes[How a Plan Ends]); the tree is the process as it was when the plan ended, opened down to where it stopped; nothing updates, and `a` offers _Chat…_ alone (`fix-relay has ended: its view, and a chat about it`; xref:19-actions.adoc#chat-ended[A Chat About Ended Work]); `c` opens its completion report (link:../shared/completion-report.adoc[Completion Report]), which `plan report <plan_id>` prints.

[#tree]
== The Tree (`plan`)

[source,text]
----
pm › plan fix-relay
fix-relay · execute · running · 2 h 10 min · pull request #214 https://github.com/plan-marshall/pm-mcp-clients/pull/214
  in pm-mcp-clients · epic relay-hardening     status --project pm-mcp-clients · epic relay-hardening
  tokens so far   412 k (380 k in · 32 k out)       plan fix-relay --tokens
  done      phase init                       2 min
  done      phase refine                     14 min
  done      phase outline                    31 min
  done      phase plan                       9 min
  running   phase execute                    25 min
    done ×2   envelope-ready
    running   envelope-ready                 run 3 · tasks: 4 of 7 done
    planned   envelope-close
  planned   phase finalize
pm ›

pm › plan docs-typo
docs-typo · execute · running · 3 min
  in pm-mcp-clients                            status --project pm-mcp-clients
  done      phase init                       1 min
  running   phase execute                    2 min
    running   sub-workflow land
  planned   phase finalize
  not in this plan: refine, outline, plan (the land lane)
pm ›
----

* The tree uses words for the states, so that it reads the same without glyphs and colour; sub-workflows carry the word `sub-workflow`. A plan of the land lane shows its `land.*` states as the sub-workflow `land` within `execute`, and the phases the lane does not call as not in this plan; `land` is never a phase.
* `plan fix-relay --all` opens every level; `--depth 2` opens two; `--tokens` prints the tokens so far by phase and by role after the tree, and `--components` adds their raw components. An ended plan's line shows its final figure.
* The third line is the plan's tokens so far (link:../shared/plan-view.adoc#tokens[Plan View, Tokens So Far]); `none yet` before the first model call.
* The second line names the plan's project and its epic, where it has one, each with the command that opens it (`status --project <project_id>`, `epic <epic_id>`), so that each is one command away.
* The first line carries the state from the same closed list as the full-screen header, the hold with its kind where one holds, and the plan's pull request by its number and its URL. An ended plan prints `ended` with its outcome instead (`fix-relay · ended: cancelled · 2 d ago`) and the tree as it ended.
