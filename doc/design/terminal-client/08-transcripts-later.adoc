== Later Changes and Scripts

The first two run a verb as one shell command, as a script does, and so does `config providers --verify`; the others run it in the console.

* A consent whose _no_ lets the step go on is answered no by its own option (`--no-icons`, `--no-advice`); without it, or `--consent` of its kind, `--no-input` stops there as at every other consent. A remembered consent needs neither.

[#t-config-harness]
=== Harnesses Again (`config harnesses`)

A later run of step 2, `config harnesses` (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-4[UC-ONB-4], _Variations_): one scan again; a harness found that is not enrolled is offered, an enrolled one no longer found is shown as missing and offered for removal, and the default can change. The consents remembered in the first run pass with their line.

[source,text]
----
pm › config harnesses
  ✓ Consent remembered: look for harnesses   (withdraw: pm-operator config consents)
  ✓  Looking for harnesses: 3 found
  ✓ Consent remembered: fetch the icons of the harnesses
  ✓ Icons fetched: 1
Harnesses · Choose the harnesses to enrol
    1) [x] Claude Code   2.4.1   ~/.local/bin/claude         ✓ supported   ★ default
    2) [x] OpenCode      —       /opt/homebrew/bin/opencode  missing: not found any more
           used by 8 roles; reassign them first: pm-operator config roles
    3) [ ] Codex         0.32.0  /opt/homebrew/bin/codex     ✓ supported   new since the last run

Keep as it is? [Enter]   toggle: 1-3   d) set the default   a) add …   l) look again   ?   › 2
  2 cannot be removed: used by 8 roles; reassign them first: pm-operator config roles
Keep as it is? [Enter]   toggle: 1-3   d) set the default   a) add …   l) look again   ?   › 3 d
    3) [x] Codex         0.32.0  /opt/homebrew/bin/codex     ✓ supported   new since the last run ✎
  default   1) Claude Code ←   3) Codex   › 3
    3) [x] Codex         0.32.0  /opt/homebrew/bin/codex     ✓ supported   ★ default ✎
Check 1 harness, Codex the default? [Enter]   toggle: 1-3   d) set the default   a) add …   l) look again   ?   › ⏎
  ✓ Consent remembered: check whether a harness is logged in
  Codex
    ✓  version 0.32.0 is supported (0.32 – 0.x)
    ✓  logged in
Harnesses · Enrol 1 harness
    Codex   ★ default   new since the last run
      Path      /opt/homebrew/bin/codex
      …
Enrol 1 harness, Codex the default? [Enter]   b) back   ?   › ⏎
✓ 1 harness enrolled: Codex 0.32.0 (default)
  Codex has no model allowed yet: run ③ Models.
----

* The proposal is the current state: every enrolled harness found is ticked, the default as recorded. A harness found that is not enrolled is offered unticked, marked `new since the last run`; ticking it adds it. An enrolled one no longer found is unticked and marked missing: it is offered for removal, and unticking an enrolled one found removes it too; `harness.confirm` lists it as `Remove OpenCode: its enrolment is deleted`. With nothing changed the prompt is `Keep as it is?`, and `Enter` ends the run without a change.
* A harness that roles use cannot be removed, neither unticked nor as missing: it stays ticked, with the roles and the verb that reassigns them (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-6[UC-ONB-6]); its default mark can still move.
* The check and the confirmation cover the harnesses that change: a new one, and an enrolled one whose version or digest changed (`was 2.3.0: checked and enrolled again`). An unchanged one keeps its enrolment.
* A new harness has no allowed model until `config models` runs; a removed one's allowed models go with it. A new default moves the steward of later advice to it (xref:07-transcripts-steps-4-7.adoc#t-roles-steward[Ask the Steward]); the roles keep their harnesses.
* With arguments: `--add`, `--remove`, `--default`, `--path` (xref:01-commands.adoc#command-tree[The Verbs]).

[#t-consents]
=== The Remembered Consents (`config consents`)

The terminal side of link:../shared/consents.adoc#remembered[Consents, The Remembered Consents]: what the runtime remembers, given in either client.

[source,text]
----
pm › config consents
Consents · The consents you said not to ask again
    1) look for harnesses                    scan_harnesses
         12 May, 10:14 · terminal
    2) fetch the icons of the harnesses      fetch_icons
         12 May, 10:14 · terminal
    3) check whether a harness is logged in  probe_harness_login
         12 May, 10:15 · Firefox on mbp-oliver
    4) look at a project's checkout          inspect_checkout
         pm-mcp-clients · 2 Jun, 09:40 · terminal
    5) run scripts of a project's checkout   run_checkout_scripts
         pm-mcp-clients · 3 scripts · 2 Jun, 09:41 · terminal   ?5 lists them
    6) approve the cost of a role task       model_cost
         pm-mcp-clients · 3 Jun, 16:02 · iPad Oliver

  A withdrawn consent is asked again the next time its action runs.

Withdraw: 1-6   q) leave   ?   › 3 6
✓ 2 consents withdrawn; they are asked again the next time.
pm ›
----

* One entry per remembered consent: the title of its kind (`common.consent.kind.<kind>`) and the kind; below it the project for a kind of a project (`inspect_checkout`, `run_checkout_scripts`, `model_cost`), for `run_checkout_scripts` the number of scripts it covers, when it was given, and where: `terminal`, or the label of the paired device that gave it in the web app. `?5` lists each script of the consent with its arguments and digest.
* Numbers withdraw at once, without a confirmation: withdrawing only brings back a question. Withdrawing is audited with the channel `cli`.
* A consent is never given here; it is given only where its action asks (xref:03-dialogues.adoc#consent[Consent]). With no remembered consent the verb prints `No consent is remembered.` and returns.

[source,text]
----
$ pm-operator config providers --verify
Providers · Checking the providers again
  GitHub (gh)                                                ✓ ready
    last check  ✓ ready, 12 May, 10:24
    ✓  github.com reachable
    ✓  token authenticates as oliver-wolff (fine-grained, expires in 9 days)
    ✓  permissions: contents, pull requests, checks (read and write)
    ✓  gh 2.71 is logged in as the same account
  SonarCloud                                                 ✗ not ready
    last check  ✓ ready, 12 May, 10:24
    ✓  sonarcloud.io reachable
    ✗  token refused: 401 "Invalid token"
       → enter the token again

Enter the token again? [Enter]   l) check again   k) continue without SonarCloud   ?   › ⏎
Providers · SonarCloud needs a token
  …
Token (not shown while you type): ›
Store and check it? [Enter]   b) back   ?   › ⏎
  SonarCloud                                                 ✓ ready
    ✓  sonarcloud.io reachable
    ✓  token authenticates as oliver-wolff (user token, no expiry known)

* `--verify` runs `providers.verify` on the recorded providers; each shows the result and the time of its last check before the new one. With `--project <project_id>` it checks the project's providers.
* A token that expires within 14 days is named in the result line.

=== Paired Devices (`web devices`)

[source,text]
----
pm › web devices
Paired devices · The browsers that can act on this machine
    1) Firefox on mbp-oliver     paired 12 May   last used today 14:02   loopback   this one
    2) Safari on iPad            paired 20 May   last used 3 d ago       network
    3) Chrome on build-box       paired 2 Jun    last used 5 weeks ago   loopback

  The console needs no pairing and is not listed. Network listener: on.

Act on a device: 1-3   o) revoke all others   n) turn the network listener off   q) leave   ?   › 2
  2) Safari on iPad
Rename or revoke? r) rename   x) revoke   b) back   ?   › r
Label [Safari on iPad] › iPad Oliver
✓ Renamed: iPad Oliver
pm › web devices revoke 3
Revoke Chrome on build-box? It is signed out at once; its open pages close with the reason.
Revoke? [Enter]   b) back   ?   › ⏎
✓ Revoked: Chrome on build-box
pm › web devices revoke --others
Revoke 1 device other than this one (iPad Oliver)?
Revoke? [Enter]   b) back   ?   › ⏎
✓ Revoked 1 device; Firefox on mbp-oliver stays paired.
pm › web devices revoke 1
Revoke Firefox on mbp-oliver? It is the browser you are using on this machine:
  its pages close and show the pairing page; a new code pairs it again.
Revoke? [Enter]   b) back   ?   › ⏎
✓ Revoked: Firefox on mbp-oliver. web pair issues a new code.
pm ›
----

* `web devices` is the terminal side of link:../shared/paired-devices.adoc[Paired Devices]: the list (`devices.list`) with label, when paired and last used, from where (loopback or the network), and which one is _this one_; the acts (`devices.act`) rename, revoke one, revoke all others, and turn the network listener off (as `web disable`); a revocation (`devices.revoke`) voids the device's token at once and closes its open pages with the reason.
* _This one_ is the browser the console's entry paired or last opened on this machine; revoking it asks first and says that its pages land on the pairing page. Revoking any other device asks too, since it cannot be undone; `--yes` answers that confirmation in a script.
* The direct forms `web devices rename <device_id> <label>`, `web devices revoke <device_id>`, and `web devices revoke --others` act at once after the confirmation; the ids are the numbers of the list or the device ids the list shows with `?`.
