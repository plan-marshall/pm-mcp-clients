[#t-later]
== Later Changes and Scripts

The first two run a verb as one shell command, as a script does, and so do `config providers --verify` and `config credentials --rotate`; the others run it in the console. The machine settings of link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-10[UC-ONB-10] start at <<t-settings>>.

$ pm-operator config harnesses --add codex --no-input

  ✓  Looking for harnesses: 3 found
  –  Icons: no   (--no-icons)
  ✓  Harnesses   Claude Code (default), OpenCode, Codex 0.32.0   (--add codex)

    ✓  version 0.32.0 is supported (0.32 – 0.x)

----

* A consent whose _no_ lets the step go on is answered no by its own option (`--no-icons`, `--no-advice`); without it, or `--consent` of its kind, `--no-input` stops there as at every other consent. A remembered consent needs neither.

[#t-config-harness]
=== Harnesses Again (`config harnesses`)

A later run of step 2, `config harnesses` (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-4[UC-ONB-4], _Variations_): one scan again; a harness found that is not enrolled is offered, an enrolled one no longer found is shown as missing and offered for removal, and the default can change. The consents remembered in the first run pass with their line.

[source,text]
----
pm › config harnesses
  ✓ Consent remembered: look for harnesses   (withdraw: pm-operator config consents)
  ✓  Looking for harnesses: 3 found
  ✓ Consent remembered: fetch the icons of the harnesses
  ✓ Icons fetched: 1
Harnesses · Choose the harnesses to enrol
    1) [x] Claude Code   2.4.1   ~/.local/bin/claude         ✓ supported   ★ default
    2) [x] OpenCode      —       /opt/homebrew/bin/opencode  missing: not found any more
           used by 8 roles; reassign them first: pm-operator config roles
    3) [ ] Codex         0.32.0  /opt/homebrew/bin/codex     ✓ supported   new since the last run

Keep as it is? [Enter]   toggle: 1-3   d) set the default   a) add …   l) look again   ?   › 2
  2 cannot be removed: used by 8 roles; reassign them first: pm-operator config roles
Keep as it is? [Enter]   toggle: 1-3   d) set the default   a) add …   l) look again   ?   › 3 d
    3) [x] Codex         0.32.0  /opt/homebrew/bin/codex     ✓ supported   new since the last run ✎
  default   1) Claude Code ←   3) Codex   › 3
    3) [x] Codex         0.32.0  /opt/homebrew/bin/codex     ✓ supported   ★ default ✎
Check 1 harness, Codex the default? [Enter]   toggle: 1-3   d) set the default   a) add …   l) look again   ?   › ⏎
  ✓ Consent remembered: check whether a harness is logged in
  Codex
    ✓  version 0.32.0 is supported (0.32 – 0.x)
    ✓  logged in
Harnesses · Enrol 1 harness
    Codex   ★ default   new since the last run
      Path      /opt/homebrew/bin/codex
      …
Enrol 1 harness, Codex the default? [Enter]   b) back   ?   › ⏎
✓ 1 harness enrolled: Codex 0.32.0 (default)
  Codex has no model allowed yet: run ③ Models.
----

* The proposal is the current state: every enrolled harness found is ticked, the default as recorded. A harness found that is not enrolled is offered unticked, marked `new since the last run`; ticking it adds it. An enrolled one no longer found is unticked and marked missing: it is offered for removal, and unticking an enrolled one found removes it too; `harness.confirm` lists it as `Remove OpenCode: its enrolment is deleted`. With nothing changed the prompt is `Keep as it is?`, and `Enter` ends the run without a change.
* A harness that roles use cannot be removed, neither unticked nor as missing: it stays ticked, with the roles and the verb that reassigns them (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-6[UC-ONB-6]); its default mark can still move.
* The check and the confirmation cover the harnesses that change: a new one, and an enrolled one whose version or digest changed (`was 2.3.0: checked and enrolled again`). An unchanged one keeps its enrolment.
* A new harness has no allowed model until `config models` runs; a removed one's allowed models go with it. A new default moves the steward of later advice to it (xref:07-transcripts-steps-4-7.adoc#t-roles-steward[Ask the Steward]); the roles keep their harnesses.
* With arguments: `--add`, `--remove`, `--default`, `--path` (xref:01-commands.adoc#command-tree[The Verbs]).

[#t-settings]
=== The Machine Settings (`config`, `settings.choose`)

The machine settings of both clients (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-10[UC-ONB-10]; the web app's side is link:../web-app/machine-settings.adoc[Web App, Machine Settings]): what the onboarding recorded, each part a number that opens it.

[source,text]
----
pm › config
Settings · How this machine is set up
  Aspects
    1) Language      Deutsch, models English
    2) Harnesses     Claude Code 2.4.1 (default), OpenCode 1.9.0
    3) Models        5 models on 2 harnesses
    4) Roles         31 roles assigned
    5) Credentials   macOS Keychain
    6) Providers     GitHub (gh) ✓ ready; SonarCloud ✓ ready
    7) Plans         Pull Request · Test first · key points
  Tokens
    8) github        GitHub · fine-grained · ⚠ expires in 9 days
    9) sonar         SonarCloud · user token · no expiry known
  10) Remembered consents   6
  11) Documents             ask each time
  12) Paired devices        3 devices · network listener off

Open: 1-12   q) leave   ?   › 8
----

* `1` to `7` run the aspect as `config <aspect>` does, a later run of its step (`onboard.entry` with `reconfigure <aspect>`); `8` and `9` open <<t-credential>> for that token; `10` <<t-consents>>; `11` <<t-documents>>; `12` <<t-devices>>. Each returns to this list when it ends; `q` leaves to the prompt.
* A token that has expired or expires within 14 days is marked `⚠` with its date; an expired one also names the plans it holds (`⚠ expired: holds 1 plan`). The status of a token is that of its last check (<<t-providers-verify>>).
* An aspect a project sets for itself is changed in that project's setup, never here; the line says only what the machine provides.

[#t-consents]
=== The Remembered Consents (`config consents`, `settings.withdraw`, `settings.remove-consent`)

The terminal side of link:../shared/consents.adoc#remembered[Consents, The Remembered Consents]: what the runtime remembers in `consents.json`, given in either client.

[source,text]
----
pm › config consents
Consents · The consents you said not to ask again
    1) look for harnesses                    scan_harnesses
         12 May, 10:14 · terminal
    2) fetch the icons of the harnesses      fetch_icons
         12 May, 10:14 · terminal
    3) check whether a harness is logged in  probe_harness_login
         12 May, 10:15 · Firefox on mbp-oliver
    4) look at a project's checkout          inspect_checkout
         pm-mcp-clients · 2 Jun, 09:40 · terminal
    5) run scripts of a project's checkout   run_checkout_scripts
         pm-mcp-clients · 3 scripts · 2 Jun, 09:41 · terminal   ?5 lists them
    6) approve the cost of a role task       model_cost
         pm-mcp-clients · 3 Jun, 16:02 · iPad Oliver

  A withdrawn consent is asked again the next time its action runs.

Withdraw: 1-6   q) leave   ?   › 3
Withdraw "check whether a harness is logged in"?
  Asked again in [2/7] Harnesses, the next time its action runs. Nothing
  recorded with it changes.
Withdraw? [Enter]   k) keep it   ?   › ⏎
✓ 1 consent withdrawn; it is asked again the next time.
Withdraw: 1-5   q) leave   ?   ›
----

* One entry per remembered consent: the title of its kind (`common.consent.kind.<kind>`) and the kind; below it the project for a kind of a project (`inspect_checkout`, `run_checkout_scripts`, `model_cost`), for `run_checkout_scripts` the number of scripts it covers, when it was given, and where: `terminal`, or the label of the paired device that gave it in the web app. `?5` lists each script of the consent with its arguments and digest.
* A number opens `settings.withdraw` for that consent: where it will be asked again, `Enter` withdraws it (`settings.remove-consent`), `k` keeps it. Several numbers are asked in turn. Withdrawing is audited with the channel `cli`.
* A consent is never given here; it is given only where its action asks (xref:03-dialogues.adoc#consent[Consent]). With no remembered consent the verb prints `No consent is remembered.` and returns.

[#t-documents]
=== The Documents Mode (`config documents`, `settings.documents-mode`, `settings.record`)

[source,text]
----
pm › config documents
Documents · How should documents be taken into a plan?
  1) Copy            they stay where they are; the copy is not kept in step
  2) Move            they leave where they are
  3) Ask each time ← the default; Copy is preselected when asked

Keep as it is? [Enter]   other: 1-2   ?   › 1
  1) Copy ✎
Copy from now on? [Enter]   b) back   ?   › ⏎
✓ Documents are copied into a plan; the start no longer asks.
----

* The value is the machine's `sources.documents_mode`: `copy`, `move`, or `ask`, the default (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#change-documents[Documents]); answering _always this_ at a plan's start writes the same setting (xref:18-starting.adoc[Starting Work]). `settings.record` records and audits it.
* `--mode copy|move|ask` answers the choice. With _Move_ the machine's default, a move is still accepted only from this client and from a browser on the loopback listener; a device on the network copies.

[#t-credential]
=== A Token Rotated or Replaced (`config credentials --rotate|--replace`, `settings.credential`, `settings.store-credential`)

[source,text]
----
$ pm-operator config credentials --rotate github
Credentials · A new token for github
  entry       github, used by GitHub (gh)
  rotate      a new secret for this entry; its kind and the providers that
              use it stay
  now         fine-grained, expires in 9 days
  Stored in the macOS Keychain; it is never shown again and never reaches a
  model or a log.

Token (not shown while you type): ›
Store the new token? [Enter]   b) back   ?   › ⏎
✓ Token github stored; 2 tokens derived from the old one dropped
  ✓ Consent remembered: check the providers with their tokens
Providers · Checking the providers that use github
  GitHub (gh)                                                ✓ ready
    ✓  github.com reachable
    ✓  token authenticates as oliver-wolff (fine-grained, expires in 90 days)
    ✓  permissions: contents, pull requests, checks (read and write)
    ✓  gh 2.71 is logged in as the same account
✓ github verified. 1 plan that waited for it goes on: fix-relay
----

* `settings.credential` asks the secret with the echo off (xref:07-transcripts-steps-4-7.adoc#t-providers-credentials[A Missing Token]); it is the operator's own act and needs no consent. `--rotate` keeps the entry's kind and its other fields; `--replace` asks the kind first, from those the provider accepts (`1) fine-grained token ← 2) classic token`), and writes a new entry of that kind under the same key.
* `settings.store-credential` writes it into the recorded store and drops every token derived from the old secret. The check that follows is `providers.verify-consent` and `providers.verify` on the providers that use the token, as in the onboarding; a failed check leads to `providers.failed` (xref:07-transcripts-steps-4-7.adoc#t-providers-verify[Check]).
* A token that has expired holds every plan that needs it (link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#UC-CTL-4[UC-CTL-4]); the hold names this verb, and the plans go on once the new token verifies, which the last line says.
* `pm-operator credentials set|rotate` stay the plain verbs of the store, without the check.

$ pm-operator config providers --verify

  GitHub (gh)                                                ✓ ready
    last check  ✓ ready, 12 May, 10:24

    ✓  token authenticates as oliver-wolff (fine-grained, expires in 9 days)
    ✓  permissions: contents, pull requests, checks (read and write)
    ✓  gh 2.71 is logged in as the same account
  SonarCloud                                                 ✗ not ready
    last check  ✓ ready, 12 May, 10:24
    ✓  sonarcloud.io reachable
    ✗  token refused: 401 "Invalid token"
       → enter the token again

Enter the token again? [Enter]   l) check again   k) continue without SonarCloud   ?   › ⏎
Providers · SonarCloud needs a token
  …
Token (not shown while you type): ›
Store and check it? [Enter]   b) back   ?   › ⏎
  SonarCloud                                                 ✓ ready
    ✓  sonarcloud.io reachable
    ✓  token authenticates as oliver-wolff (user token, no expiry known)

* `--verify` asks `providers.verify-consent` (`verify_providers`) unless it is remembered, then runs `providers.verify` on the recorded providers; each shows the result and the time of its last check before the new one. With `--project <project_id>` it checks the project's providers.
* A token that expires within 14 days is named in the result line.

[source,text]
----
pm › web devices
Paired devices · The browsers that can act on this machine
    1) Firefox on mbp-oliver     paired 12 May   last used today 14:02   loopback
    2) Safari on iPad            paired 20 May   last used 3 d ago       network
    3) Chrome on build-box       paired 2 Jun    last used 5 weeks ago   loopback

  The console needs no pairing and is not listed. Network listener: on.

Act on a device: 1-3   o) revoke all others   n) turn the network listener off   q) leave   ?   › 2
  2) Safari on iPad
Rename or revoke? r) rename   x) revoke   b) back   ?   › r
Label [Safari on iPad] › iPad Oliver
✓ Renamed: iPad Oliver
pm › web devices revoke 3
Revoke Chrome on build-box? It is signed out at once; its open pages close with the reason.
Revoke? [Enter]   b) back   ?   › ⏎
✓ Revoked: Chrome on build-box
pm › web devices listener-off
✓ The network listener is off; the devices on the network stay paired and work
  again once it is on.
pm › web devices revoke 1
Revoke Firefox on mbp-oliver? It is the browser you are using on this machine:
  its pages close and show the pairing page; a new code pairs it again.
Revoke? [Enter]   b) back   ?   › ⏎
✓ Revoked: Firefox on mbp-oliver. web pair issues a new code.
pm › web devices revoke --others
Revoke all 1 paired device? The terminal client needs no pairing; every
  browser is signed out.
Revoke? [Enter]   b) back   ?   › ⏎
✓ Revoked 1 device. No browser is paired; web pair issues a new code.

----

* `web devices` is the terminal side of link:../shared/paired-devices.adoc[Paired Devices]: the list (`devices.list`) with label, when paired and last used, and from where (loopback or the network); the acts (`devices.act`) rename (`devices.rename`), revoke one (`devices.revoke`), revoke all others (`devices.revoke-others`), and turn the network listener off (`devices.listener-off`); a revocation voids the device's token at once and closes its open pages with the reason.
* The console acts from no device, so it marks none _this one_, and _revoke all others_ revokes every paired device; its confirmation says so. The browser the console's entry paired or last opened on this machine is named when it is revoked: its pages land on the pairing page. Every revocation asks, since it cannot be undone; `--yes` answers that confirmation in a script.
* _Turn the network listener off_ (`n`, or `listener-off`) is offered only while it is on and asks nothing: it closes the HTTPS listener of the network, leaves the loopback listener open, unlike `web disable`, and keeps the devices on the network paired. `web lan` turns it on again (xref:05-transcripts-entry.adoc#t-entry-other[Another Device]).
* The direct forms `web devices rename <device_id> <label>`, `web devices revoke <device_id>`, `web devices revoke --others`, and `web devices listener-off` act at once after the confirmation where there is one; the ids are the numbers of the list or the device ids the list shows with `?`.
