Status: `DRAFT`. This design is the specification the implementation of the terminal client follows (work package link:../../plans/cli-onboarding.adoc[`cli-onboarding`]); the use cases it serves stay in `plan-marshall-documentation`; what both clients share is link:../shared/texts-and-languages.adoc[Texts and Languages].

The logical design of `pm-operator` as the operator's second client beside the web app: a console that runs the onboarding, the later changes, and the answers to the questions plans ask; the commands and their arguments, how the terminal addresses the levels of configuration, how it renders a state of a workflow, the texts it shows in English and German, and a transcript of every state of the onboarding and of the entry `pm-operator`. The web side of the same states is link:../web-app/onboarding.adoc[Web App, Onboarding]; the two documents show the same states with the same texts, and where the terminal needs something the web app does not, this document says so. Names, versions, paths, models, and figures in the transcripts are examples.

The client holds no step order and no rule of its own: it renders the state the runtime reports, offers its links, and sends the link the operator picks (link:../web-app/README.adoc#principles[Web App, Principles]). Everything below is about how a state looks and is answered in a terminal, never about what the next state is.

[#open-points]
== Open Points

Each open point names who decides it.

* *The refusal of a link for a state that moved on* (package `api-contract`, with the machine scope). Two channels answer the same state; the second answer needs an error code of its own (`state_moved`, `409`) with the current state in its detail, so that a client re-renders instead of reporting an error. It is not in the closed list of link:../../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#api-error-codes[Local API Error Codes] yet.
* *Withdrawing a remembered consent* (with link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-consent[Consent Before Acting]). The machine settings list and withdraw remembered consents; this design names the terminal verb `pm-operator config consents` (a list with numbers to withdraw) and leaves its transcript to the package that specifies the consent store.
* *The model probe and the advice in one consent state* (with link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-5[UC-ONB-5]). `catalogue.consent` asks two consents in one state; the terminal answers them together or one by one (xref:06-transcripts-steps-1-3.adoc#t-models[3 Models (catalogue.consent, catalogue.scan, catalogue.advise, catalogue.select, catalogue.enrol, catalogue.record, catalogue.done)]). The web design shows the same as two choices of one screen.
* *Answering content questions in the console* (operator, with the use cases). The specification lets content questions be answered only in the web app or through the entry session (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[Operator Channel Isolation], item 1); the console adds the channel `cli`. The change is proposed in link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-two-channels[Operator Choices in the Web App and the Terminal] and written into the requirements once the use case is agreed.
* *`console.notify` and `console.full_screen`* (the package that implements the console). New keys of `machine-config.json` (xref:04-console.adoc#notifications[Notifications], xref:15-overview.adoc#full-screen-build[How It Is Built]); their schema entries are added with the implementation.
* *An idle lock of the console* (operator). A console left open on an unattended screen answers questions for anyone at the keyboard. A lock after an idle time (notices still shown, answering after unlocking) needs a way to unlock that a coding agent cannot produce; until one is decided there is no lock, which is the accepted risk of the operator channel.
* *A native-image spike for the line editor* (package `cli-test-infra`, before `cli-onboarding`). Measure the size and the time to the first prompt with and without JLine; check terminal resize and `Ctrl+C` during a running verb in the native binary (JLine's signal handling may need reflection metadata for `sun.misc.Signal` and `ProcessBuilder$RedirectPipeImpl`), the signal handler of the FFM provider under the macOS hardened runtime, and keep the native libraries of `jline-native` out of the binary. The transcript tests drive the console through a pseudo terminal; how they get one is decided there.
