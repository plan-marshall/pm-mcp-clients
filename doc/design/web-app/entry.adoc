[#pairing]
== The Pairing Page (`/pair`)

The URL the terminal client opens or shows carries the code in its fragment (`http://127.0.0.1:7420/pair#code=KXQB-MRTN`), which the browser never sends to a server.

* *With a code in the URL*: the page reads it, removes the fragment from the address bar, and redeems it at once: opening the URL the terminal gave is the operator's act. While it redeems it shows one line, `Pairing this browser …`; then the app opens (<<after-pairing>>) with the note `Paired as Firefox on mbp-oliver` and a link _Rename_ to the paired devices (link:../shared/paired-devices.adoc[Paired Devices]).
* *A browser that is paired already* does not redeem the code: it opens its start view, and the code expires unused.
* *Without a code* (another browser, a cleared storage, the code typed from the terminal), the page asks for it:

[source,text]
----
┌──────────────────────────────────────────────────────────────────────────────┐
│ plan-marshall                                                                │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  Pair this browser                                                           │
│  A paired browser can act on this machine as you do.                         │
│                                                                              │
│  Code   [ KXQB-MRTN ]                                                        │
│                                                                              │
│  Get a code in a terminal of the machine:                                    │
│    on this machine          pm-operator web open --pair          [ Copy ]    │
│    from another computer    pm-operator web pair                 [ Copy ]    │
│                                                                              │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                     [ Pair this browser ]    │
└──────────────────────────────────────────────────────────────────────────────┘
----

* The code is accepted with or without the dash and in any case; the button is enabled once eight characters are typed.
* *A code that does not work* (mistyped, used, expired, replaced by a newer one, or the runtime restarted) gets one answer, since the runtime does not say which: the line under the input `This code does not work. Get a new one in a terminal of the machine.` with the two commands. After too many failed tries the open code stops working even when typed right; the same answer covers it.
* *On the network listener* (HTTPS) the page also shows the certificate's fingerprint, to compare with the one the terminal printed (`Fingerprint SHA-256  4F:1A:9C:…:E2:07`, _Show in full_).

[#revoked]
== A Revoked Device

When the device is revoked, its open pages are told at once (the runtime ends its event streams with the last event `stream.closed`, reason `device_revoked` with the channel and device that revoked it and when, or `device_expired`); a page opened later gets the refusal on its first request. Either way the app deletes the stored device secret and shows the pairing page with the reason above it:

[source,text]
----
  This browser is no longer paired

  It was revoked from iPad (Safari) at 14:32.

  A paired browser can act on this machine as you do. To pair this one
  again, get a code in a terminal of the machine.

  Code   [           ]

    on this machine          pm-operator web open --pair          [ Copy ]
    from another computer    pm-operator web pair                 [ Copy ]

                                                    [ Pair this browser ]
----

The reason names what the runtime reported:

[cols="1,2",options="header"]
|===
|Reason |Line

|revoked from another device
|`It was revoked from iPad (Safari) at 14:32.`

|revoked in the terminal
|`It was revoked in the terminal at 14:32.`

|all other devices revoked
|`All other devices were revoked from Firefox on mbp-oliver at 14:32.`

|this device revoked from itself
|`You revoked this browser at 14:32.`

|idle expiry
|`It was not used for 30 days, so its pairing expired.`

|no reason known (the page was not open)
|`Its pairing is no longer accepted.`
|===

* Nothing typed in an open form survives the revocation: the page that was open is replaced, not covered.
* Revoking the device the operator acts from asks first (link:../shared/paired-devices.adoc[Paired Devices]) and then lands here with `You revoked this browser`.

[#listener-off]
== The Network Listener Turned Off

When the operator turns the network listener off (`devices.listener-off`, link:../shared/paired-devices.adoc#listener-off[Paired Devices]), a page open over the network loses its connection (`stream.closed` with the reason `listener_closed`). The device stays paired, so the app does not delete its secret: it shows one page with the reason and waits.

[source,text]
----
  This machine is not reachable over the network now

  Its network access was turned off at 14:32. This browser stays paired:
  it works again once the network access is on (pm-operator, web lan).
----

* *The device that turned it off*, when it is itself on the network, asked first (`devices.listener_off.confirm_title`, link:../shared/paired-devices.adoc#listener-off[Paired Devices]) and lands here as well, not on the pairing page: its pairing stays, and no listener it can reach would take a code.
* The page reconnects on its own when the listener is on again, and opens where the operator was. It cannot tell a listener turned off from a network that is down when the runtime said nothing; then it says `This machine is not reachable over the network.` with the same way back.

[#after-pairing]
== Where the App Opens

After pairing, and on every later visit, the app asks the runtime whether the machine is onboarded:

* *Not fully onboarded*: the app opens the onboarding (link:onboarding.adoc#frame[Onboarding]) at the state the server is in: `onboard.mode` for a first run (link:onboarding.adoc#start[Start]), else the state where it stopped, with the step bar showing the steps done. This is where the operator lands who chose _in the web app_ in the terminal's question (`entry.where-to-onboard`; link:../terminal-client/05-transcripts-entry.adoc#t-entry-first[Terminal Client, Not Fully Onboarded]); the terminal returns to its prompt with the setup badge, and either client continues the run. Every other route of the app leads to the onboarding until it is complete.
* *Onboarded*: the app opens where the operator left it, first in the explorer of the projects (link:README.adoc#structure[Structure and Navigation]).
* *The runtime is not reachable* (stopped, restarting): the app says so on a page of its own, `plan-marshall is not reachable on this machine. Start it in a terminal: pm-operator`, and reconnects on its own when it is back; nothing the operator had open is lost.
