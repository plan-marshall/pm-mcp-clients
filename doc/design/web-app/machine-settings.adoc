[#aspects]
== A Later Run of One Aspect

* *Change* runs the aspect's sub-workflow again as a later run (the link `reconfigure:<aspect>` of `settings.choose`, `onboard_run: reconfigure`): it opens in the frame of the onboarding (link:onboarding.adoc#frame[Onboarding, Frame]), the step bar showing only that aspect, the current values as the proposal. The screens are those of the first run, with the consents that are not remembered asked again; at its end, or when the operator leaves it (`stepped_out`, _Back to the settings_), the server returns to `settings.choose` and the app with it.
* A later run of the harnesses offers the new ones and removes the missing ones (<<harnesses>>).
* A later change of the credential store moves the tokens (link:onboarding-steps-4-7.adoc#store-move[Onboarding, A Later Change Moves the Tokens]).
* *Ask the steward…* is the later run of the roles opened directly at the steward's consent (`roles.consent`); after the automatic run, it is where the operator asks a model for the first time.
* A changed interface language is the language of every text from then on, as in the first run.
* *⑦ Plans* in a later run also shows the optional posture of a plan (`plan_defaults.posture`: minimal, standard, full), which the first run never asks: unset by default, so that a plan asks it in its start while no level sets it (link:onboarding-steps-4-7.adoc#plan-defaults[Onboarding, ⑦ Plans]).
* An aspect a project sets for itself is changed in that project's setup, never here; the line says only what the machine provides.

Terminal: `pm-operator config <aspect>` (link:../terminal-client/08-transcripts-later.adoc#t-later[Terminal Client, Later Changes]).

[#harnesses]
== The Harnesses Again

*Change* on ② runs the harnesses' sub-workflow as a later run (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-4[UC-ONB-4], variations): the scan runs again under its consent, and the icons' consent follows as in the first run (link:onboarding.adoc#harness[Onboarding, ② Harnesses]). The choice then starts from what is enrolled:

[source,text]
----
  Choose the harnesses to enrol

  Found on this machine:                                         default

  [x] CC  Claude Code   2.5.0   ~/.local/bin/claude          ✓ supported   (•)
                                was 2.4.1: checked and enrolled again
                                tokens complete
  [ ] CX  Codex         0.40.0  /opt/homebrew/bin/codex      ✓ new since the
                                                               last run    ( )
                                tokens not reported
  [ ] OC  OpenCode      —       /opt/homebrew/bin/opencode
                                missing: not found any more
      AG  Antigravity   —       not found

  ▸ Advanced: add a harness that is not listed

  [ Back to the settings ]   [ Look again ]
                                  [ Check 1 harness, Claude Code the default ]
----

* *The proposal is the current state*: every enrolled harness that is found is ticked, the default as recorded. A harness found that is not enrolled is offered, marked `new since the last run` and not ticked; ticking it adds it.
* *Missing*: an enrolled harness no longer found is shown with the path it was enrolled at, `missing: not found any more`, and unticked: it is offered for removal. Ticking it keeps it only once it is found again (*Look again*, or its path under _Advanced_).
* *Used by roles*: a harness that roles use cannot be removed, neither by unticking it nor as missing. Its row stays ticked and locked, with `used by 6 roles; reassign them first:` and the link _Reassign them_ that opens the later run of the roles (link:onboarding-steps-4-7.adoc#roles[Onboarding, ④ Roles]) filtered to them; the harness keeps its roles until then. Its default mark can still move.
* *Default*: any ticked harness can be made the default; the change is shown in the confirmation. The default itself cannot be removed, neither by unticking it nor as missing, before another ticked harness is made the default: its row stays ticked and locked with `the default; choose another default first` (`web.settings.harnesses.default_locked`).
* *Tokens*: what each harness and version reports of its usage, as in the first run (link:onboarding.adoc#harness-tokens[Onboarding, What a Harness Reports]); a new version is shown with what its profile and verification say for that version, so a change of what a harness reports is seen here.
* *Back to the settings* (`web.settings.back`) leaves the later run without a change.
* *A changed program* (a new version or digest at the same path) is checked and enrolled again with the others; the line says what it was.
* The check (link:onboarding.adoc#harness-probe[Onboarding, Check]) runs for every ticked harness, the consent `probe_harness_login` asked unless remembered. The confirmation (link:onboarding.adoc#harness-confirm[Onboarding, Confirm]) lists what changes: each harness to enrol with its path, version and digest, the new ones marked `new since the last run`, each one to remove as `Remove OpenCode: its enrolment is deleted`, and the default in the button; with nothing changed its button reads *Keep as it is*.
* A harness added or removed changes what ③ Models can allow: the allowed models of a removed harness are removed with it, and a new one has none until ③ is run again, which the result says (`Codex has no model allowed yet: run ③ Models.`).

The texts are those of the onboarding (link:onboarding-texts.adoc#texts-shared[Onboarding, Texts]).

Terminal: `pm-operator config harnesses` (link:../terminal-client/08-transcripts-later.adoc#t-later[Terminal Client, Later Changes]).

[#providers]
== Providers Verified Again

Every provider shows the result and the time of its last verification, from the onboarding or from a later check. *Check* runs the verification of that provider (`providers.verify`, link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/02-credentials-and-operator.adoc#provider-verification[Provider Verification], _Again later_), *Check all* of every provider the machine records; the consent `verify_providers` (`providers.verify-consent`, link:onboarding-steps-4-7.adoc#providers-verify-consent[Onboarding, Consent]) comes first unless it is remembered. The lines appear in place, as in the onboarding:

[source,text]
----
  Providers                                                     [ Check all ]
    GitHub (gh)    ✓ ready        checked just now                [ Check ]
      ✓  github.com reachable
      ✓  token authenticates as oliver-wolff (fine-grained, expires in 9 days)
      ✓  permissions: contents, pull requests, checks (read and write)
      ✓  gh 2.71 is logged in as the same account
----

* A ✗ shows the provider's answer and the fix with the links of `providers.failed`: _Enter the token again_, _Check again_, _Continue without GitHub_ (recorded as not available after its confirmation). The result is kept with the time, whatever it is.
* A provider recorded as not available shows when and why; *Check* verifies it again, and a pass offers to record it as available (`providers.record`).
* An expiry within 14 days is shown as a warning on the line, not only in the detail.
* Checks that need a repository (permissions on it, check runs) stay in the project's setup.

Terminal: `pm-operator config providers --verify` (link:../terminal-client/08-transcripts-later.adoc#t-providers-verify[Terminal Client, transcript]).

[#consents]
== Remembered Consents

The list of link:../shared/consents.adoc#remembered[Consents, The Remembered Consents], the same in both clients: every consent the operator remembered (_yes, and don't ask again_), from either client, one line each: the action by its kind's title (`common.consent.kind.<kind>`, link:../shared/consents.adoc#kinds[Consents, The Kinds]), when it was given, where (`terminal`, or the label of the paired device), and for a kind of a project its project and, for `run_checkout_scripts`, how many scripts it covers.

* *Withdraw* opens `settings.withdraw` in place: `Withdraw "check whether a harness is logged in"?` with where it will be asked again (`common.consent.withdraw.*`, link:../shared/consents.adoc#remembered[Consents]) and *Keep it* or *Withdraw*. Withdrawing (`settings.remove-consent`) removes it from `consents.json`; the line is replaced by `Withdrawn: you will be asked again next time.` Nothing recorded with it changes. Both remembering and withdrawing are audited.
* With none remembered, the section says `No consent is remembered: you are asked every time.`

Terminal: `pm-operator config consents` (link:../terminal-client/08-transcripts-later.adoc#t-consents[Terminal Client, transcript]).

[#documents]
== The Documents Mode (`settings.documents-mode`, `settings.record`)

How documents are taken into a plan at its start: the machine's `sources.documents_mode` (link:../../../../plan-marshall-documentation/doc/specification/state-catalogue/09-bootstrap-and-lessons.adoc#documents-source[State Catalogue, Documents as a Source]). *Change* opens the choice in place:

[source,text]
----
  How should documents be taken into a plan?

  ( ) Copy            they stay where they are; the copy is not kept in step
  ( ) Move            they leave where they are
  (•) Ask each time   the default; Copy is preselected when asked

  [ Back to the settings ]                               [ Keep as it is ]
----

* The current value is preselected; with another chosen the button names it (`Copy from now on`), and `settings.record` records and audits it. _Always_ at a plan's start writes the same setting (link:../shared/starting-work.adoc[Starting Work]); this is where it is set back to _Ask each time_.
* On a device of the network _Move_ is disabled with its reason, as at a plan's start (`start.documents.loopback_only`): a move deletes the operator's files.

Terminal: `pm-operator config documents` (link:../terminal-client/08-transcripts-later.adoc#t-documents[Terminal Client, transcript]).

[#cleanup]
== The Cleanup's Durations (`settings.cleanup-durations`, `settings.record`)

How long ended work is kept before the cleanup offers it, the machine's `cleanup.*` (link:../shared/cleanup.adoc#durations[Cleanup, How Long Work Is Kept]; link:../../../../plan-marshall-documentation/doc/specification/timeouts/03-retention-host-config.adoc#cleanup[Timeouts & Budgets, One Cleanup]); the line sums them up (`system.cleanup.durations.summary`), and *Change* opens them in place:

[source,text]
----
  How long should ended work be kept?

  Archived plans        [ 30 ] days   ( ) never
  Archived epics        [ 30 ] days   ( ) never
  Logs of ended work    [ 30 ] days   ( ) never
  Read reports          [ 30 ] days   ( ) never
  Unenrolled projects   [ 30 ] days   ( ) never
  Ask me again after    [  3 ] days

  An item is offered when its end is older than its duration. Nothing is deleted
  without you.
  1 project has its own: pm-mcp-core (plans 90 days)

  [ Back to the settings ]                               [ Keep as it is ]
----

* The machine's values, recorded and audited by `settings.record`; with a value changed the button reads _Keep these durations_. A changed duration deletes nothing; it applies at the next check.
* *A project's own value* is listed by its project and changed in that project's setup, under ④ Own settings (link:../shared/project-onboarding.adoc#steps[Project Onboarding, Steps]); never here.
* The cleanup view's _Durations_ opens the same.

Terminal: `pm-operator config cleanup` (link:../terminal-client/26-cleanup.adoc#t-durations[Terminal Client, transcript]).

[#conflict]
== Changed Meanwhile

A value changed in another client (the terminal, another device) after this page showed it is not overwritten: the change made here is refused with `conflict`, nothing of it applied, and the line shows the current value beside the operator's choice with _Keep the current value_ and _Apply yours again_ (`common.conflict.*`). This holds for every aspect, the documents mode, and the cleanup's durations (link:../shared/work-actions.adoc#conflict[Changed in Two Clients at Once]; link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[Concurrent Changes of a Setting]).

[#credentials]
== A Token Rotated or Replaced (`settings.credential`, `settings.store-credential`, `settings.verify-providers`)

Every token the machine keeps is listed with its provider, its kind, and its expiry from the last check; one that has expired or expires within 14 days is marked `⚠`, an expired one with the plans it holds (`⚠ expired: holds 1 plan`). *Rotate* gives the entry a new secret, its kind and other fields kept; *Replace* asks the kind first, from those the provider accepts, and writes a new entry of that kind under the same key:

[source,text]
----
  A new token for github

    entry       github, used by GitHub (gh)
    rotate      a new secret for this entry; its kind and the providers
                that use it stay
    now         fine-grained, expires in 9 days

  Token   [ •••••••••••••••••••••••••••••• ]
          Stored in the macOS Keychain; it is never shown again and never
          reaches a model or a log.

  [ Back to the settings ]                         [ Store the new token ]
----

* Entering the token is the operator's own act and needs no consent. `settings.store-credential` writes it into the recorded store and drops every token derived from the old secret (`Token github stored; 2 tokens derived from the old one dropped`); while the recorded store is not available it is refused (`credential_store_unavailable`) with the cause and the fix, and nothing is written.
* Then the providers that use it are checked as in the onboarding (`settings.verify-providers` calls the providers' sub-workflow at its verification): `providers.verify-consent` unless remembered, `providers.verify`, and on a ✗ `providers.failed` with its links (link:onboarding-steps-4-7.adoc#providers-verify[Onboarding, Check]). Afterwards the page is the settings again. A plan the old token held goes on only once the new token verifies, which one line says (`1 plan that waited for it goes on: fix-relay`, link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#UC-CTL-4[UC-CTL-4]); on `providers.failed` the hold stays.
* On the LAN listener the input is replaced by the command to run in a terminal of the machine (`onboard.settings.credential.lan`: `pm-operator credentials rotate github`), as for a missing token (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-credentials[Credentials in the Web App]).
* A plan held by an expired token names this section as the act that resolves the hold.

Terminal: `pm-operator credentials rotate|set <credential_key>` (link:../terminal-client/08-transcripts-later.adoc#t-credential[Terminal Client, transcript]).

[#devices]
== Paired Devices

The count of paired devices and whether the network listener is on; *Manage* opens the list of the paired devices, to rename one, revoke one or all others, and turn the network listener off (link:../shared/paired-devices.adoc[Paired Devices]); from a browser on the network turning it off asks first, since that browser loses its access with it (`devices.listener_off.confirm_title`, `devices.listener_off.confirm_explain`, link:../shared/paired-devices.adoc#listener-off[Paired Devices, The Network Listener Turned Off]), and the browser then shows link:entry.adoc#listener-off[Entry, The Network Listener Turned Off]. The list is no state of the settings: it reads and acts through the devices' own endpoints (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#devices[CLI, Coordination & Security, Devices in Both Clients]); leaving it returns to `settings.choose`, unchanged.

Terminal: `pm-operator web devices` (link:../terminal-client/08-transcripts-later.adoc#t-devices[Terminal Client, transcript]).

[#texts]

The lines of the aspects use the summaries of the onboarding's result (link:../terminal-client/07-transcripts-steps-4-7.adoc#t-completed[Done]) and the step names `onboard.step.*`; the check lines and the links of a provider are those of `providers.verify` and `providers.failed` (link:../terminal-client/12-texts-steps-6-7.adoc#texts-onboard-providers[Texts, Providers]); a remembered consent is named by its kind's title `common.consent.kind.<kind>` (link:../shared/consents.adoc#texts[Consents, Texts]).
