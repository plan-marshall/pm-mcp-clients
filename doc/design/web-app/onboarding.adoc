[#frame]
== Frame

The onboarding fills the whole app until it is complete; the rest of the app is reached once `onboard.completed` is reached. A later run opens from the machine settings in the same frame.

[source,text]
----
┌──────────────────────────────────────────────────────────────────────────────┐
│ plan-marshall                                   Machine: mbp-oliver   ⚙  ?   │
├──────────────────────────────────────────────────────────────────────────────┤
│  ① Language ─ ② Harness ─ ③ Models ─ ④ Roles ─ ⑤ Credentials ─ ⑥ Providers   │
│  ─ ⑦ Plans ─ ✓ Done                                                          │
│  ━━━━━━━━━━━                                                                 │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  <title of the state>                                                        │
│  <one or two sentences: what this step is for>                               │
│                                                                              │
│  <content of the state>                                                      │
│                                                                              │
├──────────────────────────────────────────────────────────────────────────────┤
│  <secondary links>                                   [ <primary link> ]      │
└──────────────────────────────────────────────────────────────────────────────┘
----

* *Step bar*: the seven sub-workflows of `onboard.*`; done steps are ticked and can be opened to look at, never re-run from the bar (a re-run is a later change from the settings). The bar shows where the process is; it does not navigate ahead.
* *One route*: the onboarding is one route of the app (`/onboarding`) that renders whichever state the server reports; the app has no route per state, so it cannot show a state the server is not in. A done step opened from the step bar is shown read-only beside the current one.
* *Footer*: the links of the state; the primary one on the right. A state the server is working in (`[S]`) shows progress instead and no link.
* *Terminal*: the console `pm-operator` prints the step line `[3/7] Models` above each state, the content below it, and the links as a prompt line; `?` shows the explanation the web app shows under the title (link:../terminal-client/03-dialogues.adoc#state-frame[Terminal Client, The Frame of a State]).
* *Model at work* (`[M]` states): the content shows that a model task runs, on which harness and role, the time so far, and the expected cost; when it fails or the operator leaves it, the screen continues as the use case's variation says (without a recommendation).

[#start]
== Start (`onboard.entry`, `onboard.mode`)

[source,text]
----
  Set up this machine for plan-marshall

  Seven steps. Nothing on this machine is looked at, run, or changed until
  you say so in that step.

    ① Language    the language of this app and of the models' texts
    ② Harness     choose the coding agent the server works with first
    ③ Models      choose the agents and models other plans may use
    ④ Roles       give every role an agent and a model
    ⑤ Credentials where this machine keeps its tokens
    ⑥ Providers   the git hosts, CI and analysis services this machine uses
    ⑦ Plans       how plans run unless a project says otherwise

  You can stop at any point; the next visit continues where you stopped.

  [ Decide everything for me… ]                       [ Begin with ① ]
----

* *Decide everything for me…* is the automatic run (<<auto>>); it opens its consent first.

[#consent]
== Consent

One pattern for every `<step>.consent` state. Its content comes from the consent kind (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-consent[Consent Before Acting]); the screen adds nothing the server did not state.

[source,text]
----
  Look for harnesses on this machine?

  The server would
    • look for these programs:  claude, opencode, codex, agy
    • in:  the directories of your PATH,
           ~/.local/bin, /Applications, /opt/homebrew/bin
    • run for each one found:   <program> --version

  It would not
    • read any other file, or start a harness session
    • send anything over the network

  Cost: none.

  ( ) Ask me again next time
  ( ) Don't ask again for this action      (you can withdraw it in ⚙ Settings)

  [ Not now ]                                       [ Look for harnesses ]
----

Terminal: link:../terminal-client/06-transcripts-steps-1-3.adoc#t-harness-consent[Terminal Client, transcript].

* *Not now* (link `no`): the screen stays and shows "Nothing was done." under the title, with the same two buttons. The step bar does not move.
* The remember choice is a choice inside the screen, not a third button, so the primary button stays one action: `yes` or `yes_remember` by the choice.
* A consent with a model cost names the role, the harness, and the expected cost from earlier runs, or "not known yet" for the first run.

== ② Harness

[#harness-choose]
=== Choose (`harness.choose`)

[source,text]
----
  Choose the harness to start with

  Found on this machine:

  (•) Claude Code   2.4.1   /Users/oliver/.local/bin/claude   ✓ supported
  ( ) OpenCode      1.9.0   /opt/homebrew/bin/opencode        ✓ supported
      Codex         0.31.2  /opt/homebrew/bin/codex           ✗ cannot run workers
      Antigravity   —       not found

  The first harness also runs the advice in the next steps. You can add
  the others in ③ Models.

  ▸ Advanced: add a harness that is not listed

  [ Look again ]                              [ Check Claude Code ]
----

* Each harness is shown with its icon (link:harness-icons.adoc#icons[Harness Icons]), or with its monogram where no icon is available.
* Harnesses that cannot run workers are listed, greyed, with the reason; harnesses not found are listed so the operator sees what was looked for.
* *No harness found* (`harness.none`): the list is replaced by what was looked for, *Add a harness that is not listed* as the primary action, and a short install hint per harness with a link to its own installation page, and *Look again*.

=== Add a Harness That Is Not Listed (`harness.add`, `harness.verify-profile`)

[source,text]
----
  Add a harness

  Executable   [ /usr/local/bin/aider                         ] [ Browse ]
  Name         [ Aider              ]   id [ aider ]
  Start from   [ OpenCode ▾ ]   the closest known harness; its settings
                                are filled in below

  ▾ How it is called headless                      (from OpenCode, edit)
    Arguments      [ --message {prompt} --yes --no-pretty            ]
    MCP config     [ --mcp-config {mcp_config_file}                  ]
    Output         ( ) text  (•) JSON lines        Usage  [ field: usage ]
    Version probe  [ --version ]
  ▸ Environment, tools, commands (4 more)

  [ Cancel ]                                       [ Verify this harness ]
----

*Verify this harness* leads through its consent screen (the stages, their token cost) to the verification:

[source,text]
----
  Verifying Aider

    ✓  identity      aider 0.86.1
    ✓  detection
    ✓  launch        a headless call answered in 4.1 s
    ✗  isolation     the MCP configuration was not used: the harness
                     read ~/.aider.conf.yml instead
                     → set "Arguments" to include --no-config        [ Edit ]
    ·  classes, limits, paths, faults   not run

  [ Cancel ]                                   [ Edit the settings ]
----

* A ✗ links to the field it concerns; the stages after it are listed as not run. A pass of every stage leads to the confirmation of the profile and then to <<harness-confirm>>.
* A known harness found nowhere is added the same way with its path only; the settings are its shipped ones and are not shown.

  Choose the harnesses and models other plans may use

  ┌ Recommendation ──────────────────────────────────── by steward ┐

  │ model for screening; allow the three models below.  [ Why? ]   │

[#roles]
== ④ Roles (`roles.review`)

The step opens with the default assignment applied, as an overview; accepting it is one click.

[source,text]
----
  Give every role a harness and a model

  The default assignment is applied to all 31 roles.

    Claude Code · opus-5.5      7 roles   planning and decisions   ⓘ
    Claude Code · sonnet-5.5   16 roles   execution and review     ⓘ
    OpenCode · qwen-coder       6 roles   screening and checks     ⓘ
    ⚠ not assignable            2 roles   no fast model allowed    → assign

  [ Adjust roles ]   [ Ask the steward to refine… ]     [ Use the defaults ]
----

* Each line is one harness and model with its roles, grouped by what they do; ⓘ lists the roles and the advisory of the group. A ⚠ line opens the table filtered to its roles.
* *Use the defaults* is disabled while a ⚠ line remains; it saves the assignment.
* *Ask the steward to refine…* goes through its consent screen; the proposed departures then appear in the table, marked, each to accept or reject.
* *Adjust roles* opens the table:

[source,text]
----
  Give every role a harness and a model                 31 roles · 2 to look at

  Group: [ by phase ▾ ]   Filter: [            ]   [ Assign to selection… ]

  ▾ Planning
    [ ] refine      writer     Claude Code  sonnet-5.5  medium   default        ⓘ
    [ ] outline     writer     Claude Code  opus-5.5    high     default        ⓘ
  ▾ Review
    [ ] qgate       read_only  OpenCode     qwen-coder  —        ✎ steward      ⓘ
    [ ] screener    zero_tool  —            —           —        ⚠ no model     ⓘ
                                                                   of tier fast
  ▸ Execution (8)   ▸ Finalize (6)   ▸ Decisions (5)

  [ Back ]                                              [ Save 31 roles ]
----

The advisory of a role (ⓘ, opened in place below its row):

[source,text]
----
    outline     writer     Claude Code  opus-5.5    high     default        ⓘ
    ┌───────────────────────────────────────────────────────────────────────┐
    │ What it does   Turns the refined request into deliverables and the    │
    │                plan's lane; reads the whole affected codebase.        │
    │ What it needs  Deep reasoning over a large context; few tool calls.   │
    │ Why frontier   A weak outline costs more later than the model costs   │
    │                here: every later phase builds on it.                  │
    │ If cheaper     More loop-backs from the Q-Gate; standard tier passed  │
    │                71 % of the qualification items (frontier 92 %).       │
    │ Steward        no departure                                           │
    │                                                 [ Reset to default ]  │
    └───────────────────────────────────────────────────────────────────────┘
----

* Each row: role, class, harness, model, effort, and where the value comes from: `default`, `✎ steward` (a proposed departure, its reason in the advisory under _Steward_), `✎ changed` (the operator's), or `⚠` with the validation reason of `roles.validate` or a default that cannot be met here.
* The advisory always shows the default's what and why, also when the value departs from it; *Reset to default* per row and for all.
* *Assign to selection…* sets harness, model, and effort for the selected rows in one go; the advisories of the rows stay.
* *Save* is disabled while a row is marked ⚠; the header counts them.

[#credential-store]
== ⑤ Credentials (`store.choose`)

[source,text]
----
  Where should this machine keep its tokens?

  (•) macOS Keychain                                         ★ recommended
      Only plan-marshall's runtime reads them without asking you; any
      other program that tries makes macOS ask first.

  ( ) Files in ~/.plan-marshall-mcp/credentials/
      Readable by every program you run (mode 0600). Works everywhere,
      also without a desktop session.

  The choice holds until you change it in ⚙ Settings; a change moves the
  tokens, it never leaves a copy behind.

  [ Back ]                                     [ Use the macOS Keychain ]
----

* On Linux the first option is the Secret Service, with its own text: every program of the user can read it while it is unlocked. When it is not available now (locked, or no session bus over SSH), the option is shown greyed with the reason and how to fix it, and *Check again*.
* The primary button names the store it will use.

          Stored in the machine's credential store; it is never shown

[#providers-verify]
=== Check (`providers.verify`, `providers.failed`)

[source,text]
----
  Checking the providers

  GitHub                                                       ✓ ready
    ✓  github.com reachable
    ✓  token authenticates as oliver-wolff (fine-grained, expires in 41 days)
    ✓  permissions: contents, pull requests, checks (read and write)
    ✓  gh 2.71 is logged in as the same account

  SonarCloud                                                   ✗ not ready
    ✓  sonarcloud.io reachable
    ✗  token refused: 401 "Invalid token"
       → enter the token again                         [ Enter token ]

  [ Continue without SonarCloud ]   [ Check again ]
----

* Every provider and every check has its own line; a provider is ✓ only when all its checks are. A ✗ shows the provider's answer and the fix.

[#auto]
== Automatic Run (`auto.consent`, `auto.result`)

The consent lists everything the run does, in the form of <<consent>>, in one list; the run itself shows the step bar moving and each check as it reports. At the end:

[source,text]
----
  Everything is decided

  ① Language     Deutsch, models too           from your system      [ Change ]
  ② Harness      Claude Code 2.4.1  ✓          the first supported one [ Change ]
  ③ Models       3 models on 2 harnesses  ✓    all found              [ Change ]
  ④ Roles        default assignment, 31 roles  the default            [ Change ]
  ⑤ Credentials  macOS Keychain  ✓             available here         [ Change ]
  ⑥ Providers    GitHub (gh)  ✓                gh logged in           [ Change ]
                 SonarCloud  —                  no token: skipped     [ Add ]
  ⑦ Plans        Pull Request · Test first · key points   the default [ Change ]

  No model was asked; ask the steward to refine the roles in ⚙ Settings.

                                                 [ Finish ]
----
