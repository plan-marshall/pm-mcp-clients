[#frame]
== Frame

The onboarding fills the whole app until it is complete; the rest of the app is reached once `onboard.completed` is reached. A later run of one aspect opens from the machine settings (link:machine-settings.adoc[Machine Settings]) in the same frame. How the web app gets here after pairing is link:entry.adoc#after-pairing[Entry, Where the App Opens].

[source,text]
----
┌──────────────────────────────────────────────────────────────────────────────┐
│ plan-marshall                                   Machine: mbp-oliver   ⚙  ?   │
├──────────────────────────────────────────────────────────────────────────────┤
│  ① Language ─ ② Harness ─ ③ Models ─ ④ Roles ─ ⑤ Credentials ─ ⑥ Providers   │
│  ─ ⑦ Plans ─ ✓ Done                                                          │
│  ━━━━━━━━━━━                                                                 │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  <title of the state>                                                        │
│  <one or two sentences: what this step is for>                               │
│                                                                              │
│  <content of the state>                                                      │
│                                                                              │
├──────────────────────────────────────────────────────────────────────────────┤
│  <secondary links>                                   [ <primary link> ]      │
└──────────────────────────────────────────────────────────────────────────────┘
----

* *Step bar*: the seven sub-workflows of `onboard.*`; done steps are ticked and can be opened to look at, never re-run from the bar (a re-run is a later change from the settings). The bar shows where the process is; it does not navigate ahead.
* *One route*: the onboarding is one route of the app (`/onboarding`) that renders whichever state the server reports; the app has no route per state, so it cannot show a state the server is not in. A done step opened from the step bar is shown read-only beside the current one.
* *Footer*: the links of the state; the primary one on the right. A state the server is working in (`[S]`) shows progress instead and no link.
* *Answered elsewhere*: a state answered in the terminal or on another device while it is open here is replaced by the state the server moved to, with the line `Answered elsewhere: <answer>` (`common.error.state_moved`).
* *Terminal*: the console `pm-operator` prints the step line `[3/7] Models` above each state, the content below it, and the links as a prompt line; `?` shows the explanation the web app shows under the title (link:../terminal-client/03-dialogues.adoc#state-frame[Terminal Client, The Frame of a State]).

[#model-at-work]
=== Model at Work (`[M]` states)

[source,text]
----
  Choose the harnesses and models other plans may use

  ⠴  steward is working on Claude Code · opus-5.5          0:18   about 0.10 USD

     You can leave this page; the work continues, and the next visit shows
     its result.

  [ Continue without the advice ]
----

* The content names the role, the harness and the model, the time so far, and the expected cost (`common.model.working`).
* *Continue without the advice* leaves the model task; the state continues as the use case's variation says, without the result. A task that fails does the same and shows one line with its reason (`common.model.no_result`): `The steward gave no proposal: <reason>.`

[#start]
== Start (`onboard.entry`, `onboard.mode`)

[source,text]
----
  Set up this machine for plan-marshall

  Seven steps. Nothing on this machine is looked at, run, or changed until
  you say so in that step.

    ① Language    the language of plan-marshall and of the models' texts
    ② Harness     the coding agent the server works with first
    ③ Models      the agents and models other plans may use
    ④ Roles       an agent and a model for every role
    ⑤ Credentials where this machine keeps its tokens
    ⑥ Providers   the git hosts, CI and analysis services this machine uses
    ⑦ Plans       how plans run unless a project says otherwise

  You can stop at any point; the next visit, here or in pm-operator,
  continues where you stopped.

  [ Decide everything for me… ]                      [ Begin with step 1 ]
----

* *Decide everything for me…* is the automatic run (xref:onboarding-steps-4-7.adoc#auto[auto]); it opens its consent first.

[#consent]
== Consent

One pattern for every `<step>.consent` state. Its content comes from the consent kind (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-consent[Consent Before Acting]); the screen adds nothing the server did not state. Its fields are those of the terminal (`looks for`, `in`, `runs`, `never`, `cost`), each shown only when the consent kind states it.

[source,text]
----
  Look for harnesses on this machine?

    looks for   claude, opencode, codex, agy
    in          your PATH, ~/.local/bin, /Applications, /opt/homebrew/bin
    runs        <program> --version on each one found
    never       reads other files, starts a session, uses the network
    cost        none

    (•) yes
    ( ) yes, and don't ask again       you can withdraw it in the settings

  [ Not now ]                                       [ Look for harnesses ]
----

Terminal: link:../terminal-client/06-transcripts-steps-1-3.adoc#t-harness-consent[Terminal Client, transcript].

* *Not now* (link `no`): the screen stays and shows "Nothing was done." under the title, with the same choices. The step bar does not move.
* The remember choice is a choice inside the screen, not a third button, so the primary button stays one action: `yes` or `yes_remember` by the choice; `yes` is preselected. The primary button is the consent's action ("Look for harnesses").
* A consent that is never remembered (`harness.add-consent`, `auto.consent`) has no choice; the line `This consent is for this run only.` stands in its place.
* A consent with a model cost names the role, the harness, and the expected cost from earlier runs, or "not known yet: first run" for the first run.
* A remembered consent passes its state without a screen; the step shows one line `Consent remembered: <action>` above the result.

[#language]
== ① Language (`language.choose`)

[source,text]
----
  Choose your languages

  plan-marshall and pm-operator   ( ) English  (•) Deutsch
                                  from your system (de_DE)

  What models write and read      (•) same as above
                                  ( ) English
                                  ( ) Deutsch

  Words like Pull Request, Commit, Merge and Request stay as they are.
                                                                [ Why? ]

                                                 [ Use Deutsch for both ]
----

* The screen switches to the chosen interface language at once, before the button is pressed, so the operator sees what it will look like (the sketch is in English to be read here).
* *Why?* shows `onboard.language.choose.why` in place: models do not work equally well in every language, and _same as above_ follows a later change.
* With two different languages the button reads `Use Deutsch here, English for models`.

[#harness]
== ② Harness

The consent `harness.consent` comes first, as in <<consent>>; with _yes_ the scan runs (`Looking for harnesses … 2 of 4 programs`).

[#harness-choose]
=== Choose (`harness.choose`)

[source,text]
----
  Choose the harness to start with

  Found on this machine:

  (•) CC  Claude Code   2.4.1   /Users/oliver/.local/bin/claude   ✓ supported
  ( ) OC  OpenCode      1.9.0   /opt/homebrew/bin/opencode        ✓ supported
      CX  Codex         0.31.2  /opt/homebrew/bin/codex           ✗ cannot run workers
      AG  Antigravity   —       not found

  The first harness also runs the advice in the next steps. You can add
  the others in step 3, Models.

  Icons: initials for now.                     [ Fetch the makers' icons… ]

  ▸ Advanced: add a harness that is not listed

  [ Look again ]                                     [ Check Claude Code ]
----

* Each harness is shown with its icon (link:harness-icons.adoc#icons[Harness Icons]), or with its monogram where no icon is available.
* Harnesses that cannot run workers are listed, greyed, with the reason; harnesses not found are listed so the operator sees what was looked for.
* *Check Claude Code* leads to the login probe's consent (<<harness-probe>>).
* *Fetch the makers' icons…* is shown only when a found harness's profile names a `source` icon; it opens the consent of kind `fetch_icons` (<<harness-icons-consent>>). It is no step of the onboarding: saying no changes nothing but the icons.

[#harness-icons-consent]
=== Icons (consent `fetch_icons`)

[source,text]
----
  Fetch the icons of the found harnesses?

    runs        the runtime downloads once: the icon of Claude Code from
                anthropic.com, the icon of OpenCode from opencode.ai
    in          ~/.plan-marshall-mcp/icons/, served by the runtime itself
    never       lets your browser load anything from these sites; uses an
                icon as the mark of plan-marshall
    cost        none

    (•) yes
    ( ) yes, and don't ask again       you can withdraw it in the settings

  [ Not now ]                                            [ Fetch 2 icons ]
----

* The runtime fetches the files, never the browser (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-harness-icons[Harness Icons]); each fetched icon replaces its monogram where it was shown. A fetch that fails keeps the monogram and says so in one line with the cause.
* UC-ONB-4 names no state for this consent; the workflow needs one beside `harness.choose` (proposed: `harness.icons-consent`, returning to `harness.choose`).

[#harness-none]
=== None Found (`harness.none`)

[source,text]
----
  No harness found

  Looked for claude, opencode, codex, agy in your PATH, ~/.local/bin,
  /Applications, /opt/homebrew/bin.

  Install one, then look again:
    CC  Claude Code   docs.anthropic.com/en/docs/claude-code/setup   ↗
    OC  OpenCode      opencode.ai/docs/                              ↗

  Or add a harness that is not listed, by its program.

  [ Look again ]                     [ Add a harness that is not listed ]
----

* The install pages open in a new tab; nothing is installed from the app.
* *Look again* runs `harness.scan` again under the consent already given.

[#harness-add]
=== Add a Harness That Is Not Listed (`harness.add`, `harness.add-consent`, `harness.verify-profile`)

[source,text]
----
  Add a harness

  Executable   [ /usr/local/bin/aider                                      ]
               the full path on this machine; the browser's file dialog
               cannot name it
  Name         [ Aider              ]   Id [ aider ]
  Start from   [ OpenCode ▾ ]   the closest known harness; its settings are
                                filled in
  ▾ How it is called headless (from OpenCode):
    Arguments      [ --message {prompt} --yes --no-pretty            ]
    MCP config     [ --mcp-config {mcp_config_file}                  ]
    Output         ( ) text  (•) JSON lines        Usage  [ field: usage ]
    Version probe  [ --version ]
  ▸ and 4 more: environment, tools, commands, limits

  [ Back ]                                         [ Verify this harness ]
----

*Verify this harness* leads to its consent (`harness.add-consent`), which has no remember choice: running an unknown program is asked every time.

[source,text]
----
  Run Aider to verify these settings?

    runs        /usr/local/bin/aider with the settings above, once per stage:
                identity, detection, launch, isolation, classes, limits,
                paths, faults
    never       touches your repositories; it runs in a temporary directory
    cost        about 12 short headless calls; tokens of your Aider account

  This consent is for this run only.

  [ Not now ]                                         [ Verify this harness ]
----

Then the verification (`harness.verify-profile`), one line per stage:

[source,text]
----
  Verifying Aider

    ✓  identity      aider 0.86.1
    ✓  detection
    ✓  launch        a headless call answered in 4.1 s
    ✗  isolation     the MCP configuration was not used: the harness
                     read ~/.aider.conf.yml instead
                     → change "Arguments": add --no-config
    ·  classes, limits, paths, faults   not run

  [ Back ]                                         [ Edit the settings ]
----

* A ✗ names the field of the draft it concerns; its fix is a link to that field in `harness.add`. The stages after it are listed as not run.
* A known harness found nowhere is added the same way with its path only; the settings are its shipped ones and are not shown, and no verification runs.

[#harness-add-confirm]
=== Install the Profile (`harness.add-confirm`, `harness.install-profile`)

A pass of every stage leads to the profile to be installed:

[source,text]
----
  Install the profile of Aider

  The verified profile is installed for this machine:

    Id        aider
    Profile   ~/.plan-marshall-mcp/profiles/aider.json
    Workers   can run workers

  [ Back ]                                                 [ Install it ]
----

* `Install it` writes the profile into the machine profile set and shows `Profile of Aider installed`; the harness then goes on as a found one: the login probe's consent and the check (<<harness-probe>>), then <<harness-confirm>>.
* A profile that verification found unable to run workers reads `cannot run workers`; it is installed, but cannot be the first harness, and the screen goes back to `harness.choose`.

[#harness-probe]
=== Check (`harness.probe-consent`, `harness.probe`, `harness.blocked`)

The chosen harness's login probe has its consent first (consent kind `probe_harness_login`):

[source,text]
----
  Check whether Claude Code is logged in?

    runs        claude auth status
    never       starts a session, sends a prompt
    cost        none

    (•) yes
    ( ) yes, and don't ask again       you can withdraw it in the settings

  [ Not now ]                                        [ Check Claude Code ]
----

* A harness whose profile has no login probe is checked by one minimal headless call: `runs` names it (`one minimal headless call of Aider`), `never` says `reads your repositories`, and `cost` names its token cost.

[source,text]
----
  Checking Claude Code

    ✓  version 2.4.1 is supported (2.0 – 2.x)
    ✗  not logged in
       → log in to Claude Code in another terminal, then check again:
         claude login                                            [ Copy ]

  [ Choose another harness ]                              [ Check again ]
----

* Each check is a line that turns from a spinner to ✓ or ✗; a failing check names its fix and a command where one exists (`harness.blocked`). An unsupported version reads `version 0.9.2 is not supported (2.0 – 2.x)` with `→ install a version in 2.0 – 2.x, then check again`.

[#harness-confirm]
=== Confirm (`harness.confirm`)

----
  Enrol Claude Code

    Path      /Users/oliver/.local/bin/claude

[#models]
== ③ Models

[#models-consent]
=== Consent (`catalogue.consent`)

Two consents in one screen, each with its own cost (consent kinds `probe_harness_models` and `model_advice`), answered together or one by one:

[source,text]
----
  Ask the harnesses for their models, and a model for advice?

  1  List the models of Claude Code and OpenCode
       runs   claude models list, opencode models
       cost   none

  2  Ask the steward which harnesses and models suit which work
       runs   a steward task on Claude Code · opus-5.5
       cost   about 0.10 USD (not known yet: first run)

    (•) yes to both
    ( ) yes to both, and don't ask again    you can withdraw it in the settings
    ( ) yes to 1 only
    ( ) yes to 2 only

  [ Not now ]                       [ List the models and ask the steward ]
----

* The primary button follows the choice: `List the models and ask the steward`, `List the models`, or `Ask the steward`.
* Answering one only is valid: without the model probe, `catalogue.select` asks for model ids; without the advice, it shows no recommendation.

=== Scan and Advice (`catalogue.scan`, `catalogue.advise`)

[source,text]
----
  Choose the harnesses and models other plans may use

    ✓  Claude Code    3 models
    ✓  OpenCode       5 models
    ⠴  steward is working on Claude Code · opus-5.5      0:18   about 0.10 USD

  [ Continue without the advice ]
----

* The model task is shown as every model at work (<<model-at-work>>).

[#models-select]
=== Select (`catalogue.select`)

[source,text]
----
  Choose the harnesses and models other plans may use

  ┌ Recommendation by steward ─────────────────────────────────────┐
  │ Use Claude Code for writing roles and OpenCode with a small    │
  │ model for screening; allow the three models below.  [ Why? ]   │
  └────────────────────────────────────────────────────────────────┘

  CC Claude Code   enrolled
    [x] opus-5.5          ★ recommended
    [x] sonnet-5.5        ★ recommended
    [ ] haiku-5.5

  OC OpenCode      found, not enrolled            [x] enrol OpenCode  ★
    [x] qwen-coder-32b    ★ recommended
    [ ] deepseek-v4
    [ Add a model id ]

  [ Back ]                       [ Enrol OpenCode and allow 3 models ]
----

* The recommendation is preselected and marked; the operator's change of a preselected box removes the mark from it. *Why?* opens the rationale with cost and limits per model.
* *Without a recommendation* (the advice was not consented to, was left, or failed): the box is replaced by one line, `The steward gave no proposal: <reason>.`, or by nothing when the advice was not asked for; the models are preselected as the probe found them on the enrolled harness, and no harness is preselected for enrolment.

[source,text]
----
  Choose the harnesses and models other plans may use

  The steward gave no proposal: you continued without the advice.

  CC Claude Code   enrolled
    [x] opus-5.5
    [x] sonnet-5.5
    [x] haiku-5.5

  OC OpenCode      found, not enrolled            [ ] enrol OpenCode
    …
  [ Back ]                                          [ Allow 3 models ]
----

* A harness that cannot list its models shows *Add a model id* as its only entry; it opens an input `Model id for OpenCode`.
* Enrolling a further harness runs its consent, check and confirmation (<<harness-probe>>, <<harness-confirm>>) inline before the step completes (`catalogue.enrol`); the result is `4 models allowed on 2 harnesses`.
