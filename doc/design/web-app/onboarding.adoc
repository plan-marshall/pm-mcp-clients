[#frame]
== Frame

The onboarding fills the whole app until it is complete; the rest of the app is reached once `onboard.completed` is reached. A later run of one aspect opens from the machine settings (link:machine-settings.adoc[Machine Settings]) in the same frame. How the web app gets here after pairing is link:entry.adoc#after-pairing[Entry, Where the App Opens].

[source,text]
----
┌──────────────────────────────────────────────────────────────────────────────┐
│ plan-marshall                                   Machine: mbp-oliver   ⚙  ?   │
├──────────────────────────────────────────────────────────────────────────────┤
│  ① Language ─ ② Harnesses ─ ③ Models ─ ④ Roles ─ ⑤ Credentials ─ ⑥ Providers │
│  ─ ⑦ Plans ─ ✓ Done                                                          │
│  ━━━━━━━━━━━                                                                 │
├──────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│  <title of the state>                                                        │
│  <one or two sentences: what this step is for>                               │
│                                                                              │
│  <content of the state>                                                      │
│                                                                              │
├──────────────────────────────────────────────────────────────────────────────┤
│  <secondary links>                                   [ <primary link> ]      │
└──────────────────────────────────────────────────────────────────────────────┘
----

* *Step bar*: the seven sub-workflows of `onboard.*`; done steps are ticked and can be opened to look at, never re-run from the bar (a re-run is a later change from the settings). The bar shows where the process is; it does not navigate ahead.
* *One route*: the onboarding is one route of the app (`/onboarding`) that renders whichever state the server reports; the app has no route per state, so it cannot show a state the server is not in. A done step opened from the step bar is shown read-only beside the current one.
* *Footer*: the links of the state; the primary one on the right. A state the server is working in (`[S]`) shows progress instead and no link.
* *Answered elsewhere*: a state answered in the terminal or on another device while it is open here is replaced by the state the server moved to, with the line `Answered elsewhere: <answer>` (`common.error.state_moved`).
* *Terminal*: the console `pm-operator` prints the step line `[3/7] Models` above each state, the content below it, and the links as a prompt line; `?` shows the explanation the web app shows under the title (link:../terminal-client/03-dialogues.adoc#state-frame[Terminal Client, The Frame of a State]).

[#model-at-work]
=== Model at Work (`[M]` states)

[source,text]
----
  Choose the models plans may use

  ⠴  steward is working on Claude Code · sonnet-5.5          0:18   about 50 k tokens

     You can leave this page; the work continues, and the next visit shows
     its result.

  [ Continue without the advice ]
----

* The content names the role, the harness (the default harness, for the steward) and the model, the time so far, and the tokens expected (`common.model.working`, with `common.consent.tokens.estimate`).
* *Continue without the advice* leaves the model task; the state continues as the use case's variation says, without the result. A task that fails does the same and shows one line with its reason (`common.model.no_result`): `The steward gave no proposal: <reason>.`

[#consent]
== Consent

One pattern for every consent state (`<step>.consent`, or `<step>.<action>-consent` where a step asks several). The pattern, its fields, its choices and what _no_ does are designed once for both clients (link:../shared/consents.adoc#pattern[Consents, The Pattern]); every kind, its title, whether it can be remembered and what _no_ does with it are in link:../shared/consents.adoc#kinds[Consents, The Kinds]. The screen adds nothing the server did not state. Its fields are those of the terminal (`looks for`, `in`, `runs`, `never`, `tokens`), each shown only when the consent kind states it.

[source,text]
----
  Look for harnesses on this machine?

    looks for   claude, opencode, codex, agy
    in          your PATH, ~/.local/bin, /Applications, /opt/homebrew/bin
    runs        <program> --version on each one found
    never       reads other files, starts a session, uses the network
    tokens      none

    (•) yes
    ( ) yes, and don't ask again       you can withdraw it in the settings

  [ Not now ]                                       [ Look for harnesses ]
----

Terminal: link:../terminal-client/06-transcripts-steps-1-3.adoc#t-harness-consent[Terminal Client, transcript].

* *Not now* (link `no`): for a consent the step needs, the screen stays and shows "Nothing was done." under the title, with the same choices; the step bar does not move. For an optional one (the icons, the advice) the secondary link names what happens instead (_Use monograms_, _only list the models_) and the step goes on without it.
* The remember choice is a choice inside the screen, not a third button, so the primary button stays one action: `yes` or `yes_remember` by the choice; `yes` is preselected. The primary button is the consent's action ("Look for harnesses").
* A consent that is never remembered (`harness.add-consent`, `auto.consent`) has no choice; the line `This consent is for this run only.` stands in its place.
* A consent that calls a model names the role, the harness, and the tokens expected from earlier runs, in the number format of link:../shared/texts-and-languages.adoc#numbers[Texts and Languages, Numbers] and never in money, or "not known yet: first run" for the first run.
* A remembered consent passes its state without a screen; the step shows one line `Consent remembered: <action>` above the result, the action by the kind's title (link:../shared/consents.adoc#texts[Consents, Texts]). The remembered consents are listed and withdrawn in the machine settings (link:machine-settings.adoc#consents[Machine Settings, Remembered Consents]).

[#harness]
== ② Harnesses

One scan finds every harness of the machine; the operator chooses the ones to work with, one of them the default, and each chosen one is checked and enrolled. No state of this step needs a model: no harness is enrolled yet. The order is that of link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-4[UC-ONB-4]: the consent `harness.consent` (as in <<consent>>), the scan (`Looking for harnesses … 2 of 4 programs`), the icons' consent (<<harness-icons-consent>>), the choice (<<harness-choose>>), the check of each chosen one (<<harness-probe>>), and the confirmation (<<harness-confirm>>). With none found the step shows <<harness-none>>. A harness the binary does not know is added under _Advanced_ (<<harness-add>>) and comes back to the choice. A later run from the settings is link:machine-settings.adoc#harnesses[Machine Settings, The Harnesses Again].

[#harness-icons-consent]
=== Icons (`harness.icons-consent`, `harness.fetch-icons`)

Right after the scan, before the choice, when at least one found harness's profile names a `source` icon (consent kind `fetch_icons`):

[source,text]
----
  Fetch the makers' icons of the found harnesses?

    looks for   the makers' icons of Claude Code (anthropic.com) and
                OpenCode (opencode.ai)
    runs        one download of each, by the runtime, from the address in
                its profile; stored on this machine
    never       sends data of yours or of this machine; the maker's server
                sees only a download request from this machine's address
                (through the proxy, if one is set); your browser never
                loads them
    tokens      none

    (•) yes
    ( ) yes, and don't ask again       you can withdraw it in the settings

  [ Use monograms ]                                      [ Fetch 2 icons ]
----

* An icon is no condition of the step: *Use monograms* (link `no`) goes on to <<harness-choose>> with the monograms (link:harness-icons.adoc#icons[Harness Icons]). A remembered consent skips the screen; with no `source` icon among the found harnesses it is not shown.
* The runtime fetches the files, never the browser (link:../../../../plan-marshall-documentation/doc/specification/client-profiles/01-profile-schema.adoc#harness-icons[Client Profiles, Harness Icons]). The fetch shows one line per icon and ends in `Icons fetched: 2`; a fetch that fails keeps the monogram and says so in one line with the cause (`onboard.harness.fetch_icons.failed`), and the step goes on. The icons are stored in `~/.plan-marshall-mcp/icons/` and served by the runtime itself; none is ever used as the mark of plan-marshall.

[#harness-choose]
=== Choose (`harness.choose`)

[source,text]
----
  Choose the harnesses to enrol

  Found on this machine:                                         default

  [x] CC  Claude Code   2.4.1   ~/.local/bin/claude          ✓ supported   (•)
                                tokens complete
  [ ] CX  Codex         0.31.2  /opt/homebrew/bin/codex      ✗ cannot run workers
                                tokens not reported
  [x] OC  OpenCode      1.9.0   /opt/homebrew/bin/opencode   ✓ supported   ( )
                                tokens complete
      AG  Antigravity   —       not found

  The default runs the steward of the next steps and is proposed for
  new roles.

  ▸ Advanced: add a harness that is not listed

  [ Look again ]                [ Check 2 harnesses, Claude Code the default ]
----

* Every found harness is listed with its icon or monogram, its version and path, and whether it is supported, in the order of its client id (`claude`, `codex`, `opencode`); every supported one that can run workers is preselected, and the first of them in that order is the default. Harnesses that cannot run workers are greyed with the reason and cannot be chosen; harnesses not found are listed so the operator sees what was looked for.
* *Default* is a choice among the ticked rows; unticking the default makes the first ticked row the default, and the line under the list says so (`OpenCode is now the default.`). With no row ticked the primary button is disabled and reads `Choose at least one`.
* [[harness-tokens]]*What a harness reports of its tokens* stands below each found harness (`onboard.harness.tokens.*`): `complete`, `partial` naming what is missing (`partial: no cache figures`), or `not reported`, for this harness and version, from its profile and, for a verified profile, from its verification's stage `usage` (link:../../../../plan-marshall-documentation/doc/specification/client-profiles/01-profile-schema.adoc#token-usage[Client Profiles, Tokens, Not Money]). A figure the profile declares not applicable to the harness (no cache write) does not make it partial. It is information, never a condition of the choice: a harness that reports less is enrolled like any other, and the figures of its tasks say what was not measured. *Why?* on the line lists each figure (input, cache read, cache write, output, reasoning) as reported, not applicable, or not reported. No price or cost of a harness is shown.
* The primary button names the count and the default, and leads to the login probe's consent (<<harness-probe>>). *Look again* runs `harness.scan` again under the consent already given.
* *Advanced* opens in place and holds *Add a harness that is not listed* (<<harness-add>>).

Terminal: link:../terminal-client/06-transcripts-steps-1-3.adoc#t-harness-choose[Terminal Client, transcript].

[#harness-none]
=== None Found (`harness.none`)

[source,text]
----
  No harness found

  Looked for claude, opencode, codex, agy in your PATH, ~/.local/bin,
  /Applications, /opt/homebrew/bin.

  Install one, then look again:
    CC  Claude Code   docs.anthropic.com/en/docs/claude-code/setup   ↗
    OC  OpenCode      opencode.ai/docs/                              ↗

  Or add a harness that is not listed, by its program.

  [ Continue later ]   [ Look again ]   [ Add a harness that is not listed ]
----

* The install pages open in a new tab; nothing is installed from the app.
* *Look again* runs `harness.scan` again under the consent already given. *Continue later* sends nothing: the onboarding rests in `harness.none`, and the next visit, here or in `pm-operator`, resumes there; the page says so in one line (`web.onboard.later`).
* *When every chosen harness fails its check* (<<harness-probe>>), the step comes here as well: the title reads `No harness can be used`, and the list of what was looked for is replaced by each chosen harness with its failed check and its fix; the links are the same. The step cannot finish without one usable harness.

[#harness-probe]
=== Check (`harness.probe-consent`, `harness.probe`, `harness.blocked`)

One consent covers the login probe of every chosen harness (consent kind `probe_harness_login`), each with its command:

[source,text]
----
  Check whether the 2 chosen harnesses are logged in?

    runs        claude auth status          (Claude Code)
                opencode auth list          (OpenCode)
    never       starts a session, sends a prompt
    tokens      none

    (•) yes
    ( ) yes, and don't ask again       you can withdraw it in the settings

  [ Not now ]                                         [ Check 2 harnesses ]
----

* A harness whose profile has no login probe is checked by one minimal headless call: its `runs` line names it (`one minimal headless call of Aider`), `never` adds `reads your repositories`, and `tokens` names the tokens it uses.
* *Not now* stays: the check is needed.

The check (`harness.probe`) shows one block per chosen harness, each check a line that turns from a spinner to ✓ or ✗:

[source,text]
----
  Checking 2 harnesses

  CC Claude Code   default                                      ✓ ready
    ✓  version 2.4.1 is supported (2.0 – 2.x)
    ✓  logged in

  OC OpenCode                                                   ✗ not ready
    ✓  version 1.9.0 is supported (1.5 – 1.x)
    ✗  not logged in
       → log in to OpenCode in another terminal, then check again:
         opencode auth login                                     [ Copy ]

  [ Choose again ]   [ Leave it out ]           [ Check OpenCode again ]
----

* With every chosen harness ✓ the state passes on its own to <<harness-confirm>>.
* A failing harness holds the step (`harness.blocked`); its ✗ names the cause and the fix, with a command where one exists. An unsupported version reads `version 0.9.2 is not supported (2.0 – 2.x)` with `→ install a version in 2.0 – 2.x, then check again`. With several failing, each has its own block with its own *Leave it out* and *Check … again*.
* *Check OpenCode again* runs its probe again (`recheck`). *Leave it out* (`leave_out`) drops it from this run: its block is greyed with `left out`, and once every remaining one is ✓ the step goes on to <<harness-confirm>> without it; leaving out the default makes the first remaining one the default, with the line `Claude Code is now the default.` *Choose again* (`choose_again`) returns to <<harness-choose>> with the current choice.
* Leaving out the last chosen harness is not offered; *Choose again* stays. With every chosen harness failing, the state is not `harness.blocked` but <<harness-none>>.

[source,text]
----

  Executable   [ /usr/local/bin/aider                                      ]

               cannot name it
  Name         [ Aider              ]   Id [ aider ]
  Start from   [ OpenCode ▾ ]   the closest known harness; its settings are

  ▾ How it is called headless (from OpenCode):

  [ Back ]                                         [ Verify this harness ]
----

*Verify this harness* leads to its consent (`harness.add-consent`, consent kind `verify_harness_profile`), which has no remember choice: running an unknown program is asked every time. *Not now* stays.

[source,text]
----
  Run Aider to verify these settings?

    runs        /usr/local/bin/aider with the settings above, once per stage:
                identity, detection, launch, isolation, classes, limits,
                paths, faults, usage
    never       touches your repositories; it runs in a temporary directory
    tokens      about 12 short headless calls; tokens of your Aider account

  This consent is for this run only.

  [ Not now ]                                         [ Verify this harness ]
----

Then the verification (`harness.verify-profile`), one line per stage:

[source,text]
----
  Verifying Aider

    ✓  identity      aider 0.86.1
    ✓  detection
    ✓  launch        a headless call answered in 4.1 s
    ✗  isolation     the MCP configuration was not used: the harness
                     read ~/.aider.conf.yml instead
                     → change "Arguments": add --no-config
    ·  classes, limits, paths, faults, usage   not run

  [ Back ]                                         [ Edit the settings ]
----

* A ✗ names the field of the draft it concerns; its fix is a link to that field in `harness.add`. The stages after it are listed as not run.
* A known harness found nowhere is added the same way with its path only; the settings are its shipped ones and are not shown, and no verification runs: it goes back to <<harness-choose>> at once.

[#harness-add-confirm]
=== Install the Profile (`harness.add-confirm`, `harness.install-profile`)

A pass of every stage leads to the profile to be installed:

[source,text]
----
  Install the profile of Aider

  The verified profile is installed for this machine:

    Id        aider
    Profile   ~/.plan-marshall-mcp/profiles/aider.json
    Workers   can run workers
    Tokens    partial: no cache figures

  [ Back ]                                                 [ Install it ]
----

* *Install it* writes the profile into the machine profile set and shows `Profile of Aider installed`; its _Tokens_ is the result of the verification's stage `usage` (<<harness-tokens>>); the screen returns to <<harness-choose>>, with Aider listed among the found harnesses and ticked. From there it is checked and enrolled with the others.
* A profile that verification found unable to run workers reads `cannot run workers`; it is installed, and listed in <<harness-choose>> greyed, not to be chosen.

[#models]
== ③ Models

The models the enrolled harnesses offer, the steward's advice on them, and the operator's choice of the models plans may use. This step scans no harness and enrols none: the harnesses are those of ②. The advice is a task of the steward on the default harness.

[#models-consent]
=== Consent (`catalogue.consent`)

Two consents in one screen, each with its own tokens (consent kinds `probe_harness_models` and `model_advice`, link:../shared/consents.adoc#kinds[Consents, The Kinds]):

[source,text]
----
  Ask the harnesses for their models, and a model for advice?

  1  List the models of Claude Code and OpenCode
       runs   claude models list, opencode models
       tokens none

  2  Ask the steward which models suit which work
       runs   a steward task on the default harness, Claude Code · sonnet-5.5
       tokens not known yet: first run

    1  (•) yes   ( ) yes, and don't ask again
    2  (•) yes   ( ) yes, and don't ask again   ( ) no, without advice
       you can withdraw a remembered consent in the settings

  [ Not now ]                       [ List the models and ask the steward ]
----

* Each consent is answered on its own, and _don't ask again_ remembers its own kind only. The model probes are needed: the secondary button *Not now* refuses them (the shared pattern's _no_) and stays, nothing was done. The advice is optional: _no, without advice_ leads to <<models-select>> without a recommendation.
* The primary button follows the choice: `List the models and ask the steward`, or `List the models`.
* A remembered consent shows as one line in place of its item (`Consent remembered: ask the harnesses for their models`, with the kind's title `common.consent.kind.probe_harness_models`); with both remembered the screen is skipped.

[#models-select]
=== Select (`catalogue.select`, `catalogue.record`)

[source,text]
----
  Choose the models plans may use

  ┌ Recommendation by steward ─────────────────────────────────────┐
  │ Use opus-5.5 for planning, sonnet-5.5 for the work, and a      │
  │ small model on OpenCode for screening.              [ Why? ]   │
  └────────────────────────────────────────────────────────────────┘

  CC Claude Code   default
    [x] opus-5.5          ★ recommended
    [x] sonnet-5.5        ★ recommended
    [ ] haiku-5.5

  OC OpenCode      cannot list its models
    [x] qwen-coder-32b    ★ recommended                         [ Remove ]
    [ Add a model id ]

  [ Back ]                                            [ Allow 3 models ]
----

* One group per enrolled harness, the default marked. The recommendation is preselected and marked; the operator's change of a preselected box removes the mark from it. *Why?* opens the rationale with the limits per model.
* A harness that cannot list its models has *Add a model id*, which opens an input `Model id for OpenCode`; a model id the steward recommended for it is filled in, marked, and can be removed.
* *Without a recommendation* (no consent to the advice, the advice left, or failed): the box is replaced by one line, `The steward gave no proposal: <reason>.`, or by nothing when the advice was not asked for; every listed model is preselected, and a harness that cannot list its models starts empty.

  Choose the models plans may use

  CC Claude Code   default

    [x] haiku-5.5

  OC OpenCode      cannot list its models
    [ Add a model id ]

  [ Back ]                                            [ Allow 3 models ]
----

* A harness with no model allowed stays enrolled, but no role can use it; its group says `OpenCode: no model allowed`. The button is disabled only while no model is allowed on any harness.
* *Allow 3 models* records the allowed models per harness (`catalogue.record`) and shows `3 models allowed on 2 harnesses`.
