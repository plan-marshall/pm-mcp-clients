Status: `AGREED`.

The list views of the web app (`/reports`, `/decisions`, the running and ended work of the overview, the workstreams of an epic, and the projects) hold their items client-side already. This design gives each of them one way to use a wide window — the page template it sits on, and for a list the column window of link:navigation.adoc[Navigation] (<<templates>>) — and one shared way to find an item in the list: a filter-as-you-type control.

It changes nothing about the data: no endpoint, no record, no server-side search, and no pagination semantics.

[#templates]
== Page Templates

link:../../claude_review/ux/proposals.adoc#UX-P-03[UX-P-03] replaced the three layout modes of the list views with four page templates (link:components.adoc#templates[Components, Page Templates]):

[cols="1,2",options="header"]
|===
| Template | Width and split

| `lib/templates/TriagePage.svelte`
| The column engine: the full width of the container, shown as the column window of link:navigation.adoc#window[Navigation, The Column Window].

| `lib/templates/ObjectPage.svelte`
| The object column inside the column engine; on a page of its own at most 1440 px, centred.

| `lib/templates/WizardPage.svelte`
| 720 px, centred.

| `lib/templates/DashboardPage.svelte`
| At most 1440 px, centred.
|===

*The template's split is the only layout*: for a list view it is the column window, and no view keeps a layout mode, a layout toggle or a `pm_view_layout_<view>` choice. A view sets no page width of its own. The filter of <<filter>> stays with the view — the template owns the columns, the view owns its items, its matches and its result count.

[#filter]
== The Filter Contract

One utility (`filterText.ts`) and one component (`FilterInput.svelte`) power every adopted view.

* *Normalized substring matching*: text is decomposed (NFD), stripped of combining marks, lower-cased, and its whitespace collapsed. `Ärger` therefore matches `arger`.
* *A token holds a letter or a digit*: the query is split on whitespace, and a word that holds no letter and no digit in any script (`...`, `-`, `…`) is dropped. `fix ...` filters on `fix`; `...` alone filters on nothing. `tokenize` in `filterText.ts` applies this rule for every adopted view, and a view asks whether a filter is active by whether any token is left, never by whether the query text is blank.
* *Tokens are ANDed, fields are ORed*: every token must appear as a substring of at least one visible field. A token may not be assembled from the end of one field and the start of the next.
* *Loaded data only*: the filter runs synchronously over the items the view already holds. Typing never fetches. Reports are paginated, so the view says so while `has_older` is true and "Show older" widens the loaded set without clearing the query.
* *Served order*: matching keeps the order the runtime served; nothing is re-ranked.
* *No fuzzy matching, stemming, regex, or highlighting*: substring over normalized text is the whole contract.
* *One haystack per item*: each view builds a normalized haystack when the item list changes, not on every keystroke.
* *Empty query matches everything*: a query that leaves no token — empty, whitespace only, or punctuation only — is not a filter: every item shows and no fold opens.

[#filter-control]
=== The control

`FilterInput` renders a visible label and a labelled `<input type="search">` inside `role="search"`.

* `oninput` emits immediately; there is no debounce because the lists are bounded by what is loaded.
* `Esc` clears the query and keeps the focus; `/` focuses the field unless the focus is already in an input, textarea, select, or contenteditable element. On a view with a filter, `/` is the filter's and does not open find; `Ctrl+K` opens find on every view (link:needs-and-find.adoc#search[What Waits and Find, The Search Button]).
* A clear button appears while the query is non-empty.
* The result count sits in an `aria-live="polite"` region, e.g. "3 matches" or "No matches". The region is always in the document, empty while no filter is active, never inserted with the first query: a region added together with its text may not be announced.
* *One key pattern*: the field's label is `common.filter.label` with the list's name as its argument (_Filter: decisions_), its count `common.filter.results`, its clear control `common.filter.clear` and its empty state `common.filter.empty`; a view keeps a key of its own only for a text that says more than the shared one (`<view>.filter.no_matches`, `report.filter.loaded_only`). The labels `decisions.filter.label` and `report.filter.label` merge into the shared one, and a placeholder is an example value, never a list of the fields (link:components-fields.adoc#field-texts[Fields and Forms, Labels, Hints, Placeholders]).
* *The Projects list* takes `FilterInput` like every other list; its own filter field, without a count, `Esc` or `/`, goes.
* A view with no match shows its own empty state (`common.filter.empty` or `<view>.filter.no_matches`); pagination chrome stays visible.

Header counts keep their own meaning: the reports heading still shows the unread count of all loaded reports, and the decisions heading still shows the open-decision count. The filter's count is a separate "matches" figure.

[#field-matrices]
== Field Matrices

Every field a view can render takes part, so a query that matches only a body, an option, or a piece of evidence still finds the item.

[cols="1,3",options="header"]
|===
| View | Fields

| Reports
| `from.project`, `from.project_title`, `from.epic`, `from.epic_title`, `from.plan`, `from.plan_title`, `from.phase`, `from.role`, `from.harness`, `from.model`, `title`, `subject`, `kind`, `body`, `summary`, `status`, the localized unread/read state, the rendered created/sent time, and `created_at`.

| Decisions
| `id`, `title`, `header`, `subject`, `scope`, `asking_phase`, `asking_role`, `blocks` (raw and localized), `reversibility` (raw and localized), `description`, `change`, `waiver_gate`, `waiver_result`, `waiver_reason`, the serialized evidence values, `delivered_at`, the localized waiver title, every part's `question`, `recommendation` (key and the matching option label), `recommendation_rationale`, `recommending_role`, `answer_type`, `dependency`, every option's `key`, `label`, `tradeoff_description`, `consequences`, and dissent summary, and any note typed into the card.

| Overview — running plans
| `plan_id`, `title`, the selected project's display name and id, `epic_id`, `epic_title`, `current_phase`, `phase_state`, and the off-track signal.

| Overview — running epics
| `epic_id`, `title`, the selected project's display name and id, the needs-operator kind, and the identifiers and titles of the nested plans.

| Overview — ended work
| `id`/`item_id`, `kind`, `title`, `outcome`, `terminal_reason`, `reason`, `ended_at`, and its rendered relative date.

| Projects
| `display_name` and `project_id`; for a project being added, its checkout path. With a query, the groups _Favourites_, _Recent_ and _All projects_ become one list of matches in the order of _All projects_ (link:../shared/project-explorer.adoc#layout[Project Explorer, Favourites, Recent, All]).

| Epic — workstreams
| The workstream's `id` and `name` plus each row's `plan_id`, `title`, `status`, `wait_reason`, `wait_plan_id`, `change`, `objective`, `deliverables`, `surface`, `dependencies`, and `overlap_files`.
|===

Group headings follow their items: a project, epic, or workstream with no match disappears, and returns when the query is cleared. A folded workstream opens itself while a query is active, so a match is never hidden behind a fold.

[#adoption]
== Adoption Rule

Adopt the shared components in a view when *all* of these hold:

. The view renders a list (or several list sections) of items it already holds.
. The items carry more than one piece of text worth searching.
. Filtering can be done without a request or a change to the served order.

Do **not** add a filter to:

* a single-record view (`SettingsView`, `SystemView`, `CleanupView` and their detail panes);
* a form, a wizard step, or a picker whose list is itself the input;
* a lens's scope list whose rows choose what the next column shows, such as the projects of Running work, while it holds only a handful of rows; the list of all projects is a list and takes the filter.

A view that adopts the components must not implement its own matching rules. A new multi-element list imports `filterText` and `FilterInput`, publishes its field matrix here, and follows the result-count and empty-state behaviour above.

[#rollback]
== Rollback

Removing the filter inputs returns the views to their unfiltered lists. No data, endpoint, or stored record changes with it. The layout modes are gone and are not restored; a `pm_view_layout_<view>` key a browser still holds is no longer read and is harmless.
