[#overview]
== Overview and Problem Statement

The web app supports both light and dark themes, selectable through the user interface toggle and responding to the browser's `prefers-color-scheme`. During operation against running mock scenarios, three systemic readability defects were observed:

. **Findings review action readability in dark mode (F1):** The epic findings review button (`.review-open`, labelled "Review" or "Prüfen") rendered with `rgb(0, 0, 0)` on a dark card background (`rgb(19, 27, 46)`), resulting in an unacceptable 1.22:1 contrast ratio. The root cause was an incomplete button reset in `base.css` (`button { background: none; }` without `color: inherit;`), causing standard `<button>` elements without explicit color to fall back to the browser's default black text.
. **Undefined CSS token references (F2):** Five color tokens (`--color-accent`, `--color-accent-hover`, `--color-bg-base`, `--color-bg-subtle-hover`, `--color-warning-text`) were referenced in views and components but never declared in `tokens.css`.
. **Hard-coded color literals and light-only palettes (F3):** Over 130 hard-coded hex and rgba color literals were embedded in Svelte components and scoped styles, alongside fragile fallback patterns (`var(--token, #hex)`) that prevented dark mode from adapting effectively.

[#token-contract]
== The Design Token Contract

The design token system is declared in `pm-web-app/src/styles/tokens.css`. It establishes strict key parity between `:root`, `[data-theme="light"]`, `@media (prefers-color-scheme: dark)`, and `[data-theme="dark"]`.

=== Base Reset Invariant

All interactive elements (`button`, `input`, `select`, `textarea`) in `pm-web-app/src/styles/base.css` must declare:

[source,css]
----
button,
input,
select,
textarea {
  font-family: inherit;
  font-size: inherit;
  line-height: inherit;
  color: inherit;
}

button {
  cursor: pointer;
  background: none;
  border: none;
  padding: 0;
  color: inherit;
}
----

This invariant ensures that unstyled buttons inherit foreground colors from their surrounding theme container rather than reverting to user-agent default black text in dark contexts.

[#contrast-thresholds]
== Contrast Thresholds & Relative Luminance

All user-visible textual elements adhere to the Web Content Accessibility Guidelines (WCAG) 2.1 Level AA:

* **Normal Text (< 18pt or < 14pt bold):** Minimum contrast ratio of **4.5:1** against the effective composited background.
* **Large Text (>= 24px or >= 18.66px with weight >= 700):** Minimum contrast ratio of **3.0:1** against the effective composited background.

=== Alpha Compositing Engine

In modern web applications with layered cards, elevated panels, and modal overlays, backgrounds are frequently semi-transparent (`rgba(...)`). The contrast analyzer (`pm-web-e2e/tests/helpers/contrast.js`) walks the DOM ancestor tree from the target element up to `document.documentElement`, collecting non-transparent background layers and compositing them via the Porter-Duff source-over formula:

\[
C_{\text{composite}} = C_{\text{layer}} \times \alpha_{\text{layer}} + C_{\text{underlying}} \times (1 - \alpha_{\text{layer}})
\]

Relative luminance is computed using the standard sRGB linearisation curve:

\[
L = 0.2126 \times R_{\text{linear}} + 0.7152 \times G_{\text{linear}} + 0.0722 \times B_{\text{linear}}
\]

Contrast ratio between two luminances \(L_1\) (lighter) and \(L_2\) (darker) is defined as:

\[
\text{Ratio} = \frac{L_1 + 0.05}{L_2 + 0.05}
\]

[#audit-allowlist]
== The Audit Allowlist

Only one reasoned, functional exception is permitted to use hard-coded color literals:

* **`PairingQr.svelte`:** SVG QR code modules use `#ffffff` (quiet zone and light modules) and `#000000` (dark modules). QR code optical scanners require strict binary black-on-white module contrast regardless of operating system or browser theme.

All other components and views must reference defined tokens in `tokens.css`. Static scans in `tokens.test.ts` enforce zero unexpected color literals across `pm-web-app/src/lib/`.

[#verification-matrix]
== Automated Verification Matrix

The test pyramid enforces theme readability across three automated tiers:

. **Static & Token Unit Tests (`pm-web-app/src/styles/tokens.test.ts`):**
  * Verifies exact key parity between `:root`, `[data-theme="light"]`, `@media (prefers-color-scheme: dark)`, and `[data-theme="dark"]`.
  * Parses all `.svelte` and `.css` files to ensure every `var(--...)` reference exists in the token catalogue.
  * Static regex scanner asserting zero hard-coded `#hex`, `rgb()`, or `hsl()` literals outside the documented `PairingQr.svelte` allowlist.

. **Component Theme Tests (`pm-web-app/src/lib/views/theme.test.ts`):**
  * Mounts representative components (`EpicView`, `OverviewView`, `FindingsReviewModal`) under `data-theme="light"` and `data-theme="dark"`.
  * Asserts computed token styles, classes, and explicit readability on the "Prüfen" action button and modal dialogs.

. **Playwright E2E Theme Matrix (`pm-web-e2e/tests/theme-readability.spec.js`):**
  * 20 automated tests running against the live `pm-mock-runtime`.
  * Verifies both light and dark themes across desktop (1280×800) and mobile (375×667) viewports.
  * Audits every visible element's computed contrast ratio across `OverviewView`, `EpicView`, `PlanView`, `ReportsView`, `DecisionView`, `SystemView`, `SettingsView`, `MachineSettingsView`, `ProcessDesigner`, and `ProjectExplorerView`.
  * Captures passing visual evidence and screenshots for both themes.
