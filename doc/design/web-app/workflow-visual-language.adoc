Status: `DRAFT`. This document is the single visual authority for the icons that stand for workflow units, sub-workflows, phases, plan axes, and recipes in the web app. It is a visual contract, not a schema: the wire field is owned by `pm-workflow`, the id set and the delivered assets by `pm-web-app`.

[#purpose]
== What This Is

A workflow unit carries a stable `icon` id in its frontmatter. The runtime serves that id with the unit; the client resolves it to one delivered SVG and shows it beside the unit's name or phase badge. The text stays the accessible source of truth, and the icon is data of the unit rather than a client-side table keyed by unit name.

The visual language exists so that a person can tell an init phase from a remediation policy, or a review from a landing, without reading every label. It is deliberately small: workflows and phases, not plans, tasks, workers, projects, or arbitrary headings.

[#grammar]
== Visual Grammar

Every icon is one drawing on the same grid, so the set reads as a family even where the metaphors differ.

* *Grid*: a `24 × 24` coordinate space, with the drawing inside roughly `2..22` on both axes. No icon relies on the file's rendered size.
* *Stroke*: `2` px, monochrome, `currentColor`. Caps and joins are round.
* *Fill*: none by default. A deliberate accent may be a filled dot no larger than a `1` unit radius, always `fill="currentColor"` and never a literal colour.
* *Silhouette first*: one clear silhouette, legible at `16`, `20`, and `24` px. Shapes are told apart by outline, not by colour or by a caption.
* *No text*: no glyph, letter, number, or word inside the drawing. A question is a speech bubble, not a `?`.
* *No decoration*: no gradients, shadows, duplicate strokes, or ornamental detail that disappears at `16` px.
* *Light and dark*: one drawing serves both themes; `currentColor` makes it follow the surrounding text.

[#contract]
== Technical Contract

Every delivered file satisfies all of the following. The registry test enforces the list, so a drawn icon that breaks it fails the build rather than reaching the app.

* *SVG 1.1*, a single root `<svg>` with `xmlns="http://www.w3.org/2000/svg"` and `viewBox="0 0 24 24"`.
* *Monochrome*: `fill="none"`, `stroke="currentColor"`, `stroke-width="2"`, `stroke-linecap="round"`, `stroke-linejoin="round"` on the root.
* *No* `<text>`, `<script>`, `<image>`, `<foreignObject>`, `<style>`, or `<use>` element.
* *No external reference*: no `href`, `xlink:href`, `<image>`, data URI, or remote URL, and no embedded raster.
* *No hard-coded colour*: the only colour values are `none` and `currentColor`.
* *No CSS*: no `style` attribute, no class-driven presentation, no media query. The consumer supplies colour through `currentColor`.
* *One icon per file*, no comments or editor metadata. The file name is the id with dots replaced by hyphens: `phase.init` → `phase-init.svg`, `axis.method.test-first` → `axis-method-test-first.svg`.
* *Optimised* with SVGO before it is committed: paths collapsed and decimals reduced, without changing the silhouette.
* *Consumed as a mask*: the web app paints the SVG through `mask-image`, so only its alpha silhouette is used. The drawing must not depend on stroke colour inside the file.

[#naming]
== Naming and Stability

* The icon *id* is the contract. The delivered drawing may be refined without renaming the id, and a client never learns the file name.
* Ids follow the schema grammar `[a-z][a-z0-9._-]{0,63}`. They are stable across releases.
* The *unit name* and the *icon id* are different concepts. A unit id may be `phase-6-finalize` while its icon id is `phase.finalize`; the frontmatter states the icon explicitly, so no client derives one from the other.
* A rename or removal is a deprecation, not a silent swap: keep the old id as an alias in the registry and in the catalogue for one release, then retire it with a migration note. An unknown id always falls back to `workflow.default`, so a partially rolled-out rename renders rather than breaks.
* The family prefix is meaningful (`phase.`, `axis.`, `remediation.`, `unit.`, `flow.`, `git.`, `recipe.`). A new id joins an existing family unless the visual specification adds one.

[#licensing]
== Licensing and Provenance

The delivered set is *standalone original line art* drawn for this project. No icon-font glyph, brand logo, stock icon, or remote asset is copied, traced, or referenced.

A *blend* (any icon derived from a third-party source) is allowed only after every gate below is answered in writing in the provenance table:

. The source permits commercial use.
. The source permits modification and redistribution in this repository.
. Any required attribution can be satisfied in this document and in the app's notices.
. The drawing creates no trademark or logo confusion and is not a brand mark.
. The provenance row records author, source URL, licence, commercial-use conclusion, attribution, and approval.

The Git icon is our own trunk-commit-branch metaphor, not the Git logo. Harness artwork is unrelated and keeps its own design and legal research in link:harness-icons.adoc[Harness Icons].

[#accessibility]
== Accessibility and Usage

* *Decorative by default*: an icon beside a visible label is `aria-hidden="true"`. The label carries the meaning.
* *Named when standalone*: where an icon is not beside text, it gets an accessible name (`role="img"` with an accessible label) or a visible label. It is never the only way to identify an action.
* *No icon-only actions*: a button keeps its text or accessible name; the icon only reinforces it.
* *No colour-only meaning*: every distinction is carried by silhouette and by the text. Colour is inherited and may change with the theme.
* *Sizes*: `16` px in dense rows and badges, `20` px beside a selected unit or a heading, `24` px where the icon stands as a small illustration. Other sizes are not part of the contract.
* *Spacing*: the icon sits on the text baseline and keeps a small gap from its label; it never changes the line box enough to shift the row.
* *Focus and keyboard*: the icon is presentational and adds no focus stop or key handling.

[#mapping]
== Unit and Phase Map

The map states which icon a known unit or phase resolves to. It is the authority for the process designer's catalogue and for phase badges; a unit's own frontmatter remains the authority for the icon shown beside that unit.

Resolution rules:

* A unit's `frontmatter.icon` wins wherever the unit is shown. The map below fills the gaps for phases (which are served as bare phase tokens or as phase-unit ids) and for compiled units that carry no frontmatter.
* `phaseIconId` accepts a bare phase token (`execute`) and a phase-unit id (`phase-5-execute`).
* `unitIconId` accepts the unit id. A `remediation.` unit that is not listed resolves by its category word (`ci`, `review`, `analysis`, `build`, `merge`, `qgate`).
* Any id the registry does not know resolves to `workflow.default`. An empty frontmatter value is a schema error, not an unknown id.

[#update]
== Adding and Maintaining an Icon

A new icon is a four-file change. No view code changes, because every view resolves an id through the registry.

. *Add the SVG* under `pm-web-app/src/lib/icons/workflows/`, named by the id with dots replaced by hyphens, and satisfying <<contract>>.
. *Add the registry entry*: import the asset with Vite's `?url`, add the id to `WORKFLOW_ICON_IDS`, and add its URL to the registry map.
. *Add the catalogue row and the unit/phase map row* in this document, plus a provenance row if the drawing is not original.
. *Add `icon: <id>` to the unit's frontmatter* in the repository that owns the unit.
. *Run the checks*: `npm test`, `npm run check`, `npm run lint`, and Prettier on the changed files. The registry test fails on an orphan asset, a missing catalogue row, a duplicate id, or an unknown mapping.

Renaming an id is a deprecation: keep the old id as an alias for one release, add the new row, and note the migration in this document. Removing an icon follows the same alias rule until no shipped unit names it.
