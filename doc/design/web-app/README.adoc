[#principles]
== Principles

* *The screen is the state.* Each screen renders one state of the onboarding workflow: what the server reports for it, and one control per link it offers. The app holds no step order and no rule of its own; reloading the page, closing the browser, or opening it on another paired device shows the same state.
* *Nothing happens on its own.* No screen starts an action when it opens. Every action that looks at the machine, runs a program, or asks a model is behind a consent screen (link:onboarding.adoc#consent[Onboarding], link:../shared/consents.adoc#pattern[Consents]); every other action is behind a button that names it.
* *Say exactly what will happen.* A button is labelled with what it does ("Look for harnesses", "Enrol 2 harnesses"), never "Next" or "OK". A consent screen lists the directories, the commands, and the tokens it uses before it asks.
* *Preselected, never hidden.* Every screen opens with the proposal filled in (defaults, found harnesses, detected tools), so accepting it is one click; the overview shows everything that will be recorded, and every part of it can be changed, the detail one click away.
* *Every check reports back.* A check is a line that turns from a spinner into ✓ or ✗; a ✗ carries what failed, the answer received, and the fix. Nothing is marked done that was not checked.
* *Saying no is safe.* "Not now" never ends in an error or a warning colour; the screen stays and says that nothing was done.
* *Web and terminal say the same.* Both render the same state with the same texts from the same catalogue (link:../shared/texts-and-languages.adoc[Texts and Languages]); a link is a button in the web app and a key or a numbered choice in the terminal. Where the web app shows a table, the terminal shows a list, with the same columns as fields.
* *First run and later change look alike.* A later run of one aspect opens the same screen with the current values filled in and the step bar showing only that aspect.

[#operator-decisions]
== Decisions of the Operator

The operator of the visual redesign decided on 2026-10-25:

* *Inter, self-hosted.* The interface typeface is Inter, delivered as a variable `woff2` file in `pm-web-app/static/fonts/` with its SIL Open Font License file; the app never fetches a font from a font service (link:theme-readability.adoc[Theme Readability]).
* *The project's own UI icon set.* The interface icons are the project's own set on link:workflow-visual-language.adoc[Workflow Visual Language]; no open icon library enters the build.
* *axe-core in `pm-web-e2e`.* The automated accessibility audit of the built app runs with axe-core in the end-to-end suite.
* *stylelint in `pm-web-app`.* The token rules — no raw colour literal and no old token name in a view or a component — are enforced with stylelint in the Maven build.

Each decision is carried out by the step of the visual redesign that needs it; this section records the decision itself, not the state of its implementation.

[#shell]
=== The App Shell

One frame holds every view: a rail on the left, a top bar above the view, and — on a phone — a bottom bar below it. The view itself never draws the frame.

[cols="1,3",options="header"]
|===
|Part |Design

|Rail
|`232 px` wide, collapsible to `64 px` (icons with their labels as tooltips); this browser keeps the choice (`pm_rail_collapsed`). The head carries the `BrandMark` on its `28 px` brand square and the project's name, the mark and the name opening the start page. Three groups, in this order: *Work* (Running work, Projects, Decisions), *Records* (Reports), *Machine* (System, Process Designer, Settings). A destination that carries a count shows it beside its label: the open decisions and the unread reports. The tab title and the tab icon carry only the open decisions. A detail page keeps the destination it belongs to selected: a plan and an epic are Work, the cleanup is part of System, and the machine settings are Settings. The foot carries the language switch (`EN`/`DE`), the theme choice, and the control that collapses the rail.

|Top bar
|The path of the page — its group and its title, with the cleanup as `Machine › System › Cleanup` — the search trigger of the command palette, the live indicator (<<live-state>>), and the machine's name in a neutral pill. The pill is neutral in both modes: the machine's name is a fact, never a warning, and the connection mode travels in its title.

|Bottom bar
|Below `768 px` the rail has no room, so the four destinations a person opens most stand at the foot of the page: Running work, Decisions, Reports, and *More*. *More* opens a sheet with every destination of the three groups — the same list the rail carries — and with the language switch and the theme choice the rail's foot offers on a desktop. Each item keeps a visible label: a phone has no hover for a tooltip. The top bar still carries the path and the search trigger.

|===

[#live-state]
=== The Live Indicator

The top bar says what the event stream does, in one line: `● Live` while it is connected, `Reconnecting…` in the attention colour while it retries, and `Offline` in the danger colour with *Try again* once the retries gave up. It replaces the offline banner of the earlier frame, so the state of the connection lives in the one always-visible row rather than above the view (link:../../claude_review/ux/proposals.adoc#UX-P-12[UX-P-12]). A colour never carries the state alone: the word stands beside the dot.


[#visual-language]
== Visual Language

Every screen is built from the same frame, the same grid, the same tokens, and the same components. A view never invents a colour, a spacing, or a type size: it names a token of `pm-web-app/src/styles/tokens.css`, and the theme resolves it. The sketches below show layout and content, not pixel-exact spacing.

[#frame]
=== The Frame

The app is one rail, one column of four tiers beside it, and — on a phone — one bottom bar:

----
rail      ▣ plan-marshall        │ top bar   path › path › title   [search]  ● live  machine
          WORK                   │ ──────────────────────────────────────────────────────────
           Running               │ notices   runtime progress (a drain, an upgrade),
           Projects              │           the arrival line of reports or decisions
           Decisions 3           │ ──────────────────────────────────────────────────────────
          RECORDS                │ context   the view's own head: title, path, its actions,
           Reports 5             │           and its filters or view switches
          MACHINE                │ ──────────────────────────────────────────────────────────
           System                │ body      the view: a list, a table, a process tree, a form,
           Designer              │           a dialogue
           Settings              │ ──────────────────────────────────────────────────────────
          ◐ de  ⚙  ‹             │ live region  polite announcements, visually hidden
----

* *Rail*: the three groups of destinations (<<shell>>), their counts, the brand in the head and the language, theme and collapse controls in the foot. It stays while the person moves between views; only a phone hides it.
* *Top bar*: the path of the page, the search trigger, the live indicator, and the machine's name in a neutral pill. The path is the frame's trail; a view that has a path of its own inside its body (the plan view) keeps it, and the two say the same thing.
* *Notices*: at most one line per kind, above the view and below the top bar, never over the body. The progress line of a drain or an upgrade is on every paired device (link:../shared/system.adoc[System]); the arrival line names what arrived and holds the one step to it (link:../shared/reports.adoc#arrival[Reports, On Start], link:../shared/decisions.adoc#announce[Decisions, Announcing a Decision]). The connection state is not a notice: the live indicator of the top bar carries it (<<live-state>>).
* *Context*: the view's title, its breadcrumb where it has a path, its actions on the right, and its filter, sort, or grouping controls directly below the title. A dialogue is never a tier of the frame: it opens over the body and keeps the rail and the top bar in place.
* *Body*: one scroll container. The page itself does not scroll sideways; a wide table scrolls inside its own wrapper.
* *Bottom bar*: below `768 px`, the four destinations of the phone (<<shell>>); the rail is hidden and the body ends above the bar.
* *Live region*: a polite `aria-live` region at the end of the frame, visually hidden, carrying the quiet notices (a new report, a new decision, a project change). It never repeats a notice the operator already sees.

=== The Layout Grid

[cols="1,1,2",options="header"]
|===
|Token |Value |Use

|`--space-1` … `--space-6`
|`0.25rem` … `1.5rem`
|The steps inside a view. `--space-1`/`--space-2` inside a control, `--space-3`/`--space-4` between the parts of a row, `--space-6` around a card or a view's body.

|`--space-8`, `--space-10`, `--space-12`, `--space-16`
|`2rem`, `2.5rem`, `3rem`, `4rem`
|The gap between sections of a long view, the inset of a choice screen, and the wide steps a page and a page's section take.

|`--radius-sm` … `--radius-full`
|`6px`, `8px`, `12px`, `9999px`
|Controls and chips take `--radius-sm`; buttons `--radius-md`; cards and dialogues `--radius-lg`; counts and pills `--radius-full`. A badge is never a card and a card never a pill.

|`--shadow-1`, `--shadow-2`, `--shadow-overlay`
|three steps
|A card at rest takes `--shadow-1`; a popover takes `--shadow-2`; a dialogue takes `--shadow-overlay`. In dark, elevation is the surface step and the shadows stay faint.
|===

The content column is centred and bounded by the page template a view sits on
(link:view-density-and-filtering.adoc#templates[View Density and Filtering, Page Templates Replace the Layout Modes]): the
triage template at the full width of the window, the object and dashboard templates at `1440px`, and the wizard template
at `720px`. Every template pads the page by `--space-6` and by `--space-3` on the phone (below `480px`). A view that has
not moved yet picks its earlier bound — a reading view at `480px`, a table or a card grid at `1000px`, the explorer and
the reports list at `1200px` — and never sets an arbitrary width.

Two-column views (a list beside a detail, the process tree beside the inspector, the sources beside the chat) split at
`2fr 1fr` on the desktop. The triage template splits its list and detail `2fr 3fr` (40 / 60) and replaces the list with
the detail below `1100px`. A column that carries a live stream (chat, activity) keeps its own scroll and never pushes
the page.

|Ground
|`--color-bg-app`, `--color-bg-rail`, `--color-bg-surface`, `--color-bg-raised`, `--color-bg-subtle`

|Line

|Text

|Brand
|`--color-brand`, `--color-brand-hover`, `--color-brand-subtle`

|Attention
|`--color-attention`, `--color-attention-subtle`, `--color-attention-text`
|The dot and edge of a thing that needs the operator, the attention strip, and its text.

|Running

|Success
|`--color-success`
|The dot of a finished check, a ready project, a plan that landed.

|Danger
|`--color-danger`, `--color-danger-subtle`

A colour never carries a meaning alone: every state also has its word and, where it stands in a row, its badge glyph or icon. `--color-brand` marks exactly one primary action per screen; every other action is secondary or a plain link. A danger control is filled only for the irreversible act of its dialogue; the entry that opens the dialogue is a plain danger-coloured link.

[#themes]
=== Light and Dark Themes

The theme is a choice this browser remembers: light, dark, or system, offered together in the rail foot on a desktop and in the More sheet on a phone. `system` follows the operating system (`prefers-color-scheme`) and is what a browser with no choice, no readable storage, or a stored value that names no theme gets. The choice is kept under `pm_theme` and applied before the first paint, so a reload never shows the other theme first. Every token is defined in both themes, and a view uses only the tokens, so a theme switch never requires a view to change.

* *Light*: the app's ground is the lightest step, a card is white, text is the darkest step. The primary, success, warning, and danger roles take their darker variants so that text on a subtle background keeps a contrast ratio of at least `4.5:1`.
* *Dark*: the ground is the darkest step and a card one step above it, so a card reads as raised, never as a hole. Text is the lightest step; the roles take their lighter variants. A filled control takes `--color-on-brand` on the brand fill: white in light, the app ground in dark.
* *Never inverted*: a colour that carries meaning is not swapped between the themes (danger stays red, success stays green), and no view hard-codes a hex value. An identifier in `--font-mono` keeps the same contrast as body text; a diff keeps its added and removed roles in both themes.

[#reports-layout]
=== Reports View (`/reports`)

The list and, in place of the list, a report's detail, with the browser's back returning to the list. It is a reading view: one column, the machine's reports grouped by project, epic, and plan.

----
header
──────────────────────────────────────────────────────────────────────────
context   Reports                                              [Mark all shown read]
──────────────────────────────────────────────────────────────────────────
body      relay-hardening
            fix-relay ended: merged (#214)           2 h ago    [Show details]
            relay-docs landed                         4 h ago    [Show details]
          pm-mcp-clients
            pm-mcp-clients is onboarded              yesterday  [Show details]
──────────────────────────────────────────────────────────────────────────
          [Show 12 older]
----

* The subject is the report's own text from the catalogue with its parameters; the relative time is the only figure the client adds, and `--font-mono` is used only inside the subject (a plan id, a pull request number).
* The detail replaces the list in the same body: its head names the report and carries _Back_; its body is the completion report or the view the report leads to (link:../shared/completion-report.adoc[Completion Report]). The route stays `/reports`; the browser's back returns to the list without a reload.
* The unread state is a left rule and the word _new_, never only a background tint. _Show the details_ opens the detail and marks the report read; _Mark all shown read_ acts on the list as shown.
* Width: `1200px` on the desktop, one column on the tablet and the phone. An empty list says that nothing is new and that read reports are not shown again (link:../shared/reports.adoc#read[Reports, Reading a Report]).

header

context   System                                    [Upgrade…] [Restart…] [Stop…]
──────────────────────────────────────────────────────────────────────────
body      Runtime   pm-mcpd 0.9.1 · build 2026-10-02 (a1b2c3d)   0.10.0 available
                    running since today 08:14 · 6 h 12 min
                    memory 412 MB in use of 1 GB · CPU 4 %
                    listeners socket · loopback 127.0.0.1:7420 · network on

          Work      3 running · 1 waiting for you · 1 held · 2 paused
                    [All] [Per project]
──────────────────────────────────────────────────────────────────────────
          Workers   5 · 3 busy · 2 idle
          Jobs      build 1 of 2 slots · 1 queued · locks 3 held
          Models    [Last hour] [Today] [7 days]   [Per model] [Per role]

* The three acts are buttons in the context tier, not in the body; each opens its confirmation as a dialogue over the view. A figure that leads to what it counts is a link; a figure that is not measured says so and never shows a zero.

[#cleanup-layout]
=== Cleanup View (`/system/cleanup`)

A part of the system view, reached from its cleanup line and from a cleanup report. It shows a cleanup job: its summary, its items, and the confirmation of a deletion.

----
header
──────────────────────────────────────────────────────────────────────────
context   System › Cleanup                                        [Back to System]
──────────────────────────────────────────────────────────────────────────
body      Summary   12 plans · 2 epics · 40 logs · 1.8 GB        [Check all]
          4 kept for good · last sweep today 03:00
──────────────────────────────────────────────────────────────────────────
          Details   [x] Archived plans      30 days     1.2 GB
                    [x] Archived epics      30 days     0.5 GB
                    [ ] Logs of ended work  14 days     0.1 GB
                    Unchecked items are kept for good.
──────────────────────────────────────────────────────────────────────────
                                 [Ask me again in 3 days] [Ignore] [Delete…]
----

* The summary and the details are two cards; each item is a checkbox with its kind, its duration, and its size. An unchecked item is kept for good and the line says so.
* _Delete_ opens the confirmation as a dialogue over the view; the confirmation repeats what is freed and what stays (branches, pull requests, the remote, the checkout, the epic's ledger). _Back_ leaves everything as it is.
* The items kept for good are a separate list below the details, with their release actions. The technical residue is a read-only figure, never an item.
* Width: `1000px` on the desktop; the checklist becomes a list of labelled rows on the phone, and the acts stack at the foot of the body.

[#routes]
=== Routes and the Address Bar

Every view has a canonical path; the path is the view's address and the browser's back returns to the previous one. A route without a selection of its own (`/overview`, `/reports`, `/system`) is addressable alone; a plan and an epic are addressed by their id.

[cols="2,2,3",options="header"]
|===
|Path |View |Notes

|`/pair`, `/entry`, `/onboarding`
|Entry, pairing, onboarding
|The entry a browser reaches without a pairing; the onboarding while the machine is not onboarded.

|`/settings`, `/settings/machine`
|Settings, machine settings
|The paired devices and the aspects; the machine settings one step below.

|`/projects`, `/projects/onboard`
|Project explorer, project onboarding
|An open project onboarding is a route of its own.

|`/overview`
|Running and ended work
|Reached from the rail; no longer the start point.

|`/`
|What waits
|The start point when no place is remembered (link:needs-and-find.adoc#start-page[What Waits and Find]).

|`/start`, `/projects/{id}/start`, `/entries/{id}`
|Starting work
|A start with a project, or an entry another client opened, addressed by its id.

|`/plans/{id}`, `/epics/{id}`, `/epics/decompose`
|Plan view, epic view, decomposition
|The plan and the epic are addressed by their id.

|`/decisions`
|Decisions
|The open decisions of every project.

|`/reports`
|Reports and a report's detail
|The detail is a state of the list's route; the browser's back returns to the list.

|`/system`, `/system/cleanup`
|System, cleanup
|The cleanup is a route below the system view.

|`/designer`
|Process designer
|Opened from a project's setup, a plan node, or the machine settings.
|===

A route that is not one of these opens the overview for a paired, onboarded browser and the pairing page otherwise; it never opens a blank page. The address bar is written with `pushState` when the operator moves, and read on `popstate`, so Back and Forward move between views without a reload. A pairing code in the fragment is redeemed before the first write and never rewritten into the history (link:entry.adoc#after-pairing[Entry, Where the App Opens]).
