[#principles]
== Principles

* *The screen is the state.* Each screen renders one state of the onboarding workflow: what the server reports for it, and one control per link it offers. The app holds no step order and no rule of its own; reloading the page, closing the browser, or opening it on another paired device shows the same state.
* *Nothing happens on its own.* No screen starts an action when it opens. Every action that looks at the machine, runs a program, or asks a model is behind a consent screen (link:onboarding.adoc#consent[Onboarding], link:../shared/consents.adoc#pattern[Consents]); every other action is behind a button that names it.
* *Say exactly what will happen.* A button is labelled with what it does ("Look for harnesses", "Enrol 2 harnesses"), never "Next" or "OK". A consent screen lists the directories, the commands, and the tokens it uses before it asks.
* *Preselected, never hidden.* Every screen opens with the proposal filled in (defaults, found harnesses, detected tools), so accepting it is one click; the overview shows everything that will be recorded, and every part of it can be changed, the detail one click away.
* *Every check reports back.* A check is a line that turns from a spinner into ✓ or ✗; a ✗ carries what failed, the answer received, and the fix. Nothing is marked done that was not checked.
* *Saying no is safe.* "Not now" never ends in an error or a warning colour; the screen stays and says that nothing was done.
* *Web and terminal say the same.* Both render the same state with the same texts from the same catalogue (link:../shared/texts-and-languages.adoc[Texts and Languages]); a link is a button in the web app and a key or a numbered choice in the terminal. Where the web app shows a table, the terminal shows a list, with the same columns as fields.
* *First run and later change look alike.* A later run of one aspect opens the same screen with the current values filled in and the step bar showing only that aspect.

[#operator-decisions]
== Decisions of the Operator

The operator of the visual redesign decided on 2026-10-25:

* *Inter, self-hosted.* The interface typeface is Inter, delivered as a variable `woff2` file in `pm-web-app/static/fonts/` with its SIL Open Font License file; the app never fetches a font from a font service (link:theme-readability.adoc[Theme Readability]).
* *The project's own UI icon set.* The interface icons are the project's own set on link:workflow-visual-language.adoc[Workflow Visual Language]; no open icon library enters the build.
* *axe-core in `pm-web-e2e`.* The automated accessibility audit of the built app runs with axe-core in the end-to-end suite.
* *stylelint in `pm-web-app`.* The token rules — no raw colour literal and no old token name in a view or a component — are enforced with stylelint in the Maven build.

Each decision is carried out by the step of the visual redesign that needs it; this section records the decision itself, not the state of its implementation.

[#live-state]
=== The Live Indicator

The top bar says what the event stream does, in one line: `● Live` while it is connected, `Reconnecting…` in the attention colour while it retries, and `Offline` in the danger colour with *Try again* once the retries gave up. It replaces the offline banner of the earlier frame, so the state of the connection lives in the one always-visible row rather than above the view (link:../../claude_review/ux/proposals.adoc#UX-P-12[UX-P-12]). A colour never carries the state alone: the word stands beside the dot.


[#visual-language]
== Visual Language

Every screen is built from the same frame, the same grid, the same tokens, and the same components. A view never invents a colour, a spacing, or a type size: it names a token of `pm-web-app/src/styles/tokens.css`, and the theme resolves it. The sketches below show layout and content, not pixel-exact spacing.

[#frame]
=== The Frame

The app is one rail, one column of four tiers beside it, and — on a phone — one bottom bar:

----
rail      ▣ plan-marshall        │ top bar   lens › project › plan   [search]  ● live  machine
          WORK                   │ ──────────────────────────────────────────────────────────
           What waits ! 4        │ notices   runtime progress (a drain, an upgrade),
           Running               │           the arrival line of reports or decisions
           Projects              │ ──────────────────────────────────────────────────────────
           Decisions 3           │ context   the view's own head: title, its actions,
          RECORDS                │           and its filters or view switches;
           Reports 5             │           in a lens, one head per column
          MACHINE                │ ──────────────────────────────────────────────────────────
           System                │ body      the view: a list, a table, a process tree, a form,
           Designer              │           a dialogue; in a lens, the column window
           Settings              │ ──────────────────────────────────────────────────────────
          ◐ de  ⚙  ‹             │ live region  polite announcements, visually hidden
----

* *Rail*: the three groups of destinations (<<shell>>), their counts, the brand in the head and the language, theme and collapse controls in the foot. It stays while the person moves between views; only a phone hides it.
* *Top bar*: the breadcrumb of the page, the search trigger, the live indicator, and the machine's name as a `Chip`. The breadcrumb is the only path of the page: no view draws a second one in its head or its body.
* *Notices*: at most one line per kind, above the view and below the top bar, never over the body. The progress line of a drain or an upgrade is on every paired device (link:../shared/system.adoc[System]); the arrival line names what arrived and holds the one step to it (link:../shared/reports.adoc#arrival[Reports, On Start], link:../shared/decisions.adoc#announce[Decisions, Announcing a Decision]). The connection state is not a notice: the live indicator of the top bar carries it (<<live-state>>).
* *Context*: the view's title, its actions on the right, and its filter, sort, or grouping controls directly below the title; in a lens, each column carries its own head instead (link:navigation.adoc#column-types[Navigation, Two Column Types]). A dialogue is never a tier of the frame: it opens over the body and keeps the rail and the top bar in place.
* *Body*: one scroll container; in a lens, one per column of the window, so each column scrolls on its own (link:navigation.adoc#window[Navigation, The Column Window]). The page itself does not scroll sideways; a wide table scrolls inside its own wrapper.
* *Bottom bar*: below `768 px`, What waits, Running work, Decisions and More (<<shell>>); the rail is hidden and the body ends above the bar.
* *Live region*: a polite `aria-live` region at the end of the frame, visually hidden, carrying the quiet notices (a new report, a new decision, a project change). It never repeats a notice the operator already sees.

==== Control Tokens

Every field and every button draws its frame from the same tokens, so a field and the button beside it stand on one line (link:components-fields.adoc#form-shape[Fields and Forms, One Form Shape]):

[cols="1,1,2",options="header"]
|===
|Token |Value |Use

|`--control-height`
|`34px`; `44px` below `768px`
|The height of a field and of a `md` `Button`.

|`--control-radius`
|`--radius-md`
|The corner of a field and of a button.

|`--control-bg`
|`--color-bg-surface`
|The ground of a field.

|`--control-border`
|`--color-border-strong`
|The edge of a field at rest; `--color-danger` while it is invalid.

|`--layer-sticky`, `--layer-bar`, `--layer-menu`, `--layer-toast`, `--layer-dialog`
|`1`, `20`, `30`, `90`, `100`
|What lies above what (link:components.adoc#layers[Components, Layers]).
|===

The content is bounded by the page template a view sits on
(link:view-density-and-filtering.adoc#templates[View Density and Filtering, Page Templates]): a lens on the triage
template, the column engine, at the full width of its container, which it shows as the column window of
link:navigation.adoc#window[Navigation] — list columns of `220` to `320px`, an object column of at least `480px`, the
window by the width table there; an object on a page of its own and the dashboard template at `1440px`, centred; the
wizard template at `720px`. Every template pads the page by `--space-6` and by `--space-3` on the phone (below `480px`).
A view that has not moved yet picks its earlier bound — a reading view at `480px`, a table or a card grid at `1000px`,
the explorer at `1200px` — and never sets an arbitrary width.

The other two-column views (the process tree beside the inspector, the sources beside the start's chat) split at `2fr
1fr` on the desktop. A column that carries a live stream (chat, activity) keeps its own scroll and never pushes
the page.

[cols="2,2,3",options="header"]
|===

|< `768px`

The layout is usable down to `320px` without horizontal scrolling. A touch target is at least `2.75rem` high on the phone. Focus is never hidden: every interactive element carries the `--focus-ring`, and the focus order follows the reading order.

Each size carries its line height as `--line-height-xs` to `--line-height-3xl` and its weight as `--weight-regular` (400), `--weight-medium` (500) or `--weight-semibold` (600), in the scale of link:../../claude_review/visual-design/proposals.adoc#VD-P-03[VD-P-03]. The interface runs on Inter, self-hosted as a variable `woff2` in `pm-web-app/static/fonts/` with its SIL Open Font License; the system stack follows it as the fallback, and `font-feature-settings` turns on tabular numerals (`tnum`) and the single-storey `a` (`cv11`).

`--font-sans` is the face of every word of the interface. `--font-mono` (at `0.9em`) is the face of every identifier, path, digest, branch, commit, model id, version, count of tokens, diff line, and log line: anything the operator may compare character by character or copy. A view switches the face, never the words: a value is not translated, an identifier is never emphasised by a colour alone.

Text does not fall below `--text-xs`, and a line of copy is at most `72ch` wide. A label is short and in sentence case. A button is labelled with what it does, an imperative with its object ("Enrol 2 harnesses", never "Next"), in German the _du_ imperative ("Speichere"); a link names its destination as a noun (link:components.adoc#labels[Components, Labels]). A field's label names its value as a noun phrase, without a colon and without an instruction, and an optional field says `(optional)` after it (link:components-fields.adoc#field-texts[Fields and Forms, Labels, Hints, Placeholders]). A heading is a statement, not a question. Numerals are tabular in a table and a figure.

=== Semantic Colour Tokens

The palette is semantic: a view names the role, not the hue. The tokens are defined once for the light theme and once for the dark one.

[cols="2,3,3",options="header"]
|===
|Role |Tokens |Where

|Ground
|`--color-bg-app`, `--color-bg-rail`, `--color-bg-surface`, `--color-bg-raised`, `--color-bg-subtle`

|Line
|`--color-border`, `--color-border-strong`

|Text
|`--color-text-primary`, `--color-text-secondary`, `--color-text-muted`, `--color-on-brand`
|Body, a secondary line, a hint or a timestamp, and the label on a brand-coloured fill.

|Brand
|`--color-brand`, `--color-brand-hover`, `--color-brand-subtle`

|Attention
|`--color-attention`, `--color-attention-subtle`, `--color-attention-text`
|The dot and edge of a thing that needs the operator, the attention strip, and its text.

|Running
|`--color-running`
|The dot of running work and a progress bar.

|Success
|`--color-success`, `--color-success-subtle`
|The dot of a finished check, a ready project, a plan that landed; the subtle step has a value of its own in both themes, never an alias of `--color-bg-subtle`.

|Danger
|`--color-danger`, `--color-danger-subtle`
|The dot of a failure or a hold, the confirm button of a danger dialog, an error block.

|Neutral
|`--color-neutral`
|The dot of planned, paused or staged work.

|Kind
|`--color-kind-project`, `--color-kind-epic`, `--color-kind-plan`
|The icon of a project's, an epic's and a plan's `KindMark`, never a fill, a row or a word; the other kinds are neutral. They replace `--color-epic` and keep a measured distance from every colour above and from the mascot (link:components-tags.adoc#kind-tints[Tags and Kinds, The Three Kind Tints]).
|===

The names of design system v1 (`--color-primary`, `--color-warning`, `--color-bg-inset` and the rest) stay declared as aliases of these tokens until link:../../claude_review/visual-design/plan.adoc#VD-S-08[VD-S-08] removes them; a view may still name one, and it renders the v2 value of its theme.

A colour never carries a meaning alone: every state also has its word and, where it stands in a row, its dot or icon. One colour has one meaning (link:components-tags.adoc#tag-colour[Tags and Kinds, One Meaning per Colour]). `--color-brand` marks exactly one primary act per screen, the act of the object shown; every other act is secondary or ghost, and a link is a link, never brand-coloured. A danger control is filled only as the confirming button of a `ConfirmDialog`; the act that opens it is an entry of the overflow menu in the danger text colour, with `…`, never a visible danger button or a red link at rest (link:components.adoc#hierarchy[Components, Hierarchy]).

[#themes]
=== Light and Dark Themes

The theme is a choice this browser remembers: light, dark, or system, offered together in the rail foot on a desktop and in the More sheet on a phone. `system` follows the operating system (`prefers-color-scheme`) and is what a browser with no choice, no readable storage, or a stored value that names no theme gets. The choice is kept under `pm_theme` and applied before the first paint, so a reload never shows the other theme first. Every token is defined in both themes, and a view uses only the tokens, so a theme switch never requires a view to change.

* *Light*: the app's ground is the lightest step, a card is white, text is the darkest step. The primary, success, warning, and danger roles take their darker variants so that text on a subtle background keeps a contrast ratio of at least `4.5:1`.
* *Dark*: the ground is the darkest step and a card one step above it, so a card reads as raised, never as a hole. Text is the lightest step; the roles take their lighter variants. A filled control takes `--color-on-brand` on the brand fill: white in light, the app ground in dark.
* *Never inverted*: a colour that carries meaning is not swapped between the themes (danger stays red, success stays green), and no view hard-codes a hex value. An identifier in `--font-mono` keeps the same contrast as body text; a diff keeps its added and removed roles in both themes.

[#reports-layout]
=== Reports View (`/reports`)

The Reports lens sits on the `TriagePage` template (link:view-density-and-filtering.adoc#templates[View Density and Filtering, Page Templates]): the list column and, at `/reports/{id}`, the report's detail as the object column beside it, in the column window of link:navigation.adoc#window[Navigation]. It sets no page width of its own.

----
filters   [Filter reports]
header    Reports · 5 unread reports                          [Mark all shown read]
──────────────────────────────────────────────────────────────────────────
body      pm-mcp-clients
            ◇ relay-hardening
              • fix-relay   fix-relay ended: merged (#214)  17 d ago  [Show the details] [⋯ Report actions]
              • docs-typo   docs-typo ended: no change      17 d ago  [Show the details] [⋯ Report actions]
          This machine
            • machine       Cleanup is due: 12 candidates from 3 projects
──────────────────────────────────────────────────────────────────────────
          [Show 12 older]
----

* The subject is the report's own text from the catalogue with its parameters; the relative time is the only figure the client adds, and `--font-mono` is used only for the identifiers of the path.
* An unread row leads with a dot and sets its subject in the semibold weight; a row read by opening its detail stays beside the detail until the detail closes, without the dot and in the normal weight, and names its state _read_ in words.
* The row menu stands at the end of the row: an icon-only `⋯` (link:components.adoc#icon-button[Components, IconButton]), its accessible name _Report actions_ carrying the row's subject. It holds _Mark read_ for that one report; _Show the details_ opens the detail and marks the report read; _Mark all shown read_ acts on the list as shown.
* A report of the machine (`system.*`) stands in the group _This machine_ of its own, whatever project the wire also names (link:../shared/reports.adoc#list[Reports, The List]).
* An empty list says that nothing is new and that read reports are not shown again (link:../shared/reports.adoc#read[Reports, Reading a Report]).

=== Cleanup View (`/system/cleanup`)

A part of the system view, reached from its cleanup line and from a cleanup report. It shows a cleanup job: its summary, its items, and the confirmation of a deletion.

----
header
──────────────────────────────────────────────────────────────────────────
context   System › Cleanup
──────────────────────────────────────────────────────────────────────────
body      Summary   12 plans · 2 epics · 40 logs · 1.8 GB        [Check all]
          4 kept for good · last sweep today 03:00
──────────────────────────────────────────────────────────────────────────
          Details   [x] Archived plans      30 days     1.2 GB
                    [x] Archived epics      30 days     0.5 GB
                    [ ] Logs of ended work  14 days     0.1 GB
                    Unchecked items are kept for good.
──────────────────────────────────────────────────────────────────────────
                                       [Ask me again in 3 days] [Ignore] [⋯]
----

* The summary and the details are two cards; each item is a checkbox with its kind, its duration, and its size. An unchecked item is kept for good and the line says so.
* _Delete…_ is an entry of the overflow menu `⋯`, in the danger text colour, never a visible danger button (link:components.adoc#hierarchy[Components, Hierarchy]); it opens the confirmation as a dialogue over the view, whose confirming button is the one filled danger control; the confirmation repeats what is freed and what stays (branches, pull requests, the remote, the checkout, the epic's ledger). _Back_ leaves everything as it is.
* The items kept for good are a separate list below the details, with their release actions. The technical residue is a read-only figure, never an item.
* Width: `1000px` on the desktop; the checklist becomes a list of labelled rows on the phone, and the acts stack at the foot of the body.

[#routes]
=== Routes and the Address Bar

Every view and every object has one canonical address, in one scheme: path segments for objects, the query for the scope, the mode, the tab, an object opened in place and a side column (link:navigation.adoc#url[Navigation, Addresses and History]). The chain of columns to the left of an object is derived from the object, never written into the address.

[cols="2,2,3",options="header"]
|===
|Path |View |Notes

|`/pair`, `/entry`, `/onboarding`
|Entry, pairing, onboarding
|The entry a browser reaches without a pairing; the onboarding while the machine is not onboarded (`?step=`).

|`/`
|What waits
|The start point when no place is remembered (link:needs-and-find.adoc#start-page[What Waits and Find]); a launcher, whose items open at their own addresses.

|`/overview`
|Running work
|`?project={id}` scopes the lens to a project; `mode=ended`, `group=epic` and `follow=on` are its modes. A bare `/overview` is filled from the remembered place by a replace.

|`/epics/{id}`, `/plans/{id}`, `/plans/{id}/tasks/{task}`
|An epic, a plan, a task of a plan
|Objects of Running work; the lens's modes travel with them (`/plans/fix-relay?mode=ended`).

|`/decomposition`, `/epics/{id}/decomposition`
|Decomposition
|Not a lens (link:navigation.adoc#scope[Navigation, Where It Does Not Apply]).

|`/projects`, `/projects/{id}`
|Projects and the one project page
|`?tab=setup` opens the project's setup; without a tab it opens its work. Every id is an object's: no workflow lies below `/projects/`.

|`/project-onboarding/{entry}`
|Project onboarding
|Each open run before its enrolment, addressed by its entry (link:../shared/project-onboarding.adoc#several[Project Onboarding, Several Onboardings at Once]), so several runs open in tabs of their own; after its enrolment the run continues at `/projects/{id}?tab=setup`, and its old entry address is replaced by that one.

|`/start`, `/projects/{id}/start`, `/entries/{id}`
|Starting work
|A start with a project, or an entry another client opened, addressed by its id.

|`/decisions`, `/decisions/{id}`
|Decisions and one decision
|The open decisions of every project, and one of them beside the list.

|`/reports`, `/reports/{id}`
|Reports and a report's detail
|The detail is the object column beside the list; the browser's back returns to the list.

|`/system`, `/system/cleanup`
|System, cleanup
|The cleanup is a route below the system view; a plan or an epic it opens stands in place (`?open=plan:{id}`).

|`/settings`
|Settings
|One view with a tab per part (`PLAN-60`): `?tab=setup`, `access`, `credentials`, `consents`, `retention`, and `browser` for _This browser_ (`PLAN-85`); without a tab it opens the first. `/settings/machine` becomes `?tab=setup`, `/settings/browser` `?tab=browser`.

|`/designer`
|Process designer
|Opened from a project's setup, a plan node, or the machine settings; `?project={id}`.
|===

On any address of a lens, `open={kind}:{id}` opens an object in place and `chat=open` the chat beside its object. An old address of a moved view — `/decisions?decision={id}`, `/reports?plan={id}`, `/projects?project={id}`, `/settings/machine`, `/settings/browser`, `/projects/onboard`, `/epics/decompose` — is replaced by its address in this scheme when it is opened. A route that is not one of these opens the overview for a paired, onboarded browser and the pairing page otherwise; it never opens a blank page. The address bar is written as link:navigation.adoc#url[Navigation, Addresses and History] says — a push for a change of depth or of lens, a replace for a sibling, a mode, a tab and every selection the app makes on its own — and read on `popstate`, so Back and Forward move between views without a reload. A pairing code in the fragment is redeemed before the first write and never rewritten into the history (link:entry.adoc#after-pairing[Entry, Where the App Opens]).
