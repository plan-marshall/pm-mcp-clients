Status: `DRAFT`. The process designer is the one part of the operator's work that only the web app offers: a workflow unit is text and structure side by side, which a terminal shows poorly. The terminal client offers no designer; its `help` says where to find it (link:../terminal-client/01-commands.adoc#command-tree[Terminal Client, The Verbs]). The principles are those of the link:README.adoc#principles[Web App], with one exception said below (<<draft>>). Built by link:../../plans/implemented/web-designer.adoc[`web-designer`] on the contract of link:../../plans/implemented/designer-contract.adoc[`designer-contract`]. Names, times, and figures in the sketches are examples.

[#what]
== What Is Designed

A workflow unit the operator may own. Which units those are is the runtime's, served with the units of a project; the designer shows them in three groups:

[cols="2,3,2",options="header"]
|===
|Group |Units |In the designer

|Project-owned units
|the phase units `phase-1-init`, `phase-2-refine`, `phase-3-outline`, `phase-4-plan`, `phase-5-execute`, `phase-6-finalize`, and the `land` lane's `land`; `git.commit_and_push`, `remediation.*`, `replan`, `adjudicate.decisions`
|opened, edited, placed, removed

|Variants of the plan behaviour axes
|`landing.*`, `method.*`, `ask.*`
|opened, edited, placed, removed

|Recipes
|a recipe is a named workflow (type `recipe`) of this machine or of a project (link:../../../../pm-mcp-core/doc/specification/domain-extensions/05-recipes-and-extension-points.adoc#recipe-workflow[A Recipe Is a Workflow]), its file beside the recipe: `<PM_MCP_BASE>/recipes/<id>.pmwf` on the machine, `.marshall/recipes/<id>.pmwf` in the project
|opened, edited, placed, removed

|Compiled only
|the plan unit `plan`, `onboarding` with its aspects, `project-setup`, `epic`, `lessons`, the bootstrap and source units, `worker-task`, the entity units, `decision`, `chat`, `review`, the short landings `git.land-unit` and `git.land-removal`
|read only, as a building block; never replaced, never copied
|===

*Levels*: a unit is in force from the first level that has it: the project's copy (`.marshall/config/<unit>.pmwf`, the team's file), else this machine's copy (`<PM_MCP_BASE>/workflows/<unit>.pmwf`, the operator's, never committed), else the compiled default. A recipe of this machine is offered in every project here; a project's recipe of the same key takes its place in that project. The variant of an axis a plan chooses stays as link:../../../../pm-mcp-core/doc/specification/workflow-dsl/09-plan-instance.adoc#plan-axes[Plan Behaviour Axes] defines it. A unit for one plan only is not designed here (an open point of the use case).

[#entry]
== Where It Opens

The designer is a route of its own, `/designer`, with the project it checks against and, where one is open, the unit (`/designer?project=pm-mcp-clients&unit=phase-6-finalize&level=project`); without a project it designs for this machine (`/designer?unit=landing.pull-request&level=machine`). It opens from:

* *A project's settings* (its setup): the section _Process_ lists the project's units with the level in force (`Finalize · the project's copy`), each with _Open in the designer_, and _Design a unit_ opens the input choice for that project.
* *The plan view*: the unit a phase or a sub-workflow came from is one step away: the node offers _Open in the designer_, which opens that unit at the level it came from in the plan's project (link:../shared/plan-view.adoc#kinds[Plan View, Phase, Sub-Workflow, State]); the plan itself is not changed by it.
* *The machine settings*: _Workflow units of this machine_ lists the machine's copies and recipes, each with _Open in the designer_ and _Remove…_, and _Design a unit_ (link:machine-settings.adoc[Machine Settings]). It opens with no project chosen: the installed units are the machine's (`GET /api/v1/workflows`), the building blocks those of the machine scope (<<blocks>>), and the head reads _checked against this machine's projects_ (`designer.checked_against_machine`); choosing a project in the head is possible, never required.

*No CLI in between*: every request of the designer goes to the runtime's own `/api/v1/` on the web listener with the device's secret (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/03-web-server.adoc#web-proxy[API Access & Device Secret]); none of them is `cli_only`, so a paired device and the browser on this machine's loopback listener read, validate, place, and remove alike. Placing and removing are operator acts of the web channel; they write no audit record, since a unit's origin is its frontmatter (<<frontmatter>>).

[#input]
== Choosing the Input (`designer.open`, `designer.input`)

[source,text]
----
  Design a process                                    checked against pm-mcp-clients

  Where does the unit come from?

  ( ) Upload a file          a .pmwf file from this computer         [ Choose… ]
  ( ) Paste text             [                                                ]
  (•) Start from an installed unit
        phase-6-finalize      the project's copy · in force       [ Open ]
                              the compiled default, revision 4    [ Start from a copy ]
        landing.pull-request  this machine's copy · in force      [ Open ]
        remediation.ci-failure  the compiled default · in force   [ Start from a copy ]
        epic                  compiled only: a building block, never replaced  [ Read ]
  ( ) A new recipe           an empty recipe unit for this project or machine

  [ Back ]                                                           [ Open it ]
----

* *Upload*: a file chosen in the browser, read by the browser; it must be UTF-8 text no larger than the limit the runtime states for a unit (the line says it). Nothing is uploaded to the runtime until it is validated (<<validate>>).
* *Paste*: the text as pasted; one paste, then edited in the text pane.
* *A new recipe*: an empty unit of type `recipe` with its frontmatter to fill in (<<frontmatter>>); its key is the recipe's, which a delivered recipe must not hold (<<place>>).
* *An installed unit*: the units of the project (`GET /api/v1/projects/{project_id}/workflows`), or with no project chosen the machine's units and the compiled defaults (`GET /api/v1/workflows`), each with every level that has it and the one in force first; _Open_ opens a copy's text, _Start from a copy_ the compiled default's text as a new draft for this project or machine. A compiled-only unit opens read only.
* *Its name*: the unit's id comes from its header (`workflow phase-6-finalize version 5 format 1`), its display name from its frontmatter (`name: Finalize`); a text without a header that parses is refused before editing (`designer.input.no_header`). A text without a frontmatter opens with a finding at line 1 and the offer to add one (`designer.frontmatter.add`), which inserts the fields to fill in (<<frontmatter>>).
* *The operator's own*: what is uploaded or pasted is the operator's content, trusted like code on this machine and never screened (link:../../../../pm-mcp-core/doc/specification/model-work/07-untrusted-text-screening.adoc#local-trusted[What Is on This Machine Is Trusted]); it never runs before it is validated and placed.

[#draft]
=== The Draft

The one exception to _The screen is the state_: until it is placed, the unit being designed is the operator's draft, not a state of the runtime. It is kept in the browser of this device, so that a reload shows it again (`designer.draft.restored`); another device does not see it. Leaving the designer with a draft changed since it was last placed asks first (`designer.leave.*`).

[#editor]
== The Text and the Structure (`designer.edit`)

* *The text*: the unit's DSL in a monospaced pane with line numbers; editing is plain text, no model writes or changes it (a chat with a planning role is not part of this use case).
* *The structure*: the unit as the plan view shows a process (link:../shared/plan-view.adoc#levels[Plan View, Levels]), with its kinds and glyphs (`phase`, `↳ sub-workflow`, a state with its kind), but without any runtime state: each state in the order of the unit, its outcomes with their transitions (`done → finalize.review`), and its calls; a call opens the called unit read only, one step down, with the way back in the path.
* *Kept in step*: the structure is the runtime's parse of the text, never the client's: after a pause in typing of one second the app sends the text to the validate request and shows the structure it returns; the full findings are shown only on _Validate_. Where the text does not parse, the structure keeps its last parse, marked out of date, and says from which line (`designer.structure.not_parsed`).
* *Selection*: a node selected in the structure moves the text to its line; the cursor in the text selects its node.
* *Entries and exits in the structure*: the head of the structure shows the unit's display name and its interface: each entry as `→ <entry>` leading to the state it binds, each exit at the terminals that leave through it (`◂ done`); a unit without entries shows its starting point, one without exits its stop points.

[#frontmatter]
== The Frontmatter

The frontmatter at the top of the text (link:../../../../pm-mcp-core/doc/specification/workflow-dsl/01-grammar.adoc#unit-frontmatter[Unit Frontmatter]) is also shown as a panel above the structure, _About this unit_, kept in step with the text both ways like the structure:

[source,text]
----
  About this unit
  Name          [Finalize                                  ]
  Description   [Settles and reviews the plan's change, lands it…      ]
  Type          subworkflow        kept: it replaces a unit of this type
  Entries       start     [The execute phase ended, or a fix was made. ]
                adopt     [A plan of source pr: its head is adopted.   ]
                hand_back [The plan is handed back.                    ]
                post_run  [The post-run band runs, then the archive.   ]
  Exits         merged · no_change · handed_back · returned ·
                reenter_execute · loop_back_outline
  Author        Oliver Wolff       Modified  2026-10-14   Release 0.9.0
  Signature     none
----

* *Edited as text or in the panel*: a field changed in the panel writes its line; a line changed in the text fills the panel. An entry or exit is added with its description line directly below it, as the frontmatter requires.
* *Set on an edit*: the first change of the text sets the modification date to the day and the release to the runtime's version, and drops a signature, since it would no longer cover the content; one line says so (`designer.frontmatter.signature_dropped`).
* *The author*: the operator's name, asked once on this device and offered from then on (`designer.frontmatter.author`); `plan-marshall` is the author of the delivered units only, and a draft that still names it is a finding until the operator's name replaces it.
* *The interface of a replacing unit*: a unit that replaces another (a project-owned unit, an axis variant) keeps its type, entries, and exits; the panel shows them read only with the reason (`designer.frontmatter.interface_kept`), and a change made in the text is a finding at its line (`INV-GEN-1`). A new recipe chooses its own.
* *Findings*: the frontmatter is validated like the rest of the unit (its format, its fields, a description not directly below its element, the interface rules), each finding at its line and column, marked in the panel as in the text.

[#blocks]
== Building Blocks

The catalogue of the runtime, in the scope the designer is in: a project's as that project resolves it (`GET /api/v1/projects/{project_id}/workflows/catalogue`), or, with no project chosen, the machine's: the compiled and the machine's units and the machine's role set (`GET /api/v1/workflows/catalogue`). The pane's head names the scope (`designer.blocks.scope`). The catalogue is every element the language can use, generated by the runtime from the registries its validation uses; the app keeps no list of its own, so a block it offers is one validation accepts.

[source,text]
----
  Building blocks of pm-mcp-clients               runtime 0.9.0
  [ commit                                    ]
  ▾ primitives                                1
      git.stage-and-commit    auto
  ▾ sub-workflows                             1
      git.commit_and_push     reusable
  ─────────────────────────────────────────────
  Commit and Push · git.commit_and_push       sub-workflow
  Commits the changes of the plan's worktree and pushes its branch.
  Parameters   message_mode  enum[auto_deliverable|step_or_fallback|…]
               push_mode     enum[never|if_push_remote|always|…]
  Entries      commit   the worktree holds the changes, or is clean
  Exits        done (success, commit-result) · stepped_out
  May be used  the call clause of a state, in any unit kind
  Inserts      call git.commit_and_push entry commit (message_mode=…, push_mode=…)
                 done        -> …
                 stepped_out -> …
                                                         [ Insert ]
----

* *Groups*, each with its count, in the order a unit is written:
** *Keywords and clauses*: `state`, `skill`, `link`, `call`, `declare`, `migrate`, `start`, `entry`, `question`, … each with a template, and the frontmatter with its fields.
** *Primitives*: those of `do`, `auto`, `job`, and `guard`, each with the clauses that take it, its parameter record, and its outcomes.
** *Guards*: the guard primitives with what they read, and `depends_on_config` with its keys.
** *Links*: the link relations, each with its forms and its default form.
** *Conditions*: the condition kinds (`in_worktree`, `has_open_findings`, `all_tasks_completed`, `predicate`) and their combination with `and`, `or`, `not`.
** *Sub-workflows*: the phases as sub-workflows, the reusable sub-workflows, and the compiled ones (marked _compiled only: called, never replaced_), each by its display name and id, with its description, parameters, entries, and exits; a sub-workflow with several entries offers one insert per entry.
** *Roles*: those of the effective role set of the scope, each with its class, for a task state and a `consult`.
** *Parameters*: the declarable parameters of the unit open, each with its compiled bounds, for a `declare`.
* *Search*: one field over names, summaries, and parameter names of every group; the groups with a match open, the others close, each count then the number of matches; nothing matching says so (`designer.blocks.no_match`).
* *A block's details*: selecting a block shows its summary, its parameters with their types and bounds, its outcomes (with their classes), what it needs (a role, a skill, a configuration key), where it may be used (the clauses and the unit kinds that take it), and the text it inserts (`designer.blocks.detail.*`).
* *Insert* puts the block's text at the cursor, as the catalogue gives it (a state with its outcomes, a call with its parameters to fill in); the structure follows. A block the open unit cannot use shows its reason and cannot be inserted (`designer.blocks.not_here`).
* *Kept current*: the catalogue carries the runtime's version and a digest. When the digest the app holds differs from the one the units' record or the event of a placing names (after an upgrade, or after a placing that changes a sub-workflow or a role set), the app loads it again and says so in one line (`designer.blocks.reloaded`); a draft is never changed by it, and a block it used that is gone shows at its next validation as a finding.

[#validate]
== Validating (`designer.validate`)

_Validate_ sends the text, the unit's kind and name, and the project it is checked against (`POST /api/v1/workflows/validate`); the runtime validates it exactly as it would load it. Each stage is a line that turns into ✓ or ✗; a stage after a failed one is `– not run`:

[source,text]
----
  Validation                                           checked against pm-mcp-clients
    ✓  parses
    ✓  static rules
    ✓  compiled invariants
    ✓  composed against pm-mcp-clients
  Valid: the runtime would load it.                  [ Show the composed process ]
----

* *Findings*: each with its rule (`Rule 6`, `INV-GEN-4`, or the frontmatter's), line, and column and the runtime's message; a finding selects its line, the text marks the line with `✗` in its gutter, the structure marks its node with `✗` and the rule. Never colour alone.
* *The composed process*: when valid, the process a plan of the project would run with this unit, shown as the plan view shows a process (link:../shared/plan-view.adoc#levels[Plan View]), every node `planned`, the nodes the composition left out in their group with their reasons, under _If a plan started now in pm-mcp-clients_; nothing starts.
* *Outdated*: a change of the text after the validation marks the result `The text changed since: validate again.`; _Place…_ is enabled only for a valid result of the current text.
* *Another project*: the project it is checked against is chosen in the head; a change validates again on demand.
* *No project chosen*: a unit designed for this machine is validated against the machine target: the parse, the rules, and the invariants once, the composition against every enrolled project the unit would reach, each finding naming its project (`designer.place.project_findings`), the composed process shown per project with a choice among them. With no project enrolled the composition is `not run` and says why (`designer.validate.no_project`).

[#place]
== Placing (`designer.place-target`, `designer.validate-target`, `designer.confirm`, `designer.place`)

_Place…_ asks where the unit is to be in force:

[source,text]
----
  Where should phase-6-finalize be in force?

  ( ) On this machine          for every project here without a copy of its own;
                               yours, never committed
  (•) In the project pm-mcp-clients
                               the team's file .marshall/config/phase-6-finalize.pmwf,
                               committed and pushed as a short landing

  In force: the project's copy, else this machine's, else the compiled default.
  Now in force in pm-mcp-clients: the project's copy (revision 4).

  [ Back to the designer ]                                      [ Compare… ]
----

_Compare…_ validates the unit again against the target (`designer.validate-target`): for a project that project, for this machine every project in which it would be in force; with a finding it returns to the editor with the findings marked (<<validate>>), and only a valid unit reaches the confirmation. The confirmation shows the difference first, line by line (side by side at desktop width): against the unit at that level, or, where that level has none, against the one in force now, which the head names:

[source,text]
----
  Place phase-6-finalize in pm-mcp-clients?

  against the project's copy, revision 4          +12 lines, −3 lines
    40  state finalize.review                40  state finalize.review
                                           +41  state finalize.sbom
                                           +42    completes project:sbom
  …

  Written to .marshall/config/phase-6-finalize.pmwf, committed and pushed as a short landing;
  new plans have it once it has landed. Running plans adopt it at their next sync with
  the base only where their rule allows.

  [ Back to the designer ]                              [ Place in pm-mcp-clients ]
----

* *On this machine* (`PUT /api/v1/workflows/{unit}`): the confirmation lists the projects in which it comes into force and those that keep their own copy. The runtime validates it against every enrolled project it would reach and refuses it while any fails; the findings name each project (`designer.place.project_findings`). It is in force at once. A recipe is written beside its recipe in the machine's `recipes/` and offered in every project here, except those with a recipe of the same key, which the confirmation names; a key of a built-in or domain recipe is refused (`unit_not_designable`, `designer.place.recipe_key_taken`). While no project is enrolled, placing on this machine is refused (`no_project_to_compose`, `designer.place.no_project`).
* *In the project* (`PUT /api/v1/projects/{project_id}/workflows/{unit}`): written in the project's checkout and landed as a short landing (one commit, pushed as the project lands); a recipe's file is `.marshall/recipes/<id>.pmwf`. It takes effect for a plan when the plan's checkout or worktree has it: new plans once it has landed on the base branch. In a project whose landing is `landing.files` it is written and stays uncommitted in the operator's checkout until it is committed, which the target's hint (`designer.place.project_hint`, by the project's landing), the confirmation, and the result say. The lines of the landing turn into ✓ as they happen: `written to .marshall/config/phase-6-finalize.pmwf`, `committed a1b2c3d`, `landed: in force from now on`. A failed landing says why, leaves the unit not in force, and offers _Try again_.
* *Adoption*: a running plan adopts the new unit through the existing adoption (`config_drift`) at its next sync with the base, only where its rule allows; each plan's view says when it did (link:../shared/plan-view.adoc#live[Plan View, Live]).
* *Validated again*: placing validates the unit again; a finding refuses it (`unit_invalid`) and shows the findings (<<validate>>).
* *Unchanged*: a text equal to the unit at that level is not placed; the confirmation says so and offers no _Place_ (`designer.place.unchanged`).
* *Changed meanwhile*: placing carries the digest of the unit it replaces; if that unit changed since the difference was shown, it is refused with `conflict`, nothing placed, and the new difference is shown to confirm again (`designer.place.conflict`).
* *Never a compiled-only unit*: such a unit has no _Place…_; the runtime refuses it as well (`unit_not_designable`).
* *Only a designable name*: the unit's name, from its header, must be one the runtime lists as designable for the target, in the canonical unit-name grammar; the runtime refuses any other, and any whose file would lie outside its directory, with `unit_name_invalid` (`designer.place.name_invalid`), nothing placed or removed.
* *No audit record*: the result names the unit's author, its modification date, and its digest from what was placed (`Placed: Finalize by Oliver Wolff, 2026-10-14 · sha256:3f9a…`, `designer.place.result`); the signature the frontmatter reserves will make the origin verifiable.

[#remove]
== Removing a Placed Unit

A project's or the machine's copy can be removed: _Remove…_ in the list of installed units, in the project's setup, or in the machine settings (`DELETE /api/v1/projects/{project_id}/workflows/{unit}`, `DELETE /api/v1/workflows/{unit}`). The confirmation names the level that takes over (`Then in force: this machine's copy`) with the difference against it; a project's copy is removed as a short landing, as it was placed. Removing the machine's copy is validated like placing it, against every project that would fall back to the compiled default, and refused while any fails. The compiled default cannot be removed.

[#phone]
== At Phone Width

The input choice, then the text and the structure as two tabs, with the frontmatter panel above the structure, read only; _Validate_ with its findings and the composed process. Editing, the building blocks, and _Place…_ are not offered; one line says so (`designer.phone.note`). Placing and removing need the confirmation's difference, which needs the width.
