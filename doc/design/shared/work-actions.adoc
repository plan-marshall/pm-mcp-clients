_Relies on: link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#changes[Controlling Work, Changes] (proposed); link:../../../../plan-marshall-documentation/doc/specification/model-work/08-epic-coordination.adoc[Epic Coordination]_

Status: `DRAFT`. Shared by both clients: link:../terminal-client/19-actions.adoc[Terminal Client, Actions], link:../web-app/README.adoc[Web App].

A plan and an epic carry their actions wherever they are shown: their row in Running Work (link:plan-overview.adoc[Plan Overview]), the head of the plan view (link:plan-view.adoc[Plan View]), and an epic's level of Running Work. The actions are those of the current state only; the client takes them from the runtime and never decides itself what applies.

[#plan-actions]
== A Plan's Actions

[cols="1,2,3",options="header"]
|===
|State |Actions |Shown as

|running
|Pause, Cancel, Chat, Settings
|`running`; _Pause_ first

|pausing
|Start, Cancel, Chat, Settings
|`pausing after the task` or `after the phase`; _Start_ withdraws the pause

|paused
|Start, Abandon, Chat, Settings
|`paused` since when, by the operator

|ended
|Chat
|its outcome; its plan view, read-only (link:plan-view.adoc#ended[An Ended Plan]); a chat about it (<<chat-ended>>)
|===

* *Settings* opens the plan's own values (its overrides, link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-plan-overrides[Plan Overrides]) in every state of a plan that runs, each with where its value comes from (the plan, the project, the machine). A value may be set where the plan first needs it, or later here; it applies from where the plan next reads it.
* *Chat* opens a chat with the plan's planning role about the whole plan (<<chat>>), in every state of a plan that has not ended: running, pausing, paused, waiting for you, and held alike. An ended plan offers it alone, read-only, about its archived record (<<chat-ended>>).
* *Pause* asks where the plan holds, _after the current task_ preselected (<<pause>>); *Start* acts at once. Neither needs a confirmation: each is undone by the other.
* A plan always runs once it exists: a plan an epic starts is created and run in one act, so there is no state of a plan that waits to be started.
* *Cancel* and *Abandon* confirm first (<<confirm-end>>).
* *A plan of an epic* says on every action which epic is told (`fix-relay-epic is told`), and after it, that it was (<<epic-told>>).
* An action that applies but cannot run now is disabled with its reason (`the runtime is reconnecting`).
* *A plan's own pull request* is shown by its number with a link to the provider (`#214`), in its row, its head, and the dialogues.

[#pause]
=== Pausing a Plan

----
  Pause fix-relay?
  ─────────────────────────────────────────────────────────────────────────────
    ( ) Now                        2 tasks are withdrawn and 1 job is stopped;
                                   they run again when the plan starts
    (●) After the current task     what runs finishes: implement · 4 min,
                                   build · 2 min; nothing new starts
    ( ) After the current phase    execute runs to its end: 3 of 7 tasks left
  Its epic       relay-hardening is told
                                                       [Keep it running]  [Pause]
----

While it is pausing, its row says where it will hold and what still runs (`pausing after the task · build · 2 min`).

* *An operator wait* of the plan (a decision, a waiver request) stays open while the plan is paused, and answering it does not start the plan: the answer is recorded and the plan goes on with it once the operator starts it. A pause after the current task or phase holds at an operator wait too, since nothing runs there.
* *After a restart* of the runtime or the machine, a paused plan stays paused, a pausing plan holds at its point once it runs again, a running plan runs on from its last committed state, and an open operator wait stays open; the clients show each as it is, and nothing asks the operator again.

[#confirm-end]
=== Ending a Plan

----
  Cancel fix-relay?
  ─────────────────────────────────────────────────────────────────────────────
  What ends      the running work: 1 job, 2 tasks
  Pull request   #214 is open   (●) Close it, with the reason   ( ) Leave it open
  Its epic       relay-hardening is told
  Reason         [the approach is replaced by plan relay-v2              ]
  Afterwards     the plan is archived as cancelled; its branch stays
                                                  [Keep it running]  [Cancel the plan]
----

* The reason is required; it goes to the plan's archive, to the epic, and to the pull request's closing comment. `#214` is a link to the pull request at the provider.
* _Abandon_ is the same dialogue for a paused plan, without _What ends_, with _Keep it paused_ and _Abandon the plan_.

[#epic-told]
=== The Epic Is Told

After an action on a plan of an epic, the row of the plan shows for a moment `relay-hardening told`, and the epic's level shows the act among its events. What the epic does with it comes later, as any epic event, and a decision it raises reaches the operator as every decision does (link:decisions.adoc[Decisions]).

[#epic-actions]
== An Epic's Actions

----
  relay-hardening · epic                       3 running · 1 paused · 4 staged
  ─────────────────────────────────────────────────────────────────────────────
  [▶ Next plan: relay-reconnect-backoff]   [Findings review · 3 new]
  [Decompose again]   [Watches review · 5]   [Chat]   [Archive]   [Cancel]
----

* *Next plan* names the plan it will start: the next launchable row in the queue's order. With none launchable it is disabled and says why per row (`relay-auth-v2 waits for relay-reconnect-backoff`, `relay-docs: the surface overlaps a running plan`); with the epic's scope full it offers _Raise to 4 at once and start it_, which raises the epic's `parallelization_scope` by one and starts the plan.
* *Decompose again* asks for the instruction (`split the auth workstream; drop the docs plan`) and opens the decomposition with it (link:starting-work.adoc#decomposition[The Decomposition]).
* *Chat* opens a chat with the epic's planning role about the whole epic (<<chat>>), in every state of an epic that has not ended; an ended epic offers it alone, about its archived record (<<chat-ended>>).
* *Findings review* and *Watches review* carry their counts; new findings since the last review are also a `needs you` of the epic in Running Work.
* *Archive* runs the check first (<<archive-check>>).
* *Cancel* confirms with the choice for its plans (<<cancel-epic>>).

[#archive-check]
=== Archiving: Is It Through?

----
  Archive relay-hardening?
  ─────────────────────────────────────────────────────────────────────────────
    ✓  no plan running, pausing, or paused
    ✓  every plan shipped or ended                       11 shipped · 1 cancelled
    ✗  open findings                                     2   [Review the findings]
    ✓  the ledger is landed
    ✓  the completion review is done
    ·  watches still open                                1   go into the archive
                                                                   [Not yet]
----

Each line is a check of the runtime; a failing one leads to what is open. _Archive the epic_ is offered only when every check passes.

[#cancel-epic]
=== Cancelling an Epic

----
  Cancel relay-hardening?
  ─────────────────────────────────────────────────────────────────────────────
  Its plans      3 running · 1 paused
                 (●) Cancel them too   ( ) Let them run on without the epic
  Reason         [                                                        ]
  Afterwards     the epic is archived as cancelled
                                                  [Keep it]  [Cancel the epic]
----

[#holds]
== What Holds a Plan

A plan, an epic, or a landing that does not go on without a decision being asked shows its hold where the decision would be: on its row as the marker of what needs the operator, and first in its view.

----
  fix-relay holds: a condition                                         since 14:02
  ─────────────────────────────────────────────────────────────────────────────
  Cause        the plan reads cui-http, which this project may not read
  Tried        3 times, last 14:10
  Resolve      [Grant read access to cui-http…]   [Retry]   [End the plan…]
----

[cols="1,3",options="header"]
|===
|Hold |Its acts

|stalled
|_Retry now_, _Recycle the worker_, _End the plan…_

|condition
|the act it names, as a dialogue (_Grant read access…_, _Add the credential…_, _Raise the budget…_), _Retry now_, _End the plan…_

|integrity pause
|_Show the change_, _Accept the change…_, _Restore_, _End the plan…_

|held item of an epic
|_Retry now_, and the item's own acts

|landing failed (an epic's, or a move's removal from git)
|_Retry now_, _Show the pull request_ (by its number, with a link), and for a move's removal _Give up the removal…_
|===

* Every act is offered in both clients; a hold that clears by itself (a provider is back) leaves with a line in the events (`the provider answered again`).
* An act that cannot be undone (_Accept the change_, _End the plan_, _Give up the removal_) confirms first and names what follows.
* *Give up the removal* ends the short landing that removes moved documents from git: the removal's branch is dropped and the files remain tracked in git where they were, and the source keeps its copy; the two are no longer one, and the dialogue says so.
* *End the plan* is the plan's _Cancel_ (<<confirm-end>>).

[#review]
== Reviewing Findings or Watches

The review goes through the items of one register, one at a time, open ones first; the list beside it shows each item's disposition so far.

----
  relay-hardening · findings review                               3 of 7 decided
  ─────────────────────────────────────────────────────────────────────────────
  F-0004  Reconnect loses the last event                                   open
  ─────────────────────────────────────────────────────────────────────────────
  Statement   After a reconnect the relay resends from the stored cursor, but
              the cursor is written after the event is delivered.
  Rules       a fix must hold for every transport; covered by a test that
              drops the connection between delivery and cursor write
  Origin      landing of relay-reconnect (#211) · 2 days ago
  Proposal    Promote to a plan: it needs a change across two modules
              (the planning role)
  ─────────────────────────────────────────────────────────────────────────────
  [Keep ▾ as defect | as watch]  [Drop]  [Promote to a plan]  [Edit]  [Chat]
                              [Accept the remaining 4 proposals]   [Finish]
----

* *Keep* as a defect (a finding) or as a watch: the item may change its register.
* *Drop* asks for the reason in one line.
* *Promote to a plan* shows the planning role at work, then its draft of the staged plan (objective, deliverables, surface, dependencies) with _Stage it_, _Edit_, and _Back_.
* *Edit* asks what to adapt or add, in the operator's words; the planning role rewrites the statement and the rules, and the read-back shows old against new with _Accept_, _Instruct again_, and _Discard_.
* *Chat* opens the chat (<<chat>>) about this item or the whole register; an accepted change becomes the item's disposition or its rewrite.
* *Accept the remaining proposals* lists them all once, each with its proposal, for one confirmation.
* *An item from outside the machine* (a finding from a review comment) carries `untrusted`, and its text is shown as text, never rendered.
* *Finish* writes the decisions to the epic's ledger, where they are landed; leaving before keeps them, and the review opens where it stopped, in either client.

[#chat]
== Chatting with the Planning Role

In a chat the operator discusses a plan or an epic with its planning role, asks, and has it propose changes. It is one dialogue wherever it is opened: from a plan's actions (the whole plan), from an epic's actions (the whole epic), from the decomposition (the draft, link:starting-work.adoc#decomposition[The Decomposition]), and from a review (one item or the whole register, <<review>>), and in the three places of <<chat-places>>: inside a decision, while starting, and about ended work. The runtime routes it: a plan's chat to the plan's planning role `replan`, an epic's chat, also in its decomposition and its review, to the epic's planning role `decompose`.

----
  Chat · fix-relay · with replan                                 the whole plan
  ─────────────────────────────────────────────────────────────────────────────
  You      Can the cursor test also cover the SSE transport?
  replan   Yes. TASK-4 tests one transport only; I propose a second test.
  ─────────────────────────────────────────────────────────────────────────────
  Proposed change                              applies after the current task
  - TASK-4  cursor write order: a test for the websocket transport
  + TASK-4  cursor write order: a test per transport, websocket and SSE
  Its epic   relay-hardening is told
                                                         [Reject]  [Accept]
  ─────────────────────────────────────────────────────────────────────────────
  [Your message                                                 ]  [Send]
                                                                [End the chat]
----

* *The head* names the subject, the role the chat goes to, and the scope.
* *The transcript* shows the operator's messages and the role's answers in order, the newest at the bottom; while the role works, its line says so (`replan answers`). The operator's words are their own, interpreted with a read-back as in a decision (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#change-own-words[Own Words]); the role reads the content of the plan or the epic as data, and an item from outside the machine stays marked `untrusted` and is shown as text, never rendered.
* *A proposed change* is a read-back, old against new, with _Accept_ and _Reject_; nothing changes without _Accept_, and a rejected change is gone. To have it otherwise, the operator says so in the next message.
* *Accept* applies the change through the subject's own path and its checks: in the decomposition the draft and its checks; in a review the item's disposition or rewrite; on an epic its staged plans, through the epic's checks (surfaces disjoint, dependencies without a cycle); on a plan a revision, through the guards of a first plan (the outline, the derivation, the task graph, the Q-Gate), which makes a new version of the plan (`the plan's version becomes 8`). A check that fails says why and changes nothing; the chat goes on.
* *A running plan* goes on while the chat runs: a question never touches it, and an accepted revision takes effect at the next task boundary (`applies after the current task`): what runs finishes, the revision is applied, and the plan runs on. A pausing plan takes it at that boundary too and then holds at its point; a paused plan takes it at once and stays paused.
* *A chat's revision is the operator's own act*: it spends nothing of the plan's re-planning budget, and the runtime never opens a chat by itself. A change to a plan of an epic tells the epic (<<epic-told>>).
* *End the chat* closes it; a proposal not yet accepted is dropped with it. The transcript is kept with the plan or the epic, among its events, and is never sent elsewhere.
* *Chat is disabled* with its reason while no configuration of the routed role qualifies (`no configuration of replan qualifies yet`).
* *In the web app* the chat is a panel beside the view it was opened from (the plan view, the epic view, the decomposition, the review), the message field at its bottom; at phone width it takes the screen, and _End the chat_ returns to the view.

[#chat-places]
=== The Same Chat in Three More Places

Each place changes only the chat's scope, the role it is routed to, and what an accepted proposal does there; the dialogue, the read-back of every proposal, and the rule that nothing changes without _Accept_ are those above.

[cols="2,3,2,4",options="header"]
|===
|Place |Scope |Role |What a proposal does

|Inside a decision, at `decision.answer` (link:decisions.adoc#chat[A Chat Before Answering])
|the decision: question, why now, evidence, what it blocks, reversibility, parts and options, the recommendation and the votes
|the role of the task that asked; for one a server rule raised or a quorum escalated, `replan` or `decompose`
|a proposed answer becomes the operator's own words and goes through `decision.interpret` and `decision.read-back`; a revision is applied as on a plan, and the decision stays open unless the revision removes the need for it. The chat never answers.

|While starting, at `start.sources` (link:starting-work.adoc#chat[Chatting About the Request])
|the entry: its stored sources, untrusted ones marked, and its description
|`refine` for a plan, `decompose` for an epic; not for a recipe
|a rewrite of the description or an addition to it, stored through `start.store-description`; never another source

|About ended work (<<chat-ended>>)
|the archived record: outcome, reason, history, decisions, re-planning records, events
|`replan` for a plan, `decompose` for an epic
|a follow-up plan: its description, which opens the start of a new plan; the archive never changes
|===

[#chat-ended]
=== A Chat About Ended Work

An ended plan or epic offers one action, _Chat_: a read-only chat about how it went (`why was it handed back?`, `what did the re-planning decide?`). It is opened from the ended work's row, from the ended plan view, and from the ended epic view (link:plan-overview.adoc#ended[Ended Work]).

----
  Chat · codeberg-issues · with replan                        its archived record
  ─────────────────────────────────────────────────────────────────────────────
  You      Why was it cancelled, and what would a new attempt need?
  replan   You cancelled it: replaced by relay-v2. Its outline was done; the
           provider's tests waited for the relay's new event API.
  ─────────────────────────────────────────────────────────────────────────────
  Proposed follow-up plan                 read only: the archive stays as it is
  + Add the Codeberg issue provider on top of relay-v2.
  + follows codeberg-issues, cancelled: replaced by relay-v2
                                               [Reject]  [Start a plan with it]
----

* *Scope and role*: the archived record, read from the archive: the outcome, the reason, the history, the decisions, the re-planning records, the events. An ended plan's chat goes to `replan`, an ended epic's to `decompose`; it runs at the project's scope and never changes the archive.
* *The one proposal is a follow-up plan*: a description drafted in the chat that names the ended plan or epic, read back. _Start a plan with it_ ends the chat and opens the start of a new plan in the same project with that description stored (link:starting-work.adoc#sources[The List of Sources]); the operator goes on from ① Sources as with any start, and nothing starts before _Start the plan_.
* *The transcript* is kept with the archive entry, among its events.
* *Disabled* with its reason while no configuration of the routed role qualifies, as every chat.
