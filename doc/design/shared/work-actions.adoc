A plan and an epic carry their actions wherever they are shown: their row in Running Work (link:plan-overview.adoc[Plan Overview]), the head of the plan view (link:plan-view.adoc[Plan View]), and an epic's level of Running Work. The actions are those of the current state only; the client takes them from the runtime and never decides itself what applies.

[#plan-actions]
== A Plan's Actions

The actions of the plan's state (`plan.actions`):

[cols="1,2,3",options="header"]
|===
|State |Actions |Shown as

|running
|Pause, Cancel, Chat, Settings
|`running`; _Pause_ first

|pausing
|Start, Cancel, Chat, Settings
|`pausing after the task` or `after the phase`; _Start_ withdraws the pause

|paused
|Start, Abandon, Chat, Settings
|`paused` since when, by the operator

|waiting for you
|Pause, Cancel, Chat, Settings, beside the decision it waits for
|`waiting for you`; the decision first (link:decisions.adoc[Decisions])

|held
|Pause, Cancel, Chat, Settings, and the acts of its hold
|`held` with the hold's kind (`holds: a condition`); the hold first (<<holds>>)

|ended
|Chat
|its outcome (<<outcomes>>); its plan view, read-only (link:plan-view.adoc#ended[An Ended Plan]); a chat about it (<<chat-ended>>)
|===

* *Settings* opens the plan's own values (<<settings>>) in every state until the plan has ended.
* *Chat* opens a chat with the plan's planning role about the whole plan (<<chat>>), in every state of a plan that has not ended: running, pausing, paused, waiting for you, and held alike. An ended plan offers it alone, read-only, about its archived record (<<chat-ended>>).
* *Pause* asks where the plan holds, _after the current task_ preselected (`plan.pause-when`, <<pause>>); *Start* acts at once (`plan.start`): a paused plan runs on from where it rests, a pausing one has its pause withdrawn. Neither needs a confirmation: each is undone by the other.
* A plan always runs once it exists: a plan an epic starts is created and run in one act, so there is no state of a plan that waits to be started.
* *Waiting for you* and *held* offer the actions of a running plan; the decision is answered in its own view (link:decisions.adoc[Decisions]), the hold resolved by its acts (<<holds>>), whose _End the plan_ is _Cancel_.
* *Cancel* and *Abandon* confirm first (<<confirm-end>>). They are one end, named by the state the plan is in: a running, pausing, waiting, or held plan is cancelled, a paused one abandoned. Only the cancel of a plan held by an integrity pause is that pause's _Abort_, which ends the plan as `aborted` (<<holds>>).
* *A plan of an epic* says on every action which epic is told (`relay-hardening is told`), and after it, that it was (<<epic-told>>).
* An action that applies but cannot run now is disabled with its reason (`the runtime is reconnecting`).
* *A plan's own pull request* is shown by its number with a link to the provider (`#214`), in its row, its head, and the dialogues.

[#pause]
=== Pausing a Plan

----
  Pause fix-relay?
  ─────────────────────────────────────────────────────────────────────────────
    ( ) Now                        2 tasks are withdrawn and 1 job is stopped;
                                   they run again when the plan starts
    (●) After the current task     what runs finishes: implement · 4 min,
                                   build · 2 min; nothing new starts
    ( ) After the current phase    execute runs to its end: 3 of 7 tasks left
  Its epic       relay-hardening is told
                                                       [Keep it running]  [Pause]
----

While it is pausing (`plan.pausing`), its row says where it will hold and what still runs (`pausing after the task · build · 2 min`); once it holds, it is `paused` (`plan.paused`).

* *An operator wait* of the plan (a decision, a waiver request) stays open while the plan is paused, and answering it does not start the plan: the answer is recorded and the plan goes on with it once the operator starts it. A pause after the current task or phase holds at an operator wait too, since nothing runs there.
* *After a restart* of the runtime or the machine, a paused plan stays paused, a pausing plan holds at its point once it runs again, a running plan runs on from its last committed state, and an open operator wait stays open; the clients show each as it is, and nothing asks the operator again.

[#confirm-end]
=== Ending a Plan

----
  Cancel fix-relay?
  ─────────────────────────────────────────────────────────────────────────────
  What ends      the running work: 1 job, 2 tasks
  Pull request   #214 is open   (●) Close it, with the reason   ( ) Leave it open
  Its epic       relay-hardening is told
  Reason         [the approach is replaced by plan relay-v2              ]
  Afterwards     the plan is archived as cancelled; its branch stays
                                                  [Keep it running]  [Cancel the plan]
----

* The dialogue is `plan.confirm-end`; confirmed, the plan ends (`plan.end`) and is archived with its outcome and the reason (`plan.archived`).
* The reason is required; it goes to the plan's archive, to the epic, and to the pull request's closing comment. `#214` is a link to the pull request at the provider.
* _Abandon_ is the same dialogue for a paused plan, without _What ends_, with _Keep it paused_ and _Abandon the plan_.
* _Abort_ is the same dialogue for a plan held by an integrity pause (`Abort fix-relay?`), with _Keep it held_ and _Abort the plan_; afterwards the plan is archived as aborted.
* The plan's lesson claim is released with the end, and its open tasks, workers, and jobs end; nothing of this asks the operator.

[#outcomes]
=== How a Plan Ends

Wherever ended work is shown (its row in Ended Work, its plan view, its epic's view, the chat about it), a plan names its outcome from one closed list, and an epic its end:

[cols="1,3",options="header"]
|===
|Outcome |Set by

|`merged`
|the plan's landing: its pull request merged

|`no change`
|a recipe that found nothing to change: no commit, no pull request

|`handed back`
|the work delivered for the operator to take over: an open pull request, a branch, or the changes in the working tree, with what is missing documented

|`returned`
|only the planning result exists: nothing was implemented, no branch and no pull request are left

|`cancelled`
|the operator's _Cancel_ of a running, pausing, waiting, or held plan

|`abandoned`
|the operator's _Abandon_ of a paused plan

|`released`
|the release of the project, whatever the plan's state

|`aborted`
|the _Abort_ of an integrity pause, with the operator's reason
|===

An epic ends `completed` (archived because it is through, <<archive-check>>), `cancelled` (the operator's _Cancel_, <<cancel-epic>>), or `released` (the release of the project, which ends it together with its plans, each `released`; the epic's ledger stays in the repository untouched, and the end is recorded on this machine only). The reason stands beside the outcome wherever the operator gave one.

[#epic-told]
=== The Epic Is Told

After an action on a plan of an epic (`plan.inform-epic`), the row of the plan shows for a moment `relay-hardening told`, and the epic's level shows the act among its events: paused, started, cancelled, abandoned, revised in a chat, or settings changed, with the reason. The _Abort_ of a plan held by an integrity pause is a cancel to the epic: the epic is told `cancelled`, and the plan's row in the epic shows `abandoned`, as for every plan that ended `aborted`, while the plan keeps its outcome `aborted` wherever it is shown as ended work (<<outcomes>>). What the epic does with it comes later, as any epic event, and a decision it raises reaches the operator as every decision does (link:decisions.adoc[Decisions]). The release of a project is no act on one plan: it ends the epic with its plans, so nothing is told.

[#settings]
=== A Plan's Settings

_Settings_ gives one plan its own value of an aspect without changing the project's or the machine's (link:../../../../plan-marshall-documentation/doc/use-cases/06-controlling-work.adoc#UC-CTL-5[UC-CTL-5]); the levels and their origins are those of the settings (link:../terminal-client/02-levels.adoc#level-model[Machine, Project, Plan]).

----
  Settings · fix-relay                                     execute · running
  ─────────────────────────────────────────────────────────────────────────────
  Plan defaults   landing    landing.pull-request              from the project
                  method     method.test-first                 from the machine
                  asking     ask.key-points                    from the plan
                  posture    standard                          from the plan
                  base       main                              from the plan
  Roles           implement  Claude Code · sonnet-5.5          from the plan
                  review     Codex · gpt-5.3                   from the project
  Integrations    git        native                            from the project
  Providers       issues     GitHub                            from the project
  ─────────────────────────────────────────────────────────────────────────────
  Its epic       relay-hardening is told of a change            [Close]
----

* *`plan-settings.open`* shows the plan's value per aspect with where it comes from (the plan, the project, the team, the machine), grouped as the settings group them: the plan defaults (with the plan's posture and base branch, asked in `init.options` where no level sets them), the roles, the integrations, the providers. Selecting an aspect (`plan-settings.aspect`) opens its value; _Close_ leaves the settings.
* *`plan-settings.value`* is the dialogue of that aspect as the settings show it, the current value preselected, with one more choice where the plan has its own: _Use the project's value_ (or the machine's), which removes the plan's value.
* *`plan-settings.validate`* checks the value against the machine and the project: an enrolled harness, an allowed model, an available provider, a landing variant that fits the project and the plan. A refused value says why (`landing.main is refused: the base branch of pm-mcp-clients is protected`; `landing.files is refused: a plan from local changes needs a landing that commits`) and returns to the value.
* *`plan-settings.apply`* writes the plan's value, audited, and says from where it applies (`Applies where fix-relay next reads it; the plan's version becomes 8.`). What runs keeps the value it started with; nothing that has run runs again.
* *Too late*: a change whose new version would not contain where the plan is (its state and its call stack: the landing variant while the plan lands) is refused with the reason (`Too late: fix-relay is landing; the new version would not contain where it is. Nothing changed.`) and returns to the list of aspects.
* A value set where the plan first needs it (link:starting-work.adoc[Starting Work], the options asked when needed) is the same plan value; setting it here before it is asked means it is not asked.
* *A plan of an epic*: the epic is told (`settings changed`, with the aspect; <<epic-told>>).
* *Changed meanwhile*: `plan-settings.apply` refused with `conflict` returns to `plan-settings.value` with the current value (<<conflict>>).

[#conflict]
=== Changed in Two Clients at Once

One rule for every recorded value the operator changes: a machine setting (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-10[UC-ONB-10]; link:../web-app/machine-settings.adoc#conflict[Web App, Machine Settings], link:../terminal-client/08-transcripts-later.adoc#t-documents[Terminal Client, The Documents Mode]), a project's own value (link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc#UC-PRJ-1[UC-PRJ-1], link:project-onboarding.adoc#steps[Project Onboarding, ④ Own settings]), and a plan's value (<<settings>>) (link:../../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#concurrent-changes[Concurrent Changes of a Setting]).

----
  Landing · fix-relay
  ─────────────────────────────────────────────────────────────────────────────
  Changed meanwhile: it is now landing.main. Yours was not applied.
  Yours        landing.files
                                [Keep the current value]  [Apply yours again]
----

* *The revision travels with the change*: the dialogue of a value keeps the revision of the settings it was opened with, and the change is sent against it. The client never compares values itself.
* *The first change wins*: a change against an older revision is refused with `conflict` (`409`), and nothing of it is applied. The dialogue stays open with the current value and the operator's own choice beside it, still selected.
* *Apply yours again* sends the same choice against the current revision, through the same checks (a refused value, too late); *Keep the current value* closes the dialogue. Nothing is merged, nothing is overwritten unseen, and the runtime never retries by itself.
* *In the terminal* the line is printed above the question again, `Apply yours again? [Enter]   k) keep the current value` (`operator.actions.key.keep_current`, link:../terminal-client/22-texts-actions.adoc#actions-keys[Terminal Client, Keys of the Actions]); with `--no-input` the verb stops there with `common.conflict.no_input`.
* Texts: `common.conflict.*` (link:work-actions-texts.adoc#texts-conflict[Texts, Changed Meanwhile]).

[#epic-actions]
== An Epic's Actions

----
  relay-hardening · epic          automatic · 3 running · 1 paused · 4 staged
  ─────────────────────────────────────────────────────────────────────────────
  [▶ Next plan: relay-reconnect-backoff]   [Automatic: on]   [Findings review · 3 new]
  [Decompose again]   [Watches review · 5]   [Chat]   [Archive]   [Cancel]
----

The actions follow the epic's state (`epic.actions`; the states of link:epic-view.adoc#layout[Epic View]); between its events the epic rests (`epic.active`):

[cols="1,3",options="header"]
|===
|State |Actions

|running
|Next plan, Automatic, Common files, Decompose again, Findings review, Watches review, Chat, Archive, Cancel

|waiting for you
|those of running, beside what it waits for (a decomposition, a decision, link:decisions.adoc[Decisions])

|held
|those of running, and the acts of its hold (<<holds>>), whose end is _Cancel_

|landing
|those of running; _Archive_ disabled until the ledger has landed (`the ledger is landing`)

|ended
|Chat, read-only, about its archived record (<<chat-ended>>)
|===

* *Next plan* names the plan it will start (`epic.next-work`): the next launchable row in the queue's order. With none launchable it is disabled and says why per row (`relay-auth-v2 waits for relay-reconnect-backoff`, `relay-docs waits: overlap with relay-auth-v2`; a plan that waits for an overlap is never started beside that plan, <<epic-auto>>); with the epic's scope full it says so and asks to raise the scope (`epic.raise-scope`): _Raise to 4 at once and start it_, which raises the epic's `parallelization_scope` by one and starts the plan, or _Leave it_, which starts nothing.
* *Automatic* switches whether the epic starts its plans by itself (`epic.auto`, <<epic-auto>>).
* *The scope* is never asked when an epic starts: it is the project's `epic.parallelization_scope`, 1 by the machine's default. It is raised here, one at a time, or in the project's settings.
* *Decompose again* asks for the instruction (`split the auth workstream; drop the docs plan`) and opens the decomposition with it (link:starting-work.adoc#decomposition[The Decomposition]).
* *Chat* opens a chat with the epic's planning role about the whole epic (<<chat>>), in every state of an epic that has not ended; an ended epic offers it alone, about its archived record (<<chat-ended>>).
* *Findings review* and *Watches review* carry their counts; new findings since the last review are also a `needs you` of the epic in Running Work.
* *Archive* runs the check first (<<archive-check>>); on an epic whose completion review has not run yet, the completion review before it.
* *Cancel* confirms with the choice for its plans (<<cancel-epic>>).

[#epic-auto]
=== Automatic: On or Off

An epic starts its launchable plans by itself, up to how many may run at once, while _Automatic_ is on; off, it starts none and the operator starts each with _Next plan_ (link:../../../../plan-marshall-documentation/doc/specification/model-work/08-epic-coordination.adoc#epic-auto[An Epic Runs by Itself]).

* *The toggle* names the state it is in (`Automatic: on`, `Automatic: off`) and switches it in one act, without a confirmation: each is undone by the other. The request names the value it sets, never a flip, so that two clients switching at once both end at the value of the last; setting the value it already has changes nothing and says so (`relay-hardening already starts its plans by itself`).
* *Switched on*, the epic starts at once what can start, up to the limit, and the line after the toggle says what (`relay-token-store started (2 of 3 at once)`, or `nothing can start now: relay-docs waits: overlap with relay-auth-v2`). *Switched off*, what runs goes on; nothing new starts by itself.
* *Its default* is the project's `epic.auto_start` (the machine's default: on); a new epic takes it and the ready step of its start shows it, never asking (link:starting-work.adoc#ready[Starting Work, Ready]). The toggle changes this epic only; the project's default is changed in the project's settings.
* *In both modes* the epic reacts to its plans' ends as link:epic-view.adoc#reactions[Epic View, What the Epic Does by Itself] shows: it records a landing and judges what it means downstream, holds the plans that depend on a plan that ended without landing, and keeps a plan that overlaps a running one waiting; with it on, it also starts the next plans and, once through, runs its completion review. _Next plan_ stays offered in both: with it on, it mostly says why nothing can start, or offers to raise the scope.
* *Common files*: beside the toggle the epic shows how many files a plan may share with a running plan and still start beside it (`Common files allowed: 0`, the epic's `overlap_max_files`, taken from the project's `epic.overlap_max_files` when the epic started). The operator changes it here, for this epic, as the toggle is changed: one act naming the value it sets, told among the epic's events, and the epic at once starts what the new value admits. The project's default is changed in the project's settings.
* *Told*: the switch is among the epic's events (`you switched automatic off`).

[#archive-check]
=== Archiving: Is It Through?

----
  Archive relay-hardening?
  ─────────────────────────────────────────────────────────────────────────────
    ✓  no plan running, pausing, or paused
    ✓  every plan shipped or ended                       11 shipped · 1 cancelled
    ✗  open findings, not decided yet                    2   [Review the findings]
    ✓  the ledger is landed
    ✓  the completion review is done
    ·  carried into the archive         3 kept findings · 5 watches
                                                                   [Not yet]
----

*The completion review first*: an automatic epic has run its completion review once it was through (link:epic-view.adoc#reactions[Epic View, What the Epic Does by Itself]); an epic that has not, a manual one, runs it when the operator chooses _Archive_ (`epic.review-completion`), and the check follows once it is done. Meanwhile the dialogue shows the line `the completion review runs first` (`control.archive.review_first`) in place of the checks and offers _Not yet_, which closes the dialogue and lets the review run on; _Archive_ chosen again shows the check once the review is done. A review that stages further plans leaves the epic not through, and the check names those plans; a review that is held shows as the failing line `the completion review is done`, leading to its hold (<<holds>>).

Each line is a check of the runtime (`epic.archive-check`); a failing one leads to what is open. _Archive the epic_ is offered only when every check passes. Only an open finding, one not decided yet, holds the archive: the kept findings and the watches are listed as carried and go into the archive with the epic's ledger (`epic.archive`), so nothing it found or watched is lost.

[#cancel-epic]
=== Cancelling an Epic

----
  Cancel relay-hardening?
  ─────────────────────────────────────────────────────────────────────────────
  Its plans      3 running · 1 paused
                 (●) Cancel them too   ( ) Let them run on without the epic
  Reason         [                                                        ]
  Afterwards     the epic is archived as cancelled
                                                  [Keep it]  [Cancel the epic]
----

The dialogue is `epic.confirm-cancel`; confirmed, the epic's tasks are withdrawn, its plans end or run on as chosen, and its ledger is archived as cancelled (`epic.cancel`). An epic held by an integrity pause is cancelled the same way; the cancel is that pause's _Abort_, and the epic ends `cancelled`.

[#holds]
== What Holds a Plan

A plan, an epic, or a landing that does not go on without a decision being asked shows its hold where the decision would be: on its row as the marker of what needs the operator, and first in its view. A hold is one of exactly five kinds: `stalled`, `condition`, `integrity_pause`, `held`, `landing_failed`. A paused plan is no hold: pausing is the operator's own choice, and the plan shows it by its state.

----
  fix-relay holds: a condition                                         since 14:02
  ─────────────────────────────────────────────────────────────────────────────
  Cause        the plan reads cui-http, which this project may not read
  Tried        3 times, last 14:10
  Resolve      [Grant read access to cui-http…]   [Retry]   [End the plan…]
----

[cols="1,3",options="header"]
|===
|Hold |Its acts

|stalled
|_Retry now_, _Recycle the worker_, _End the plan…_

|condition
|the act it names, as a dialogue (_Grant read access…_, _Add the credential…_, which opens the credential of the machine's settings (link:../web-app/machine-settings.adoc#credentials[Machine Settings, Credentials]; terminal `credentials set <credential_key>`), _Raise the budget…_), _Retry now_, _End the plan…_

|integrity pause
|the tampered file with its recorded and current size and digest; _Accept the change…_, _Abort the plan…_ (an epic's: _Cancel the epic…_)

|held item of an epic
|_Retry now_, the item's own acts, _End the plan…_ for a plan's item, _Cancel the epic…_

|landing failed (an epic's, or a move's removal from git)
|_Retry now_, _Show the pull request_ (by its number, with a link), and for a move's removal _Give up the removal…_; for an epic's, _Cancel the epic…_
|===

* *After the act* (`hold.apply`): released (`hold.released`), the plan, the epic, or the landing goes on, and the view says so (`fix-relay goes on`); still held, the hold is shown again (`hold.show`) with what still holds and its cause (`Still held: the plan reads cui-http, which this project may not read`), its acts offered again.
* Every act is offered in both clients; a hold that clears by itself (a provider is back) leaves with a line in the events (`the provider answered again`).
* *An integrity pause* shows no diff and offers no restore, since the prior content is not kept: the hold names the tampered file (`plan fix-relay · references.json`) with its recorded and current size and SHA-256 digest; _Accept the change…_ accepts it as it is, after a confirmation that shows the same facts, and the runtime verifies again before the plan goes on; the other way out is _Abort the plan…_ (an epic's _Cancel the epic…_). An operator wait of the paused scope stays open and cannot be answered until the pause ends.
* *The act* is the operator's (`hold.resolve`), applied by the runtime (`hold.apply`).
* An act that cannot be undone (_Accept the change_, _End the plan_, _Abort the plan_, _Cancel the epic_, _Give up the removal_) confirms first and names what follows.
* *Give up the removal* ends the short landing that removes moved documents from git: the removal's branch is dropped and the files remain tracked in git where they were, and the source keeps its copy; the two are no longer one, and the dialogue says so.
* *End the plan* is the plan's _Cancel_, *Cancel the epic* the epic's (<<confirm-end>>, <<cancel-epic>>); *Abort the plan* is the cancel of a plan held by an integrity pause, that pause's resolution _abort_, which ends the plan as `aborted` with the operator's reason (<<outcomes>>).

[#review]
== Reviewing Findings or Watches

The review goes through the items of one register (`review.open`), one at a time, open ones first (`review.item`); the list beside it shows each item's disposition so far.

----
  relay-hardening · findings review                               3 of 7 decided
  ─────────────────────────────────────────────────────────────────────────────
  F-0004  Reconnect loses the last event                                   open
  ─────────────────────────────────────────────────────────────────────────────
  Statement   After a reconnect the relay resends from the stored cursor, but
              the cursor is written after the event is delivered.
  Rules       a fix must hold for every transport; covered by a test that
              drops the connection between delivery and cursor write
  Origin      landing of relay-reconnect (#211) · 2 days ago
  Proposal    Promote to a plan: it needs a change across two modules
              (the planning role)
  ─────────────────────────────────────────────────────────────────────────────
  [Keep ▾ as a finding | to the watches]  [Drop]  [Promote to a plan]  [Edit]
  [Chat]                      [Accept the remaining 4 proposals]   [Finish]
----

* *Keep* (`review.keep`) keeps the item as a finding (to be fixed) or moves it to the watches (to be checked again); in a review of the watches it keeps the item as a watch or moves it to the findings. The item's register is preselected.
* *Drop* (`review.drop`) asks for the reason in one line.
* *Promote to a plan* shows the planning role at work (`review.draft-plan`), then its draft of the staged plan (objective, deliverables, surface, dependencies) with _Stage it_, _Edit_, and _Back_ (`review.confirm-plan`). _Edit_ asks what to change in the draft (`review.instruct-plan`), the planning role drafts the plan again (`review.redraft-plan`), and the read-back shows the plan old against new (`review.read-back-plan`): _Accept_ returns to the confirmation with the new draft, _Instruct again_ asks again, _Discard_ returns with the draft before. _Stage it_ stages the row and returns to the item, promoted.
* *Edit* asks what to adapt or add, in the operator's words (`review.instruct`); the planning role rewrites the statement and the rules (`review.rewrite`), and the read-back shows old against new (`review.read-back`): _Accept_ applies the change and returns to the item, _Instruct again_ asks again, _Discard_ returns to the item unchanged.
* *The operator's words* in _Edit_ and _Chat_ are not interpreted: the planning role works from them, and only what it proposes passes a read-back before it applies.
* *Chat* opens the chat (<<chat>>) about this item or the whole register; an accepted change becomes the item's disposition or its rewrite.
* *Accept the remaining proposals* lists them all once, each with its proposal, for one confirmation.
* *An item from outside the machine* (a finding from a review comment) carries `untrusted`, and its text is shown as text, never rendered.
* *Finish* (`review.commit`) writes the decisions to the epic's ledger, where they are landed; leaving before keeps them, and the review opens where it stopped, in either client.

[#chat]
== Chatting with the Planning Role

In a chat the operator discusses a plan or an epic with its planning role, asks, and has it propose changes. It is one dialogue wherever it is opened: from a plan's actions (the whole plan), from an epic's actions (the whole epic), from the decomposition (the draft, link:starting-work.adoc#decomposition[The Decomposition]), and from a review (one item or the whole register, <<review>>), and in the three places of <<chat-places>>: inside a decision, while starting, and about ended work. The runtime routes it: a plan's chat to the plan's planning role `replan`, an epic's chat, also in its decomposition and its review, to the epic's planning role `decompose`.

----
  Chat · fix-relay · with replan                                 the whole plan
  ─────────────────────────────────────────────────────────────────────────────
  You      Can the cursor test also cover the SSE transport?
  replan   Yes. TASK-4 tests one transport only; I propose a second test.
  ─────────────────────────────────────────────────────────────────────────────
  Proposed change                              applies after the current task
  - TASK-4  cursor write order: a test for the websocket transport
  + TASK-4  cursor write order: a test per transport, websocket and SSE
  Its epic   relay-hardening is told
                                                         [Reject]  [Accept]
  ─────────────────────────────────────────────────────────────────────────────
  [Your message                                                 ]  [Send]
                                                                [End the chat]
----

* *The head* names the subject, the role the chat goes to, and the scope; opening it (`chat.open`) gives the role the facts of the subject as data, and is refused with the reason where the role does not qualify.
* *The message field* is the chat's operator wait (`chat.turn`): each message goes to the role (`chat.reply`), whose answer joins the transcript.
* *The transcript* shows the operator's messages and the role's answers in order, the newest at the bottom; while the role works, its line says so (`replan answers`). The operator's messages are not interpreted: the role answers them, and they are never read back. The role reads the content of the plan or the epic as data, and an item from outside the machine stays marked `untrusted` and is shown as text, never rendered.
* *A proposed change* is the one thing read back (`chat.read-back`, link:../../../../plan-marshall-documentation/doc/specification/model-work/06-envelopes-questions-deadlines.adoc#own-words[Own Words]): old against new, in one sentence beside the operator's message it answers, with _Accept_ and _Reject_; nothing changes without _Accept_, and a rejected change is gone. To have it otherwise, the operator says so in the next message.
* *Accept* (`chat.apply`) applies the change through the subject's own path and its checks: in the decomposition the draft and its checks; in a review the item's disposition or rewrite; on an epic its staged plans, through the epic's checks (surfaces disjoint, dependencies without a cycle); on a plan a revision, through the guards of a first plan (the outline, the derivation, the task graph, the Q-Gate), which makes a new version of the plan (`the plan's version becomes 8`). A check that fails says why and changes nothing; the chat goes on.
* *A running plan* goes on while the chat runs: a question never touches it, and an accepted revision takes effect at the next task boundary (`applies after the current task`): what runs finishes, the revision is applied, and the plan runs on. A pausing plan takes it at that boundary too and then holds at its point; a paused plan takes it when the operator starts it again (`applies when fix-relay starts again`).
* *When a revision is proposed*: the role proposes a revision of a plan only in Phase 5 (`execute`) or in finalize before the merge; earlier, while the plan is still being written, and after the merge, it answers and proposes none, and the chat says so once (`fix-relay proposes no change yet: a revision comes in execute or in finalize, until its merge`).
* *Its phase*: a chat opened on a plan is the sub-workflow `chat` called within the phase the plan is in, and has that phase from its call stack; the plan view shows it there like every sub-workflow (link:plan-view.adoc#kinds[Phase, Sub-Workflow, State]).
* *A chat's revision is the operator's own act*: it spends nothing of the plan's re-planning budget, and the runtime never opens a chat by itself. A change to a plan of an epic tells the epic (<<epic-told>>).
* *End the chat* closes it (`chat.end`); a proposal not yet accepted is dropped with it. The transcript is kept with the plan or the epic, among its events, and is never sent elsewhere.
* *Chat is disabled* with its reason while no configuration of the routed role qualifies (`no configuration of replan qualifies yet`).
* *In the web app* the chat is a panel beside the view it was opened from (the plan view, the epic view, the decomposition, the review), the message field at its bottom; at phone width it takes the screen, and _End the chat_ returns to the view.

[#chat-places]
=== The Same Chat in Three More Places

Each place changes only the chat's scope, the role it is routed to, and what an accepted proposal does there; the dialogue, the read-back of every proposal, and the rule that nothing changes without _Accept_ are those above.

[cols="2,3,2,4",options="header"]
|===
|Place |Scope |Role |What a proposal does

|Inside a decision, at `decision.answer` (link:decisions.adoc#chat[A Chat Before Answering])
|the decision: question, why now, evidence, what it blocks, reversibility, parts and options, the recommendation and the votes
|the role of the task that asked; for one a server rule raised or a quorum escalated, `replan` or `decompose`
|a proposed answer becomes the operator's own words and goes through `decision.interpret` and `decision.read-back`; a revision is applied as on a plan, and the decision stays open unless the revision removes the need for it. The chat never answers.

|While starting, at `start.sources` (link:starting-work.adoc#chat[Chatting About the Request])
|the entry: its stored sources, untrusted ones marked, and its description
|`refine` for a plan, `decompose` for an epic; not for a recipe
|a rewrite of the description or an addition to it, stored through `start.store-description`; never another source

|About ended work (<<chat-ended>>)
|the archived record: outcome, reason, history, decisions, re-planning records, events
|`replan` for a plan, `decompose` for an epic
|a follow-up plan: its description, which opens the start of a new plan; the archive never changes
|===

[#chat-ended]
=== A Chat About Ended Work

An ended plan or epic offers one action, _Chat_: a read-only chat about how it went (`why was it handed back?`, `what did the re-planning decide?`). It is opened from the ended work's row, from the ended plan view, and from the ended epic view (link:plan-overview.adoc#ended[Ended Work]).

----
  Chat · codeberg-issues · with replan                        its archived record
  ─────────────────────────────────────────────────────────────────────────────
  You      Why was it cancelled, and what would a new attempt need?
  replan   You cancelled it: replaced by relay-v2. Its outline was done; the
           provider's tests waited for the relay's new event API.
  ─────────────────────────────────────────────────────────────────────────────
  Proposed follow-up plan                 read only: the archive stays as it is
  + Add the Codeberg issue provider on top of relay-v2.
  + follows codeberg-issues, cancelled: replaced by relay-v2
                                               [Reject]  [Start a plan with it]
----

* *Scope and role*: the archived record, read from the archive: the outcome, the reason, the history, the decisions, the re-planning records, the events. An ended plan's chat goes to `replan`, an ended epic's to `decompose`; it runs at the project's scope and never changes the archive.
* *The one proposal is a follow-up plan*: a description drafted in the chat that names the ended plan or epic, read back. _Start a plan with it_ ends the chat and opens the start of a new plan in the same project with that description stored (link:starting-work.adoc#sources[The List of Sources]); the operator goes on from ① Sources as with any start, and nothing starts before _Start the plan_.
* *The transcript* is kept beside the archive entry, outside the archived record, which stays as it ended.
* *Disabled* with its reason while no configuration of the routed role qualifies, as every chat.
