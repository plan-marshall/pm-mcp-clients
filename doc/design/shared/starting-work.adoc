Status: `DRAFT`. Shared by both clients: link:../terminal-client/18-starting.adoc[Terminal Client, Starting Work], link:../web-app/README.adoc[Web App].

Starting a plan or an epic is one guided run in which the operator only says what the work comes from. The server gathers each source, stores it, and screens what came from outside; the client shows each source's progress as a check line, like the onboarding's (link:project-onboarding.adoc[Project Onboarding]). Everything else the work needs is asked later, where it is needed.

[#steps]
== Steps

----
  a plan:    ① Sources ─ ② Ready ─ ✓ Started
  an epic:   ① Sources ─ ② Ready ─ ✓ Started ─ ③ Decomposition
----

* *The setup gate* (`start.open`, `start-epic.open`): starting is offered only on an onboarded machine and in a ready project. Where either is missing, the start opens on the refusal instead of ①: what is missing (`this machine is not fully onboarded: providers`, `pm-mcp-clients is not ready: credential sonar`) and the one action that goes on there (_Continue the onboarding_, _Continue the setup_); nothing of an entry is created.

* *① Sources* (`start.sources`, `start-epic.sources`): the list of the sources so far, and the ways to add one (<<sources>>). A plan first shows the choice between _from sources_ and _a recipe_ (`start.choose`), only where the project has a recipe; an epic starts from sources only.
* *② Ready* (`start.ready`, `start-epic.ready`): what the work starts from, one line per source; the title and the id proposed from the sources, both editable; _Start the plan_ or _Start the epic_.
* *Creating* (`start.create`, `start-epic.create`): the server checks again what creation needs. Where something changed meanwhile (the id was taken, a source is gone or changed, a lesson was claimed by another plan, the gate no longer holds), nothing is created and the run returns to ② with the cause on the line concerned (`could not be created: the id codeberg-provider-issues is taken`).
* *✓ Started*: the plan or the epic exists, with _Follow it_ (a plan's view, link:plan-view.adoc[Plan View]; an epic's view, link:epic-view.adoc[Epic View]) and _Back to the project_.
* *③ Decomposition* (an epic only, `decomposition`): after the epic has started, the cut of the epic into workstreams and plans, drafted by the planning role and shaped by the operator before anything is committed (<<decomposition>>). The run goes on into it from ✓; _Follow it_ leads to the epic view, where the decomposition stands first as what waits for the operator.

[#sources]
== The List of Sources

----
  Start a plan in pm-mcp-clients                              ① Sources ─ ② Ready
  ─────────────────────────────────────────────────────────────────────────────
  What does the plan start from?

    ✓  Description   "Add a Codeberg provider for issues"           stored
    ✓  Documents     doc/concepts/forgejo.adoc, 1 file              copied
    ▶  Issue         https://codeberg.org/forgejo/forgejo/issues/4711         screening
    ✗  Issue         https://github.com/plan-marshall/pm-mcp-clients/issues/212
                                                not found   [Try again] [Remove]

  + Description   + Documents   + Issue   + Lesson   + Local changes   + Pull request
  ─────────────────────────────────────────────────────────────────────────────
                                                      [Continue]  (waits for 1 source)
----

* *A source's line*: its kind, what it is (the start of a description, the paths, an issue's reference and, once fetched, its title), and its state: `checking`, `fetching`, `screening`, `stored`, `copied`, `moved`, `flagged`, or the cause of a failure with _Try again_ and _Remove_. A stored source can be removed until the start.
* *What may be added*: an epic offers description, documents, and issue; a plan also lesson (only when the project has unclaimed lessons), local changes (only when the checkout has some), and pull request. A plan with local changes or a pull request takes no issue and no lesson besides, and the line says why another kind is not offered (`a plan that adopts a pull request takes only descriptions and documents besides`).
* *Continue* is offered once there is at least one source and every source is stored, screened or accepted; until then it names what it waits for.
* *Trust*: a source from outside the machine shows `untrusted` until its screening passed, then nothing; the operator's own sources never show a mark.
* *States*: each kind of source is a sub-workflow of its own, and its states are named `source-<kind>.<state>` (`source-documents`, `source-issue`, `source-pr`, `source-lesson`, `source-local-changes`); each subsection names those it shows.

[#adopt]
=== Adopting an Epic from Elsewhere

Where the project's ledger holds an epic that does not run on this machine (another machine started it), `start-epic.open` offers it before ①, instead of a new one: `relay-hardening is in the ledger of pm-mcp-clients but does not run on this machine`, with _Adopt relay-hardening_ and _Start a new epic_. Adopting takes no sources: the epic's store on this machine is created from its ledger, and the run ends at ✓ with _Follow it_.

[#description]
=== A Description

An editor of several lines: the operator writes what the work is. _Add_ stores it as a source; several descriptions are several sources. The text is the operator's, never screened (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#change-local-trusted[What Is on This Machine Is Trusted]).

[#documents]
=== Documents

* *Picking* (`source-documents.pick`): files or one directory. The web app browses the checkout first, then the operator's home directory, through the server's listing; the terminal client takes paths, completed against its working directory. A directory shows what it holds (`12 files: 9 adoc, 3 svg`) before it is added.
* *Checked* (`source-documents.check`): each file with a check line; a file that cannot be used names its cause (`not readable`, `larger than 10 MB`, `a link that leads outside`), and the others can be added without it.
* *Copy or move* (`source-documents.mode`): the machine's default chosen, _always_ beside it; then stored (`source-documents.store`).
* *Only from this machine*: the listing, a move, and documents outside the checkout are accepted only from the terminal client and from a browser on the loopback listener. On a device of the network the web app offers the checkout's files by copy only: _Move_ and the operator's home directory are shown disabled with their reason (`only on this machine: a move deletes your files, and your home directory is not shown to other devices`).
** *Copy*: the originals stay where they are; the copy is not kept in step with them, and the dialogue says so.
** *Move*: the documents leave where they were. A file git tracks is removed from git by a short landing (`git.land-removal`, one commit landed as the project lands); the source's line shows `moved · removing from git`, then `moved`, and the work may start meanwhile. Until it is landed, the landing is a row of the project's running work; if it fails, it waits for the operator there.

----
  Copy or move the documents?
    (●) Copy     they stay where they are; the copy is not kept in step   ← the machine's default
    ( ) Move     they leave where they are
    [ ] Always do this, don't ask again
    With Move, 3 files tracked by git are removed from git by a short landing.
                                                                   [Add documents]
----

[#issue]
=== An Issue

* *Naming* (`source-issue.name`, `source-issue.resolve`): one field that takes a number (`212`, `#212`: the project's own repository) or a URL; a number is shown at once as the URL of the issue in the project's repository, and the URL is what is stored and shown from then on, also for a pull request. The field takes a URL of GitHub, GitLab, or a Forgejo forge such as Codeberg; the forge is shown as soon as it is recognised (`Codeberg · forgejo/forgejo`).
* *Another repository* asks first (`source-issue.grant`): _Read issues of forgejo/forgejo?_ with _this time_, _for this project_, and _No, remove it_; a forge without a credential says that only a public issue can be read, and where a credential is added.
* *Progress* (`source-issue.fetch`, `source-issue.store`, `source-issue.screen`): `fetching`, then `screening`, each as a check line; then the issue's title, labels, and state.
* *Failed* (`source-issue.failed`): the cause (`not found`, `not readable`, `provider unavailable`) with _Try again_ and _Remove it_.
* *Flagged* (`source-issue.flagged`): the spans the screener flagged, quoted as text with their reason, and _Use it anyway_ (with a reason, which is recorded) or _Remove it_. The flagged text is never rendered as Markdown and its links are inert.

[#lesson]
=== A Lesson

* *Choosing* (`source-lesson.choose`): the unclaimed lessons of the project, newest first, each with its title and when it was recorded.
* *Checked* (`source-lesson.resolve`): the lesson is read and its premise checked against the checkout, as a check line.
* *Unavailable*: a lesson claimed by another plan meanwhile, retired, or in a damaged store shows the cause (`claimed by another plan`, `retired`, `the lesson store is damaged`) with _Choose another_.
* *Its premise no longer holds* (`source-lesson.premise`): the evidence (`ConfigLoader.java no longer exists`) with _Use it anyway_ (the evidence goes into the plan), _Retire it_, and _Remove it_.
* *Stored* (`source-lesson.store`): the lesson is claimed for the plan when the plan is created.

[#local-changes]
=== Local Changes

* *Preview* (`source-local-changes.preview`): what the checkout has changed against its branch, as files with their counts of lines.
* *Confirm* (`source-local-changes.confirm`): _Add the local changes_, or _Not now_, which leaves the list as it was.
* *Stored* (`source-local-changes.store`): the preview is recorded; the changes are captured when the plan is created. A change made in the checkout after the preview is captured with the rest, and the creation names it (`2 files changed since the preview; captured with the rest`).

[#pull-request]
=== A Pull Request

* *Naming* (`source-pr.name`): one field that takes a number or the URL of a pull request of the project's own repository; a number is shown at once as its URL, and the URL is what is stored and shown.
* *Checked* (`source-pr.observe`): fetched and checked as check lines: it is open, its head branch is writable by the agent identity.
* *Failed* (`source-pr.failed`): the cause (`not open`, `its head branch is not writable`, `not found`) with _Try again_ and _Remove it_.
* *Screened* (`source-pr.store`, `source-pr.screen`): like an issue; then shown with its title and its changed files.
* *Flagged* (`source-pr.flagged`): as a flagged issue (<<issue>>): the spans with their reason, _Use it anyway_ (with a reason) or _Remove it_.

[#ready]
== Ready

----
  Start a plan in pm-mcp-clients                              ① Sources ─ ② Ready
  ─────────────────────────────────────────────────────────────────────────────
  The plan starts from
    Description   "Add a Codeberg provider for issues"
    Documents     doc/concepts/forgejo.adoc
    Issue         https://codeberg.org/forgejo/forgejo/issues/4711 · Issue comments API

  Title   [Codeberg provider for issues                         ]
  Id      [codeberg-provider-issues     ]  ← from the title
                                                                 [Start the plan]
----

* The title is proposed from the first description, else from the first issue's title, else from the first document's name; the id from the title, or `issue-<number>` for a plan from one issue alone.
* An id that is taken or refused shows why, with a free proposal (`codeberg-provider-issues-2`).
* *What is not asked here*: posture, base branch, outline review, how many plans an epic runs at once. Each is asked where the plan or the epic first needs it, and not at all where the project or the machine sets it; the operator meets it as a decision (link:decisions.adoc[Decisions]). How many plans an epic runs at once is asked when its first plan is to start, only where the project sets no `epic.parallelization_scope`.

[#recipe]
== A Recipe

* *Choosing* (`recipe.choose`): the project's recipes, each with its name, what it does in one line, and where it comes from (a domain, the project).
* *Parameters* (`recipe.parameters`): one line per parameter, with the options the server resolved (`modules: 9 found`) and its proposal preselected and marked `proposed`, as the onboarding's choices are (link:../web-app/onboarding.adoc[Web App, Onboarding]); then _Run coverage?_ with the parameters as chosen, and _Run the recipe_.
* *A recipe that takes a request* asks its parameters first, then its sources, as in <<sources>>, and runs from there.
* *Started*: the plan, its id from the recipe and the time (`recipe-coverage-2026-10-12-14-05-00`).

[#decomposition]
== The Decomposition

----
  relay-hardening · decomposition                 ① ─ ② ─ ✓ ─ ③ Decomposition
  ─────────────────────────────────────────────────────────────────────────────
  ▾ WS-1  Reconnect                                       3 plans
      ✓  relay-reconnect-backoff      objective · 4 deliverables · pm-relay
      ✓  relay-cursor-order           objective · 2 deliverables · pm-relay, pm-api
      ●  relay-reconnect-docs         edited — accept or discard the change
  ▾ WS-2  Authentication                                  2 plans
      ✗  relay-auth-v2                surface overlaps relay-cursor-order (pm-api)
      ○  relay-token-rotation         after relay-auth-v2
  ─────────────────────────────────────────────────────────────────────────────
  [+ Add a plan]  [Chat]  [Draft again…]                 [Agree]  (1 check fails)
----

* *The draft* is shown while the planning role works on it, workstream by workstream, as in the onboarding's progress (`drafting WS-2`).
* *A plan* opens to its objective, deliverables, expected surface, dependencies, and order, with _Keep_, _Edit_, and _Drop_. _Edit_ and _Add a plan_ ask for the operator's words; the planning role rewrites or drafts, and the read-back shows old against new with _Accept_, _Instruct again_, and _Discard_.
* *The checks* of the server are marks on the plans concerned (`✗` with the reason); _Agree_ is disabled while one fails and says how many.
* *Chat* opens the chat with the epic's planning role about the whole draft (link:work-actions.adoc#chat[Chatting with the Planning Role]); an accepted change goes into the draft, and the checks run on it again.
* *Draft again* asks for an instruction and replaces the draft, keeping what the operator decided where the plan is still in it.
* *Leaving* keeps the draft and the decisions made on it; the review continues where it stopped, in either client. The epic starts no plan before its first decomposition is agreed.
* *A later run* (_Decompose again_, or the epic's own recut) shows the shipped, running, pausing, and paused plans locked and greyed (a paused plan is the operator's to start or abandon, never the decomposition's), and marks each staged plan as `unchanged`, `changed`, `new`, or `dropped`, a change opening to old against new.
* *Agree* is enabled once every check passes (`every check passes`); it commits the cut (`committed`), and the epic then starts the plans that can start.

[#leaving]
== Leaving and Coming Back

The entry waits with its sources while the operator is away, in either client; a source still being fetched or screened goes on. The project's actions show _Continue starting_ (with the entry's kind and its number of sources) as their first action while an entry is open, and _Abandon_ deletes the entry and its source directory.
