Status: `DRAFT`. Shared by both clients: link:../terminal-client/18-starting.adoc[Terminal Client, Starting Work]; the web app's view: designed by its package link:../../plans/web-start.adoc[`web-start`].

Starting a plan or an epic is one guided run in which the operator only says what the work comes from. The server gathers each source, stores it, and screens what came from outside; the client shows each source's progress as a check line, like the onboarding's (link:project-onboarding.adoc[Project Onboarding]). Everything else the work needs is asked later, where it is needed.

[#steps]
== Steps

----
  a plan:    ① Sources ─ ② Ready ─ ✓ Started
  an epic:   ① Sources ─ ② Ready ─ ✓ Started ─ ③ Decomposition
----

* *The setup gate* (`start.open`, `start-epic.open`): starting is offered only on an onboarded machine and in a ready project. Where either is missing, the start opens on the refusal instead of ①: what is missing (`this machine is not fully onboarded: providers`, `pm-mcp-clients is not ready: credential sonar`) and the one action that goes on there (_Continue the onboarding_, _Continue the setup_); nothing of an entry is created.

* *① Sources* (`start.sources`, `start-epic.sources`): the list of the sources so far, and the ways to add one (<<sources>>). A plan first shows the choice between _from sources_ and _a recipe_ (`start.choose`), only where the project has a recipe; an epic starts from sources only.
* *② Ready* (`start.ready`, `start-epic.ready`): what the work starts from, one line per source; the title and the id proposed from the sources, both editable; _Start the plan_ or _Start the epic_. A recipe passes it too (<<recipe>>). Where the project's landing does not fit the sources, it is refused here with the reason (<<landing-refused>>).
* *Creating* (`start.create`, `start-epic.create`, `recipe.create`): the server checks again what creation needs. Where something changed meanwhile (the id was taken, a source is gone or changed, a lesson was claimed by another plan, a recipe is gone or changed, the gate no longer holds), nothing is created and the run returns to ② with the cause on the line concerned (`could not be created: the id codeberg-provider-issues is taken`).
* *✓ Started*: the plan or the epic exists, with _Follow it_ (a plan's view, link:plan-view.adoc[Plan View]; an epic's view, link:epic-view.adoc[Epic View]) and _Back to the project_.
* *③ Decomposition* (an epic only, `decomposition`): after the epic has started, the cut of the epic into workstreams and plans, drafted by the planning role and shaped by the operator before anything is committed (<<decomposition>>). The run goes on into it from ✓; _Follow it_ leads to the epic view, where the decomposition stands first as what waits for the operator.

[#sources]
== The List of Sources

----
  Start a plan in pm-mcp-clients                              ① Sources ─ ② Ready
  ─────────────────────────────────────────────────────────────────────────────
  What does the plan start from?

    ✓  Description   "Add a Codeberg provider for issues"           stored
    ✓  Documents     doc/concepts/forgejo.adoc, 1 file              copied
    ▶  Issue         https://codeberg.org/forgejo/forgejo/issues/4711         screening
    ✗  Issue         https://github.com/plan-marshall/pm-mcp-clients/issues/212
                                                not found   [Try again] [Remove]

  + Description   + Documents   + Issue   + Lesson   + Local changes   + Pull request
  ─────────────────────────────────────────────────────────────────────────────
  [Chat]                                              [Continue]  (waits for 1 source)
----

* *A source's line*: its kind, what it is (the start of a description, the paths, an issue's reference and, once fetched, its title), and its state: `checking`, `fetching`, `screening`, `stored`, `copied`, `moved` (while a moved source's removal lands, `moved · removing from git`, `start.state.removing_from_git`; with `landing.files`, `moved · removal left uncommitted`, `start.state.removal_uncommitted`), `flagged`, `unscreened`, or the cause of a failure with _Try again_ and _Remove_. A stored source can be removed until the start.
* *What may be added*: an epic offers description, documents, and issue; a plan also lesson (only when the project has unclaimed lessons), local changes (only when the checkout has some), and pull request. `start.sources` offers only the kinds that combine with those already in the list: a pull request or the local changes only beside descriptions and documents, and never both; so once an issue or a lesson is in the list neither is offered, and once one of them is in it, no issue, lesson, or the other. The line says why a kind is not offered (`a plan that adopts a pull request takes only descriptions and documents besides`).
* *Continue* is offered once there is at least one source and every source is stored, screened or accepted (a flagged one with its reason, an unscreened one as untrusted); until then it names what it waits for.
* *Trust*: a source from outside the machine shows `untrusted` until its screening passed, then nothing; a source accepted while unscreened keeps the `untrusted` mark. The operator's own sources never show a mark.
* *Chat* opens a chat about the request before it starts (<<chat>>), once at least one source is stored and every source from outside the machine is screened; until then it is disabled with that reason.
* *States*: each kind of source is a sub-workflow of its own, and its states are named `source-<kind>.<state>` (`source-documents`, `source-issue`, `source-pr`, `source-lesson`, `source-local-changes`); each subsection names those it shows.

[#adopt]
=== Adopting an Epic from Elsewhere

Where the project's ledger holds an epic that does not run on this machine (another machine started it), `start-epic.open` offers it before ①, instead of a new one: `relay-hardening is in the ledger of pm-mcp-clients but does not run on this machine`, with _Adopt relay-hardening_ and _Start a new epic_. Adopting takes no sources: the epic's store on this machine is created from its ledger, and the run ends at ✓ with _Follow it_.

[#description]
=== A Description

An editor of several lines: the operator writes what the work is. _Add_ stores it as a source; several descriptions are several sources. The text is the operator's, never screened (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#change-local-trusted[What Is on This Machine Is Trusted]).

[#documents]
=== Documents

* *Picking* (`source-documents.pick`): files or one directory. The web app browses the checkout first, then the operator's home directory, through the server's listing; the terminal client takes paths, completed against its working directory. A directory shows what it holds (`12 files: 9 adoc, 3 svg`) before it is added.
* *Checked* (`source-documents.check`): each file with a check line; a file that cannot be used names its cause (`not readable`, `larger than 10 MB`, `a link that leads outside`), and the others can be added without it.
* *Copy or move* (`source-documents.mode`): asked only while the machine's `sources.documents_mode` is `ask`, its default; _Copy_ is preselected. _Always_ stores the choice as the machine's `copy` or `move`, after which the step is not asked and the line just says `copied` or `moved`; the machine's settings set it back to `ask` (link:../web-app/machine-settings.adoc[Web App, Machine Settings], link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-10[UC-ONB-10]). Then stored (`source-documents.store`).
* *Only from this machine*: the listing, a move, and documents outside the checkout are accepted only from the terminal client and from a browser on the loopback listener. On a device of the network the web app offers the checkout's files by copy only: _Move_ and the operator's home directory are shown disabled with their reason (`only on this machine: a move deletes your files, and your home directory is not shown to other devices`).
** *Copy*: the originals stay where they are; the copy is not kept in step with them, and the dialogue says so.
** *Move*: the documents leave where they were. A file git tracks is removed from git by a short landing (`git.land-removal`, one commit landed by the project's landing, `landing.pull-request` or `landing.main`); the source's line shows `moved · removing from git`, then `moved`, and the work may start meanwhile. Until it is landed, the landing is a row of the project's running work; if it fails, it waits for the operator there. With `landing.files` nothing is committed: the removal stays in the working tree, and the line says so (`moved · removal left uncommitted`). A release of the project waits for a removal still landing (link:project-explorer.adoc#release[Project Explorer, Release and Unenrol]).

----
  Copy or move the documents?
    (●) Copy     they stay where they are; the copy is not kept in step   ← preselected
    ( ) Move     they leave where they are
    [ ] Always do this, don't ask again (the machine's settings change it)
    With Move, 3 files tracked by git are removed from git by a short landing.
                                                                   [Add documents]
----

[#issue]
=== An Issue

* *Naming* (`source-issue.name`, `source-issue.resolve`): one field that takes a number (`212`, `#212`: the project's own repository) or a URL; a number is shown at once as the URL of the issue in the project's repository, and the URL is what is stored and shown from then on, also for a pull request. The field takes a URL of GitHub, GitLab, or a Forgejo forge such as Codeberg; the forge is shown as soon as it is recognised (`Codeberg · forgejo/forgejo`).
* *Another repository* asks first (`source-issue.grant`): _Read issues of forgejo/forgejo?_ with _this time_, _for this project_, and _No_; _No_ fails the source with the cause `not granted` (`source-issue.failed`).
* *A forge without a credential* fetches without one: a public issue is read, the line saying `no credential for Codeberg: only a public issue can be read`; another fails with the cause `no credential for Codeberg`, naming where a credential is added.
* *Progress* (`source-issue.fetch`, `source-issue.store`, `source-issue.screen`): `fetching`, then `screening`, each as a check line; then the issue's title, labels, and state.
* *Failed* (`source-issue.failed`): the cause (`not found`, `not readable`, `not granted`, `no credential for <forge>`, `rate limited until <time>`, `provider unavailable`) with _Try again_ and _Remove it_.
* *Rate limited*: a fetch the forge refuses for its rate limit, with or without a credential, fails with the cause `rate_limited` and the time the limit resets (`resets_at`): `rate limited until 14:40`. It is not retried by itself; the operator tries again then, or, where it ran without a credential, adds one for the forge, whose limit is higher (link:../web-app/machine-settings.adoc#credentials[Machine Settings, Credentials]; terminal `config credentials`), and the line says so (`add a credential for Codeberg for a higher limit`).
* *Flagged* (`source-issue.flagged`): the spans the screener flagged, quoted as text with their reason, and _Use it anyway_ (with a reason, which is recorded) or _Remove it_. The flagged text is never rendered as Markdown and its links are inert.
* *Unscreened* (`source-issue.unscreened`): the screening fails closed. Where the screener failed, or no configuration of the role `screener` qualifies, the source stays unscreened with the cause (`the screening failed: <cause>`, `no configuration of the role screener qualifies`) and no model reads it; _Try again_, _Remove it_, or _Accept it as untrusted_ (with a reason, which is recorded like that of a flagged source). An accepted source keeps its `untrusted` mark (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#change-screen-stored[Screened Once Stored]).

[#lesson]
=== A Lesson

* *Choosing* (`source-lesson.choose`): the unclaimed lessons of the project, newest first, each with its title and when it was recorded.
* *Checked* (`source-lesson.resolve`): the lesson is read and its premise checked against the checkout, as a check line.
* *Unavailable*: a lesson claimed by another plan meanwhile, retired, or in a damaged store is not stored; the choice (`source-lesson.choose`) is shown again with the cause (`claimed by another plan`, `retired`, `the lesson store is damaged`), to choose another lesson or leave the choice.
* *Its premise no longer holds* (`source-lesson.premise`): the evidence (`ConfigLoader.java no longer exists`) with _Use it anyway_, which stores the lesson with the evidence (`source-lesson.store`), _Retire it_, which retires it in the lesson store, and _Remove it_, which leaves it as it is for a later plan; after either of the two nothing is added.
* *Stored* (`source-lesson.store`): the lesson is claimed for the plan when the plan is created. It is retired when the plan lands its changes (the merge of `landing.pull-request`, the push of `landing.main`), and released when the plan ends without landing them (handed back with `landing.files`, cancelled, abandoned, released, or aborted).

[#local-changes]
=== Local Changes

* *Preview* (`source-local-changes.preview`): what the checkout has changed against its branch, as files with their counts of lines.
* *Confirm* (`source-local-changes.confirm`): _Add the local changes_, or _Not now_, which leaves the list as it was.
* *Stored* (`source-local-changes.store`): the preview is recorded; the changes are captured as a snapshot commit when the plan is created, and the plan takes the land lane and lands them by the project's landing. A change made in the checkout after the preview is captured with the rest, and the creation names it (`2 files changed since the preview; captured with the rest`).
* *None left*: where the checkout has no local changes any more when the preview runs, the source fails with that cause (`the checkout has no local changes any more`), to be removed.
* *A landing that commits*: a plan from the local changes needs a landing that commits them; with the project's `landing.files` it is refused at ② (<<landing-refused>>).

[#pull-request]
=== A Pull Request

* *Naming* (`source-pr.name`): one field that takes a number or the URL of a pull request of the project's own repository; a number is shown at once as its URL, and the URL is what is stored and shown.
* *Checked* (`source-pr.observe`): fetched and checked as check lines: it is open, its head branch is writable by the agent identity.
* *Failed* (`source-pr.failed`): the cause (`not open`, `its head branch is not writable`, `not found`, `rate limited until <time>` as for an issue, <<issue>>) with _Try again_ and _Remove it_.
* *Stored and screened* (`source-pr.store`, `source-pr.screen`): its title and body like an issue's; its changed files are stored as the pull request's head and are code from outside, possibly from a fork: the line shows them marked `untrusted` (`3 changed files · untrusted`) unless the operator authored the pull request. They are never screened and never read by a model as instructions; the plan's own gates (its review, its integrity checks) apply to them as to every change it lands (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#change-local-trusted[What Is on This Machine Is Trusted]).
* *Flagged* (`source-pr.flagged`) and *unscreened* (`source-pr.unscreened`): as an issue's (<<issue>>): _Use it anyway_ or _Accept it as untrusted_ (each with a reason), _Try again_ where unscreened, or _Remove it_.

[#chat]
=== Chatting About the Request

At `start.sources` (`start-epic.sources`) the operator may talk the request through with the role that will plan it before it starts: what the model understood, what is unclear, what is out of scope (link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#UC-STA-1[UC-STA-1], link:../../../../plan-marshall-documentation/doc/use-cases/05-starting-work.adoc#UC-STA-2[UC-STA-2]). It is the one chat of both clients (link:work-actions.adoc#chat[Chatting with the Planning Role]); only its scope, its role, and what a proposal does differ.

----
  Chat · a new plan in pm-mcp-clients · with refine                  the request
  ─────────────────────────────────────────────────────────────────────────────
  You      What did you understand, and what is unclear?
  refine   A provider that reads Codeberg issues. Unclear: comments too, and
           should pull requests of Codeberg follow?
  ─────────────────────────────────────────────────────────────────────────────
  Proposed addition to the description
  + Comments are read with the issue. Pull requests of Codeberg are out of
  + scope for this plan.
                                                         [Reject]  [Accept]
----

* *Scope*: the entry: its stored sources, those from outside the machine marked `untrusted` and read as data, and its description. Nothing of a plan exists yet; the head names the entry (`a new plan in pm-mcp-clients`).
* *Role*: a plan's entry goes to `refine`, an epic's to `decompose`. _Chat_ is disabled with its reason while no configuration of the role qualifies, and is not offered for a recipe.
* *The one change it may propose is the description*: a rewrite of one description of the entry, or an addition to it, read back old against new. _Accept_ stores it through the start's own path (`start.store-description`), as the operator's description; where the entry has no description yet, an addition becomes its first. A start chat never changes, adds, or removes another source.
* *Optional*: starting never waits for a chat, and _Continue_ stays as it is while a chat is open; leaving the entry keeps the chat with it.
* *The transcript* stays with the entry and goes with its source directory to the plan or the epic at `start.create`, kept for audit and not a source the work reads; abandoning the entry deletes it.
* *In the web app* the chat is the panel beside the list of sources, as beside a plan view.

[#ready]
== Ready

----
  Start a plan in pm-mcp-clients                              ① Sources ─ ② Ready
  ─────────────────────────────────────────────────────────────────────────────
  The plan starts from
    Description   "Add a Codeberg provider for issues"
    Documents     doc/concepts/forgejo.adoc
    Issue         https://codeberg.org/forgejo/forgejo/issues/4711 · Issue comments API

  Title   [Codeberg provider for issues                         ]
  Id      [codeberg-provider-issues     ]  ← from the title
                                                                 [Start the plan]
----

* The title is proposed from the first description, else from the first issue's title, else from the first document's name; the id from the title, or `issue-<number>` for a plan from one issue alone.
* An id that is taken or refused shows why, with a free proposal (`codeberg-provider-issues-2`).
* *What is not asked here*: posture, base branch, outline review. Each is asked where the plan or the epic first needs it, and not at all where the project or the machine sets it; the operator meets it as a decision (link:decisions.adoc[Decisions]). How many plans an epic runs at once is never asked: a new epic takes the project's `epic.parallelization_scope` (machine default 1); the operator raises it through the epic's _Next plan_, which offers to raise it by one when the scope is full (link:work-actions.adoc#epic-actions[An Epic's Actions]), or in the project's settings.

[#landing-refused]
=== A Landing That Does Not Fit

A plan from the local changes needs a landing that commits them. Where the project's landing is `landing.files`, ② shows the reason in place of _Start the plan_ (`Files only does not fit: a plan from local changes needs a landing that commits`) and offers a landing for this plan alone, `landing.pull-request` or `landing.main`, as the plan's own value, written to its overrides when the plan is created (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-plan-overrides[Plan Overrides]); or the operator goes back to ① and removes the local changes. _Start the plan_ is enabled once the landing fits.

[#recipe]
== A Recipe

* *Choosing* (`recipe.choose`): the project's recipes, each with its name, what it does in one line, and where it comes from (a domain, the project).
* *Parameters* (`recipe.parameters`): one line per parameter, with the options the server resolved (`modules: 9 found`) and its proposal preselected and marked `proposed`, as the onboarding's choices are (link:../web-app/onboarding.adoc[Web App, Onboarding]); then on to ②. A parameter without an option (no module the recipe can work on, no domain of it in the project) shows its reason (`modules: none the recipe can work on`), and the recipe cannot run: the operator chooses another or leaves.
* *A recipe that takes a request* asks its parameters first, then its sources, as in <<sources>>, with their failures and screening; a chat is not offered for a recipe.
* *Ready* (`start.ready`): as for a plan (<<ready>>): the recipe and its parameters, the title and the id proposed from the recipe and the time (`recipe-coverage-2026-10-12-14-05-00`), both editable; _Run the recipe_.
* *Creating* (`recipe.create`): re-checks what creation needs; a recipe gone or changed meanwhile (its domain or the project removed or changed it), an id taken, or a gate that no longer holds returns to ② with the cause, and nothing is created.
* *Leaving* keeps the entry with the recipe and the parameters chosen, in either client; abandoning it deletes the entry (<<leaving>>).

[#decomposition]
== The Decomposition

----
  relay-hardening · decomposition                 ① ─ ② ─ ✓ ─ ③ Decomposition
  ─────────────────────────────────────────────────────────────────────────────
  ▾ WS-1  Reconnect                                       3 plans
      ✓  relay-reconnect-backoff      objective · 4 deliverables · pm-relay
      ✓  relay-cursor-order           objective · 2 deliverables · pm-relay, pm-api
      ●  relay-reconnect-docs         edited — accept or discard the change
  ▾ WS-2  Authentication                                  2 plans
      ✗  relay-auth-v2                surface overlaps relay-cursor-order (pm-api)
      ○  relay-token-rotation         after relay-auth-v2
  ─────────────────────────────────────────────────────────────────────────────
  [+ Add a plan]  [Chat]  [Draft again…]                 [Agree]  (1 check fails)
----

* *The draft* is shown while the planning role works on it, workstream by workstream, as in the onboarding's progress (`drafting WS-2`).
* *A plan* opens to its objective, deliverables, expected surface, dependencies, and order, with _Keep_, _Edit_, and _Drop_ (`decomposition.review`). _Edit_ and _Add a plan_ ask for the operator's words (`decomposition.instruct`); the planning role rewrites or drafts the plan (`decomposition.rewrite`), and the read-back (`decomposition.read-back`) shows old against new with _Accept_ (on to the checks, `decomposition.check`), _Instruct again_ (back to the words, which keep what was written), and _Discard_ (back to the review, the plan as it was).
* *The checks* of the server are marks on the plans concerned (`✗` with the reason); _Agree_ is disabled while one fails and says how many.
* *Chat* opens the chat with the epic's planning role about the whole draft (link:work-actions.adoc#chat[Chatting with the Planning Role]); an accepted change goes into the draft, and the checks run on it again.
* *Draft again* asks for an instruction and replaces the draft, keeping what the operator decided where the plan is still in it.
* *Leaving* keeps the draft and the decisions made on it; the review continues where it stopped, in either client. The epic starts no plan before its first decomposition is agreed.
* *A later run* (_Decompose again_, or the epic's own recut) shows the shipped, running, pausing, and paused plans locked and greyed (a paused plan is the operator's to start or abandon, never the decomposition's), and marks each staged plan as `unchanged`, `changed`, `new`, or `dropped`, a change opening to old against new.
* *Agree* is enabled once every check passes (`every check passes`); it commits the cut (`committed`), and the epic then starts the plans that can start.

[#leaving]
== Leaving and Coming Back

The entry waits with its sources (a recipe's with its parameters) while the operator is away, in either client; a source still being fetched or screened goes on. An entry never expires: it has no time limit, like a decision, and stays among the project's open entries until it is started or abandoned, or deleted with the release of its project. The project's actions show _Continue starting_ (with the entry's kind and its number of sources) as their first action while an entry is open, and _Abandon_ deletes the entry and its source directory.

[#texts]
== Texts

Keys of the area `start`, shared by both clients. They are listed in their own parts: link:starting-work-texts.adoc[Starting Work, Texts] (the steps, ready, the recipe, the decomposition) and link:starting-work-sources-texts.adoc[Starting Work, Texts of the Sources].
