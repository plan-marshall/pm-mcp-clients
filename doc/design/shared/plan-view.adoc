Status: `DRAFT`. Shared by both clients: link:../terminal-client/16-plan-view.adoc[Terminal Client, The Plan View], link:../web-app/README.adoc[Web App].

A plan's process is not a fixed list of phases: it is the plan's composed workflow, whose phases are sub-workflows, which call sub-workflows of their own. The plan view shows that process level by level, each node with its state, from the plan down to the leaves. Everything it shows comes from the runtime's process of the plan; the client derives no state.

[#levels]
== Levels

----
  pm-mcp-clients › relay-hardening › fix-relay
  fix-relay                                   execute · running · 2 h 10 min
  tokens so far   412 k (380 k in · 32 k out)
  ├─ ✓ phase  init                            done · 2 min
  ├─ ✓ phase  refine                          done · 14 min
  ├─ ✓ phase  outline                         done · 31 min
  ├─ ✓ phase  plan                            done · 9 min
  ├─ ▶ phase  execute                         running · 25 min
  └─ ○ phase  finalize                        planned
----

A plan of the land lane calls fewer phases; the land lane is a choice of phases, never a phase of its own, and its `land.*` states run as a sub-workflow within `execute`:

----
  docs-typo                                   execute · running · 3 min
  ├─ ✓ phase  init                            done · 1 min
  ├─ ▶ phase  execute                         running · 2 min
  │    └─ ▶ ↳ sub-workflow  land              running
  ├─ ○ phase  finalize                        planned
  └─   not in this plan: refine, outline, plan (the land lane)
----

* *The head*: the path project › epic › plan, or project › plan for a plan of no epic (<<way-out>>); the plan's title; its current phase; its state, from the closed list of Running Work (link:plan-overview.adoc#item-rows[A Plan, an Epic]): `running`, `pausing` with its point (`pausing after the task`), `paused`, `waiting for you`, `held`; for a held plan the kind of its hold (`holds: a condition`, link:work-actions.adoc#holds[What Holds a Plan]); how long it runs; its own pull request by its number with a link (`#214`); its tokens so far (<<tokens>>); and its actions (link:work-actions.adoc#plan-actions[A Plan's Actions]).
* *The plan*: its phases, the six of `init`, `refine`, `outline`, `plan`, `execute`, `finalize` that the plan unit calls, in the order it calls them, each with its state (done, running, planned, waiting for you, or failed); the phases its composition left out (another lane, a step the project does not need) are a group of their own at the end, each with its reason.
* *A phase, a sub-workflow*: its workflow, opened below it: the states in the order of the workflow, the calls marked as sub-workflows, each with its state; a sub-workflow opens the same way, through every level of nesting.
* *A leaf*: a state that calls nothing; opening it shows what runs or ran in it (<<leaf>>).
* A level shows its nodes one line each; what the line cannot hold (times, counts) is the next line, or one step away.

[#states]
== The State of a Node

Each node shows its state as a glyph and a word, never as colour alone:

[cols="1,1,1,3",options="header"]
|===
|State |Glyph |ASCII |Means

|done
|`✓`
|`+`
|entered and left; with how often, when more than once

|running
|`▶`
|`>`
|the plan is in it, or in a node below it; with the run it is in

|waiting for you
|`!`
|`!`
|the plan waits for the operator in it, or below it; leads into the decision (link:decisions.adoc[Decisions])

|failed
|`✗`
|`x`
|left with a failure; the plan went on by its fallback or waits

|planned
|`○`
|`o`
|in the plan's composition, not reached yet

|not taken
|`–`
|`-`
|a branch the plan did not take where the workflow branched

|not in this plan
|`·`
|`.`
|left out by the composition, with its reason (another lane, a step the project does not need)
|===

* A node that contains the plan's current position is _running_ (or _waiting for you_), whatever its earlier runs were; the path from the plan to the current position is marked at every level, and one key or click jumps to it.
* A node the plan ran more than once (a loop-back, a step that fired again) shows how often and which run it is in: `done ×2`, `running · run 3`.
* A state the plan ran under an earlier version of its composition shows as it was when it ran; when a new version changes what is planned, the view says `The plan changed: <event>` once and shows the new plan.

[#kinds]
== Phase, Sub-Workflow, State

[cols="1,1,3",options="header"]
|===
|Kind |Shown as |Opens

|Phase
|the word `phase` and the phase's name
|the phase's workflow

|Sub-workflow
|`↳` and the word `sub-workflow`, with its name (`git.commit_and_push`, `remediation.ci-failure`, `land`, a landing variant `landing.pull-request`, a chat `chat`)
|the sub-workflow's workflow

|State
|its name, with its kind where it matters (`job`, `tasks`, `waits for you`)
|a leaf: what runs or ran in it
|===

The web app draws the kinds with the icons of its design system; the terminal uses the words and the glyph `↳` (ASCII `->`). A sub-workflow called within a phase (a remediation unit, a landing variant, a chat the operator opened) has that phase: it is shown below the phase it is called in.

[#leaf]
== A Leaf

A leaf shows what runs or ran in it:

* *A job*: its kind, its status, since when it runs or how long it ran, its outcome; a job that waits for a build slot says so (`waits for a build slot`).
* *Tasks* (a state that hands work to workers): one line per task, with its role, the worker serving it (harness and model), its attempt, its status, and its outcome; how many tasks of how many are done.
* *A finalize step*: its outcome and its firings (`fired 2×: failure, then done`).
* *A state that waits for the operator*: what waits (a decision, a waiver request), and the way into it.
* Its times: when it was entered and left, for each run.

[#tokens]
== Tokens So Far

The second line of the head says how many tokens the plan has used so far, with the split: `tokens so far   412 k (380 k in · 32 k out)` (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#change-token-usage[Tokens, Not Money]).

* *The figure* is the runtime's: the sum of the plan's usage records, `tokens = in + out`, in the number format of link:texts-and-languages.adoc#numbers[Texts and Languages, Numbers]. The client adds nothing up.
* *Coverage*: where some tasks of the plan were measured and others not, the figure is a floor with `≥` and the count beside it (`≥ 412 k (≥ 380 k in · ≥ 32 k out) · 2 of 17 tasks not measured`). Where model calls happened but no task's usage was measured, the line says `not measured` with the coverage (`not measured · 3 of 3 tasks not measured`), never `0` and never a `≥`. Before the plan's first model call it says `none yet`.
* *Only usage*: no limit, no warning, no projection, no money. A re-planning or a waiver stays an event of the plan's history, never a figure of this line.
* *Live*: the line follows the plan's events and changes when a task's usage is recorded, at most once a second.
* One step from the line: the same figure by phase and by role, each with its raw components (input, cache read, cache write, output, reasoning) as a detail, as the completion report shows them (link:completion-report.adoc#tokens[Completion Report, Tokens]); for an ended plan the line shows the final figure and leads to its completion report.

[#position]
== Where It Is

* The path from the plan to the level shown is always visible (`fix-relay › finalize › remediation.ci-failure`), each part a way back up.
* The plan view opens at the plan's level with the path to the current position open down to the running phase; a jump opens it down to the running leaf.

[#way-out]
=== Its Project and Its Epic

From a plan, its project is always one step away, and its epic, where it has one, wherever the plan view was opened from (Running Work, the project, the epic, a decision, ended work, a report or a completion report; link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#UC-PLN-1[UC-PLN-1]):

* *The path in the head* is `project › epic › plan` (`pm-mcp-clients › relay-hardening › fix-relay`), the project by its display name, the epic by its title; a plan of no epic shows `project › plan`. Each part is one step: in the web app a link, in the terminal a key (link:../terminal-client/16-plan-view.adoc#full-screen-keys[Terminal Client, Keys]).
* *The project* opens the project in Running Work, its plans and epics (link:plan-overview.adoc#levels[Plan Overview]); *the epic*, where there is one, opens its epic view (link:epic-view.adoc[Epic View]), so that a plan opened from its epic's view goes back to the epic in that step.
* The way back to where the view was opened (the browser's back, `Esc` in the terminal) stays as it is; the path is the way to the plan's own context, wherever the operator came from.
* An ended plan's path leads the same way: to its project, and to its epic where it has one, live or as it ended.
* Both come from the plan's process, which names its project with a link and, where the plan has one, its epic with a link (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#change-process-resource[The Plan's Process as a Structure]).

[#live]
== Live

The view follows the plan's events: a node entered becomes _running_, one left _done_ or _failed_, and a new version of the composition reads the process again; the selection stays on its node by id. A plan that ends shows its last state, and the view says so.

[#ended]
=== An Ended Plan

An ended plan, opened from Ended Work (link:plan-overview.adoc#ended[Ended Work]) or from a remembered place, shows read-only as it ended: every node with its last state, the outcome (link:work-actions.adoc#outcomes[How a Plan Ends]), the reason where the operator gave one, and the end time in the head; no live update, and no action but _Chat_, a read-only chat about it (link:work-actions.adoc#chat-ended[A Chat About Ended Work]). Its head also leads to its completion report in one step (_Completion report_, `report.completion.open`): how the plan went, with its outcome, deliverables, re-planning, decisions, tokens, and duration (link:completion-report.adoc[Completion Report]); the report of the plan's end leads there too (link:reports.adoc#detail[Reports, The Detail]).
