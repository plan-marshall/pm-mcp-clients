Status: `DRAFT`. Shared by both clients: link:../terminal-client/17-projects.adoc[Terminal Client, Projects]; the web app: designed by its package link:../../plans/web-projects.adoc[`web-projects`].

Onboarding a project is one guided run: the checkout, a look at it on consent, the project's identity, its enrolment, the operator's own values of the project, the team's settings, its architecture, how its work lands, its roles, the descriptions of its modules, and the commit of the team's configuration. Its order is the setup's (link:../../../../pm-mcp-core/doc/specification/domain-extensions/04-setup-state-machine.adoc[Setup State Machine]). It follows the onboarding of the machine in everything shared: the frame, consent, check lines, preselection, own values against the machine's (link:../web-app/onboarding.adoc[Web App, Onboarding]; link:../terminal-client/03-dialogues.adoc[Terminal Client, Dialogues]).

[#steps]
== Steps

The step line counts the project's steps as the machine's onboarding counts its own; the terminal client shows them as `[n/10]`:

----
  ① Checkout ─ ② Identity ─ ③ Enrolment ─ ④ Own settings ─ ⑤ Team settings
  ─ ⑥ Architecture ─ ⑦ Landing ─ ⑧ Roles ─ ⑨ Descriptions ─ ⑩ Commit ─ ✓ Ready
----

* *① Checkout* (`project.checkout`, `project.consent`, `project.detect`, `project.run-consent`, `project.probe`): the path of the checkout, the terminal client proposing its working directory.
** *The consent to look at it* (`inspect_checkout`): the server reads the checkout and runs the version probes of the host tools, and changes nothing; the consent lists what is read and which probes run. _Not now_ stays at the consent. What can be read is read (a build wrapper's version from its pinned properties); host tools are resolved only from the absolute directories of the operator's login `PATH`, never from a relative entry or a directory inside the checkout, and recorded with their path and digest; the check lines show what was found.
** *The consent to run scripts* (`run_checkout_scripts`), only where a script of the checkout must run to be known: it names every script with its arguments, and the scripts run as confined jobs. Its answers are _yes_ (this run), _yes, for this project_, and _no_. _Yes, for this project_ is remembered in the machine's `consents.json`, keyed by the project and the digest of each script, never in the enrolment, and asked again only for a script that changed (link:consents.adoc#remembered[Consents, The Remembered Consents]). _No_ goes on to ②, what needs the scripts marked `unknown`, and is not asked again in this run.
* *② Identity* (`project.identity`): the id proposed from the remote's name, the display name from its owner and name, both editable; the pilot choice only while this version of `PM-MCP` keeps the plan lifecycle closed (the lifecycle gate), with one sentence of what it means.
* *③ Enrolment* (`project.enrolment`, `project.enrol`): everything to be enrolled as a list, each line with where it comes from (`detected`, `from machine`, `default`): the root, the build wrappers and their pinned files, the host tools, the language servers, the scripts, the budgets, the write paths, the build environment (<<build-environment>>); the container engine is not in the list but a choice of its own, off, with its warning before it can be turned on. After the enrolment the setup's first states run as check lines: the run recorded as a first run (`setup.entry`), `.marshall/config/` created, holding no copy of a workflow unit: the project takes the machine's or the default unit until its team places one (`setup.prepare-workspace`), the operator file and the role set validated (`setup.check-operator-files`).
* *④ Own settings* (`project.operator`, `setup.probe-integration-variants`, `setup.verify-credentials`): the operator's values of the project, and only those, each with the machine's value preselected and marked `from machine`: the model language, the allowed models, the role assignment, the method and asking axes, the integration variant and credential of each provider, the commit identity (link:../terminal-client/02-levels.adoc#origins[Where a Value Comes From]). The posture is not asked here (<<later-run>>). Accepting a line as proposed records nothing for the project; only a changed line is the project's. Then each integration's variant is probed and its credential or CLI tool verified, as check lines; a variant that is invalid or a credential that is refused returns to ④ with its finding on the line concerned. The landing axis and the providers' declaration are not here: they are the team's (⑦). A value changed in another client meanwhile is refused with `conflict` and shown with its current value, to be applied again or kept (link:work-actions.adoc#conflict[Changed in Two Clients at Once]).
* *⑤ Team settings* (`setup.project-settings`): base branch, branch prefix, the lanes; each preselected from what the setup derived and marked `team`, because it is committed for everyone who works on the project.
* *⑥ Architecture* (`setup.detect-domains`, `setup.discover-modules`, `setup.seed-build-map`): the project's type as the setup found it: the domains that apply, each with what made it apply (a descriptor, files), changeable where the team's `domains.json` allows; a project of a type no other descriptor covers gets the domain `general-dev`, and the line says so. Then the modules each build system's parser found, as a tree with their build system and packaging, and the build map derived from them, confirmed or its routes customised, here and nowhere else (`team`).
* *⑦ Landing* (`setup.select-providers`, `setup.configure-finalize`, `setup.probe-merge-queue`, `setup.merge-queue`): how the team's work lands, each line `team`. The providers: the CI provider derived from the remote (or overridden), the code analysis providers, the review bots. The finalize steps, and the landing variant (`landing.pull-request`, `landing.main`, `landing.files`) with the machine's default preselected and marked `from machine`; it is validated here against the project, and a machine default that does not fit (`landing.main` onto a protected base branch, `landing.pull-request` without a provider of pull requests) is refused on its line with the reason, the line waiting for another choice. Where the base branch has no enforced merge queue and could have one, a check line says so with _Check again_ and _Skip_.
* *⑧ Roles* (`setup.qualify-consent`, `setup.qualify-roles`): asked only where roles need grading. The consent to qualify the roles, of kind `model_cost`, with what runs (one qualification task per role on its assigned model) and the tokens it is expected to use; then the qualification with its progress, one line per role.
* *⑨ Descriptions* (`setup.enrich-consent`, `setup.enrich-architecture`): asked only where modules need a description. The consent to describe the modules, of kind `model_cost`, with what runs (one task of the role `enrich` per module), what it writes (`.marshall/project-architecture/`, committed in ⑩), and the tokens it is expected to use; then one line per module turning from waiting to running to ✓.
* *⑩ Commit* (`setup.commit-changes`, `setup.land-changes`): the team's configuration as a list of files, to commit or to leave in the checkout uncommitted. _Commit_ makes one commit and pushes it where the checkout has a push remote, and the line says which (`pushed to origin`, `not pushed: no push remote`); _Leave_ ends the run with the files left to commit.
* *✓ Ready* (`project.completed`): what is ready, what was skipped with its reason, and the three actions of a project: add an epic, add a plan, its running work (link:project-explorer.adoc#actions[Project Explorer]).

[#consents]
=== The Two Consents of Tokens

The consents of ⑧ and ⑨ are consents of kind `model_cost` (link:consents.adoc#kinds[Consents, The Kinds]), shown like every consent (link:consents.adoc#pattern[Consents, The Consent State]): what runs, what it never does, the tokens expected from earlier runs (`about 210 k tokens (from 3 earlier runs)`, never money) or `not known yet: first run`, and the answers _yes_, _yes, and don't ask again_, and _not now_ (`common.consent.*`). A remembered consent is listed in the machine settings and withdrawn there (link:consents.adoc#remembered[Consents, The Remembered Consents]). _Not now_ skips the step with its reason, and the run goes on; a later run of the setup offers it again (`project.step.skipped`):

* *⑧ not now*: the roles stay unqualified; the project is ready, and the tasks of an unqualified role take its conservative fallback where they arise (a role `screener` without a qualified configuration leaves an external source unscreened, link:starting-work.adoc#issue[Starting Work, An Issue]).
* *⑨ not now*: the architecture keeps what discovery found, `.marshall/project-architecture/` gets no descriptions of the modules, and the project is ready without them.

[#build-environment]
=== The Build Environment

The build environment of the project's jobs is the operator's login environment as the terminal client captures it, never the runtime's own.

* *From the terminal client*: the client captures it and sends it; the line says `from your login` and opens to its variables.
* *From the web app*: the line takes the environment the terminal client last captured on this machine and says so (`captured by the terminal client 2 d ago`), opening to its variables.
* *None captured yet* (the web app on a machine whose terminal client never captured one): the line names the command that captures it, `pm-operator project add` (or `pm-operator project setup <project_id>`) in a terminal of this machine, from the operator's login, and the enrolment waits for it; the run can also be continued in the terminal client.

[#later-run]
=== A Later Run

A later run of the setup, from the project's _Setup_ (link:project-explorer.adoc#actions[Actions of a Project]), opens its states with the project's current values. Its architecture is reconciled with the checkout: the domains and modules that are new, gone, or changed since the last run are marked so (`new`, `gone`, `changed`), the qualification of ⑧ is offered where it was skipped, and the descriptions of ⑨ for the modules that changed or have none. A run of one aspect alone (the operator's values, the team settings, the build map, the providers, the finalize steps, the qualification, the architecture) opens only that aspect's states, with the project's current values as the proposal. Every choice of a later run offers _Step out_ (`project.setup.step_out`), which returns to the project with what was already written left uncommitted for the next commit; the first run offers none. The run of the operator's values shows two values the first run does not ask: the project's posture (`plan_defaults.posture`, optional, unset unless the operator sets it; while neither the project nor the machine sets it, every plan asks it, link:starting-work.adoc[Starting Work]) and the cleanup's durations of the project's plans, epics, and logs (link:cleanup.adoc#durations[Cleanup, How Long Work Is Kept]), each with the machine's value preselected and marked `from machine`.

[#not-ready]
== Not Ready Yet

A step that cannot pass (a credential refused, a tool missing, the modules not discoverable) shows its check line with the cause and the fix and waits in `setup.needs-repair`, whose _Try again_ (`project.repair.retry`) runs the step again (link:../web-app/onboarding.adoc#harness-probe[the check of a harness] is the pattern); the project is enrolled but not ready, and the explorer shows it so, with _Continue the setup_ as its first action. Closing the client changes nothing: the run waits where it stopped, in either client.

* *A machine that is not fully onboarded*: a project's onboarding starts only once the machine's onboarding is complete. Until then _Add a project_ is disabled with the reason (the runtime refuses the start with `machine_not_onboarded`) (`this machine is not fully onboarded: providers`) and the way to go on (_Continue the onboarding_).

[#setup-decisions]
== When the Setup Asks

A decision of the project's setup (a question of its workspace scope) reaches the operator as every decision does (link:decisions.adoc#setup[Decisions, A Project's Setup Asks]): announced with its project, shown on the project's row of Running Work as `setup needs you` (link:plan-overview.adoc#project-row[Plan Overview, A Project]), and answered in either client. It holds the setup only, never a plan; the run goes on from where it asked once it is answered.

[#several]
== Several Onboardings at Once

Each project's onboarding runs in a scope of its own (an entry until its enrolment, opened by `POST /api/v1/project-onboardings` and addressed as `/api/v1/entries/{entry_id}`; then the project's workspace scope), so several run at once and none waits for another.

* *Before its enrolment* a run has no project id: the explorer lists it under _Being added_ by the path of its checkout, with the step it waits at, _Continue_, and _Abandon_ (link:project-explorer.adoc#being-added[Being Added]). _Abandon_ deletes the entry; nothing was enrolled.
* *After its enrolment* it is listed by its project id like every project, not ready, with _Continue the setup_.
* *The terminal client* shows one badge per open run at its prompt (`pm [setup pm-mcp-clients 4/10]`); `Enter` on the empty prompt continues the most recent, `project setup <id>` a specific one (link:../terminal-client/17-projects.adoc#several[Terminal Client, Several at Once]).
* *The web app* gives each run a route of its own, so that each can be open in its own tab and continued from its address.
