Onboarding a project is one guided run: the checkout, a look at it on consent, the project's identity, its enrolment, its setup, what it takes from the machine or sets of its own, its architecture, its roles, the descriptions of its modules, and the commit of the team's configuration. It follows the onboarding of the machine in everything shared: the frame, consent, check lines, preselection, own values against the machine's (link:../web-app/onboarding.adoc[Web App, Onboarding]; link:../terminal-client/03-dialogues.adoc[Terminal Client, Dialogues]).

[#steps]
== Steps

The step line counts the project's steps as the machine's onboarding counts its own; the terminal client shows them as `[n/9]`:

----
  ① Checkout ─ ② Identity ─ ③ Enrolment ─ ④ Team settings ─ ⑤ Own settings
  ─ ⑥ Architecture ─ ⑦ Roles ─ ⑧ Descriptions ─ ⑨ Commit ─ ✓ Ready
----

* *① Checkout* (`project.checkout`, `project.consent`, `project.detect`, `project.run-consent`, `project.probe`): the path of the checkout, the terminal client proposing its working directory; the consent to look at it, listing what is read and the version probes of the host tools that run; what can be read is read (a build wrapper's version from its pinned properties); host tools are resolved only from the absolute directories of the operator's login `PATH`, never from a relative entry or a directory inside the checkout, and recorded with their path and digest; where a script of the checkout must run to be known, a second consent names every script with its arguments and asks first (`run_checkout_scripts`, per project, recorded with the enrolment, asked again only for a script that changed), and the scripts run as confined jobs; the check lines of what was found.
* *② Identity* (`project.identity`): the id proposed from the remote's name, the display name from its owner and name, both editable; the pilot choice only while the release's plan lifecycle is not open, with one sentence of what it means.
* *③ Enrolment* (`project.enrolment`, `project.enrol`): everything to be enrolled as a list, each line with where it comes from (`detected`, `from machine`, `default`): the root, the build wrappers and their pinned files, the host tools, the language servers, the scripts, the budgets, the write paths, the build environment (<<build-environment>>); the container engine is not in the list but a choice of its own, off, with its warning before it can be turned on.
* *④ Team settings* (the setup's choices that write the team's configuration): base branch and branch prefix, the lanes, the providers of the team's CI and analysis, the finalize steps, and the build map (`setup.seed-build-map`), which is confirmed here and nowhere else; each preselected from what the setup derived, each marked `team` because it is committed for everyone who works on the project.
* *⑤ Own settings* (`project.operator`): every aspect the project may set, with the machine's value preselected and marked `from machine`: the model language, the allowed models, the role assignment, the providers and their credentials, the plan defaults, the integration variants, the commit identity (link:../terminal-client/02-levels.adoc#origins[Where a Value Comes From]). Accepting a line as proposed records nothing for the project; only a changed line is the project's.
* *⑥ Architecture* (`setup.detect-domains`, `setup.discover-modules`): the project's type as the setup found it: the domains that apply, each with what made it apply (a descriptor, files), changeable where the team's `domains.json` allows; a project of a type no other descriptor covers gets the domain `general-dev`, and the line says so; the modules each build system's parser found, as a tree with their build system and packaging.
* *⑦ Roles* (`setup.qualify-consent`, `setup.qualify-roles`): the consent to qualify the roles, of kind `model_cost`, with what runs (one qualification task per role on its assigned model) and its expected cost; then the qualification with its progress, one line per role.
* *⑧ Descriptions* (`setup.enrich-consent`, `setup.enrich-architecture`): the consent to describe the modules, of kind `model_cost`, with what runs (one task of the role `enrich` per module), what it writes (`.marshall/project-architecture/`, committed in ⑨), and its expected cost; then one line per module turning from waiting to running to ✓. When the operator says no, the setup goes on without it: the architecture keeps what discovery found, `.marshall/project-architecture/` gets no descriptions of the modules, the project is ready, and a later run of its setup offers the descriptions again.
* *⑨ Commit* (`setup.commit-changes`): the team's configuration as a list of files, to commit in the checkout or to leave there uncommitted; nothing is pushed.
* *✓ Ready* (`project.completed`): what is ready, and the three actions of a project: add an epic, add a plan, its running work (link:project-explorer.adoc#actions[Project Explorer]).

[#consents]
=== The Two Consents of Cost

The consents of ⑦ and ⑧ are consents of kind `model_cost` (link:consents.adoc#kinds[Consents, The Kinds]), shown like every consent (link:consents.adoc#pattern[Consents, The Consent State]): what runs, what it never does, its expected cost from earlier runs or `not known yet: first run`, and the answers _yes_, _yes, and don't ask again_, and _not now_ (`common.consent.*`). A remembered consent is listed in the machine settings and withdrawn there (link:consents.adoc#remembered[Consents, The Remembered Consents]).

* *⑦ not now*: the step waits at its consent; the project is enrolled but not ready, since its roles are not qualified.
* *⑧ not now*: the project is ready without descriptions (above).

[#build-environment]
=== The Build Environment

The build environment of the project's jobs is the operator's login environment as the terminal client captures it, never the runtime's own.

* *From the terminal client*: the client captures it and sends it; the line says `from your login` and opens to its variables.
* *From the web app*: the line takes the environment the terminal client last captured on this machine and says so (`captured by the terminal client 2 d ago`), opening to its variables.
* *None captured yet* (the web app on a machine whose terminal client never captured one): the line names the command that captures it, `pm-operator project add` (or `pm-operator project setup <project_id>`) in a terminal of this machine, from the operator's login, and the enrolment waits for it; the run can also be continued in the terminal client.

[#later-run]
=== A Later Run

A later run of the setup, from the project's _Setup_ (link:project-explorer.adoc#actions[Actions of a Project]), opens its states with the project's current values. Its architecture is reconciled with the checkout: the domains and modules that are new, gone, or changed since the last run are marked so (`new`, `gone`, `changed`), and the descriptions of ⑧ are offered for the modules that changed or have none.

[#not-ready]
== Not Ready Yet

A step that cannot pass shows its check line with the cause and the fix and waits (link:../web-app/onboarding.adoc#harness-probe[the check of a harness] is the pattern); the project is enrolled but not ready, and the explorer shows it so, with _Continue the setup_ as its first action. Closing the client changes nothing: the run waits where it stopped, in either client.

* *A machine that is not fully onboarded*: a project's onboarding starts only once the machine's onboarding is complete. Until then _Add a project_ is disabled with the reason (`this machine is not fully onboarded: providers`) and the way to go on (_Continue the onboarding_).

[#several]
== Several Onboardings at Once

Each project's onboarding runs in a scope of its own (an entry until its enrolment, then the project's workspace scope), so several run at once and none waits for another.

* *Before its enrolment* a run has no project id: the explorer lists it under _Being added_ by the path of its checkout, with the step it waits at, _Continue_, and _Abandon_ (link:project-explorer.adoc#being-added[Being Added]). _Abandon_ deletes the entry; nothing was enrolled.
* *After its enrolment* it is listed by its project id like every project, not ready, with _Continue the setup_.
* *The terminal client* shows one badge per open run at its prompt (`pm [setup pm-mcp-clients 5/9]`); `Enter` on the empty prompt continues the most recent, `project setup <id>` a specific one (link:../terminal-client/17-projects.adoc#several[Terminal Client, Several at Once]).
* *The web app* gives each run a route of its own, so that each can be open in its own tab and continued from its address.
