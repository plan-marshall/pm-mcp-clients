Onboarding a project is one guided run: the checkout, a look at it on consent, the project's identity, its enrolment, its setup, and what it takes from the machine or sets of its own. It follows the onboarding of the machine in everything shared: the frame, consent, check lines, preselection, own values against the machine's (link:../web-app/onboarding.adoc[Web App, Onboarding]; link:../terminal-client/03-dialogues.adoc[Terminal Client, Dialogues]).

[#steps]
== Steps

The step line counts the project's steps as the machine's onboarding counts its own:

----
  ① Checkout ─ ② Identity ─ ③ Enrolment ─ ④ Team settings ─ ⑤ Own settings ─ ⑥ Architecture
  ─ ⑦ Roles ─ ⑧ Commit ─ ✓ Ready
----

* *① Checkout* (`project.checkout`, `project.consent`, `project.detect`): the path of the checkout, the terminal client proposing its working directory; the consent to look at it, listing what is read and the version probes of the host tools that run; what can be read is read (a build wrapper's version from its pinned properties); host tools are resolved only from the absolute directories of the operator's login `PATH`, never from a relative entry or a directory inside the checkout, and recorded with their path and digest; where a script of the checkout must run to be known, a second consent names every script with its arguments and asks first (`run_checkout_scripts`, per project, recorded with the enrolment, asked again only for a script that changed), and the scripts run as confined jobs; the check lines of what was found.
* *② Identity* (`project.identity`): the id proposed from the remote's name, the display name from its owner and name, both editable; the pilot choice only while the release's plan lifecycle is not open, with one sentence of what it means.
* *③ Enrolment* (`project.enrolment`, `project.enrol`): everything to be enrolled as a list, each line with where it comes from (`detected`, `from machine`, `default`): the root, the build wrappers and their pinned files, the host tools, the language servers, the scripts, the budgets, the write paths, the build environment; the container engine is not in the list but a choice of its own, off, with its warning before it can be turned on.
* *④ Team settings* (the setup's choices that write the team's configuration): base branch and branch prefix, the lanes, the providers of the team's CI and analysis, the build map, the finalize steps; each preselected from what the setup derived, each marked `team` because it is committed for everyone who works on the project.
* *⑤ Own settings* (`project.operator`): every aspect the project may set, with the machine's value preselected and marked `from machine`: the model language, the allowed models, the providers and their credentials, the plan defaults, the integration variants, the commit identity (link:../terminal-client/02-levels.adoc#origins[Where a Value Comes From]). Accepting a line as proposed records nothing for the project; only a changed line is the project's.
* *⑥ Architecture* (`setup.detect-domains`, `setup.discover-modules`, `setup.seed-build-map`, and later `setup.enrich-architecture`): the project's type as the setup found it: the domains that apply, each with what made it apply (a descriptor, files), changeable where the team's `domains.json` allows; the modules each build system's parser found, as a tree with their build system and packaging; the build map to confirm. The enrichment runs after the roles are qualified: one line per module turning from waiting to running to ✓ as the role `enrich` describes it, behind its consent with its expected cost. What it writes is `.marshall/project-architecture/`, committed in ⑧. When the operator says no to the enrichment's consent, the setup goes on without it: the architecture keeps what discovery found, `.marshall/project-architecture/` gets no descriptions of the modules, the project is ready, and a later run of its onboarding offers the enrichment again.
* *⑦ Roles* (`setup.qualify-roles`): the role assignment proposed from the machine like ⑤, then the qualification, behind its consent with its expected cost, with its progress.
* *⑧ Commit* (`setup.commit-changes`): the team's configuration as a list of files, to commit and push, or to leave in the checkout.
* *✓ Ready* (`project.completed`): what is ready, and the three actions of a project: add an orchestrator, add a plan, its running work (link:project-explorer.adoc#actions[Project Explorer]).

[#not-ready]
== Not Ready Yet

A step that cannot pass shows its check line with the cause and the fix and waits (link:../web-app/onboarding.adoc#harness-probe[the check of a harness] is the pattern); the project is enrolled but not ready, and the explorer shows it so, with _Continue the setup_ as its first action. Closing the client changes nothing: the run waits where it stopped, in either client.
