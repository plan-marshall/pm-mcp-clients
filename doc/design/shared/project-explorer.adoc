Status: `DRAFT`. Shared by both clients: link:../terminal-client/17-projects.adoc[Terminal Client, Projects]; the web app: designed by its package link:../../plans/web-projects.adoc[`web-projects`].

The explorer is where the operator finds a project among all the machine's projects, and goes from it to its work. It is the counterpart of _Running Work_ (link:plan-overview.adoc[Plan Overview]): Running Work shows only what runs, the explorer every enrolled project.

[#layout]
== Favourites, Recent, All

----
  Projects                                                     + Add a project
  ─────────────────────────────────────────────────────────────────────────────
  ★ Favourites
    ★ pm-mcp-clients     ready    ! 2   3 plans · 1 epic   2 min ago
    ★ pm-mcp-core        ready          2 plans                    9 min ago
  Recent
      plan-marshall      setup needs: credential sonar             yesterday
      cui-http           ready                                     3 d ago
  Being added
      ~/git/cui-parent   step 2 of 10: Identity        [Continue]  [Abandon]
  All projects                                    [ filter ]   by name ▾
      API-Sheriff        ready                                     5 weeks ago
      cui-http           ready                                     3 d ago
      …
----

* *Favourites*: the projects the operator marked, in the operator's order; always first.
* *Recent*: the projects the operator worked with last, newest first, at most five; a favourite is not repeated here.
* *All projects*: every enrolled project, by name, or by _most used_ (how often the operator worked in it over the last four weeks); a filter on name and id narrows the list, and with a filter the three groups become one list of matches.
* *Being added*: the projects whose onboarding has not reached its enrolment yet (<<being-added>>); shown only while there is one.
* *Add a project* starts the onboarding of a project (link:project-onboarding.adoc[Project Onboarding]). On a machine that is not fully onboarded it is disabled with the reason (`this machine is not fully onboarded: providers`) and _Continue the onboarding_ beside it.
* A released project is listed with `released` and offers to be enrolled again; an unenrolled one is not listed (<<release>>).

[#being-added]
=== Being Added

A project's onboarding that has not reached its enrolment has no project id yet (link:project-onboarding.adoc#several[Several Onboardings at Once]). It is listed by the path of its checkout, with the step it waits at, _Continue_, which opens the run where it stopped, and _Abandon_, which deletes the entry after a confirmation (nothing was enrolled). Once enrolled, it leaves the group and is listed by its project id like every project, not ready, with _Continue the setup_ until it is.

A project's running work shows its own pull requests by their numbers, each a link to the provider, where the client shows its plans (link:plan-overview.adoc#item-rows[A Plan, an Epic]).

[#actions]
== Actions of a Project

Selecting a project offers, in this order:

. *Add an epic*: starts an epic in the project.
. *Add a plan*: starts a plan in the project.
. *Running work*: the project's level of Running Work, its plans and epics (link:plan-overview.adoc#levels[Two Levels, Two Views]).
. *Ended work*: its ended plans and epics, newest first (link:plan-overview.adoc#ended[Ended Work]).
. *Setup*: a later run of the project's onboarding, opened at what the operator chooses (link:project-onboarding.adoc#later-run[A Later Run]); releasing and unenrolling the project are among its choices (<<release>>).
. *Favourite*: mark or unmark it.

A released project offers _Enrol again_ first, which runs its onboarding again from its identity with its current values and reopens its plan lifecycle, then _Ended work_. A project that is not ready offers _Continue the setup_ first and the two _Add_ actions disabled, with the reason. The two _Add_ actions lead into the start of an epic and of a plan (link:starting-work.adoc[Starting Work]); while an entry of the project is open, _Continue starting_ comes first (link:starting-work.adoc#leaving[Leaving and Coming Back]).

[#release]
== Release and Unenrol

The project's setup offers, after its aspects, _Release the project…_ and _Unenrol the project…_ (link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc#UC-PRJ-3[UC-PRJ-3]); _Release_ only while the project is not released. Each confirms first with what it ends (`project.release-confirm`).

----
  Release pm-mcp-clients?
  ─────────────────────────────────────────────────────────────────────────────
  What ends      3 plans, each ended as released and archived; 1 epic,
                 released with its plans and archived
                 1 entry not started yet, deleted with its sources
                 the setup run of pm-mcp-clients, ended where it stands
  Pull requests  #214, #219 are open   (●) Close them, with the reason
                                       ( ) Leave them open
  Reason         [                                                         ]
  Afterwards     no plan runs in pm-mcp-clients; it stays listed as released
                 and can be enrolled again with its values
                                                  [Keep it]  [Release the project]
----

* *Release* ends every plan of the project, whatever its state (running, pausing, paused, waiting for the operator, held), with the outcome `released`, never `cancelled` or `abandoned`, and archives it like a completed plan; its branch stays, and its open pull request is closed or left as the confirmation chose. Every epic of the project ends with the `terminal_reason` `released` and is archived; its plans end with the release, so nothing is left to tell it. The project's pending entries (starts not finished, link:starting-work.adoc#leaving[Starting Work, Leaving and Coming Back]) are deleted with their sources, and a running onboarding of the project (a later run of one of its aspects, link:project-onboarding.adoc#later-run[A Later Run]) is ended where it stands. Then the project's plan lifecycle is closed. The reason is required; it goes to every plan's archive and to the closing comments. Each line of _What ends_ is shown only where there is something to end.
* *A removal from git still landing* (`project.release-wait`): where a moved document's `git.land-removal` of the project runs (link:starting-work.adoc#documents[Starting Work, Documents]), the release lets it finish before it ends anything, so that no removal is left half landed: after the confirmation a check line waits for it within its bound (`project.release.waiting`). When it does not finish in its bound, the release is refused, nothing has ended, and the removal is named with its row in Running Work (`project.release.wait_refused`); the operator releases again once it landed or was resolved there.
* *Unenrol* removes the project's enrolment and nothing else: its checkout and the team's `.marshall/` stay as they are, and so does the project's machine store with the archive of its ended plans and epics. Enrolled again from the same checkout, the project finds its store and its archive again. Unenrolling deletes nothing; the store becomes an item of the cleanup, offered once `cleanup.unenrolled_after_days` have passed and deleted only by the operator's decision (link:cleanup.adoc#what[Cleanup, What the Cleanup Covers]; link:../../../../plan-marshall-documentation/doc/use-cases/04-projects.adoc#UC-PRJ-3[UC-PRJ-3]). It is refused while work runs: the dialogue lists the running plans and epics instead, each leading to its actions (link:work-actions.adoc[Actions on Plans and Epics]), and offers _Release the project…_, which ends them.

----
  pm-mcp-clients cannot be unenrolled while work runs
  ─────────────────────────────────────────────────────────────────────────────
    ▸ plan  fix-relay           execute · running                      [Actions]
    ◇ epic  relay-hardening     running · 2 of 3 at once               [Actions]
  End them first, or release the project, which ends them.
                                                  [Back]  [Release the project…]
----

* *The reason*: the release asks it (it closes the pull requests and goes to every archive); unenrolling takes an optional one, recorded in the audit trail.
* *Afterwards*: a released project stays listed with `released` and offers _Enrol again_; an unenrolled one leaves the list, and a client that shows it says so and moves to the list.

[#marks]
== Favourites, Recent, Most Used

* The operator marks a favourite from the project's actions, or with one key or click on its row, and orders the favourites by moving them; the marks are the runtime's, so both clients and every paired browser show the same.
* _Recent_ and _most used_ come from the runtime: it counts what the operator does in a project in either client (opening it, starting an epic or a plan, answering a decision, changing its configuration); a client never counts on its own.
* Where the operator left the explorer (the group, the filter, the selected project) is remembered like the overview's start point: per browser, and per terminal user (link:plan-overview.adoc#persistence[Where the Operator Left It]).
