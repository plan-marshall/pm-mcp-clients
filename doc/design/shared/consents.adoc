Nothing happens on the machine until the operator says so: every action that looks at the machine, runs a program found on it, writes to its credential store on its own, calls a provider, or spends model tokens waits in a consent state first. What the operator does with their own hands needs none: a token the operator types is stored on that act alone. This design is the one place that says how a consent state looks and behaves in both clients, which kinds of consent there are, where the remembered ones are listed and withdrawn, and the texts they share. A client's part shows its own rendering and links here.

[#pattern]
== The Consent State

A consent state is `<sub-workflow>.consent`, or `<sub-workflow>.<action>-consent` where a step asks several. Both clients render it alike, the web app as a screen in the step's frame, the terminal as a block of fields with its prompt; the content comes from the consent kind and from what the server states, and a client adds nothing of its own.

* *Title*: the action as a question, the state's own key (`onboard.harness.consent.title`: "Look for harnesses on this machine?", `project.consent.title`: "Look at the checkout {path}?").
* *Fields*, each shown only when the server states it, in this order:
** _looks for_ (`common.consent.field.looks_for`): what is looked for (the harnesses the profiles know, the CLI tools of the providers);
** _in_ (`common.consent.field.in`): where it is looked for (the directories of the login `PATH`, the checkout);
** _runs_ (`common.consent.field.runs`): what is run, each command with its arguments (a version probe, a login probe, a named script of the checkout, a role task on its harness and model);
** _never_ (`common.consent.field.never`): what it never does (reads other files, starts a session, uses the network, writes to the checkout);
** _tokens_ (`common.consent.field.tokens`): `none` (`common.consent.tokens.none`), an estimate of the tokens the action uses (`common.consent.tokens.estimate`, `.estimate_runs` with the number of earlier runs it comes from), or `not known yet: first run` (`common.consent.tokens.unknown`); a consent that calls a model names the role, the harness, and the model. The estimate is a count of tokens in the number format of link:texts-and-languages.adoc#numbers[Texts and Languages, Numbers], never money (link:../../../../pm-mcp-core/doc/specification/client-profiles/01-profile-schema.adoc#token-usage[Tokens, Not Money]).
* *Answers*, the links of the state:
** _yes_ (`yes`, `common.consent.yes`): the action runs this time;
** _yes, and don't ask again_ (`yes_remember`, `common.consent.yes_remember`): the action runs and the consent is remembered (<<remembered>>); offered only for a kind that can be remembered (<<kinds>>). Where it is not offered, `This consent is for this run only.` (`common.consent.once_only`) stands in its place;
** _not now_ (`no`, `common.consent.no`): nothing is looked at, nothing is run, nothing is recorded.
* *Where the answers sit*: the web app makes the remember choice a choice inside the screen, _yes_ preselected, and the primary button the consent's action; _Not now_ is the secondary button. The terminal has no `Enter` default: `y) yes   r) yes, and don't ask again   n) not now` (German `j`, `m`, `n`), and `Enter` alone asks again. A consent that ends work has no `r` and adds the leave key: `y) yes   n) no   q) leave` (German `j`, `n`, `v`); `q` sends nothing. Nothing runs until the operator gave one of the two yes answers.
* *What no does*: for a required action the state stays, `Nothing was done.` (`common.consent.nothing_done`) stands under the title with the same answers, and the step does not move; for an optional action (<<kinds>>, column _With no_) the process goes on without it and says what it goes on with (the monograms, no recommendation, what the scripts would have found unknown, the step skipped with its reason). A _no_ is never shown as an error: no `✗`, no colour of an error.
* *A remembered consent* passes its state without a question; the client shows one line, `Consent remembered: {action}` (`common.consent.remembered`, the argument the kind's title of <<texts>>), and the terminal adds where it is withdrawn (`common.consent.withdraw_hint`).
* *A consent covers its kind, never a wider one*: consent to look for harnesses runs no login or model probe, and each is asked where its action is.
* *Help*: `?` in the terminal and _Why?_ in the web app show the full list behind a shortened field (every script of `project.run-consent` with its arguments, every check of the automatic run).

[#auto]
=== The Automatic Run's One Consent

The automatic run (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-2[UC-ONB-2]) asks once, in `auto.consent` (kind `auto_run`), for everything it does: the consents of the steps it runs, each listed by its kind's title (<<texts>>) with what it looks for and runs, and that the run asks no model for advice. Its only tokens are those of the login probe of a harness whose profile has no login probe of its own (`auth_probe: null`): one minimal headless call, paid with tokens of the harness's account, listed with its expected tokens (link:../../../../pm-mcp-core/doc/specification/client-profiles/01-profile-schema.adoc#login-probe[Login Probe]). The consent is asked before the scan, so it lists that cost for every harness the profiles know without a login probe; only where there is none does its tokens field say `none` (`common.consent.tokens.none`), and never otherwise. The consent covers exactly those actions, for this run only: it is never remembered, it has no remember choice (`common.consent.once_only` stands in its place), and it does not remember the kinds it lists. _No_ goes back to `onboard.mode`, nothing done. A kind the operator remembered earlier is listed as remembered and not asked again.

* `catalogue.consent` asks two kinds at once, each with its own answer and tokens: _no_ to the model probes keeps the state, _no_ to the advice goes on without it.
* A consent of `run_checkout_scripts` is asked again for a script whose digest changed since it was remembered; the state names the changed scripts (`common.consent.changed_scripts`) and offers only those.
* A grant is not a consent: reading the issues of another repository is a read grant, kept and shown with the grants, never in the list of <<remembered>>.
* `store.consent` is asked only for an OS store; choosing the files goes from `store.choose` to `store.check` without it. `providers.verify-consent` follows `providers.credentials`: storing the typed token is the operator's own act, calling the provider with it is the machine's.

[#remembered]
== The Remembered Consents

Both clients list the remembered consents in their machine settings (link:../../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-10[UC-ONB-10], `settings.choose`): the web app in its section _Remembered consents_ (link:../web-app/machine-settings.adoc#consents[Web App, Machine Settings]), the terminal with `pm-operator config consents` (link:../terminal-client/08-transcripts-later.adoc#t-consents[Terminal Client, transcript]). The list is what the runtime keeps in its machine store `consents.json`, the only place a remembered consent lives, from either client, one line per consent:

* the action by its kind's title (<<texts>>) and its kind;
* when it was given;
* where: the channel, `terminal` or the web app with the label of the paired device that gave it;
* for a kind of a project (`inspect_checkout`, `run_checkout_scripts`, `model_cost`) the project;
* for `run_checkout_scripts` how many scripts it covers; its detail names each script with its digest.

*Withdraw* opens `settings.withdraw`: the consent by its title, and where it will be asked again (the consent state of its kind, <<kinds>>, column _Asked in_), with _Keep it_ (`keep`, back to the list) and _Withdraw_ (`withdraw`). Withdrawing (`settings.remove-consent`) removes it from `consents.json`; nothing recorded with it changes, and the consent state is asked again the next time its action runs, which the list then says in place of the line. Both remembering and withdrawing are audited, with the channel and the device. A consent is never given in this list; it is given only in the state that asks it (<<pattern>>). With none remembered, the list says so. The texts of the list are each client's own (`web.settings.consents.*`, `operator.consents.*`); those of `settings.withdraw` are shared (<<texts>>).

[#texts]
== Texts

The consent texts both clients show are keys of the area `common` (link:texts-and-languages.adoc#keys[Keys and Packs]).

*Defined in link:../terminal-client/09-texts-common.adoc#texts-common[Terminal Client, Texts: Common], used by both*: `common.consent.yes`, `.yes_remember`, `.no`, `.nothing_done`, `.remembered`, `.withdraw_hint` (the terminal only), `.once_only`; the fields `common.consent.field.looks_for`, `.in`, `.runs`, `.never`, `.tokens`; the estimates `common.consent.tokens.none`, `.estimate`, `.estimate_runs`, `.unknown`. The title of each consent state is defined with its step's texts.

*Defined here*: the title of each kind, a lowercase action that reads in a list and as the `{action}` of `common.consent.remembered`, the texts of `settings.withdraw` (`{where}` the step and the state that asks the kind, for example `[5/7] Credentials`), and the line of changed scripts.
