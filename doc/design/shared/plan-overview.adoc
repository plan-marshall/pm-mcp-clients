`PM-MCP` runs many plans and epics over many projects. The overview is where the operator sees what runs and what needs attention, in two dimensions: the projects, and in a project its plans and epics. This document is what both clients show; how each draws it is its own design.

[#levels]
== Two Levels, Two Views

----
  Projects                          A project
  ─────────                         ───────────────────────────────────────────
  ! pm-mcp-clients   3 · 1  2 ◀──── by plan:          by epic:
    pm-mcp-core      2 · 0            plans, flat,      epics, each with
    plan-marshall    0 · 1            each naming its   its plans below it; the
                                      epic      plans of none at the end
----

* *Projects*: only those with running work (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#change-running-work[Running Work]): an active plan or epic, or an open decision of the project's setup. Ended and archived plans never appear here; a project with nothing running does not either. What ended is a list of its own (<<ended>>).
* *A project, by plan*: its active plans, flat. Each plan names the epic it belongs to; in the web app the name is a link to that epic, in the terminal a key moves there.
* *A project, by epic*: its active epics, each with its active plans below it; the plans that belong to no epic follow as a group of their own (`without epic`), so both views hold the same plans.
* The operator switches between the two views of a project at any time; the view is part of where the operator left the overview (<<persistence>>).

[#project-row]
== A Project

[cols="1,3",options="header"]
|===
|Element |Shown as

|Needs the operator
|a marker with the count (`! 2`), first in the row; absent when nothing needs the operator

|Name
|the project's display name; its id where it has none

|Active work
|plans and epics, counted apart (`3 plans · 1 epic`)

|Setup
|`setup needs you` when only its setup waits for the operator
|===

Order: projects that need the operator first, then by their latest activity. A project whose running work ends (its last active plan and epic ended, and no decision of its setup waits) leaves the list; while it is selected, the client says so and moves the selection to its neighbour.

[#item-rows]
== A Plan, an Epic

[cols="1,2,2",options="header"]
|===
|Element |Plan |Epic

|Kind
|its icon, colour, and the word `plan`
|its icon, colour, and the word `epic`

|Needs the operator
|the marker with the count and the kind of the first, from one closed list: `decision`, `waiver`, `waits for you`, `integrity pause`, `stalled`, `needs a fix`, `held`, `landing failed`, `paused by you`, `setup` (`! 2 · decision`, `! paused by you`)
|the same, counting its plans' items too, and `new findings` of its own

|Title
|the plan's title
|the epic's title

|Where it is
|the current phase and the state in it, from one closed list: `running`, `pausing` with its point (`pausing after the task`), `paused`, `waiting for you`, `stalled`
|its plans: `2 running · 3 staged`

|Time
|since when it runs, and since when it is in the current phase (`2 h 10 min · in execute 25 min`)
|since when it runs

|Progress
|tasks done of all (`7 of 12 tasks`)
|plans shipped of all (`4 of 9 plans`)

|Belongs to
|its epic, or nothing
|—

|Pull request
|its own pull request once it has one, by its number with a link to the provider (`#214`)
|—
|===

* Order within a project: those that need the operator first, then the most recently active; the plans below an epic in the same order.
* Times are shown as durations, rounded to what matters (`25 min`, `2 h 10 min`, `3 d`), and computed at each redraw; nothing counts in place by the second.
* Selecting a plan leads into its plan view (link:plan-view.adoc[Plan View]), selecting an epic into its epic view (link:epic-view.adoc[Epic View]); selecting the marker leads to what waits: a decision or a waiver request (link:decisions.adoc[Decisions]), a hold (link:work-actions.adoc#holds[What Holds a Plan]), new findings (link:work-actions.adoc#review[Reviewing Findings or Watches]).

[#distinction]
== Telling Them Apart

A plan and an epic differ by three things at once, so that none carries the meaning alone: an icon, a colour, and a word. The web app takes its icons from the icon set of its design system (link:../../plans/web-design.adoc[`web-design`], under a permissive licence such as Apache-2.0, MIT, or ISC); the terminal uses a glyph, with ASCII where UTF-8 is missing:

[cols="1,1,1,2",options="header"]
|===
|Kind |Terminal glyph |ASCII |Colour

|Plan
|`▸`
|`>`
|the plan colour of the design system (terminal: cyan)

|Epic
|`◇`
|`<>`
|the epic colour (terminal: magenta)

|Needs the operator
|`!`
|`!`
|the attention colour (terminal: yellow), always with the count
|===

[#ended]
== Ended Work

A project's ended plans and epics are a list of their own, apart from Running Work, so that what runs is never crowded by what ended (link:../../../../plan-marshall-documentation/doc/use-cases/03-plans.adoc#change-ended-work[Ended Work]).

----
  pm-mcp-clients · ended work                                         page 1 of 3
  ─────────────────────────────────────────────────────────────────────────────
  ▸ plan  fix-relay               completed   #214                  today 11:20
  ◇ epic  relay-hardening         archived                          yesterday
  ▸ plan  codeberg-issues         cancelled   replaced by relay-v2  2 d ago
  ▸ plan  docs-cleanup            abandoned   no longer needed      5 d ago
  ─────────────────────────────────────────────────────────────────────────────
                                                          [Newer]  [Older]
----

* *Where*: per project, opened from the project's level of Running Work (_Ended work_) and from the project's actions in the explorer (link:project-explorer.adoc#actions[Actions of a Project]), also for a project with nothing running.
* *A row*: the kind as in Running Work (<<distinction>>), the title, the outcome (a plan: completed, cancelled, abandoned; an epic: archived, cancelled), the plan's own pull request by its number with a link, the reason where the operator gave one, and when it ended.
* *Order and paging*: newest first, a page at a time, with _Newer_ and _Older_; the runtime pages, the client never loads the whole archive.
* *Opening one*: an ended plan opens its plan view, an ended epic its epic view, both read-only and as it ended: the last state of every node, the outcome, the reason, and the end time in the head, and no action (link:plan-view.adoc#live[Plan View, Live]; link:epic-view.adoc#layout[Epic View]).
* A plan that ends while the operator looks at Running Work leaves it and appears at the top of its project's ended work.

[#live]
== Live

The overview follows the runtime's events and changes in place: a plan that starts or ends, a phase change, a decision that arrives or is answered, an epic's plan that starts. The selection is anchored to the selected item's id, never to its row: rows that move do not move the selection. A client that lost the connection says so on the overview and reads everything again when it is back.

[#persistence]
== Where the Operator Left It

The overview remembers the project, the view (by plan, by epic), and the selected plan or epic, and opens there the next time:

* the web app per browser, in its local storage beside its device secret;
* the terminal client per user, in its state directory (link:../terminal-client/15-overview.adoc[The Overview]).

A remembered plan that has ended falls back to its project; a project that no longer has running work falls back to the list of projects.
