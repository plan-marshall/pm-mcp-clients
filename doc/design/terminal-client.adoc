Status: `DRAFT`. This design is the specification the implementation of the terminal client follows (work package link:../plans/cli-onboarding.adoc[`cli-onboarding`]); the use cases it serves and the web design stay in `plan-marshall-documentation`.

The logical design of `pm-operator` as the operator's second client beside the web app: the commands and their arguments, how the terminal addresses the levels of configuration, how it renders a state of a workflow, the texts it shows in English and German, and a transcript of every state of the onboarding and of `pm-operator start`. The web side of the same states is link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc[Onboarding Screens]; the two documents show the same states with the same texts, and where the terminal needs something the web app does not, this document says so. Names, versions, paths, models, and figures in the transcripts are examples.

The client holds no step order and no rule of its own: it renders the state the runtime reports, offers its links, and sends the link the operator picks (link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc[Onboarding Screens, Principles]). Everything below is about how a state looks and is answered in a terminal, never about what the next state is.

[#commands]
== Command Model

[#command-tree]
=== The Verbs

The onboarding adds three verbs to the terminal verbs of `pm-operator` (link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#command-tree[Command Tree]) and gives the existing verb `config` its aspects. Every one of them is an operator verb (`[op]`): a choice of the onboarding is an operator act (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-two-channels[Operator Choices in the Web App and the Terminal]), and `start` issues a pairing code, which only an operator verb may do.

----
pm-operator start [--auto] [--pair] [--no-wait]           [op]  start the runtime, onboard a new machine, open the web app (UC-WEB-1)
pm-operator onboard [--auto] [--consent <kind>]...        [op]  the onboarding in the terminal, guided or automatic (UC-ONB-1, UC-ONB-2)
pm-operator config <aspect> [<level>] [<choices>]         [op]  one aspect of the onboarding as a later change (UC-ONB-3 to UC-ONB-9)
    language       [--interface <locale>] [--model same|<locale>]
    harness        [--client <client_id>] [--path <executable>]
    models         [--enrol <client_id>]... [--allow <client_id>:<model>]... [--no-advice]
    roles          [--defaults] [--set <role>=<client_id>:<model>[:<effort>]]... [--reset <role>|--reset-all]
    credentials    [--store os|file]
    providers      [--use <provider>[:native|:cli]]... [--without <provider>]...
    plan-defaults  [--landing pull-request|main|files] [--method test-first|tests-after]
                   [--asking every-phase|key-points|questions-only]
    consents       the remembered consents, to withdraw one
pm-operator config show [<aspect>|<key>] [<level>]           [op]  effective values with their origin
pm-operator config set <key> <value> [<level>]                [op]  one plain key at one level
pm-operator config unset <key> [<level>]                      [op]  remove a key at one level; the next level's value applies

<level>:   --machine (the default) | --project <project_id>|.|? | --plan <plan_id>|?
common:    --no-input   never ask; stop at the first choice not given (exit code 3)
           --yes        accept the confirmations of the displayed changes (never a consent)
           --consent <kind>   the operator's yes to one consent kind for this run (never remembered)
----

* *`start`* is `web open` with the flow of link:../../../plan-marshall-documentation/doc/use-cases/02-web-app.adoc#UC-WEB-1[UC-WEB-1]; on a machine that is not onboarded it first offers the onboarding (<<t-start-first>>). `--auto` runs the automatic onboarding before the web app opens; `--pair` pairs the browser even when one is paired; `--no-wait` prints the ways in once and exits instead of waiting in `start.wait`.
* *`onboard`* runs the onboarding workflow of the machine scope from the state it is in: the first run from `onboard.entry`, an interrupted run from where it stopped, an onboarded machine from `onboard.completed`, where it offers the aspects to change (<<t-completed>>).
* *`config <aspect>`* starts the sub-workflow of one aspect as a later run (`onboard_run: reconfigure`), with the current values as the proposal, and answers each choice state from its arguments where they give one (<<direct-verbs>>). The aspects are the seven steps of the onboarding: `language`, `harness`, `models`, `roles`, `credentials`, `providers`, `plan-defaults`.
* *`config show|set|unset`* keep what `pm-operator config` already is: the operator's configuration keys of `machine-config.json` and `local-config.json`. A key that an aspect owns (`language.*`, `credentials.store`, `providers.*`, `plan_defaults.*`, the role assignment) is changed only through its aspect, because the aspect validates and checks it; `config set` refuses it and names the aspect verb. `show` lists every key, the aspect-owned ones included.

[#one-surface]
=== One Surface in Every Language

Command names, options, option values, aspect names, consent kinds, state ids, and link relations are the same in every language; only the texts are translated (link:../../../plan-marshall-documentation/doc/design/03-texts-and-languages.adoc#two-languages[Texts and Languages, Two Languages]). A command line, a script, a support answer, and the documentation work in every language without change. The key of a prompt is a mnemonic of its label and therefore a text: it comes from the catalogue with the label and follows the language (`y) yes`, `j) ja`; <<keys>>).

[#direct-verbs]
=== A Direct Verb Runs a Sub-Workflow

`config <aspect>` and `onboard` drive the same states as the dialogue; their arguments are answers given in advance. The client walks the workflow:

. It sends the request that starts the run (`config <aspect>`) or reads the current state (`onboard`).
. In a server state (`[S]`) or a model state (`[M]`) it shows the progress and waits for the next state (<<waiting>>).
. In a choice state (`[O]`) it looks for an answer among the arguments: an option of the aspect for a choice, `--consent <kind>` for a consent state of that kind, `--yes` for a confirmation of a displayed change (`harness.confirm`, `harness.add-confirm`, the move of `config credentials`). An answer the state accepts is sent as its link; the state is printed as one line with the answer (`✓ Interface language  Deutsch   (--interface de)`).
. A choice state without an answer among the arguments is shown as the dialogue and asks; with `--no-input` the client stops there instead (<<no-input>>).
. It ends when the sub-workflow reaches its done state (`language.done` and the others) or the onboarding rests in `onboard.completed`.

An argument the state does not accept (a locale without a pack, a model the catalogue does not allow) is not sent: the client shows the state with the refusal in place of the preselection and asks, or with `--no-input` stops with exit code `3` and the refusal. An argument that no state of the run asked for is reported after the run (`--landing main was not used: the landing is set by the project's team`), never silently dropped.

A consent is never implied: no argument but `--consent <kind>` answers a consent state, `--yes` never does, and `--consent` holds for this run only and is never remembered (`yes_remember` exists only as the dialogue's `r`). A secret is never an argument: `providers.credentials` always asks with the echo off, and with `--no-input` stops and names `pm-operator credentials set <credential_key>`.

[#exit-codes]
=== Exit Codes

[cols="1,4",options="header"]
|===
|Code |Meaning

|`0`
|done: the sub-workflow reached its done state, the onboarding rests in `onboard.completed`, `start` ended by `q`, or a read-only verb answered.

|`1`
|refused by the runtime: an error code of `pm-api` (<<refusals>>), printed with its text and fix.

|`2`
|usage: an unknown verb, option, or option value (picocli).

|`3`
|not finished: the run stopped at a choice it was not given (`--no-input`), or the operator left it (`q`) before its done state; the state stays where it is.

|`4`
|operator checks: no interactive terminal, or a coding-agent environment (link:../../../plan-marshall-documentation/doc/specification/cli-and-security/02-credentials-and-operator.adoc#operator-channel-isolation[Operator Channel Isolation], item 2).

|`130`
|interrupted with `Ctrl+C`; the state stays where it is, as with `q`.
|===

[#levels]
== Levels

[#level-model]
=== Machine, Project, Plan

The onboarding records machine values, and they are defaults, not final values: a project may set its own for every aspect but the three that are facts of the machine (the interface language, the enrolled harnesses, the credential store), and a plan overrides what its overrides allow (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#machine-defaults[Onboarding, The machine sets defaults]). The terminal addresses a level with one option and shows, for every value, the level it comes from.

[cols="2,2,2,2",options="header"]
|===
|Aspect |Machine |Project |Plan

|`language`
|interface and model language (`machine-config.json`)
|model language (`user_language` of `local-config.json`)
|—

|`harness`
|the enrolled harnesses
|—
|—

|`models`
|the model catalogue
|the project's allowed models, from those the enrolled harnesses offer (`projects/<project_id>/model-catalogue.json`)
|—

|`roles`
|the machine role assignment
|the project's role assignment (`projects/<project_id>/role-assignments.json`)
|override per role (`overrides.json`)

|`credentials`
|the credential store
|— (entries per project with `pm-operator credentials set --project`)
|—

|`providers`
|availability, variant, and credential per provider
|variant (`integrations.*.variant`) and credential
|the optional providers and the variant of an integration (`overrides.json`)

|`plan-defaults`
|landing, method, asking
|method and asking (`local-config.json`); landing with origin `team`, kept with the team's configuration and changed through the project setup
|bound at its start; shown, not changed later
|===

A dash is not a level of that aspect: `config harness --project p` is refused with usage exit code `2` and the text that names the levels the aspect has. The project column of `language` holds only the model language, since the interface language is the operator's.

[#addressing]
=== Addressing a Level

* *Machine* is the default: no level option, or `--machine`. A working directory inside an enrolled project never selects the project on its own: the operator who wants the project says so, so that a command typed in a checkout never changes a project by surprise.
* *Project*: `--project <project_id>`; `--project .` is the project of the working directory by the project resolution rule (as `pm-mcp enter` resolves it); `--project ?` (or `--project` with no value) shows a numbered list of the enrolled projects to pick from.
* *Plan*: `--plan <plan_id>`, which names its project too; `--plan ?` lists the live plans, of the project given with `--project`, or of every project.
* Every dialogue on a project or a plan names it in its step line (<<state-frame>>), so the operator always sees which level the answer goes to.

[source,text]
----
$ pm-operator config roles --plan ?
Which plan?
  1) pm-mcp-clients   cli-onboarding        execute · 3 of 9 tasks
  2) pm-mcp-clients   message-catalogue     outline
  3) pm-mcp-core      session-log           finalize · waiting for review
Plan? 1-3   q) leave   › 1
----

[#origins]
=== Where a Value Comes From

Each value carries its origin, one of `default` (shipped with the release), `machine`, `project`, `team` (the project's team configuration in `.marshall/config/`), and `plan`. The nearest level wins; a value that overrides another names it.

[source,text]
----
$ pm-operator config show plan-defaults --project pm-mcp-clients
Plan defaults · project pm-mcp-clients

  Landing   Branch and Pull Request   team      overrides machine: Commit on main
  Method    Test first                machine
  Asking    At the key points         default

Change: pm-operator config plan-defaults --project pm-mcp-clients
  Landing is set by the project's team (.marshall/config/); change it in the project setup.
----

* The origin is a word in its own column, never a colour only, so it survives a copy into an issue and a terminal without colour.
* `config show` without an aspect or key lists every aspect and then every plain key, grouped as in `machine-config.json`, with the origin column.
* In a dialogue on a project or a plan, a proposal that comes from a lower level says so beside the preselection (`← from machine`), and accepting it records nothing at this level: the level keeps deferring, so a later change of the machine value reaches it. Only a changed line is written at the addressed level.

[#running-plan]
=== A Running Plan

A plan's axes are bound when it starts; `config show plan-defaults --plan <plan_id>` shows them with origin `plan` (or the level they were taken from at the start) and `config plan-defaults --plan <plan_id>` is refused with the text that names when they were bound. The overrides of a running plan (roles, providers) can change: `config roles --plan <plan_id>` shows the plan's effective assignment and writes the plan's overrides; each change composes a new instance version of the plan (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-plan-overrides[Plan Overrides]), and the client says so before the confirmation (`Applies from the plan's next step; the plan's version becomes 7.`).

[#dialogue]
== Dialogues

[#state-frame]
=== The Frame of a State

A state is printed as three parts, the counterpart of the web app's frame (link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc#frame[Onboarding Screens, Frame]):

----
[3/7] Models · Choose the harnesses and models other plans may use          ← step line

  <content: the facts, the proposal, the choices>                           ← content

Enrol and allow 3 models? [Enter]   other: 1-5   b) back   q) leave   ?      ← prompt line
----

* *Step line*: `[n/7]`, the step's name, `·`, and the title of the state. A later run of one aspect has no counter (`Models · …`); a run on a project or a plan adds its level (`Models · project pm-mcp-clients · …`). Server states print no step line of their own: their progress lines follow the step line of their step.
* *Content*: indented by two spaces, at most 80 columns; a web table is a list with the same columns as fields (link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc#frame[Onboarding Screens, Principles]); a long value (a path, a digest) is shortened in the middle with `…` and shown in full by `?`.
* *Prompt line*: the primary link as a question with `[Enter]`, then the other links with their keys, then `?`. The prompt ends with `› ` where the operator types.
* A new state is printed below the previous one, never over it: the scrollback is the transcript of the run. Only a check line and a progress line are rewritten in place while they run (<<checks>>).

[#keys]
=== Links as Keys and Numbers

Input is read by line (`System.console()`, no line editing, link:../../../plan-marshall-documentation/doc/specification/cli-and-security/01-cli-and-installer.adoc#cli-implementation[CLI Implementation]): the operator types a key or numbers and presses `Enter`.

* *`Enter` alone* takes the primary link, which is the preselection: the proposal of the state as it stands.
* *Numbers* pick from a list. In a single choice a number picks one item and is sent at once when the state has nothing else to decide; in a multiple choice (models, providers, review bots) numbers toggle items (`2 5`, ranges `3-7`) and the list is printed again until `Enter` accepts it. Where a state has several choices (the languages, the plan axes), their items are numbered across the whole state, so one line answers several (`2 5 8`).
* *Letters* take the other links. The key of a link relation is a text of the catalogue (`operator.key.<relation>`, <<texts-operator-keys>>), one letter, the mnemonic of its label in the interface language; within one language a relation has the same key in every state that offers it. Two relations share a key only when no state offers both: a test runs every state of the scenarios in every language and fails on a state that offers two links with the same key, or a key that is a digit or `?`.
* *`?`* prints the explanation of the state (the text the web app shows under the title and behind _Why?_); `?<n>` prints the explanation of item `n` (the advisory of a role, the rationale of a recommended model, the full value of a shortened one).
* *`q`* (German `v`) leaves the dialogue: nothing is sent, the state stays where it is, and the client prints where the run stopped and the command that continues it (<<resume>>).
* An input the state does not offer is answered with one line (`3 is not offered here: 1-2, a, l, q`) and the same prompt; nothing is sent.

[#preselection]
=== Preselection on `Enter`

Every choice state opens with its proposal filled in and marked `←` (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#preselect-first[Preselect as much as possible, hide nothing]); the prompt names what `Enter` does in words (`Use Deutsch for both? [Enter]`), never "OK". A proposal with a reason says it beside the mark (`← from your system`, `← recommended`, `← from machine`). When the operator changes a line, the state is printed again with the changed line marked `✎` and the prompt names the new primary action (`Use these defaults?` becomes `Save these choices?`).

[#explanation]
=== The Explanation on `?`

`?` prints, indented below the prompt, the explanation of the state from the catalogue and then the prompt again. It never changes the state and never sends a request. The explanation of an item (`?3`) is the advisory of a role, the rationale of a model, a consent's full list, or the full value of a shortened field.

[#consent]
=== Consent

A consent state is printed as in link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc#consent[Onboarding Screens, Consent]: the action, what it looks at, what it runs, what it never does, and the cost, each a field. Its prompt has no `Enter` default: `y) yes   r) yes, and don't ask again   n) not now`; `Enter` alone prints `Type y, r or n.` and asks again. Nothing happens on the machine until the operator typed `y` or `r`. In German:

[source,text]
----
[2/7] Harness · Auf dieser Maschine nach Harnesses suchen?
  sucht nach   claude, opencode, codex, agy
  in           deinem PATH, ~/.local/bin, /Applications, /opt/homebrew/bin
  führt aus    <program> --version für jeden gefundenen
  niemals      liest andere Dateien, startet eine Sitzung, nutzt das Netzwerk
  Kosten       keine

j) ja   m) ja, und merken   n) nicht jetzt   ?   › ⏎
Gib j, m oder n ein.
j) ja   m) ja, und merken   n) nicht jetzt   ?   › j
----

`n` sends `no`: the state stays, the client prints `Nothing was done.` under the title, the prompt again, and the step does not move. It is never shown as an error (no `✗`, no colour of an error). A remembered consent passes its state without a question; the client prints one line, `✓ Consent remembered: look for harnesses   (withdraw: pm-operator config consents)`.

[#checks]
=== Check Lists

A check is one line that starts with a spinner and ends in `✓` or `✗` (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#verify-reports[Every verification reports back]):

----
    ⠹  login                                                 (spinner while it runs)
    ✓  version 2.4.1 is supported (2.0 – 2.x)
    ✗  not logged in
       → claude login, then check again
----

* The line is rewritten in place while it runs and stays as it ended. A `✗` is followed by its answer (what was received) and its fix (`→ …`); a fix that is a command is printed alone on its line so it can be copied.
* A check the run did not reach is listed as `·  <check>   not run`. A group (a provider, a profile stage) ends in its own `✓ ready` or `✗ not ready`.
* Without a terminal that renders the spinner (output not a terminal, `TERM=dumb`), a check is printed once, when it ends.

[#waiting]
=== Waiting, Progress, and a Model at Work

While the state is a server state, the client shows what the runtime reports on the event stream (`GET /api/v1/events`): the checks as they report, a line of progress (`Looking for harnesses …  3 of 4 programs`), and the time so far after five seconds. A model state shows the role, the harness and model, the time so far, and the expected cost from earlier runs or `cost not known yet` (link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc#frame[Onboarding Screens, Frame], Model at work):

----
  ⠼  steward is working on Claude Code · opus-5.5      0:42   about 0.08 USD
     q) leave: the advice continues; pm-operator onboard shows its result
----

`q` and `Ctrl+C` leave while the server works; the work continues in the runtime, and the next run shows the state it reached. The client never stops a server state and offers no `cancel` the use cases do not name.

[#resume]
=== Interruption and Resume

The state lives in the runtime, never in the client. The operator stops anywhere with `q` or `Ctrl+C`; the client prints where and how to continue, and exits with `3` or `130`:

----
Stopped at [3/7] Models. Nothing was sent.
Continue: pm-operator onboard   (or in the web app: pm-operator start)
----

* The next `pm-operator onboard`, or the web app, opens at the same state with the same proposal (link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-1[UC-ONB-1], Variations).
* *Another channel moved the state*: the client follows the event stream while it waits for input. When the state changes (the operator answered in the web app), it prints `Answered in the web app: <answer>` and the new state; the typed but unsent input is dropped. A link sent for a state that has moved on is refused by the runtime, and the client prints the new state instead of an error (<<open-points>>, the code of that refusal).
* *Connection lost*: the runtime stopped or restarted (a drain, an upgrade). The client says so, starts the runtime on demand as for every request, re-reads the state, and continues there; a link whose answer did not arrive is never sent twice without reading the state first.

[#refusals]
=== Refusals and Errors

A refused request is printed as a `✗` line with the text of its error code from the catalogue (`common.error.<code>`), the detail the runtime sent, and the fix (`→ …`), and the client exits with `1` unless the state offers a way on, which it then prompts for. `internal_fault` prints its `audit_id` and `pm-operator status`. An error is never printed as a stack trace, and a refusal never ends in a colour or a word of alarm (link:../../../plan-marshall-documentation/doc/design/03-texts-and-languages.adoc#style[Texts and Languages, How Texts Are Written]).

[#no-input]
=== Without Prompts

* *`--no-input`* never asks: a choice state answered by the arguments is passed, the first one that is not ends the run with exit code `3`, its state printed and one line naming the option that answers it (`Needs a choice: --landing pull-request|main|files`), or for a consent the `--consent <kind>` that gives it, or for a secret the `pm-operator credentials set` command.
* Like every operator verb it runs only where the operator checks pass, in an interactive terminal.
* There is no machine-readable output: every interaction goes through the verbs, which validate what they write, and nothing outside the runtime reads or writes the configuration as data.

[#terminal]
=== The Terminal Itself

* *Width*: content is laid out for 80 columns; a wider terminal (`COLUMNS`) gives long values more room, a narrower one wraps fields below their names. Nothing is cut that `?` cannot show.
* *Colour*: `✓` green, `✗` red, the preselection bold, the step line bold; never the only carrier of a meaning. No colour when standard output is not a terminal, with `NO_COLOR` set, or with `TERM=dumb` (picocli ANSI).
* *Characters*: `✓ ✗ ← ✎ · → …` and the spinner need a UTF-8 locale; without one the client prints `ok`, `x`, `<-`, `*`, `-`, `->`, `...` and a spinner of `|/-\`.
* *Copying*: the copy keys of `start.wait` write the terminal's clipboard sequence (OSC 52), which reaches the clipboard of the operator's own computer also over SSH; on a local terminal the platform's clipboard tool where one is found (`pbcopy`, `wl-copy`, `xclip`). Whether a terminal honours OSC 52 cannot be detected, so after a copy the client says `Copied, if your terminal allows it; the text is above.` and the text stays on the screen to select. A key is not offered where neither path exists (no terminal for OSC 52, no tool locally).

[#language]
=== Language of the Terminal

The client prints in the interface language of the machine (`language.interface`); before it is recorded, in the system's language where a pack exists (`LC_ALL`, `LC_MESSAGES`, `LANG`, in that order), else in English. After `language.choose` the client switches at once: the state is printed again in the chosen language before it is recorded, so the operator sees it first (link:../../../plan-marshall-documentation/doc/design/02-onboarding.adoc#language[Onboarding Screens, Language]). `pm-mcp` keeps English (link:../../../plan-marshall-documentation/doc/design/03-texts-and-languages.adoc#two-languages[Texts and Languages, Two Languages]).

[#transcripts]
== Transcripts

One transcript per state or per short sequence of states; the states each one shows are named above it, and <<state-coverage>> lists every state with its transcript. The operator's input follows `› `; `⏎` stands for `Enter` alone. A check is shown as it ended. The transcripts are in English; the German texts are those of <<texts>>, and one German transcript (<<t-language>>) shows the switch.

[#texts]
== Texts

Every text of the onboarding and of `start` in the terminal, as keys of the message catalogue with the English and the German text (link:../../../plan-marshall-documentation/doc/design/03-texts-and-languages.adoc#keys[Texts and Languages, Keys and Packs]). Arguments are ICU arguments; a plural is written `{n, plural, one {…} other {…}}`. German addresses the operator with _du_, and the words of the glossary stay as they are (link:../../../plan-marshall-documentation/doc/design/03-texts-and-languages.adoc#glossary[Glossary]).

* *Shared with the web app*: the keys of the areas `common` and `onboard` are the texts both clients show; the web app adds keys of its own for what only it needs (a button, a tooltip), and the terminal adds the keys of the area `operator` for what only it needs (the prompt line, the keys, the result lines). The labels of links are shared: a button in the web app and a key's label in the terminal read the same.
* *Titles are questions or names, links are actions* (link:../../../plan-marshall-documentation/doc/design/03-texts-and-languages.adoc#style[How Texts Are Written]). The prompt of a primary link is the action as a question (`operator.prompt.primary` wraps the shared label: `{action}? [Enter]`).
* The tables below are the content of the packs `common`, `onboard`, and `operator` for these flows. Where a text has a plural, the German has its own forms.

[#open-points]
== Open Points

Each open point names who decides it.

* *The refusal of a link for a state that moved on* (package `api-contract`, with the machine scope). Two channels answer the same state; the second answer needs an error code of its own (`state_moved`, `409`) with the current state in its detail, so that a client re-renders instead of reporting an error. It is not in the closed list of link:../../../plan-marshall-documentation/doc/specification/runtime-model/01-processes-and-transport.adoc#api-error-codes[Local API Error Codes] yet.
* *Withdrawing a remembered consent* (with link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#change-consent[Consent Before Acting]). The machine settings list and withdraw remembered consents; this design names the terminal verb `pm-operator config consents` (a list with numbers to withdraw) and leaves its transcript to the package that specifies the consent store.
* *The model probe and the advice in one consent state* (with link:../../../plan-marshall-documentation/doc/use-cases/01-onboarding.adoc#UC-ONB-5[UC-ONB-5]). `catalogue.consent` asks two consents in one state; the terminal answers them together or one by one (<<t-models>>). The web design shows the same as two choices of one screen.
