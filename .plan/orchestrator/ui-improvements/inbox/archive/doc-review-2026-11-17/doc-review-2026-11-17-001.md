# Doc review 2026-11-17: specifications move to the repository that implements them

This comes from the doc-review session of `plan-marshall-documentation` (worktrees `review-2026-11-17`). The operator has decided the principle below and asked for the move to be planned and run from this repository, not from the documentation repository. Nothing in this epic was edited. This message is the only channel, and the epic decides how to cut and order the work.

## Operator decision (O1-A, 2026-11-17)
"The spec should be completely in the implementation module. Here (documentation-repo) only the requirements should remain and point to the corresponding implementation / documentation."

What this means:
- Every specification, and its implementation watch document, lives in the repository that implements it, as the specifications of the engine already do in `pm-mcp-core` (its `doc/Specification.adoc`, `doc/specification/`, `doc/ImplementationWatch.adoc`, `doc/implementation-watch/`, `doc/Traceability.adoc`, and ADR 007 there).
- When a section is implemented, it stays where it is, condensed and pointing to the code, as ADR 027 of `pm-mcp-core` says. The documentation repository's rule that deletes implemented sections goes away with its specifications.
- The documentation repository keeps the requirements. Their `Implementation:`, `Verified by:` and `Documentation:` lines point into the code repositories. Use cases, the roadmap, `later-improvements`, open questions and articles also stay there.
- Specifications that belong to `pm-mcp-parent` stay in the documentation repository: `module-structure.adoc` with its watch document, and `implementation-watch/cross-cutting.adoc`. The operator does not want them moved to the parent.

## The task for this repository
Move into `pm-mcp-clients` the specification content that the client modules implement (`pm-api`, `pm-relay`, `pm-operator`, `pm-exec`, `pm-mock-runtime`, `pm-web-app`). The Modules table of `module-structure.adoc` decides, through the specification documents it lists for each module. Here is the reviewer's reading, for the epic to check:
- `cli-and-security/01-cli-and-installer` (relay binary, `pm-operator`, the harness bundle installer, the installation layout) and the client side of `02-operator-channel`.
- `runtime-model/03-relay`, `05-mock-runtime`, and `06-event-catalogue`. The event catalogue is the message catalogue of `pm-api`.
- `harness-integration` (harness detection for the operator checks, and the bundle manifest the installer reads), unless the epic finds that the bundle content side belongs with the model-facing content in `plan-marshall-mcp`.
- The matching watch items of `implementation-watch/cli-and-security.adoc`, `runtime-model.adoc` and `harness-integration.adoc`. Watch ids are kept, never renumbered.

The daemon-side parts belong in `plan-marshall-mcp`, which has no active orchestrator. Those parts are `runtime-model/01` and `04`, `cli-and-security/03-web-server`, the server side of `02`, `mcp-tools`, and the reference `evaluation.adoc`. That half is tracked in the plain plan `plan-marshall-mcp/doc/specification-move-plan.md` (plan-marshall-mcp #125). Before either side moves anything, the two runs agree the section-level cut as one table (task 2 there). A specification part that both repositories implement is split at section boundaries. Neither half may be left without a home.

## What the move must deliver (Done-when, for the epic to adopt or recut)
- `pm-mcp-clients/doc/` holds the moved specifications, their watch documents and a `Traceability.adoc`, the same way `pm-mcp-core` does. Relate them to the existing `doc/design/`: the design either becomes the specification or links to it, never a second statement of the same thing. Record that choice in an ADR of this repository.
- The anchors survive the move, and every link is rewritten. Links from the documentation repository become absolute `https://github.com/plan-marshall/pm-mcp-clients/blob/main/doc/...`. Links from here into the documentation repository are relative sibling paths.
- The pull request in `plan-marshall-documentation` beside the code pull request does the following:
  - It removes the moved documents and their index rows in `Specification.adoc` and `ImplementationWatch.adoc`, and points to this repository's index.
  - It updates `CLAUDE.md`, `doc/developer/project-setup.adoc` and the project skills (`traced-implementation`, `doc-review`, `ingest-ideas`) for the new home.
  - It extends `.claude/skills/doc-review/scripts/trace.py` so that links, anchors, watch backlinks and traceability resolve against the `pm-mcp-clients` checkout beside it. Today it checks only the work packages there, with `--with-plans`.
  - `trace.py` reports `BROKEN LINKS 0` against a baseline taken before the move, with nothing new.
- No content changes ride along. The move is mechanical, and a content check proves that every line of the moved documents survives.

## Ordering and conflicts
- Start after the review pull requests have landed (`pm-mcp-core` first, then `plan-marshall-documentation`; branch `docs/review-2026-11-17`, not yet opened). The review edits these same documents. Starting earlier would move a text that is about to change.
- Running plans that edit the moved documents, such as design or command-tree packages that touch `cli-and-security`, should either land before the move or be rebased onto it. The epic decides which.
