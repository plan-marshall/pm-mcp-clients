## The six decisions (operator, 2026-11-09, one at a time; record: the session's `.plan/temp/d5-findings.md`)

1. **Context** — first answer of the operator: "Shouldn't that depend on the chat context? If it is a plan / epic chat
   … we should aim for warm workers and only re-configured (with infos and skills) if they must be restarted." Decided
   **B′**: one warm `read_only` worker per open chat (plan, epic with decomposition and review, decision, start
   entry; ended work fresh per turn); a turn carries the message, the subject's changes since the last reply and the
   changed files; a new generation (idle release 600 s, slot pressure, context budget, crash) is re-primed with the
   skills, a pushed core per subject and the transcript window (core ≤ 6000, window ≤ 12000 tokens), the rest pulled
   by `pm://` URI; the context summary → the "knows" line (D4 review decision 7 now designed); a paused plan's chat
   runs. **Changes one AGREED D4 sentence**: "an idle chat holds no worker" (`web-app/chat.adoc:71`).
2. **Embedded controls** — **C**: the chat carries out only its own proposal; a decision, hold, queued revision or a
   named act gets a live status card with one act, _Open it_ (web: beside the chat, `chat=open` kept for the same
   subject, another subject pushed; terminal `o`, leaving the chat kept). The plan view and its row show a queued chat
   revision.
3. **Acts** — **R1, acts only**. Option B (act proposals carried out by the client) was decided and then **withdrawn
   by the operator**: "The scenario you consider is that a chat controls itself. So this would a duplicate of the core
   machinery. Therefore all interaction (from the chat) must always be an operator input. The chat should not
   establish its own workflow interactions." No operator act from a chat; the role may only name one (ref kind `act`);
   content proposals and `chat.apply` unchanged (R2 removing `chat.apply` and R3 no proposals refused). Confirmed
   later: `origin {kind: chat, chat_id, turn_id}` on every chat-led change; the turn address `chat=open&turn=`.
4. **MCP** — **A**: the existing job connection through the relay, `read_only` set; new resources
   `pm://chat/{chat_id}/turns`, `pm://plan|epic/{id}/history{?since}`, `pm://entry/{id}/sources[/{source_id}]`,
   `pm://archive/{plan_id}/record`, `pm://epic/{id}/record`; skill `skill://pm/chat/SKILL.md`. No new server or tool.
5. **Events** — **C**: one narrative of the subject (closed `chat.line.*` catalogue of message keys, never model
   text), read three ways: runtime-written notice turns between replies (folded), the role's `since_last_turn`, the
   history resources. Proposal against an older version refused `conflict`; out of the revision window `lapsed`.
6. **Terminal** — **A, full parity**: knows line, numbered starters, `older` pages (operator confirmed: `↑` stays the
   line editor's history), status lines with `o`, a named act printed as its command and never run, the chat
   following its stream with `–` notice lines; new part `terminal-client/28-chat.adoc`.

Also decided: the prototype "Matches" (no change); the use-case changes stay inline as D4 (not a "Changes to the
Specification" part); the hidden-chat badge counts notice lines that name a decision or a hold; the engine refuses a
reply whose `act` ref names an act the subject does not offer (`invalid_arguments`).
